# RFC 7523 — JSON Web Token (JWT) Profile for OAuth 2.0 Client Authentication and Authorization Grants

[← voltar ao roteiro](../oauth-guide.md)

## 1. Contexto e motivação

Esta RFC define, na verdade, **duas extensões independentes** que só compartilham o mesmo mecanismo de base (um JWT assinado apresentado ao token endpoint) — vale separar isso logo de cara, porque é fácil confundir as duas:

- **§2.1 — JWT como Authorization Grant**: um jeito de trocar uma asserção assinada por terceiro confiável (JWT ou SAML) diretamente por um access_token, sem passar pelo fluxo interativo de `/authorize`. Pensado para pontes entre sistemas de identidade baseados em asserção (SAML, federações) e o modelo de token do OAuth.
- **§2.2 — JWT como Autenticação de Client**: um jeito do **client** provar sua identidade no token endpoint assinando um JWT com sua própria chave privada, em vez de apresentar um `client_secret` estático. É o método amplamente conhecido como **`private_key_jwt`**.

A motivação da segunda metade conecta direto com algo que já vimos: um `client_secret` estático, se vazar, é uma credencial de impersonação completa e permanente até ser rotacionado — e um vazamento do lado do AS (banco de dados comprometido) também expõe esse segredo. Com `private_key_jwt`, o AS só precisa conhecer a **chave pública** do client — nada secreto passa pela rede, e um vazamento do armazenamento do AS não dá a ninguém a capacidade de se passar pelo client.

## 2. Terminologia e papéis

Nenhum papel novo. Introduz:
- **JWT Bearer Grant** — `grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer`, parâmetro `assertion` carregando o JWT.
- **Client Assertion** — `client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer` + `client_assertion` (o JWT assinado pelo client), usado **junto** com qualquer `grant_type` normal — não substitui o grant, substitui *como o client se autentica* dentro dele.

## 3. Fluxo

**§2.1 — como grant** (obter token direto de uma asserção externa):
```
POST /token
grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer
&assertion=<JWT assinado pelo emissor confiavel: iss, sub, aud=AS, exp...>

AS valida a assinatura (chave publica do issuer, previamente confiavel/registrada)
AS → Client: access_token — sem interacao do resource owner
```

**§2.2 — como autenticação de client** (`private_key_jwt`, combinável com qualquer grant):
```
POST /token
grant_type=authorization_code (ou refresh_token, client_credentials...)
&code=...
&client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer
&client_assertion=<JWT assinado com a chave PRIVADA do client>

Claims do client_assertion: iss=client_id, sub=client_id, aud=token_endpoint, exp, jti

AS valida com a chave PUBLICA do client (jwks/jwks_uri, registrados via RFC 7591)
```

## 4. Parâmetros e endpoints normativos

Nenhum endpoint novo — as duas metades reaproveitam o `/token` da RFC 6749.

- Grant (§2.1): `grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer`, `assertion`.
- Autenticação de client (§2.2): `client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer`, `client_assertion` — usado **ao lado** de qualquer `grant_type`, não no lugar dele.
- Claims esperadas no `client_assertion`: `iss`/`sub` = `client_id`, `aud` = identificador do token endpoint/AS, `exp` (obrigatório, vida curta), `jti` (recomendado, identificador único para detectar replay).
- `jwks`/`jwks_uri` registrados via **RFC 7591** são exatamente o que o AS usa para localizar e validar a chave pública do client.

## 5. Segurança já tratada na própria RFC 7523

- **Nenhum segredo compartilhado necessário para autenticação de client** — o AS só precisa da chave **pública**; um vazamento do armazenamento do AS não dá capacidade de impersonação (diferente de um `client_secret` vazado).
- **Proteção contra replay via `exp` + `jti`**: uma `client_assertion` capturada só vale por uma janela curta, e o `jti` (se rastreado pelo AS) permite rejeitar reapresentação da mesma asserção — mesmo espírito do code de uso único, aplicado aqui ao próprio artefato de autenticação.
- **`aud` amarra a asserção a um AS específico** — uma `client_assertion` construída para um AS não deveria ser aceita por outro, mesmo que apresentada lá. É mais uma instância do mesmo padrão recorrente de restrição de audience que já vimos motivar a RFC 8707 e aparecer no `aud` dos Request Objects da RFC 9101.
- Para o grant do §2.1: o AS precisa de uma relação de confiança **pré-estabelecida** com o emissor (`iss`) da asserção — JWTs autoassinados de partes desconhecidas obviamente não deveriam ser aceitos; isso normalmente significa chave/certificado do emissor pré-registrado ou descoberto via federação confiável.

## 6. Relação com outras RFCs

- A metade de autenticação de client é exatamente o **`private_key_jwt`** já mencionado no capítulo da RFC 9700 ("prefere métodos assimétricos a `client_secret` estático") — é aqui que esse método é definido concretamente.
- `jwks`/`jwks_uri` usados para validar assinaturas vêm do metadata da **RFC 7591** — conexão direta com aquele capítulo.
- Descoberto via **RFC 8414**: `token_endpoint_auth_methods_supported` listaria `private_key_jwt` se suportado, e `token_endpoint_auth_signing_alg_values_supported` indica quais algoritmos de assinatura o AS aceita.
- O grant do §2.1 é conceitualmente antecessora/irmã da **RFC 8693 (Token Exchange)** — ambas fazem ponte entre "tenho algum tipo de token/asserção externa" e "quero um token OAuth", mas a 8693 é mais geral (qualquer tipo de token, distinção subject/actor explícita, direcionamento por audience/resource). A 8693 não substituiu a 7523 — coexistem para níveis de complexidade diferentes.
- Vale distinguir das **outras** duas assinaturas de JWT que já vimos no roteiro, para não confundir: o Request Object da **RFC 9101 (JAR)** protege a integridade da *authorization request*; o `client_assertion` desta RFC autentica o *client* no token endpoint; e o JWT-bearer grant desta mesma RFC troca uma *asserção externa* por token. Três propósitos diferentes, todos usando "um JWT assinado" como mecanismo.

## 7. O que mudou desde a publicação (2015)

- A metade de **autenticação de client** (`private_key_jwt`) cresceu bastante em relevância — explicitamente recomendada sobre segredo estático pela RFC 9700 (2025), uma década depois, e exigida por perfis FAPI para clients confidenciais em muitos casos. Segue a mesma trajetória "recomendado → cada vez mais esperado" que já vimos com PKCE (embora `private_key_jwt` não tenha virado obrigatório universal como o PKCE).
- A metade do **grant JWT-bearer** (§2.1) cresceu comparativamente menos — seu caso de uso de "ponte" foi em boa parte absorvido por designs novos usando a RFC 8693 (Token Exchange), mais flexível. A 7523 continua válida e mais simples, ainda usada especialmente em pontes legadas SAML-para-OAuth.

> **Nota de laboratório**: implementado em [`rfc7523/`](../../rfc7523/README.md) — réplica do lab básico da RFC 6749, mas **sem `client_secret` nenhum**: o client-demo gera seu próprio par de chaves RSA, registra a pública via `jwks` (RFC 7591), e autentica todo `grant_type` (Authorization Code, refresh, Client Credentials) via `client_assertion` (§2.2). O AS rastreia `jti` já usados para detectar replay — há até um botão que reenvia deliberadamente a mesma assertion para provar a rejeição. O grant do §2.1 (JWT-bearer) fica de fora, por escolha. Os demais labs (`rfc6749/`, `rfc7636/`, `rfc9126/`, `rfc7592/`) continuam usando `client_secret_basic`/`client_secret_post`.
