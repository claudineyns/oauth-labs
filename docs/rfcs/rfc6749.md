# RFC 6749 — The OAuth 2.0 Authorization Framework

[← voltar ao roteiro](../oauth-guide.md)

## 1. Contexto e motivação

Antes do OAuth, o padrão para um app de terceiros acessar dados de um usuário em outro serviço era o **anti-padrão de senha**: o usuário entregava sua senha do serviço (ex: e-mail) diretamente ao app de terceiros. Isso implicava: acesso irrestrito (sem escopo), impossível revogar seletivamente, e a senha ficava armazenada em outro lugar.

O OAuth 2.0 resolve isso introduzindo **autorização delegada**: o resource owner concede ao client um **token de acesso** com escopo e validade limitados, emitido por um authorization server, sem o client nunca ver a credencial do usuário.

RFC 6749 substitui o OAuth 1.0 (RFC 5849), simplificando ao remover a assinatura criptográfica de cada request em favor de TLS obrigatório + bearer tokens (definidos separadamente na RFC 6750).

## 2. Terminologia e papéis

- **Resource Owner** — a entidade capaz de conceder acesso a um recurso protegido (tipicamente o usuário final).
- **Client** — a aplicação que solicita acesso em nome do resource owner.
- **Authorization Server (AS)** — emite tokens de acesso após autenticar o resource owner e obter sua autorização.
- **Resource Server (RS)** — hospeda os recursos protegidos, aceita e valida access tokens.

**Tipos de client** (dimensão relevante para escolha de grant type e segurança):
- **Confidential** — capaz de manter um `client_secret` em segredo (ex: servidor backend).
- **Public** — não consegue manter segredo (ex: SPA, app mobile, CLI).

**Perfis de client**: web application (confidential, roda no servidor), user-agent-based application (public, roda no browser), native application (public, roda no dispositivo).

## 3. Fluxos (Grant Types)

A RFC define 4 grant types. **Nota de atualização**: RFC 9700 (2025) deprecia Implicit e ROPC — descritos aqui por completude histórica, mas não devem ser usados em projetos novos.

**a) Authorization Code Grant** — o fluxo central, para clients confidenciais (e hoje, com PKCE, também públicos):
```
1. Client → User-Agent: redireciona para AS /authorize?response_type=code&client_id=...&redirect_uri=...&scope=...&state=...
2. AS autentica o resource owner e obtém consentimento
3. AS → User-Agent → Client: redirect_uri?code=AUTH_CODE&state=...
4. Client → AS: POST /token  grant_type=authorization_code&code=AUTH_CODE&redirect_uri=...&client_id=...&client_secret=...
5. AS → Client: access_token (+ refresh_token opcional)
```
Vantagem: o access token nunca passa pelo user-agent/browser, apenas o code (de vida curtíssima, uso único).

**b) Implicit Grant** *(deprecado pela RFC 9700)* — o AS devolvia o access_token diretamente no fragmento da URL de redirect, sem passo de troca de code. Existia porque SPAs não podiam fazer o passo 4 sem expor client_secret. Hoje resolvido por Authorization Code + PKCE.

**c) Resource Owner Password Credentials (ROPC)** *(deprecado pela RFC 9700)* — o usuário entregava usuário/senha diretamente ao client, que trocava por um token no AS. Reintroduz o próprio anti-padrão que o OAuth existe para eliminar; só fazia sentido para clients de altíssima confiança (ex: 1st-party).

**d) Client Credentials Grant** — sem resource owner; o client se autentica com suas próprias credenciais para agir em nome de si mesmo (machine-to-machine, ex: serviço de backend chamando outra API).
```
Client → AS: POST /token  grant_type=client_credentials&client_id=...&client_secret=...&scope=...
AS → Client: access_token
```

**Refresh Token** — mecanismo transversal aos grants: o AS pode emitir um `refresh_token` junto ao access_token, usado para obter novos access tokens sem repetir a interação com o resource owner:
```
Client → AS: POST /token  grant_type=refresh_token&refresh_token=...&client_id=...&client_secret=...
```

**Manter ou rotacionar o refresh token na renovação?** A própria RFC 6749 (§6) já responde: é facultativo do AS. Se ele emitir um novo `refresh_token` na resposta, o client deve descartar o antigo e passar a usar o novo; se o campo vier ausente, o client mantém o que já tinha — a ausência do campo já é o sinal de "não mudou". A RFC 9700 aperta essa regra depois, recomendando rotação a cada uso (sobretudo para clients públicos); o lab deste projeto já rotaciona sempre.

## 4. Parâmetros e endpoints normativos

**Endpoints:**
- **Authorization endpoint** — interação com o resource owner (via user-agent/browser).
- **Token endpoint** — comunicação back-channel client↔AS (troca de code/credentials por tokens).
- **Redirection endpoint** — URI no client para onde o AS devolve o resultado da autorização.

**Parâmetros-chave da authorization request:** `response_type` (`code` ou `token`), `client_id`, `redirect_uri`, `scope`, `state` (anti-CSRF, opaco, gerado pelo client e validado no retorno).

**Parâmetros-chave da token response:** `access_token`, `token_type` (tipicamente `Bearer`), `expires_in`, `refresh_token`, `scope`.

**Erros padronizados**: `invalid_request`, `unauthorized_client`, `access_denied`, `unsupported_response_type`, `invalid_scope`, `server_error`, `temporarily_unavailable` — devolvidos como redirect (authorization endpoint) ou JSON (token endpoint).

## 5. Segurança já tratada na própria RFC 6749

- **Open redirector**: validar `redirect_uri` contra um valor pré-registrado, não apenas prefixo.
- **CSRF no callback**: uso do parâmetro `state`.
- **Interceptação do authorization code**: code deve ter vida curta e uso único; mitigado mais tarde de forma mais robusta pela RFC 7636 (PKCE).
- **TLS obrigatório** em todos os endpoints que trocam credenciais/tokens.

A RFC 6749 é deliberadamente um framework "esqueleto" — ela documenta as opções mas deixa várias decisões de segurança para a RFC 6819 (Threat Model) e, mais tarde, para a RFC 9700 (BCP).

## 6. Relação com outras RFCs

- **RFC 6750** define como o `access_token` do tipo Bearer é efetivamente usado nas chamadas ao resource server (este documento só define como obtê-lo).
- **RFC 6819** cataloga as ameaças específicas de cada grant type descrito aqui.
- **RFC 7636 (PKCE)** foi criada especificamente para mitigar a fraqueza do Authorization Code Grant em clients públicos.
- **RFC 9700** revisita e restringe as escolhas desta RFC à luz de 10+ anos de exploração em produção.
- **OAuth 2.1** (draft) efetivamente reescreve este documento incorporando essas correções como obrigatórias.

## 7. O que mudou desde a publicação (2012)

- Implicit e ROPC: de "opções válidas" para "não usar" (RFC 9700).
- PKCE: de "só para clients públicos" para "obrigatório para todos" (RFC 9700).
- `redirect_uri`: de comparação flexível para **exact string match** obrigatório.
- Bearer tokens simples (sem sender-constraining) são hoje considerados insuficientes para cenários de alta sensibilidade — ver RFC 8705 (mTLS) e RFC 9449 (DPoP) no item 6.
