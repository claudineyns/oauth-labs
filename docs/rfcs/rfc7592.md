# RFC 7592 — OAuth 2.0 Dynamic Client Registration Management Protocol

[← voltar ao roteiro](../oauth-guide.md)

## 1. Contexto e motivação

A RFC 7591 cobre só a **criação** de um registro de client (`POST /register`). Depois de criado, não havia forma padronizada de ler a configuração atual, atualizá-la (trocar `redirect_uris`, rotacionar o `client_secret`, mudar `grant_types`) ou apagar o registro. A RFC 7592 fecha esse ciclo, publicada **na mesma data** que a 7591 — as duas são, na prática, duas metades de um único ciclo de vida de registro.

Cenários motivadores: o `redirect_uri` de um client muda (o app migrou de domínio), um portal self-service quer mostrar/editar os dados do app registrado, um client é descomissionado e precisa de baixa formal (diferente de simplesmente deixar os tokens expirarem sozinhos).

## 2. Terminologia e papéis

Nenhum papel novo, nenhum conceito genuinamente novo — reaproveita tudo da RFC 7591: `registration_access_token` e `registration_client_uri`, devolvidos na resposta da criação, são exatamente a credencial e a URL que esta RFC usa para gerenciar aquele client específico.

## 3. Fluxo — três operações sobre `registration_client_uri`

Todas autenticadas com `Authorization: Bearer <registration_access_token>`.

**Leitura (GET)**:
```
GET /register/s6BhdRkqt3 HTTP/1.1
Authorization: Bearer reg-23410913-abewfq.123483

200 OK
{ "client_id": "s6BhdRkqt3", "redirect_uris": [...], ... }
```

**Atualização (PUT — substituição completa, não patch parcial)**:
```
PUT /register/s6BhdRkqt3 HTTP/1.1
Authorization: Bearer reg-23410913-abewfq.123483
Content-Type: application/json

{ "client_id": "s6BhdRkqt3", "redirect_uris": ["https://client.exemplo.org/novo-callback"], ... }
```
O client precisa reenviar a metadata **inteira** desejada — não é um PATCH. A resposta pode vir com um `registration_access_token` **novo** (o AS pode rotacioná-lo a cada atualização), e o client precisa passar a usar o novo a partir daí.

**Exclusão (DELETE)**:
```
DELETE /register/s6BhdRkqt3 HTTP/1.1
Authorization: Bearer reg-23410913-abewfq.123483

204 No Content
```

## 4. Parâmetros e endpoints normativos

- Não introduz um endpoint genérico novo no discovery document — `registration_client_uri` é **específico por client**, devolvido só na resposta da criação (RFC 7591), diferente de `registration_endpoint` (que é uma capacidade geral do AS, descoberta via RFC 8414).
- Métodos: `GET` (ler), `PUT` (atualizar — substituição completa), `DELETE` (apagar).
- Autenticação: `Bearer <registration_access_token>` em toda chamada — um token cujo único propósito é autorizar operações de gerenciamento sobre **um** registro específico, nada mais.

## 5. Segurança já tratada na própria RFC 7592

- **`registration_access_token` é uma credencial de alto valor**: quem o possui pode ler (possivelmente o `client_secret`), **modificar** `redirect_uris` (o que efetivamente redireciona para onde o AS está disposto a mandar authorization codes) ou **apagar** o registro inteiro. A RFC é explícita: esse token merece proteção pelo menos equivalente à de um `client_secret` — perdê-lo é arguivelmente pior, porque dá controle de configuração, não só autenticação.
- **A semântica de substituição completa do PUT é um risco operacional real**: como não é um patch parcial, um client que reenvia um objeto de metadata incompleto (esquecendo um campo que "não pensou que precisava tocar") corre o risco de **apagar silenciosamente** configuração de segurança já existente — por exemplo, resetar `token_endpoint_auth_method` para um padrão, ou perder uma entrada de `redirect_uris` ainda em uso.
- **Baixa de registro e revogação de token são preocupações relacionadas, mas distintas**: apagar o registro do client **não garante automaticamente** que tokens já emitidos parem de funcionar — a menos que a implementação do AS explicitamente encadeie essa revogação (RFC 7009). É recomendado, não estritamente exigido pelo protocolo em si.
- **Rotação do `registration_access_token` na atualização** é uma defesa em profundidade opcional — mesmo princípio de rotação já visto em refresh tokens (RFC 6749/RFC 9700), aplicado aqui à credencial de gerenciamento de registro.

## 6. Relação com outras RFCs

- Companheira direta e indissociável da **RFC 7591** — 7591 cria, 7592 gerencia, usando exatamente as credenciais que a 7591 já devolve. Publicadas juntas por serem duas metades do mesmo ciclo de vida.
- Conecta com a **RFC 7009 (Token Revocation)**: apagar um registro de client deveria levar à consideração de revogar os tokens pendentes daquele client — são problemas adjacentes (revogar um **token** vs. dar baixa num **client**), e uma implementação madura tipicamente encadeia as duas coisas por política, ainda que os protocolos não exijam isso formalmente um do outro.
- O `registration_access_token` em si é, funcionalmente, um bearer token nos termos da **RFC 6750** — as mesmas considerações de transporte/segurança se aplicam, mesmo com um propósito (gerenciar registro) exclusivo deste par de RFCs.
- Diferente de `registration_endpoint`, **não é descoberto genericamente via RFC 8414** — `registration_client_uri` é inerentemente específico por instância de client, não uma capacidade geral do AS.

## 7. O que mudou desde a publicação (2015)

- Publicada junto com a RFC 7591, manteve-se igualmente estável; sua adoção acompanha de perto a da 7591 — onde há criação dinâmica, o gerenciamento (7592) é o complemento natural esperado, embora algumas implantações optem por suportar só a criação e tratar atualização/exclusão por um processo administrativo fora de banda, tratando o gerenciamento self-service ao vivo como hardening opcional em vez de requisito.
- Sem mudança significativa de uso — continua sendo uma peça relativamente nicho, mas estável, mais visível em contextos de federação/portais self-service corporativos, sempre ao lado da 7591.

> **Nota de laboratório**: implementado em [`rfc7592/`](../../rfc7592/README.md) — o AS expõe `GET`/`PUT`/`DELETE` em `/register/:clientId`, autenticados pelo `registration_access_token` (GET omite o `client_secret`; PUT rotaciona o token de gerenciamento a cada chamada). No client-demo, o registro em si é uma **ação manual do usuário** ("Registrar client agora"), e nenhuma outra funcionalidade fica disponível até ela ser concluída; apagar o registro (DELETE) devolve o app a esse mesmo estado bloqueado, exigindo um novo registro manual.
