# RFC 8707 — Resource Indicators for OAuth 2.0

[← voltar ao roteiro](../oauth-guide.md)

## 1. Contexto e motivação

Este é o capítulo onde fechamos a pergunta que deixamos em aberto desde o capítulo da RFC 6819: **a segmentação clara de nomes de scope por recurso já não resolveria o "confused deputy" sozinha, sem precisar de um mecanismo de audience?**

### A análise prometida: scope segregado resolve?

Considere o cenário de sempre: um token emitido com `scope=accounts:read` (pensado para a API de contas) é apresentado, por engano ou má-fé, à API de pagamentos. Se os nomes de scope forem bem segregados (`accounts:read` nunca significa nada em nenhum outro serviço), a API de pagamentos, ao checar se o token tem `payments:read`/`payments:write`, **não vai encontrar** — e rejeita. Nesse caso concreto, nomenclatura limpa **funciona** e evita a ação indevida.

O problema é que essa proteção depende inteiramente de **disciplina de implementação em cada resource server**, não de uma garantia estrutural:

- **Nada obriga** um resource server a checar o nome de scope específico dele. Um serviço mal implementado (bug de regex, checagem frouxa tipo "tem algum scope que comece com `read`", ou pior, só conferir `active: true` sem olhar o `scope` de verdade) aceita o token mesmo com nomenclatura perfeita — porque a proteção nunca era do protocolo, era do código de quem escreveu aquele resource server especificamente.
- **A unicidade global de nomes de scope é um problema de governança organizacional, não técnico.** Numa empresa grande, com muitos times construindo muitas APIs ao longo do tempo, garantir que ninguém nunca reaproveite um nome de scope (ou reaproveite por engano, copiando um serviço existente) é disciplina que degrada com o tempo — não é algo que o protocolo garante.
- **Confused deputy não é só "escopo errado foi concedido"** — é "a parte errada aceitou essa credencial". Mesmo um token com scope corretamente nomeado e corretamente checado pode ser aceito por um resource server que **não deveria** receber tokens daquele tipo (ex.: um ambiente de staging menos confiável que, por coincidência, expõe um endpoint que também checa `accounts:read`). Nomenclatura de scope não distingue "este RS deveria aceitar" de "este RS não deveria" — ela só distingue "o que pode ser feito", não "com quem o token pode falar".

**Conclusão**: segmentação de scope é uma mitigação real e vale a pena manter como defesa em profundidade — reduz bastante o risco na prática. Mas não é um substituto estrutural para uma restrição de audience, porque depende de disciplina de nomenclatura e implementação correta em **todo** resource server, em vez de uma garantia reforçada pelo próprio protocolo, independente de como os scopes foram nomeados. É exatamente essa lacuna que a RFC 8707 fecha.

## 2. Terminologia e papéis

Nenhum papel novo. Introduz:
- **`resource`** — parâmetro novo, uma URI absoluta (sem fragmento) identificando o resource server que o client pretende usar com o token resultante.
- **Resource Indicator** — o nome que a RFC dá a essa declaração explícita, feita pelo client no momento do pedido: "este token é para conversar com **este** destinatário".

## 3. Fluxo

```
GET /authorize?response_type=code&client_id=...&resource=https://api.exemplo.com/pedidos&scope=...

ou, no token endpoint (qualquer grant, incluindo client_credentials):

POST /token
grant_type=...&resource=https://api.exemplo.com/pedidos&...

AS valida se o client tem permissao de obter token para ESSE resource, com ESSE scope
AS emite o token restrito aquele resource
```

O parâmetro pode aparecer **mais de uma vez** na mesma requisição, se o client quiser um token válido para vários recursos — cabe ao AS decidir se emite um único token multi-audience ou recusa por ambiguidade (política de cada implantação).

## 4. Parâmetros e endpoints normativos

Nenhum endpoint novo — estende tanto a requisição de autorização (RFC 6749 §4.1.1) quanto a requisição de token, com o parâmetro `resource`.
- Também utilizável na **RFC 8693 (Token Exchange)** — que já usa exatamente esse mesmo parâmetro; a RFC 8707 generaliza `resource` para os grants padrão, não só para troca de token.
- Descoberta via **RFC 8414**: campo de metadata indicando suporte ao parâmetro.

## 5. Segurança já tratada na própria RFC 8707

- O AS **deve validar** se o client está autorizado a obter token para o `resource` pedido, com aquele `scope` — não deve simplesmente aceitar qualquer `resource` que o client informe.
- Recomenda que resource servers **validem a audience** dos tokens que recebem — é aqui que a decisão tomada no pedido (`resource`) precisa efetivamente "pousar" em algum lugar verificável: a claim `aud` de um JWT access token (RFC 9068), ou o campo `aud` de uma resposta de introspecção (RFC 7662).
- Reforça, de forma estrutural (não dependente de nomenclatura), exatamente a proteção que a análise do item 1 mostrou que a segmentação de scope sozinha não conseguia garantir.

## 6. Relação com outras RFCs

- Resolve diretamente a preocupação de "confused deputy" catalogada na **RFC 6819**, reforçada pela **RFC 9700**.
- A claim `aud` da **RFC 9068** (JWT access tokens) e o campo `aud` da resposta de introspecção da **RFC 7662** são exatamente onde a decisão de `resource` desta RFC fica registrada no token — mesma divisão "pedido vs. token" que já vimos entre a RFC 8693 e a RFC 9068.
- Companheira direta da **RFC 8693 (Token Exchange)**, que já usava esse mesmo parâmetro antes desta RFC generalizá-lo para os grants padrão.
- Fecha o ciclo aberto desde o capítulo da RFC 6819 e revisitado na RFC 8693 (cenário do gateway) e na RFC 9068.

## 7. O que mudou desde a publicação (2020)

- Adoção crescente, particularmente em implantações com múltiplos resource servers/microsserviços e em perfis adjacentes a FAPI — que, no seu contexto FSI, já esperam indicação explícita de recurso em vez de depender só de disciplina de nomenclatura de escopo, exatamente como a análise do item 1 concluiu.
- Continua sendo, junto com a RFC 8693, a resposta estrutural moderna ao problema que a RFC 6819 catalogou informalmente mais de uma década antes.
