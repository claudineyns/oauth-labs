# RFC 6819 — OAuth 2.0 Threat Model and Security Considerations

[← voltar ao roteiro](../oauth-guide.md)

## 1. Contexto e motivação

Publicada poucos meses depois da RFC 6749/6750 (janeiro de 2013), a RFC 6819 não é uma especificação de protocolo — é **Informational**, um documento de *threat modeling* clássico: descreve a arquitetura, lista os ativos a proteger, cataloga sistematicamente as ameaças por ponto da arquitetura, e recomenda mitigações. Ela existe porque a RFC 6749 é, por design, um "framework esqueleto" que deixa várias decisões de segurança em aberto para quem implementa — a 6819 é o documento que preenche essa lacuna com uma análise estruturada, não normativa.

Vale reter: é o **catálogo de ameaças mais citado do ecossistema OAuth** até hoje — praticamente toda extensão de segurança posterior (PKCE, Resource Indicators, a própria RFC 9700) resolve uma ameaça específica que já estava documentada aqui, anos antes de existir uma RFC dedicada à mitigação.

## 2. Terminologia e papéis

Não introduz papéis novos — reaproveita client, authorization server, resource server e resource owner da RFC 6749. Introduz, sim, vocabulário de threat modeling: **ativos** (o que precisa ser protegido — credenciais do usuário, `client_secret`, authorization code, access/refresh token, dados do resource owner) e **ameaças** organizadas por onde ocorrem na arquitetura, cada uma com descrição, impacto e contramedida sugerida.

## 3. "Fluxo" — estrutura do documento

Não há fluxo de protocolo aqui; a RFC segue a estrutura clássica de um threat model:
- **§3** — recapitula a arquitetura OAuth 2.0 (papéis e fluxo) para dar contexto à análise.
- **§4** — resume as proteções que a RFC 6749/6750 já embutem (TLS, validação de `redirect_uri`, expiração de token, escopo).
- **§5** — o catálogo de ameaças propriamente dito, organizado por alvo: ameaças ao **client** (§5.1), ao **authorization server** (§5.2), ao **resource owner** (§5.3) e ao **resource server** (§5.4).

## 4. Parâmetros e endpoints normativos

Nenhum — a RFC 6819 não define protocolo, parâmetro ou endpoint. É puramente analítica.

## 5. Ameaças e mitigações mais relevantes do catálogo (§5)

Uma seleção das que mais moldaram o resto do ecossistema (o documento tem dezenas de itens numerados; estes são os que valem lembrar):

- **Interceptação do authorization code** — se o `redirect_uri` não usa TLS, ou se um app malicioso registra o mesmo esquema de URI customizado (comum em mobile), o code pode ser capturado antes do client legítimo. **Esta é, literalmente, a ameaça que a RFC 7636 (PKCE) foi criada para resolver** — a 6819 já sugeria informalmente vincular a requisição de autorização à troca de token, o que o PKCE formalizaria com um par verifier/challenge três anos depois.
- **CSRF no endpoint de redirecionamento** — sem o parâmetro `state` validado, um atacante pode injetar seu próprio authorization code na sessão da vítima. Mitigação: `state` opaco e vinculado à sessão do usuário (o lab já implementa isso).
- **Open redirector via `redirect_uri` mal validado** — comparação flexível (prefixo, wildcard) permite phishing e vazamento de code/token. Mitigação recomendada aqui (mas só obrigatória depois, na RFC 9700): **exact match**.
- **Vazamento de token via `Referer`, logs ou histórico do browser** — reforça por que a RFC 6750 desaconselha o token na query string.
- **Reuso do authorization code** — um code já trocado por token deve ser rejeitado se apresentado de novo (sinal de comprometimento); o lab já implementa isso como uso único.
- **"Confused deputy" / substituição de token entre resource servers** — um token emitido para um recurso sendo aceito por outro. Prenuncia diretamente a RFC 8707 (Resource Indicators).
- **Clickjacking na tela de consentimento** — a UI de autorização pode ser embutida em um iframe invisível para induzir cliques de "autorizar".
- **Força bruta contra `client_secret`** de clients públicos ou mal protegidos — reforça a fragilidade estrutural da distinção confidential/public já discutida na RFC 6749.
- **Comprometimento do armazenamento do authorization server** — vazamento de tokens/segredos armazenados sem proteção adequada no lado do AS.

## 6. Relação com outras RFCs

- É a base conceitual de quase todo o resto do roteiro de segurança: **RFC 7636 (PKCE)** resolve a ameaça de interceptação de code; **RFC 8707 (Resource Indicators)** resolve a confused deputy; **RFC 9700 (BCP)** pega dezenas das recomendações "SHOULD" daqui e as torna "MUST" à luz de mais de uma década de exploração real.
- Complementa diretamente RFC 6749/6750 — é o documento que assume o papel de "e se algo der errado?" que as specs de protocolo deliberadamente não cobrem.
- Deu origem, mais tarde, a ameaças específicas que motivaram RFCs fora deste roteiro — notavelmente ataques de "mix-up" entre múltiplos authorization servers, endereçados pela RFC 9207 (AS Issuer Identification).

## 7. O que mudou desde a publicação (2013)

- Nunca foi revisada — é um retrato de ameaças de mais de uma década atrás, ainda assim citada como referência-base.
- Muitas mitigações que aqui eram "recomendadas" (PKCE universal, exact-match de `redirect_uri`) viraram obrigatórias na RFC 9700.
- Ameaças ligadas ao ROPC, que aqui recebiam mitigação, hoje são resolvidas de forma mais direta: a RFC 9700 simplesmente deprecia o grant type em vez de tentar mitigar em torno dele.
- Classes de ameaça inteiramente novas surgiram depois e não podiam constar aqui: ataques específicos de JWT (`alg=none`, confusão de chave), phishing de device code (só relevante após a RFC 8628, de 2019), e ataques de downgrade de PKCE — nenhum existia como categoria em 2013.
