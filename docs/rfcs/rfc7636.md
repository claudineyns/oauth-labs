# RFC 7636 — Proof Key for Code Exchange by OAuth Public Clients (PKCE)

[← voltar ao roteiro](../oauth-guide.md)

## 1. Contexto e motivação

PKCE nasce diretamente de uma ameaça já catalogada na RFC 6819: **interceptação do authorization code** em clients públicos. O cenário concreto que motivou a RFC (2015): apps mobile usam esquemas de URI customizados (`myapp://callback`) como `redirect_uri` — e **mais de um app instalado no mesmo dispositivo pode registrar o mesmo esquema**. Um app malicioso registrando `myapp://callback` pode capturar o `code` destinado ao app legítimo e correr para trocá-lo por um token antes dele.

O problema de fundo: client público, por definição (RFC 6749), **não tem `client_secret`** — então a defesa padrão do token endpoint (autenticar o client com o secret) simplesmente não existe para esse tipo de client. Quem tem o code intercetado e sabe o `client_id` (público, sem segredo nenhum) consegue completar a troca sozinho.

A solução da RFC 7636: exigir prova de posse de um segredo que **o próprio client gerou no início do fluxo** — um segredo que o interceptador nunca viu, porque só interceptou o code, não a requisição original.

## 2. Terminologia e papéis

Nenhum papel novo — mas introduz vocabulário criptográfico específico:
- **`code_verifier`** — string aleatória de alta entropia (43 a 128 caracteres, do conjunto `[A-Z] [a-z] [0-9] "-" "." "_" "~"`), gerada pelo client e mantida em segredo até o passo final.
- **`code_challenge`** — derivado do `code_verifier`, é o que efetivamente viaja na requisição de autorização (front-channel, visível no browser/redirect).
- **`code_challenge_method`** — como o challenge foi derivado: `plain` (challenge = verifier, sem transformação) ou `S256` (challenge = `BASE64URL(SHA256(verifier))`, **recomendado**, e na prática hoje quase obrigatório).

## 3. Fluxo

```
1. Client gera code_verifier (aleatório, alta entropia)
2. Client calcula code_challenge = BASE64URL(SHA256(code_verifier))     [método S256]
3. Client → AS: GET /authorize?...&code_challenge=xxx&code_challenge_method=S256
4. AS associa code_challenge (+ método) ao authorization code que vai emitir
5. AS → Client: redirect com code=...
6. Client → AS: POST /token  grant_type=authorization_code&code=...&code_verifier=<verifier original>
7. AS recalcula BASE64URL(SHA256(code_verifier)) e compara com o code_challenge armazenado
8. Bate → emite tokens. Não bate → invalid_grant.
```

O ponto central: quem intercepta só o `code` (passo 5→6) **não tem o `code_verifier`** — ele nunca trafegou, só o challenge derivado dele trafegou, e com S256 o hash é de mão única (ver o challenge não permite reconstruir o verifier). A troca no passo 6 falha para o atacante mesmo que ele tenha o code e o `client_id`.

## 4. Parâmetros e endpoints normativos

Nenhum endpoint novo — estende os parâmetros da RFC 6749:
- **`code_challenge`** (na authorization request) — obrigatório quando o client usa PKCE.
- **`code_challenge_method`** (na authorization request, opcional) — `plain` ou `S256`. Se omitido, o texto original da RFC assume `plain` como padrão — um detalhe hoje considerado prática ruim; a expectativa atual é o AS **exigir** `S256` explicitamente.
- **`code_verifier`** (no token request) — obrigatório se a authorization request usou `code_challenge`.
- Se o AS suporta PKCE e a authorization request trouxe `code_challenge`, ele **deve** exigir e validar `code_verifier` na troca — se não bater (ou estiver ausente), a resposta é `invalid_grant`.

## 5. Segurança já tratada na própria RFC 7636 (§5)

- **`plain` vs `S256`**: com `plain`, o challenge **é** o verifier — qualquer um que veja a requisição de autorização inicial (histórico de browser, proxy, log) também vê o verifier, anulando a proteção para aquela requisição específica. Com `S256`, ver o challenge não permite derivar o verifier (hash unidirecional) — por isso a RFC já recomendava `S256` como preferencial, e a prática atual é essencialmente exigi-lo sempre, evitando `plain` a menos que o dispositivo seja incapaz de SHA-256.
- **Ataque de downgrade**: um atacante que force o client a não usar PKCE (ou a cair para `plain`) reabre a janela original. Mitigação: o AS deve aplicar PKCE de forma consistente por política (hoje, universalmente — ver RFC 9700), não apenas quando o client "lembra" de mandar o parâmetro.
- Note que PKCE mitiga **interceptação do code**, não CSRF por si só — a RFC 9700 discute que o `code_verifier` só serve como proteção CSRF adicional se o client o vincular à sessão do browser (ex.: um cookie); sozinho, sem esse vínculo, PKCE não substitui `state`.

## 6. Relação com outras RFCs

- É a mitigação direta e nomeada da ameaça de interceptação de authorization code catalogada na **RFC 6819** — fecha o ciclo que abrimos naquele capítulo.
- Escopada originalmente (o próprio título da RFC diz) para **clients públicos** — a **RFC 9700** torna obrigatória para **todo client**, inclusive confidencial: mesmo com `client_secret`, PKCE protege se o secret vazar, já que o verifier é um segredo adicional e independente.
- No draft **OAuth 2.1**, PKCE deixa de ser uma "extensão opcional" e passa a fazer parte da própria definição do Authorization Code Grant.
- Interage com as próximas RFCs do roteiro (**RFC 9126 PAR**, **RFC 9101 JAR**) — ambas mudam **como** o `code_challenge` é transmitido (via back-channel ou objeto de requisição assinado, em vez de query string crua), mas não alteram o mecanismo de verificação em si.

## 7. O que mudou desde a publicação (2015)

- De "recomendado para clients públicos" para "obrigatório para todo client" (RFC 9700, uma década depois).
- `plain` como método, embora ainda definido, é hoje considerado essencialmente obsoleto na prática — implementações bem-comportadas exigem `S256`.
- PKCE deixou de ser só uma mitigação para apps nativos e passou a ser parte central da arquitetura recomendada para SPAs também — junto com a substituição do Implicit Grant por Authorization Code + PKCE.

> **Observação sobre o lab**: o `rfc6749/authorization-server` e o `client-demo` implementam o Authorization Code Grant conforme o piso da RFC 6749, **sem PKCE** — não há `code_challenge`/`code_verifier` em nenhum passo do fluxo. Esse gap foi fechado em [`rfc7636/`](../../rfc7636/README.md): réplica autocontida do lab da RFC 6749, com PKCE (S256 obrigatório) na Authorization Code Grant, um fluxo dedicado que simula interceptação de code com `code_verifier` incorreto (mostrando a rejeição `invalid_grant` na prática), e revogação de token (RFC 7009) com cascata por família.
