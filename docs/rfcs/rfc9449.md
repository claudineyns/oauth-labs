# RFC 9449 — OAuth 2.0 Demonstrating Proof of Possession (DPoP)

[← voltar ao roteiro](../oauth-guide.md)

## 1. Contexto e motivação

Mesmo problema de fundo da RFC 8705 (mTLS): bearer token roubado = acesso total até expirar, fraqueza que a RFC 6750 já apontava desde o capítulo 2 deste roteiro. Mas mTLS exige PKI completa, certificados, e sofre com o problema real de terminação de TLS em gateways/load balancers que já discutimos. O DPoP propõe uma alternativa **mais leve**: sender-constraining implementado inteiramente na **camada de aplicação**, com um par de chaves assimétrico comum — sem PKI, sem certificado, sem CA — funcionando sobre HTTPS normal, sobrevivendo a qualquer proxy no meio do caminho, porque nada depende da conexão TLS em si, só de um objeto assinado enviado como header HTTP comum.

É particularmente atraente para clients públicos — SPAs, apps mobile, CLIs — que já conseguem gerar/guardar um par de chaves localmente (Web Crypto API no browser, secure enclave no mobile) sem precisar gerenciar um ciclo de vida de certificado.

## 2. Terminologia e papéis

Nenhum papel novo. Introduz:
- **DPoP proof** — um JWT **assinado a cada requisição individual** (não uma vez por token — uma vez por *chamada*), carregando `htm` (método HTTP), `htu` (URI, sem query/fragmento), `iat`, `jti` (único por proof), e a **chave pública do client embutida no próprio header** (`jwk`).
- **Header `DPoP`** — carrega esse JWT de prova em cada requisição, tanto ao obter o token quanto ao usá-lo.
- **Token vinculado a DPoP** — `token_type: DPoP` (não `Bearer`!) — só é válido se acompanhado de uma prova DPoP correspondente à chave usada na emissão.
- **`ath`** (access token hash) — quando a prova acompanha uma chamada ao resource server, carrega um hash do próprio access_token, amarrando a prova aquele token específico.
- **`jkt`** (JWK thumbprint) — aparece na claim `cnf` do token emitido (`cnf.jkt`), espelhando exatamente o `cnf.x5t#S256` da RFC 8705 — só que aqui é o thumbprint da chave pública, não de um certificado.

## 3. Fluxo

**1. Client gera um par de chaves** (uma vez, guardado localmente).

**2. Requisição de token, com prova DPoP:**
```
POST /token
DPoP: <JWT: header={typ:"dpop+jwt", alg, jwk:<chave publica>}, payload={htm:"POST", htu:"https://as.exemplo.com/token", iat, jti}>
grant_type=...&code=...

AS valida a prova (assinatura bate com o jwk embutido, htm/htu conferem, iat recente, jti nao repetido)
AS emite o access_token com token_type=DPoP, vinculado: cnf.jkt = thumbprint dessa chave
```

**3. Requisição de recurso, com uma prova NOVA (fresca por requisição) + o token vinculado:**
```
GET /api/recurso
Authorization: DPoP <access_token>      — repare: esquema "DPoP", não "Bearer"!
DPoP: <JWT: header={jwk: mesma chave publica}, payload={htm:"GET", htu:"https://rs.exemplo.com/api/recurso", iat, jti, ath:<hash do access_token>}>

RS valida:
1) o access_token em si (introspeccao ou JWT local) — confirma cnf.jkt = X
2) a assinatura da prova bate com o jwk do proprio header da prova
3) calcula o thumbprint desse jwk, compara com cnf.jkt do token — precisa bater
4) htm/htu conferem com esta requisicao exata
5) ath bate com o hash do access_token apresentado
6) jti nao foi reaproveitado (dentro de uma janela razoavel)
```

A diferença mecânica central em relação ao mTLS: em vez de amarrar a uma **conexão** (certificado TLS), o DPoP amarra a uma **chave usada para assinar uma prova nova a cada requisição** — sem exigência nenhuma de camada de transporte, sobrevive a qualquer proxy no meio do caminho.

## 4. Parâmetros e endpoints normativos

- **Header `DPoP`** — novo, carrega a prova, tanto na requisição de token quanto na de recurso.
- **Esquema `Authorization: DPoP <token>`** — substitui `Bearer` para tokens vinculados assim; detalhe visível na própria mensagem HTTP.
- `token_type` na resposta do token endpoint vira `DPoP`, não `Bearer`.
- Descoberto via RFC 8414: `dpop_signing_alg_values_supported`.
- Erro característico no resource server: token DPoP apresentado sem prova válida/correspondente → `401` com `WWW-Authenticate: DPoP ...` e algo como `error="invalid_dpop_proof"`.
- O header da prova DPoP deve trazer `typ: dpop+jwt` — mesmo princípio de autodeclaração de tipo que já vimos em `typ: at+jwt` na RFC 9068, mesma razão: evitar que uma prova DPoP seja confundida com qualquer outro JWT.

## 5. Segurança já tratada na própria RFC 9449

- **Proteção contra replay via `jti` + janela curta de `iat`**: como cada requisição exige uma prova nova, o servidor pode aplicar uma janela de frescor bem apertada (rejeitar provas com `iat` de mais de poucos segundos atrás) e rastrear `jti`s recentes — proteção de replay muito mais rígida que um único bearer token de vida longa, já que uma prova capturada fica inútil quase imediatamente.
- **`htm`/`htu` amarram a prova à requisição exata**: uma prova feita para uma chamada específica (método + URL) não serve para outra, mesmo capturada a tempo.
- **`ath` amarra a prova ao token**: impede que um atacante que tenha capturado um access_token válido **e** alguma prova DPoP não relacionada (de outra chave/outro token) misture os dois — a prova precisa referenciar explicitamente o hash do token com que está sendo usada.
- **A chave privada nunca sai do client** — mesma garantia central do mTLS/`private_key_jwt`: só a prova (uma assinatura) trafega, nunca a chave. Clients em browser podem usar chaves não-extraíveis (Web Crypto API) — mesmo JS malicioso na mesma página não consegue exfiltrar a chave em si (embora ainda possa pedir ao browser para assinar provas arbitrárias enquanto tiver acesso — DPoP protege contra roubo/replay de token na rede, não contra um runtime de client totalmente comprometido).
- Comparado ao mTLS: DPoP não tem os mesmos controles de revogação em nível de PKI (listas de revogação de certificado, controles de CA) — mas para a ameaça específica de "token roubado da rede ou de um log", é igualmente eficaz, a um custo de infraestrutura muito menor.

## 6. Relação com outras RFCs

- Irmã direta/alternativa da **RFC 8705 (mTLS)** — mesmo objetivo (sender-constraining contra a fraqueza de bearer da RFC 6750), mecanismo diferente (prova assinada na aplicação vs. certificado na camada TLS). A RFC 9700 recomenda qualquer um dos dois.
- `cnf.jkt` em access tokens JWT é a instância específica do DPoP do mesmo ponto de extensão `cnf` que a RFC 9068 definiu e a RFC 8705 já usava (com `x5t#S256`) — mesma estrutura, mecanismos diferentes.
- `typ: dpop+jwt` espelha exatamente o mesmo princípio de autodeclaração de tipo do `typ: at+jwt` da RFC 9068.
- Descoberto via `dpop_signing_alg_values_supported` da RFC 8414.
- Particularmente adequado a clients públicos (SPAs, mobile, CLI) que já geram chave efêmera — resolve a lacuna de autenticação forte para esse tipo de client que já discutimos nos capítulos da RFC 6749/RFC 9700, sem exigir `client_secret` nem PKI.
- No seu contexto FSI: **FAPI 2.0 trata DPoP como um dos dois mecanismos aceitáveis de sender-constraining** (ao lado de mTLS) no perfil baseline.

## 7. O que mudou desde a publicação (2023)

- Uma das RFCs mais recentes deste roteiro — adoção crescendo ativamente, sobretudo em arquiteturas com muito SPA/mobile, onde o custo de PKI do mTLS sempre foi mal ajustado.
- Cada vez mais vista como recomendação padrão para sender-constraining em implantações novas que ainda não têm infraestrutura de mTLS, dado o custo operacional bem menor.
- Suporte de ferramentas (integração com Web Crypto API em bibliotecas OAuth, SDKs mobile) amadureceu rápido desde a publicação.

> **Nota de laboratório**: implementado em [`rfc9449/`](../../rfc9449/README.md) — confirmando a observação acima, roda em HTTP puro, sem quebrar a simplificação mantida até a RFC 8705. Client público (sem `client_secret`, sem `jwks` pré-registrada — a chave viaja embutida em cada prova). Todo `access_token`/`refresh_token` carrega `cnf_jkt`; o AS valida a prova na emissão (inclusive conferindo, na renovação, que a prova vem da mesma chave já vinculada ao `refresh_token`), e o RS valida na chamada ao recurso. Os logs de montagem (`logs.sh client`) e validação passo a passo (`logs.sh as`/`logs.sh rs`) foram um requisito explícito deste lab — cada checagem (assinatura, `typ`, `htm`/`htu`, janela de `iat`, `jti`, `ath`, thumbprint vs. `cnf.jkt`) é logada individualmente, com o motivo exato de rejeição quando falha. Dois botões de ataque: usar o token como `Bearer` simples (sem prova) e reenviar a mesma prova (replay) — ambos corretamente rejeitados.
