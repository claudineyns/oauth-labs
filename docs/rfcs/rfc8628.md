# RFC 8628 — OAuth 2.0 Device Authorization Grant

[← voltar ao roteiro](../oauth-guide.md)

## 1. Contexto e motivação

Nenhum dos 4 grants originais da RFC 6749 serve bem um dispositivo sem browser utilizável e sem teclado decente — smart TVs, dispositivos de streaming, consoles, CLIs, IoT. Antes desta RFC (2019), as opções eram todas ruins: implementar um teclado na tela para digitar usuário/senha (péssima UX, e reintroduz o próprio anti-padrão que o OAuth existe para eliminar), usar ROPC (também ruim, e depois deprecado), ou simplesmente não ter um jeito padronizado de fazer autorização delegada nesse tipo de dispositivo.

A ideia central: **tirar a etapa de digitação de credenciais do dispositivo limitado** e transferi-la para um segundo dispositivo que o usuário já tem à mão (celular, notebook) e que tem browser e teclado de verdade. O dispositivo limitado só mostra um código curto e uma URL; o usuário acessa essa URL em outro aparelho, digita o código, se autentica normalmente — e o dispositivo original fica consultando o AS em segundo plano até a autorização ser concluída.

Exemplo que praticamente todo mundo já viu: "Para ativar, acesse netflix.com/ativar e digite o código ABCD-1234" na Smart TV — essa experiência **é** esta RFC.

## 2. Terminologia e papéis

O dispositivo (o client) não tem user-agent utilizável — não há redirect de navegador em nenhum momento deste fluxo. Vocabulário novo:
- **`device_code`** — opaco, alta entropia, fica só no dispositivo, nunca é mostrado ao usuário; usado para consultar (poll) o token endpoint.
- **`user_code`** — curto, pensado para digitação humana (charset restrito, evita caracteres ambíguos como `0`/`O`, `1`/`I`/`l`) — é o que aparece na tela do dispositivo e o usuário digita no segundo aparelho.
- **`verification_uri`** — a URL curta que o usuário acessa no segundo dispositivo.
- **`verification_uri_complete`** (opcional) — mesma URL já com o `user_code` embutido como query param, útil para QR code (usuário só escaneia, sem digitar nada).

## 3. Fluxo

```
1. Device → AS: POST /device_authorization   client_id=...&scope=...
2. AS → Device: { device_code, user_code, verification_uri, verification_uri_complete, expires_in, interval }
3. Device exibe: "Acesse <verification_uri> e digite o código <user_code>" (ou um QR code)
4. Usuário, em OUTRO dispositivo: abre verification_uri, digita o user_code (ou escaneia o QR)
5. AS autentica o usuário normalmente — mesma tela de login/consentimento do Authorization Code Grant
6. Enquanto isso, Device consulta em loop:
   POST /token  grant_type=urn:ietf:params:oauth:grant-type:device_code&device_code=...&client_id=...
   - AS responde authorization_pending (400) enquanto o passo 4-5 nao terminou
   - Device espera `interval` segundos entre tentativas (AS pode responder slow_down se o poll for rapido demais)
7. Assim que o usuario conclui a autorizacao, o proximo poll retorna a resposta normal de token (access_token, refresh_token...)
```

## 4. Parâmetros e endpoints normativos

- **Device authorization endpoint** — novo endpoint, `POST /device_authorization` (URI definida pelo AS; descoberta depois via RFC 8414 como `device_authorization_endpoint`).
- Request: `client_id` (obrigatório), `scope` (opcional).
- Response: `device_code`, `user_code`, `verification_uri`, `verification_uri_complete` (opcional), `expires_in`, `interval` (padrão 5s se omitido).
- **Reaproveita o `/token` existente da RFC 6749**, com um `grant_type` novo: `urn:ietf:params:oauth:grant-type:device_code` — não cria um mecanismo de emissão paralelo.
- **Erros específicos do polling (§3.5)**: `authorization_pending` (ainda aguardando), `slow_down` (client consultando rápido demais, deve aumentar o intervalo em pelo menos 5s), `access_denied` (usuário negou), `expired_token` (usuário demorou demais, `device_code`/`user_code` expiraram).

## 5. Segurança já tratada na própria RFC 8628 (§5)

- **Entropia baixa do `user_code` é uma escolha deliberada** (precisa ser digitável por humano) — a RFC exige que o AS **limite tentativas** (rate limiting) contra o endpoint de verificação, e recomenda expiração curta (minutos) para reduzir a janela de força bruta. É um perfil de risco bem diferente dos tokens de alta entropia do resto do OAuth, e a RFC é explícita sobre essa contrapartida.
- **`device_code` deve ficar confidencial** no dispositivo — como esse grant costuma ser usado por clients públicos (sem `client_secret`), ele funciona, durante a janela de espera, quase como uma credencial ao portador.
- **`slow_down`/`interval`** protegem o AS contra polling agressivo.
- A RFC já reconhece risco de phishing (mostrar um código real para induzir o usuário a autorizar algo que não pediu), mas sem uma defesa estrutural forte além de recomendar que a tela de consentimento deixe claro **quem** está pedindo acesso — o problema completo só ficaria evidente na prática, anos depois (ver item 7).

## 6. Relação com outras RFCs

- Adiciona um 5º grant type à **RFC 6749**, para a classe de dispositivo que os 4 originais não atendiam bem.
- Reaproveita a infraestrutura do token endpoint da RFC 6749 — só um `grant_type` novo, sem endpoint de emissão paralelo.
- Descoberto via **RFC 8414** como `device_authorization_endpoint` — mesmo padrão de descoberta de `revocation_endpoint`/`introspection_endpoint`, categoria 4 do roteiro.
- **PKCE (RFC 7636) não se aplica aqui** — não há `redirect_uri` nem interceptação de code neste fluxo; é um risco de forma diferente (ver item 5).
- Fecha o ciclo com a **RFC 6819**: no capítulo daquela RFC, já apontei que "phishing de device code" é uma classe de ameaça que só existiria depois da publicação da 8628 (2019) — este é o capítulo onde essa ameaça finalmente aparece.
- Fora do roteiro, mas conceitualmente parente: **CIBA** (Client-Initiated Backchannel Authentication, extensão OpenID Connect) — outro padrão de autenticação "desacoplada" do dispositivo que inicia o pedido.

## 7. O que mudou desde a publicação (2019)

- A spec em si permanece estável, sem revisão formal — mas um padrão de abuso real emergiu **depois** da publicação e não estava no radar do threat model original: **phishing de device code**. O atacante inicia o próprio fluxo (obtém um `user_code` legítimo) e engana a vítima — por pretexto de "suporte técnico", por exemplo — para que ela acesse a `verification_uri` e digite o código do atacante, autenticando-se para a sessão do atacante. Foi explorado em campanhas reais e amplamente reportadas contra contas Microsoft 365 a partir de 2022.
- Mitigações que surgiram depois são **práticas operacionais**, não emendas formais à RFC: exibir contexto adicional durante o consentimento para dificultar o pretexto (ex.: "number matching" — pedir que o usuário confirme um número específico exibido no dispositivo original), reduzir a vida útil do código, e orientação de conscientização de segurança.
- Vale reter: este é um exemplo direto de um grant tecnicamente correto, cujo risco real só apareceu com a escala de uso em produção — o tipo de lição que a RFC 6819 tenta antecipar, mas nem sempre consegue.

> **Nota de laboratório**: este grant tem uma forma visualmente diferente dos demais labs do projeto (sem redirect, com um loop de polling) — um bom candidato a laboratório futuro, simulando um "dispositivo" fazendo polling enquanto um segundo "aparelho" (outra aba do browser) completa a autorização.
