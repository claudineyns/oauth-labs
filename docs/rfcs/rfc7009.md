# RFC 7009 — OAuth 2.0 Token Revocation

[← voltar ao roteiro](../oauth-guide.md)

## 1. Contexto e motivação

RFC 6749 define como obter um token, RFC 6750 como usá-lo — mas nenhuma das duas define uma forma padronizada de **desfazer** isso: dizer ao authorization server "este token não vale mais, invalide agora". Antes da RFC 7009, revogação era proprietária de cada AS (quando existia), sem endpoint interoperável.

Cenário motivador central: o usuário faz logout de um client. Sem revogação, o client só pode "esquecer" o token localmente — o token continua tecnicamente válido no AS/RS até expirar naturalmente. Outro cenário: um refresh token vaza ou é suspeito de comprometimento — revogá-lo imediatamente limita o dano, em vez de esperar o TTL passar. A RFC 7009 fecha essa lacuna com um único endpoint novo: o **revocation endpoint**.

## 2. Terminologia e papéis

Nenhum papel novo. Introduz **revogação** como uma ação de primeira classe — antes, o único jeito de um token "morrer" no OAuth 2.0 puro era por expiração natural.

## 3. Fluxo — uma única requisição

Simples e síncrono: o client autentica-se e informa qual token revogar.

```
POST /revoke HTTP/1.1
Host: as.exemplo.com
Content-Type: application/x-www-form-urlencoded
Authorization: Basic czZCaGRSa3F0MzpnWDFmQmF0M2JW

token=45ghiukldjahdnhzdauz&token_type_hint=refresh_token
```

Resposta em caso de sucesso: **`200 OK`, corpo vazio** — e aqui está o detalhe mais importante da RFC: a resposta é `200` **independentemente** de o token existir, já estar expirado ou já ter sido revogado antes. Só há erro se a requisição for malformada ou a autenticação do client falhar.

## 4. Parâmetros e endpoints normativos

- **Revocation endpoint** — novo endpoint (URI definida pelo AS, tipicamente `/revoke`; mais tarde tornou-se descobrível via RFC 8414 como o campo `revocation_endpoint`).
- **`token`** (obrigatório) — o valor do token a revogar (access ou refresh token).
- **`token_type_hint`** (opcional) — `access_token` ou `refresh_token`, uma dica para o AS otimizar a busca; se o hint não bater, o AS ainda deve tentar o outro tipo antes de desistir.
- **Autenticação do client** — as mesmas regras do token endpoint (client confidencial deve se autenticar; client público deve, no mínimo, apresentar seu `client_id`, e o AS deve validar que é o mesmo client ao qual o token foi emitido).
- **Semântica de cascata (§2.1)**: revogar um `access_token` não implica revogar o `refresh_token` associado (fica a critério do AS). Revogar um **`refresh_token`**, porém, **deveria** também invalidar todo `access_token` derivado dele — senão a revogação vira meio-efeito: o refresh morre, mas o access token continua vivo até expirar sozinho.

## 5. Segurança já tratada na própria RFC 7009

- **`200 OK` sempre, mesmo para token inexistente/já revogado** — decisão deliberada para não transformar o endpoint num oráculo: um atacante não consegue usar respostas diferentes para descobrir se um token "adivinhado" é válido. Mesmo raciocínio da RFC 6750 ao não vazar `error_description` para quem não tentou se autenticar.
- **Autenticação obrigatória do client** — impede que qualquer parte não relacionada revogue o token de outra pessoa (um vetor de negação de serviço óbvio se o endpoint fosse aberto).
- **Cascata refresh → access recomendada** — evita que a revogação pareça bem-sucedida mas deixe tokens filhos "esquecidos" ainda válidos.
- TLS obrigatório, como em todo endpoint que manipula token/credencial.

## 6. Relação com outras RFCs

- Completa o ciclo de vida iniciado pela RFC 6749 (emissão) e pela RFC 6750 (uso) — a 7009 é o "desligar".
- Descoberto formalmente via **RFC 8414** (Authorization Server Metadata) como `revocation_endpoint` — categoria 4 do roteiro.
- Complementar (não sobreposto) à **RFC 7662 (Token Introspection)**: introspecção responde "esse token ainda é válido, quais são as claims?"; revogação executa "invalide esse token agora". Geralmente coexistem no mesmo AS como endpoints irmãos.
- A recomendação de **rotação de refresh token com detecção de reuso** da RFC 9700 depende diretamente da revogação em cascata desta RFC — detectar reuso sem uma revogação rápida e eficaz por trás é só metade da mitigação.

## 7. O que mudou desde a publicação (2013)

- A RFC em si permanece estável e amplamente implementada, sem revisões relevantes.
- O que mudou ao redor dela: passou de "endpoint proprietário, se existir" para campo padrão e esperado no discovery document (RFC 8414) de qualquer AS moderno.
- Com a rotação de refresh token + detecção de reuso da RFC 9700 (2025), revogação deixou de ser só um "recurso de conveniência para logout" e virou **infraestrutura de segurança ativa** — a resposta a um sinal de comprometimento depende dela funcionar rápido.
- Tokens sender-constrained (DPoP/mTLS) reduzem um pouco a urgência de revogação como *resposta a roubo* (posse sozinha deixa de bastar) — mas revogação continua essencial para logout legítimo e retirada de consentimento, que são cenários independentes de roubo.

> **Observação sobre o lab**: o `rfc6749/authorization-server` já faz rotação de refresh token (invalida o antigo a cada uso), mas ainda não expõe um endpoint `/revoke` nem um botão de logout que efetivamente revoga no AS (o "sair" do client demo hoje só limpa a sessão local). Esse é o gap natural que um lab da RFC 7009 fecharia.
