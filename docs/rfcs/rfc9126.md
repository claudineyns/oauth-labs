# RFC 9126 — OAuth 2.0 Pushed Authorization Requests (PAR)

[← voltar ao roteiro](../oauth-guide.md)

## 1. Contexto e motivação

A requisição de autorização tradicional (RFC 6749 §4.1.1) manda todos os parâmetros como query string, via o browser (front-channel): `GET /authorize?response_type=code&client_id=...&redirect_uri=...&scope=...&state=...&code_challenge=...&code_challenge_method=...`. Conforme extensões se acumulam — PKCE, Resource Indicators, Rich Authorization Requests — essa URL cresce, e cresce exposta exatamente onde a RFC 6750 já nos ensinou a não colocar nada sensível: **histórico do browser, logs de servidor/proxy, header `Referer`**.

Tem um segundo problema, mais sutil: como os parâmetros chegam ao AS via uma URL que passou pelo browser do usuário, a integridade deles depende de um canal que não é autenticado como vindo do client — nada impede, em tese, adulteração no caminho (extensão de browser maliciosa, cadeia de redirecionamento manipulada) antes de chegar ao AS.

A solução da RFC 9126: o client **empurra** (push) todos os parâmetros da requisição de autorização direto para o AS, por um canal autenticado nos bastidores (back-channel, POST), *antes* de tocar o browser. Em troca, recebe uma referência curta e opaca — o `request_uri` — que é tudo que vai para a URL que o browser efetivamente vê.

## 2. Terminologia e papéis

Nenhum papel novo. Introduz:
- **Pushed Authorization Request endpoint** — endpoint novo (comumente `/par`), onde o client faz o POST autenticado com os parâmetros.
- **`request_uri`** — referência opaca, de vida curta e uso único, devolvida pelo PAR endpoint, usada no lugar da lista de parâmetros na requisição de autorização de fato.

## 3. Fluxo

```
1. Client → AS: POST /par  (autenticado — client_secret, mTLS, private_key_jwt...)
   response_type=code&client_id=...&redirect_uri=...&scope=...&state=...&code_challenge=...&code_challenge_method=S256

2. AS valida os parametros (mesma validacao que faria num /authorize normal) e os guarda server-side

3. AS → Client: { request_uri: "urn:ietf:params:oauth:request_uri:6esc_11ACC5bwc014ltc14eY22c", expires_in: 60 }

4. Client → User-Agent: redireciona para
   GET /authorize?client_id=...&request_uri=urn:ietf:params:oauth:request_uri:6esc_11ACC5bwc014ltc14eY22c

5. AS busca os parametros guardados pelo request_uri, segue com login/consentimento normalmente
6. ... resto do Authorization Code Grant sem mudanca (redirect com code, troca por token...)
```

O ponto central: a URL que o browser efetivamente navega no passo 4 é **minúscula e opaca** — nenhum `scope`, `code_challenge` ou `redirect_uri` visível ali. `request_uri` é de uso único e vida curta (tipicamente ~60s, mesma ordem de grandeza de um authorization code) para limitar a janela de replay.

## 4. Parâmetros e endpoints normativos

- **PAR endpoint** — novo, descoberto via RFC 8414 como `pushed_authorization_request_endpoint`.
- Request: o mesmo conjunto de parâmetros de uma authorization request normal, como corpo `application/x-www-form-urlencoded`, **mais autenticação do client** (mesmos métodos do token endpoint).
- Response: `request_uri` (formato `urn:ietf:params:oauth:request_uri:<valor>`) e `expires_in`.
- A requisição de autorização em si fica reduzida a `client_id` + `request_uri` — o AS deve rejeitar se a referência for desconhecida, expirada, já usada, ou se vier acompanhada de outros parâmetros conflitantes.
- Erro característico: referência inválida/expirada/já usada (`invalid_request_uri` na terminologia comum de implementações, análogo ao "sua referência está velha").

## 5. Segurança já tratada na própria RFC 9126

- **Integridade por autenticação do canal**: como o push acontece por um back-channel autenticado, o AS tem garantia forte de que os parâmetros vieram mesmo do client registrado — diferente do front-channel via browser, sujeito a log, cache, extensão maliciosa ou simples vazamento antes de chegar ao AS.
- **Redução de exposição em URL**: mitiga diretamente a preocupação (já vista na RFC 6750 e na RFC 6819) de parâmetros sensíveis vazando via histórico de browser, `Referer` e logs de proxy — agora nada sensível trafega numa URL logável.
- **`request_uri` de uso único e vida curta** — mesma lógica do authorization code: limita a janela de replay. Vale notar que reutilizar um `request_uri` capturado não dá privilégio novo a um atacante — só reproduziria o mesmo fluxo já iniciado pelo client legítimo, para o mesmo `redirect_uri` já registrado, não abre uma rota nova.
- PAR reduz a necessidade de assinar a requisição (como a próxima RFC do roteiro, JAR, propõe) no caso simples, já que a integridade vem da autenticação do canal — mas as duas técnicas **podem se combinar**: empurrar via PAR um objeto de requisição assinado (JWT) dá integridade por assinatura *e* URL opaca ao mesmo tempo.

## 6. Relação com outras RFCs

- Generaliza o princípio que já vimos na **RFC 6750** ("nunca token na URL") para **todos** os parâmetros sensíveis da requisição de autorização, não só o token.
- Companheira direta da **RFC 9101 (JAR)**, próximo capítulo do roteiro — endereçam a mesma preocupação (integridade/tamanho do front-channel) por mecanismos diferentes e combináveis.
- Descoberta via **RFC 8414** como `pushed_authorization_request_endpoint` — mesmo padrão de descoberta das RFCs 7009/7662/8628.
- Especialmente relevante para **RFC 7636 (PKCE)**: `code_challenge`/`code_challenge_method` são exatamente o tipo de parâmetro que se beneficia de sair da URL visível.
- Recomendada pela **RFC 9700** e **exigida (não apenas recomendada)** por perfis setoriais — no seu contexto FSI, vale destacar: o **FAPI 2.0** (OpenID Foundation) torna PAR **obrigatório**, no mesmo padrão que já vimos com sender-constraining no capítulo da RFC 9700.

## 7. O que mudou desde a publicação (2021)

- Spec relativamente recente e estável; adoção cresceu bastante em setores regulados, puxada pela exigência do FAPI 2.0.
- Está seguindo a mesma trajetória que o PKCE seguiu: de "medida de hardening opcional" para "expectativa de baseline" em authorization servers voltados ao público, especialmente em contextos de alta sensibilidade.
- Combinação com JAR (RFC 9101) — "empurrar um objeto de requisição assinado" — está virando padrão comum em implementações conformes a FAPI.

> **Nota de laboratório**: nenhum lab construído ainda para esta RFC — o cenário natural seria comparar lado a lado a URL de autorização "antes" (todos os parâmetros visíveis) e "depois" (só `client_id` + `request_uri`), tornando a redução de exposição literalmente visível.
