# RFC 8693 — OAuth 2.0 Token Exchange

[← voltar ao roteiro](../oauth-guide.md)

## 1. Contexto e motivação

Cenário típico de arquitetura de microsserviços: um gateway/BFF recebe um token do app do usuário para chamar a API-1. Para atender essa chamada, o gateway precisa agora chamar a API-2 **como parte do mesmo pedido**. Repassar o **mesmo** token adiante é exatamente o anti-padrão de "confused deputy" que já discutimos no capítulo da RFC 6819 — o token foi emitido pensando na API-1, não na API-2.

A RFC 8693 resolve isso formalizando um mecanismo para **trocar um token de segurança por outro**: o gateway apresenta o token que recebeu e obtém de volta um token novo, especificamente re-direcionado (audience) e/ou re-escopado para a API-2 — carregando, de forma explícita, tanto **quem originalmente pediu** (o usuário) quanto **quem está agindo agora** (o gateway).

Também cobre cenários correlatos: tradução de formato de token (ex.: uma asserção SAML por um JWT OAuth), confiança cross-domain (trocar um token emitido por um IdP por outro aceito num sistema que confia em IdP diferente, quando há relação de confiança configurada no AS), e "downscoping" — trocar um token amplo por um mais restrito antes de repassá-lo adiante, aplicando least-privilege na própria cadeia de chamadas.

## 2. Terminologia e papéis

Introduz vocabulário genuinamente novo em relação à RFC 6749:
- **Subject** — a entidade sobre quem o token fala (tipicamente o resource owner/usuário final).
- **Actor** — quem está efetivamente agindo no momento, que pode ser diferente do subject (ex.: o gateway agindo em nome do usuário).
- **Impersonação vs. Delegação**:
  - **Impersonação** — o token novo representa só o subject; o fato de um intermediário (actor) ter solicitado a troca não fica registrado. O resource server downstream vê "isto é o usuário", como se ele tivesse chamado diretamente.
  - **Delegação** — o token novo registra **os dois**: subject e actor. O resource server downstream enxerga explicitamente "isto é o usuário, mas o gateway está agindo em nome dele agora" — uma cadeia de custódia auditável.
- **Security token** — termo deliberadamente genérico (não "access token") porque a RFC troca qualquer formato: JWT, asserção SAML, access token, ID Token, refresh token.

## 3. Fluxo

Uma única requisição ao token endpoint já existente, com um `grant_type` novo:

```
POST /token
grant_type=urn:ietf:params:oauth:grant-type:token-exchange
&subject_token=<token a trocar>
&subject_token_type=urn:ietf:params:oauth:token-type:access_token
&resource=https://api-2.exemplo.com
&scope=... (opcional, mais restrito que o original)
&actor_token=... &actor_token_type=... (opcional — presente em delegação, representa quem esta pedindo a troca)
```

Resposta no formato padrão do token endpoint, com um campo novo obrigatório: **`issued_token_type`** — informa que TIPO de token voltou (já que a troca pode devolver algo diferente de um access_token OAuth comum).

## 4. Parâmetros e endpoints normativos

Nenhum endpoint novo — reaproveita o `/token` da RFC 6749, com `grant_type=urn:ietf:params:oauth:grant-type:token-exchange`.

- **`subject_token`** (obrigatório) — o token a trocar.
- **`subject_token_type`** (obrigatório) — URI identificando o tipo (pré-registrados: `...token-type:access_token`, `:refresh_token`, `:id_token`, `:saml1`, `:saml2`, `:jwt`).
- **`actor_token` / `actor_token_type`** (opcionais) — presentes quando a troca representa delegação.
- **`resource`** / **`audience`** (opcionais) — indicam o destino pretendido do token novo.
- **`scope`** (opcional) — permite pedir um escopo mais restrito que o original.
- Resposta: formato padrão (`access_token`, `token_type`, `expires_in`, `scope`, `refresh_token` opcional) **+ `issued_token_type`** (obrigatório, novo).

## 5. Segurança já tratada na própria RFC 8693

- **Risco de escalonamento de privilégio via troca**: o AS precisa validar rigorosamente se o client que está pedindo a troca tem autorização para trocar aquele `subject_token` especificamente pelo recurso/audience pedido — sem isso, o Token Exchange vira, ele mesmo, um vetor de escalonamento (um serviço trocando um token de baixo privilégio que legitimamente possui por um de alto privilégio que não deveria conseguir).
- O AS deve aplicar política sobre **quais clients podem atuar como "actor"** em delegação, e quais combinações subject/actor são permitidas — não é "qualquer client troca qualquer token por qualquer coisa".
- O token resultante deve, em geral, **restringir ou manter** — nunca ampliar — o escopo/audience do token original. Token Exchange existe para re-direcionar e reduzir, não para ganhar privilégio.
- Cadeias de delegação (um actor trocando em nome de outro actor que já agia em nome de um subject) devem ficar registradas/auditáveis — o conceito de uma claim `act` encadeada (mais detalhada em perfis JWT posteriores) nasce daqui.

## 6. Relação com outras RFCs

- Reaproveita a infraestrutura do token endpoint da RFC 6749 — mesmo padrão de extensão via `grant_type` novo que a RFC 8628 usa.
- É a solução formal para o cenário de "confused deputy" catalogado na **RFC 6819**: em vez de replay do mesmo token entre resource servers, o mecanismo correto é trocar por um token novo, corretamente audienciado.
- Companheira direta da **RFC 8707 (Resource Indicators)** — ambas usam um parâmetro `resource` para indicar o destino do token; são specs do mesmo espaço de problema (ambientes com múltiplos resource servers). Isso é mais uma peça relevante para a pergunta em aberto que anotamos para o capítulo da RFC 8707: Token Exchange mostra que a questão de audience não é só "evitar um ataque passivamente" — é também "ter um mecanismo ativo para emitir tokens corretos em cadeias de chamada legítimas".
- Formato-agnóstica, conecta com a **RFC 7523 (JWT Profile for OAuth 2.0)** — JWT é um dos tipos de subject/actor token reconhecidos.
- Conceito equivalente ao padrão "on-behalf-of" usado por alguns provedores (ex.: Azure AD/Entra ID), que antecede e depois se alinha a esta RFC.

## 7. O que mudou desde a publicação (2020)

- Spec estável, sem revisão — mas ganhou relevância crescente com a adoção de arquiteturas de microsserviços/service mesh: Token Exchange virou peça padrão em padrões de API gateway / BFF, exatamente para o problema "chamar a API downstream com um token corretamente escopado".
- Ganhou tração em arquiteturas zero-trust, onde cada hop de serviço deveria carregar um token distintamente escopado/audienciado, em vez de um único token amplo circulando por toda a cadeia — particularmente relevante para o seu contexto FSI, em cadeias de APIs internas bancárias.
- A distinção subject/actor e o padrão de claim `act` encadeada foram adotados de forma informal por várias implementações de mercado como a forma de-facto de representar cadeias de delegação em JWTs, mesmo sem uma RFC separada fechando a estrutura exata da claim (isso vive mais em documentos de perfil/convenções de fornecedor construídas sobre esta base).

> **Nota de laboratório**: nenhum lab construído ainda para esta RFC — o cenário natural exigiria um segundo resource server e um serviço "gateway" trocando tokens entre eles, mostrando a troca como alternativa ao replay do mesmo token entre APIs.
