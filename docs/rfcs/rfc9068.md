# RFC 9068 — JSON Web Token (JWT) Profile for OAuth 2.0 Access Tokens

[← voltar ao roteiro](../oauth-guide.md)

## 1. Contexto e motivação

A RFC 6749 deixa o formato do `access_token` deliberadamente indefinido — é uma string opaca, ponto final. Essa flexibilidade foi proposital, mas criou um problema real de interoperabilidade: **vários fornecedores passaram a usar JWT como access token de forma independente, cada um com seu próprio conjunto de claims** — um resource server construído para entender o JWT de um fornecedor não entendia o de outro, mesmo os dois sendo nominalmente "access token em JWT". Boa parte do ganho de interoperabilidade que o JWT deveria trazer se perdia.

A RFC 9068 formaliza a **estrutura** de um JWT quando usado como access token — claims obrigatórias/recomendadas e, principalmente, um valor de `typ` no header que **autodeclara** "isto é especificamente um access token JWT", evitando confusão com outros tipos de JWT circulando por aí (notavelmente, o ID Token do OIDC).

## 2. Terminologia e papéis

Nenhum papel novo. Introduz:
- **JWT Access Token** — um JWT que segue este perfil específico.
- **`typ: at+jwt`** no header — marcador de tipo explícito, para diferenciar de qualquer outro JWT (como um ID Token) que por acaso tenha claims parecidas.

## 3. "Fluxo" — não há fluxo novo, é um formato aplicado ao que já existe

Esta RFC não define endpoint nem grant novo — ela governa o **formato** do valor que já volta no campo `access_token` da resposta padrão do token endpoint (RFC 6749 §5.1), quando o AS escolhe emitir tokens em JWT em vez de opacos.

Claims exigidas/recomendadas pelo perfil:
- **`iss`** (obrigatória) — o identificador do AS (mesmo valor do `issuer` da RFC 8414).
- **`exp`**, **`iat`** (obrigatórias).
- **`aud`** (obrigatória) — identifica o(s) resource server(s) destinatário(s).
- **`sub`** (obrigatória) — de quem o token fala (o resource owner, em grants delegados; o próprio client, em Client Credentials).
- **`client_id`** (obrigatória) — deliberadamente distinta de `sub`, já que num grant delegado `sub` é o usuário e `client_id` é o app agindo.
- **`jti`** (obrigatória) — identificador único do token.
- **`scope`** (recomendada) — mesma string espaço-delimitada de sempre.
- `auth_time`, `acr`, `amr` (opcionais) — descrevem como/quando o resource owner se autenticou, emprestadas conceitualmente do ID Token do OIDC.

## 4. Parâmetros e endpoints normativos

Nenhum endpoint novo. O único parâmetro normativo relevante é de **header**, não de protocolo: `typ` deve ser `at+jwt` (ou `application/at+jwt`), e `alg` precisa ser um algoritmo de assinatura de verdade (nunca `none`).

## 5. Segurança já tratada na própria RFC 9068

- **`typ: at+jwt` previne confusão de tipo de token**: sem essa autodeclaração explícita, um resource server (ou uma biblioteca mal implementada) poderia aceitar por engano um JWT emitido para **outro propósito** (um ID Token do OIDC, por exemplo, que também é um JWT com claims parecidas) como se fosse um access token válido — uma classe real de vulnerabilidade histórica ("confusão de JWT"). O `typ` explícito permite ao código de validação do RS checar, antes de confiar em qualquer outra coisa, se aquele JWT realmente foi emitido para ser um access token.
- **`aud` restringe quais resource servers podem aceitar o token** — operacionaliza diretamente a preocupação de restrição de audience que já vimos na RFC 6819 (confused deputy) e que a RFC 8707 (Resource Indicators, ainda por vir) formaliza do lado da requisição. A 9068 é o "ponto de pouso": é aqui que essa decisão de audience fica registrada dentro do próprio token.
- **Sem criptografia por padrão**: um JWT access token normalmente é assinado (JWS), não criptografado — suas claims são legíveis por qualquer um que tenha o token, diferente de um token opaco (cujo "significado" fica trancado dentro do AS). É uma troca real: legibilidade/validação local ganha, confidencialidade do conteúdo perde. A RFC permite (não exige) usar JWE por cima quando as claims forem sensíveis — o mesmo par JWS/JWE que já vimos na RFC 9101 (JAR).
- **Revogação fica mais difícil de aplicar em tempo real**: validação local por assinatura significa que o RS confia no token até o `exp`, sem checar de novo com o AS — a mesma troca que já apontamos no capítulo da RFC 7662 (introspecção): JWT evita o round-trip de rede, mas perde a capacidade do AS dizer "na verdade, acabei de revogar esse token" no meio da vida dele. Mitigado, na prática, com tempos de vida curtos ou um padrão híbrido (JWT para o caso comum + checagem extra de revogação só em operações de alto valor).

## 6. Relação com outras RFCs

- Estratégia concorrente/complementar direta à **RFC 7662 (Introspecção)** — o "ponto de pouso" da troca já discutida no capítulo anterior: validar localmente por assinatura vs. perguntar ao AS a cada requisição.
- `iss` amarra diretamente ao `issuer` do metadata da **RFC 8414** — mesmo valor, mesma âncora de identidade.
- `aud` é o mecanismo concreto que operacionaliza a preocupação de audience da **RFC 6819**, e é o alvo natural do que a **RFC 8707 (Resource Indicators)** deixa o *client* pedir do lado da requisição — vale reter a divisão: 8707 é sobre o pedido ("quero um token para ESTE recurso"), 9068 é sobre o token ("é aqui que essa decisão fica registrada").
- É um dos formatos que o `issued_token_type` da **RFC 8693 (Token Exchange)** pode indicar — a troca de token pode devolver exatamente um JWT seguindo este perfil.
- `jti` espelha o mesmo conceito de unicidade/controle de replay já visto no `client_assertion` da RFC 7523.
- Não precisa de relação especial com a **RFC 7519 (JWT)** além de ser a spec de formato-base sobre a qual este perfil se apoia — é exatamente por isso que a 7519 não tem capítulo próprio neste roteiro, mas aparece referenciada em vários pontos.

## 7. O que mudou desde a publicação (2021)

- Relativamente recente, mas com espírito retroativo: formaliza algo que **muitos fornecedores já faziam de forma ad-hoc havia anos** — JWT como access token já existia na prática bem antes de 2021, só sem estrutura comum. Por isso a adoção foi rápida: formalizou prática já existente em vez de introduzir algo totalmente novo.
- Cada vez mais tratada como expectativa padrão para novas implementações de AS que optam por tokens em formato JWT, em vez de cada fornecedor reinventar nomes de claim.
- Conecta com uma tendência maior, que veremos nos próximos capítulos (RFC 8705 mTLS, RFC 9449 DPoP): amarrar o access token JWT a uma chave/certificado específico via uma claim `cnf` (confirmation) — exatamente o ponto de extensão que este perfil habilita para sender-constraining.

> **Nota de laboratório**: nenhum lab construído ainda para esta RFC — todos os labs deste projeto emitem tokens **opacos** (48 caracteres hex), nunca JWT. Seria o gap natural: trocar o formato do `access_token` por um JWT seguindo este perfil, e então o resource server passaria a validar por assinatura local em vez de ler o Redis diretamente (fechando também o gap que já apontamos no capítulo da RFC 7662).
