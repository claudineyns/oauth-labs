# RFC 8705 — OAuth 2.0 Mutual-TLS Client Authentication and Certificate-Bound Access Tokens

[← voltar ao roteiro](../oauth-guide.md)

## 1. Contexto e motivação

Esta RFC define **duas coisas distintas**, do mesmo jeito que a RFC 7523 definia duas metades independentes — vale separar de novo para não confundir:

- **mTLS como autenticação de client**: o client se autentica no AS apresentando um certificado X.509 durante o próprio handshake TLS, em vez de (ou além de) qualquer credencial no nível OAuth. É mais uma alternativa assimétrica ao `client_secret`, ao lado do `private_key_jwt` (RFC 7523 §2.2) que já vimos.
- **Tokens vinculados a certificado (certificate-bound)**: o AS amarra o access_token emitido ao certificado usado na conexão — mesmo que o token (bearer) vaze, ele só funciona em conexões que reapresentem o **mesmo certificado**. É o mecanismo de *sender-constraining* que a RFC 6750 já apontava como necessário desde o segundo capítulo deste roteiro: "bearer token roubado = acesso total até expirar" — esta RFC (e a próxima, DPoP) são as duas respostas a isso.

As duas metades são combináveis e, na prática, o valor real está em usá-las **juntas**: autenticar via mTLS *e* vincular o token resultante ao mesmo certificado.

> **Marco do projeto**: é aqui, formalmente, que os labs deste projeto passam a precisar de TLS de verdade — até agora, HTTP puro foi uma simplificação deliberada (ver [[feedback-tls-deferred]]), mantida exatamente até este capítulo.

## 2. Terminologia e papéis

Nenhum papel novo. Introduz:
- **`tls_client_auth`** — o client apresenta um certificado X.509 emitido por uma PKI que o AS confia (cadeia validada até uma CA confiável) — modelo tradicional de PKI corporativa.
- **`self_signed_tls_client_auth`** — o client usa um certificado **autoassinado**, mas sua chave pública foi pré-registrada no AS fora de banda — sem cadeia de CA, o AS só confere "essa chave bate com o que tenho registrado para este client_id?" — mesmo espírito de confiança prévia do `private_key_jwt` (RFC 7523), só que via certificado em vez de JWK.
- **Token vinculado a certificado** — um access_token (opaco ou JWT) associado ao certificado do client, seja no armazenamento do AS (token opaco) ou como claim `cnf` dentro do próprio JWT (RFC 9068 — exatamente o ponto de extensão que já antecipamos no capítulo anterior).

## 3. Fluxo

**Autenticação do client via mTLS, no token endpoint:**
```
Handshake TLS: client apresenta certificado X.509
               (validado via PKI — tls_client_auth —
                ou via chave pré-registrada — self_signed_tls_client_auth)

POST /token   (sobre essa mesma conexao mTLS)
grant_type=...&client_id=...   — sem client_secret, sem client_assertion:
                                  o certificado É a credencial
```

**Emissão do token vinculado** (automática, quando o AS suporta):
```
Ao emitir o access_token, o AS calcula o thumbprint SHA-256 do certificado
usado no handshake e o vincula ao token:
  - token opaco: guardado server-side, associado ao registro do token
  - token JWT:   embutido como cnf: { "x5t#S256": "<thumbprint>" }
```

**Validação no resource server:**
```
Client → RS: mesma conexao mTLS (apresenta o certificado de novo)
             + Authorization: Bearer <token vinculado>

RS: 1) valida o token normalmente (introspeccao ou verificacao local do JWT)
    2) calcula o thumbprint do certificado apresentado NESTA conexao
    3) compara com o thumbprint vinculado ao token
    4) thumbprint diferente → rejeita, mesmo que o token em si seja "valido"
```

Esse passo 4 é a propriedade de segurança central: só possuir a string do bearer token deixa de ser suficiente — é preciso também ter a chave privada correspondente para reestabelecer a conexão mTLS com o mesmo certificado.

## 4. Parâmetros e endpoints normativos

- Nenhum endpoint novo — estende a autenticação do token endpoint com 2 métodos novos (`tls_client_auth`, `self_signed_tls_client_auth`), registrados via `token_endpoint_auth_method` no registro do client (RFC 7591).
- Resposta de introspecção (RFC 7662) ganha um membro `cnf` com `x5t#S256` quando o token introspectado é vinculado a certificado.
- JWT access tokens (RFC 9068) carregam `cnf.x5t#S256` quando vinculados.
- Descoberto via RFC 8414: `tls_client_certificate_bound_access_tokens` (booleano) + os dois métodos aparecendo em `token_endpoint_auth_methods_supported`.

## 5. Segurança já tratada na própria RFC 8705

- Fecha exatamente a fraqueza estrutural que a RFC 6750 já apontava desde o início deste roteiro: bearer token roubado deixa de bastar sem a chave privada correspondente.
- **Terminação de mTLS num proxy/load balancer quebra tudo isso** — se um gateway termina o TLS antes da requisição chegar ao AS/RS, eles nunca veem o certificado real do client; ele precisa ser repassado por um canal confiável (um header assinado que o backend só aceita porque confia especificamente naquele gateway, via mTLS entre gateway e backend). Essa é **exatamente** a preocupação que já levantamos na discussão sobre gateway do cenário B — o "TLS termination quebra mTLS" que ficou marcado como pendência lá atrás.
- **Rotação de certificado**: como o token está amarrado a um certificado específico, quando o client renova/troca o certificado, tokens já emitidos e vinculados ao certificado antigo ficam inutilizáveis — tempos de vida curtos de token ajudam a absorver isso naturalmente, sem precisar de um mecanismo explícito de "migrar" vínculos.
- **Modelo de confiança do `self_signed_tls_client_auth`**: sem cadeia de CA, o AS depende inteiramente de ter pré-registrado a chave pública exata esperada para aquele `client_id` — mesma disciplina de confiança prévia do JWKS na RFC 7523.

## 6. Relação com outras RFCs

- Resolve diretamente a fraqueza que a **RFC 6750** já sinalizava desde o capítulo 2 deste roteiro — um bom fechamento de ciclo.
- Estende a **RFC 9068** (JWT access tokens) via `cnf.x5t#S256`, e a **RFC 7662** (introspecção) via o membro `cnf` na resposta — ambas referenciadas antecipadamente nos capítulos anteriores.
- Método de autenticação de client alternativo ao **`private_key_jwt`** (RFC 7523 §2.2) — os dois são baseados em chave assimétrica (sem segredo compartilhado), mas mTLS reaproveita infraestrutura de PKI/TLS, enquanto `private_key_jwt` usa JWS/JWKS. A RFC 9700 recomenda qualquer um dos dois sobre segredo estático, sem preferir um especificamente — é escolha de implantação, conforme a infraestrutura já existente.
- Irmã direta da **RFC 9449 (DPoP)**, próximo capítulo — as duas são mecanismos de *sender-constraining*, resolvendo o mesmo problema (roubo de bearer token) por caminhos diferentes: mTLS amarra na camada de transporte (exige PKI/mTLS completo, mais pesado, mais forte), DPoP amarra na camada de aplicação (mais leve, sem PKI, funciona sobre HTTPS comum sem a complicação de terminação de mTLS).
- Descoberta via **RFC 8414** através dos novos campos de metadata.

## 7. O que mudou desde a publicação (2020)

- Spec estável, cada vez mais exigida (não só recomendada) em setores de alta garantia — no seu contexto FSI, vale lembrar: **FAPI 2.0 trata sender-constraining (mTLS OU DPoP) como praticamente obrigatório** no perfil baseline, não como hardening opcional.
- A armadilha operacional de "terminação de TLS no gateway quebra mTLS" virou um problema bem documentado conforme mais organizações tentaram isso na prática — provedores de nuvem (AWS ALB, vários API gateways) adicionaram suporte específico a "passthrough de mTLS" ou "encaminhamento de certificado via header confiável" justamente para essa fricção.
- A **RFC 9449 (DPoP)**, próximo capítulo, nasceu em parte porque a exigência de infraestrutura do mTLS (PKI completa, configuração cuidadosa de gateway) é pesada para muitas implantações — especialmente SPAs e apps mobile, onde gerenciar certificado de cliente é incômodo. DPoP costuma ser descrito como "a alternativa mais leve ao mTLS para sender-constraining" — um bom gancho para o próximo capítulo.

> **Nota de laboratório**: nenhum lab construído ainda para esta RFC — e, diferente dos capítulos anteriores, este é o primeiro que exigiria genuinamente TLS real (certificados de cliente, possivelmente uma CA pequena) para fazer sentido, rompendo a simplificação de HTTP puro mantida em todos os labs até aqui.
