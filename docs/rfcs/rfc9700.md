# RFC 9700 — Best Current Practice for OAuth 2.0 Security (BCP 240)

[← voltar ao roteiro](../oauth-guide.md)

## 1. Contexto e motivação

RFC 9700 (janeiro de 2025) é uma **BCP** (Best Current Practice), não uma spec de protocolo — não define parâmetro, endpoint ou mensagem novos. É o destilado de mais de uma década de ataques reais e lições aprendidas em produção, consolidando num único documento normativo o que antes estava espalhado entre RFC 6819 (catálogo informal de ameaças), a experiência coletiva da comunidade e um draft de segurança que circulou por quase 10 anos (`draft-ietf-oauth-security-topics`, com ~20 revisões entre 2016 e 2024) antes de virar RFC.

O efeito prático: várias recomendações que a RFC 6819 fazia como "SHOULD"/sugestão viram aqui **MUST** — obrigação normativa. É, na prática, **o capítulo de segurança da OAuth 2.1** (o draft de consolidação reescreve RFC 6749 + 6750 + PKCE incorporando exatamente estes mandatos).

Este é o documento para onde todo capítulo anterior deste guia já apontava quando eu disse "isso vira obrigatório na RFC 9700" — aqui é onde essa promessa se resolve.

## 2. Terminologia e papéis

Nenhum papel novo. Reforça e endurece a distinção client confidential/public da RFC 6749 (a maioria dos mandatos abaixo nasceu de ataques que exploravam justamente a fragilidade estrutural de clients públicos).

## 3. "Fluxo" — não há fluxo novo, há restrições sobre os fluxos existentes

Como BCP, o documento não introduz mensagens — ele restringe o que já existe. Os mandatos mais importantes, agrupados:

**a) Grant types**
- **Implicit Grant (`response_type=token`) — MUST NOT ser usado.** Access token nunca deve voltar no fragmento da URL de redirect.
- **Resource Owner Password Credentials (ROPC) — MUST NOT ser usado.**
- **PKCE — obrigatório para TODO client no Authorization Code Grant**, não só para públicos como a RFC 7636 originalmente escopou. Fecha de vez a interceptação de code (RFC 6819 §5) para qualquer tipo de client.

**b) Redirect e CSRF**
- **`redirect_uri` — exact string match obrigatório** (nada de prefixo/wildcard) — a mitigação que a RFC 6819 já recomendava vira mandato.
- **`state` continua recomendado**; o `code_verifier` do PKCE também pode servir como proteção CSRF, mas só se o client vincular esse verifier à sessão do browser (ex.: um cookie) — PKCE sozinho, sem esse vínculo, não substitui `state`.
- **Ataques de "mix-up"** (client confunde qual authorization server respondeu, quando fala com mais de um AS) — mitigados por identificação explícita do emissor na resposta de autorização (mecanismo formalizado depois na RFC 9207, fora deste roteiro).

**c) Tokens**
- **Refresh token rotation** — cada uso de um refresh token deve invalidar o anterior e emitir um novo (o lab já faz isso). Vai além: recomenda **detecção de reuso** — se um refresh token já invalidado for apresentado de novo, é sinal de comprometimento, e a família inteira de tokens dele deve ser revogada (o lab ainda não implementa essa detecção).
- **Tokens sender-constrained (DPoP ou mTLS) são recomendados** onde viável, especialmente para clients públicos e cenários de alto valor — eleva o que a RFC 6750 apontava como fraqueza estrutural (bearer = posse é igual a acesso) de "considerar no futuro" para "recomendação ativa hoje".
- **Restrição de audience/escopo** para evitar que um token emitido para um resource server seja aceito por outro — reforça diretamente a preocupação de "confused deputy" da RFC 6819, que veremos com mais detalhe na RFC 8707 (já há uma pergunta em aberto anotada no roteiro para aquele capítulo: avaliar se segmentar melhor os nomes de scope já não resolveria o problema).
- **Vida curta e uso único** para authorization codes e tempos de expiração curtos para access tokens — reforço do que já era prática recomendada.

**d) Autenticação do client**
- Prefere métodos assimétricos (`private_key_jwt` via RFC 7523, ou mTLS via RFC 8705) a `client_secret` estático transmitido por request, onde for viável — um segredo compartilhado estático é, estruturalmente, mais fácil de vazar/forçar do que uma assinatura com chave privada.

**e) Apps nativos**
- A requisição de autorização **não deve** rodar dentro de uma *webview* embutida no app (sem acesso à barra de URL, sem garantia de isolamento de sessão/cookies) — deve abrir o browser do sistema. Formalizado com mais detalhe pela RFC 8252 (OAuth 2.0 for Native Apps, fora deste roteiro).

## 4. Parâmetros e endpoints normativos

Nenhum endpoint novo. Efetivamente promove `code_challenge`/`code_challenge_method` (originalmente da RFC 7636) a parâmetros que devem estar presentes em toda authorization request, independentemente do tipo de client.

## 5. Segurança — este documento inteiro é a seção de segurança

(Ver item 3 acima — os mandatos listados ali *são* o conteúdo normativo desta RFC. Não há uma seção separada de "ameaças tratadas": aqui a ameaça e a mitigação obrigatória são apresentadas juntas, ponto a ponto.)

## 6. Relação com outras RFCs

- Constrói diretamente sobre a **RFC 6819** — pega dezenas de recomendações informais de lá e as torna obrigatórias.
- Torna a **RFC 7636 (PKCE)** universal (não mais restrita a clients públicos).
- Deprecia formalmente 2 dos 4 grants originais da **RFC 6749** (Implicit, ROPC).
- Recomenda ativamente **RFC 8705 (mTLS)** e **RFC 9449 (DPoP)** para sender-constraining.
- Reforça a preocupação de audience que a **RFC 8707 (Resource Indicators)** resolve.
- É, na prática, o capítulo de segurança do **OAuth 2.1** (draft de consolidação).
- Relacionada (fora do roteiro) à RFC 9207 (AS Issuer Identification, mitigação de mix-up) e à RFC 8252 (OAuth for Native Apps, guidance de webview).

## 7. O que essa RFC representa no arco do tempo

Diferente dos capítulos anteriores, aqui a pergunta "o que mudou desde a publicação" se inverte: esta RFC é recente (2025) e é justamente o marco que **consolida** mais de dez anos de mudança incremental (2012–2024) em um único documento normativo — antes dela, "as boas práticas" viviam espalhadas em um draft de segurança de vida longa, em blog posts, em catálogos como a RFC 6819, e na experiência tácita da comunidade.

O que já se percebe evoluindo **além** dela: perfis de segurança setoriais como o **FAPI** (OpenID Foundation, financial-grade API) já tornam **obrigatório** — não apenas recomendado — o que a 9700 apenas sugere: sender-constraining (DPoP/mTLS) sempre, PAR e JAR sempre, RAR para autorização de granularidade fina. Para o seu contexto FSI, vale ter em mente que a RFC 9700 é o piso mínimo hoje — não o teto — e que specs como FAPI 2.0 (fora deste roteiro, mas vale mencionar) partem exatamente daqui para exigir mais.
