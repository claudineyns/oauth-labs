# RFC 6750 — Bearer Token Usage

[← voltar ao roteiro](../oauth-guide.md)

## 1. Contexto e motivação

A RFC 6749 define como um `access_token` é **obtido**, mas deixa deliberadamente de fora como ele é **usado** para acessar um recurso protegido — esse é o escopo exclusivo da RFC 6750. Ela formaliza o tipo de token mais comum do OAuth 2.0: o **bearer token**.

Definição central: um bearer token é uma credencial na qual **qualquer parte que o possua pode usá-lo**, sem precisar provar posse de nenhuma chave criptográfica associada — na prática, "quem tem o token, tem o acesso" (analogia clássica: um cheque ao portador). Essa é a contrapartida direta à assinatura por requisição do OAuth 1.0, que a RFC 6749 removeu em favor de simplicidade — a RFC 6750 é o preço dessa simplicidade: como não há prova de posse, **toda a segurança recai sobre como o token é transportado e armazenado**, não sobre o protocolo em si.

Esse é o ponto que mais vale reter na recapitulação: bearer = simples de implementar, mas roubável e reutilizável por qualquer um até expirar. É exatamente essa lacuna que, anos depois, motivou mecanismos de *sender-constraining* (RFC 8705 mTLS, RFC 9449 DPoP — item 6 do roteiro), que amarram o token a quem o solicitou.

## 2. Terminologia e papéis

Nenhum papel novo em relação à RFC 6749 — client, resource server, authorization server e resource owner continuam os mesmos. A RFC 6750 apenas define precisamente:
- **Bearer Token** — o tipo de credencial (valor de `token_type` no token endpoint é literalmente `"Bearer"`).
- **Bearer Token Usage** — as regras de como o resource server deve aceitar (ou rejeitar) esse token nas requisições.

## 3. Fluxo(s) — as 3 formas de transmitir o token (§2)

A RFC define 3 métodos para o client apresentar o `access_token` ao resource server — e uma regra transversal importante: **o client NÃO DEVE usar mais de um método na mesma requisição** (se usar, o RS deve responder `400 invalid_request`).

**a) Authorization Request Header Field (§2.1)** — método **recomendado**, deve ser suportado por todo resource server:
```
GET /recurso HTTP/1.1
Authorization: Bearer mF_9.B5f-4.1JqM
```

**b) Form-Encoded Body Parameter (§2.2)** — só é permitido quando o método HTTP é POST/PUT e o corpo é inteiramente `application/x-www-form-urlencoded` (não pode coexistir com outro conteúdo). Não é recomendado — existe para clients que não conseguem manipular headers HTTP.
```
POST /recurso HTTP/1.1
Content-Type: application/x-www-form-urlencoded

access_token=mF_9.B5f-4.1JqM
```

**c) URI Query Parameter (§2.3)** — **desaconselhado explicitamente**: URLs vazam em logs de servidor/proxy, em histórico do browser e no header `Referer` para terceiros. Só deve ser usado como último recurso.
```
GET /recurso?access_token=mF_9.B5f-4.1JqM HTTP/1.1
```

*(Os 3 métodos — e a rejeição por uso simultâneo — já estão implementados e testados no laboratório [`rfc6749/resource-server`](../../rfc6749/resource-server/src/index.js).)*

## 4. Parâmetros e endpoints normativos

A RFC 6750 não define endpoints novos (usa os da RFC 6749); ela define:
- `token_type = "Bearer"` no corpo da resposta do token endpoint (RFC 6749 §5.1).
- **`WWW-Authenticate` (§3)** — header de resposta do resource server para sinalizar erro ou desafiar autenticação:
  ```
  WWW-Authenticate: Bearer realm="exemplo", error="invalid_token", error_description="o token expirou"
  ```
- **3 códigos de erro normativos (§3.1)**:
  - `invalid_request` — 400, requisição malformada (ex.: token em mais de um lugar).
  - `invalid_token` — 401, token ausente/expirado/revogado/malformado.
  - `insufficient_scope` — 403, token válido mas sem o escopo necessário (o header deve incluir `scope` com o escopo exigido).
- Regra sutil e fácil de esquecer: se **nenhum** token foi enviado, o RS deve responder `401` **sem** `error`/`error_description` no `WWW-Authenticate` — só `Bearer realm="..."`. Incluir o motivo do erro para quem não tentou se autenticar vaza informação desnecessária a um client não autenticado.

## 5. Segurança já tratada na própria RFC 6750 (§5)

Essa seção de segurança é desproporcionalmente grande para uma RFC "de uso" — exatamente porque bearer = posse é igual a acesso:
- **TLS obrigatório em toda requisição que carrega o token**, não só na emissão — um bearer token trafegando sem TLS é equivalente a vazar a credencial.
- **Tempo de vida curto** é recomendado como mitigação central, já que não há como revogar posse de quem já capturou o token (replay livre até expirar).
- **Armazenamento**: bearer tokens devem ser tratados como segredos (equivalentes a senhas) tanto no client quanto no resource server — nunca em texto claro em log, cache ou storage não protegido.
- **Nunca colocar o token na URL de página** (reforça por que o método de query é desaconselhado — vaza via `Referer`, cache de proxy e histórico do browser).
- **Escopo reduzido** — tokens devem carregar o menor escopo possível, para limitar o dano de um roubo (prenuncia diretamente a RFC 8707 Resource Indicators e a RFC 9396 RAR, no item 6).

> **Nota de laboratório**: os labs práticos deste projeto rodam em HTTP puro (`http://localhost`), a despeito dessa exigência de TLS — simplificação deliberada, mantida até o capítulo da RFC 8705 (mTLS, item 6), onde TLS real passa a ser o próprio mecanismo em estudo. Até lá, o foco é a mecânica de grant/token, não a camada de transporte.

## 6. Relação com outras RFCs

- Depende inteiramente da **RFC 6749** para emissão — 6750 só cobre uso.
- O formato de erro (`WWW-Authenticate` com `error`/`error_description`) estabeleceu o padrão reaproveitado depois por outras extensões do OAuth.
- **RFC 8705 (mTLS)** e **RFC 9449 (DPoP)** existem justamente para resolver a fraqueza estrutural que a própria 6750 documenta em §5: bearer token roubado = acesso total até expirar. Ambas adicionam prova de posse por cima do que seria, de outra forma, um bearer token puro.
- **RFC 9068 (JWT Profile for Access Tokens)** formaliza um formato específico de bearer token (JWT) — a 6750 é agnóstica quanto ao formato do token (opaco ou estruturado).
- **RFC 9700 (BCP)** reforça a recomendação de tokens sender-constrained para cenários sensíveis, uma extensão direta da preocupação já levantada aqui.

## 7. O que mudou desde a publicação (2012)

- A RFC em si não foi revisada, mas a prática evoluiu: hoje é comum tratar o método de query string como **inaceitável** (não apenas desaconselhado) em implementações modernas — muitas nem o suportam.
- Uma errata posterior esclareceu que o nome do esquema de autenticação (`Bearer`) é **case-insensitive**, seguindo a regra geral de esquemas HTTP Auth (RFC 7235) — o resource server do lab já trata isso corretamente com um regex `/^Bearer /i`.
- O que era "considerado seguro o suficiente" em 2012 (bearer puro + TLS) hoje é visto como piso mínimo — para APIs financeiras ou de alto valor, a expectativa atual (RFC 9700, perfis como FAPI) é sender-constraining via mTLS ou DPoP.
