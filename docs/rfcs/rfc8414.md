# RFC 8414 — OAuth 2.0 Authorization Server Metadata

[← voltar ao roteiro](../oauth-guide.md)

## 1. Contexto e motivação

Até esta RFC (2018), um client que integrasse com um authorization server precisava saber, configurado manualmente/fora de banda, a URL de cada endpoint relevante — `/authorize`, `/token`, e conforme o ecossistema cresceu, também `/revoke` (RFC 7009), `/introspect` (RFC 7662), `/device_authorization` (RFC 8628), `/par` (RFC 9126)... Isso não escala: qualquer mudança de URL no AS quebra configuração estática espalhada por todo client; bibliotecas OAuth genéricas não conseguem suportar "qualquer AS compatível" sem hardcoding por implantação.

A RFC 8414 resolve isso com um **documento de descoberta**: um JSON publicado numa URL *well-known* padronizada, descrevendo de uma vez só todos os endpoints e capacidades do AS. Um client (ou um integrador humano) busca **um único documento** e aprende tudo que precisa. É, essencialmente, a extração e generalização — para OAuth puro, sem exigir a pilha OIDC inteira — do padrão já usado pelo OpenID Connect Discovery (`/.well-known/openid-configuration`), que é anterior a esta RFC.

## 2. Terminologia e papéis

Nenhum papel novo. Introduz:
- **Authorization Server Metadata** — o documento JSON em si.
- **Well-Known URI** — mecanismo de descoberta (RFC 8615): `https://{host-do-issuer}/.well-known/oauth-authorization-server{/caminho-se-houver}`. Detalhe que confunde bastante gente: se o `issuer` tem um caminho (ex.: `https://as.exemplo.com/tenant1`), o `.well-known/...` é **inserido antes** desse caminho — `https://as.exemplo.com/.well-known/oauth-authorization-server/tenant1` — não anexado depois.
- **`issuer`** — o campo mais importante do documento: uma URL que identifica o AS de forma única, e que deve bater exatamente com o valor usado como `iss` em qualquer lugar (tokens JWT, `aud` de um Request Object da RFC 9101 etc.).

## 3. Fluxo

Não é bem um "fluxo" OAuth — é uma consulta simples e pública:

```
GET /.well-known/oauth-authorization-server HTTP/1.1
Host: as.exemplo.com

200 OK
Content-Type: application/json
{
  "issuer": "https://as.exemplo.com",
  "authorization_endpoint": "https://as.exemplo.com/authorize",
  "token_endpoint": "https://as.exemplo.com/token",
  "revocation_endpoint": "https://as.exemplo.com/revoke",
  "introspection_endpoint": "https://as.exemplo.com/introspect",
  "jwks_uri": "https://as.exemplo.com/jwks.json",
  "response_types_supported": ["code"],
  "grant_types_supported": ["authorization_code", "refresh_token", "client_credentials"],
  "token_endpoint_auth_methods_supported": ["client_secret_basic", "private_key_jwt"],
  "code_challenge_methods_supported": ["S256"],
  "pushed_authorization_request_endpoint": "https://as.exemplo.com/par",
  "device_authorization_endpoint": "https://as.exemplo.com/device_authorization"
}
```

## 4. Parâmetros e endpoints normativos

- **Well-known URI** é o próprio "endpoint" — GET, sem autenticação, público por design.
- **`issuer`** — único campo obrigatório.
- Campos que já encontramos ao longo do roteiro, todos opcionais mas praticamente universais na prática: `authorization_endpoint`, `token_endpoint`, `jwks_uri`, `scopes_supported`, `response_types_supported`, `grant_types_supported`, `token_endpoint_auth_methods_supported`, `code_challenge_methods_supported` (RFC 7636 — como o AS anuncia suporte a PKCE e quais métodos), `revocation_endpoint` (RFC 7009), `introspection_endpoint` (RFC 7662), `device_authorization_endpoint` (RFC 8628), `pushed_authorization_request_endpoint` + `require_pushed_authorization_requests` (RFC 9126), `request_parameter_supported`/`request_uri_parameter_supported`/`require_signed_request_object` (RFC 9101).

Esse documento é, literalmente, o índice que amarra quase todo endpoint que as RFCs deste roteiro foram introduzindo até aqui.

## 5. Segurança já tratada na própria RFC 8414

- **Validação do `issuer` é crítica**: ao buscar metadata em `https://{issuer}/.well-known/...`, o campo `issuer` devolvido no JSON **deve** bater exatamente com o valor consultado. Sem essa checagem, um client poderia ser induzido a confiar em metadata que na verdade descreve um AS diferente do pretendido — uma variante de ataque de "mix-up", da mesma família de preocupação que já vimos no capítulo da RFC 9700 (identificação do emissor).
- **TLS obrigatório** para buscar o documento — um documento de metadata adulterado em trânsito poderia redirecionar o client inteiro para endpoints controlados por atacante: é, em essência, um vetor de personificação completa do AS.
- **Cache não deve ser cego/eterno** — a RFC não prescreve uma política específica, mas alerta que metadata em cache desatualizada pode tanto quebrar integração (endpoints mudaram) quanto, em cenários de cache comprometido, redirecionar clients de forma maliciosa.
- **Sem autenticação para buscar** — é proposital: o documento não é sensível (é para bootstrapar confiança, como uma chave pública), mas isso também significa que qualquer um pode ver exatamente o que o AS suporta — reconhecimento de baixo risco, não uma vulnerabilidade em si.

## 6. Relação com outras RFCs

- Modelo direto do **OpenID Connect Discovery** (`/.well-known/openid-configuration`), que é anterior — a 8414 é a versão "OAuth puro" do mesmo padrão, com campos amplamente compatíveis.
- É o mecanismo de descoberta para praticamente todo endpoint introduzido pelas RFCs já cobertas: **RFC 7009** (`revocation_endpoint`), **RFC 7662** (`introspection_endpoint`, próximo capítulo), **RFC 8628** (`device_authorization_endpoint`), **RFC 9126** (`pushed_authorization_request_endpoint`), **RFC 9101** (flags de suporte a Request Object).
- Complementa **RFC 7591/7592 (Dynamic Client Registration)** — um client que descobre as capacidades do AS via 8414 pode se registrar dinamicamente de forma inteligente (ex.: só pedir métodos de PKCE que o AS realmente suporta).
- Conecta com a preocupação de mix-up da RFC 9700 via a validação do `issuer`.

## 7. O que mudou desde a publicação (2018)

- Spec estável e hoje essencialmente universal — praticamente todo AS sério publica esse documento; virou expectativa de baseline, não um extra opcional.
- O conjunto de campos que ela pode descrever cresceu organicamente conforme cada RFC companheira foi publicada (PAR, JAR, e mais adiante DPoP) — o documento de metadata é um índice vivo que vai absorvendo novas capacidades sem precisar de um mecanismo de descoberta novo a cada extensão.
- O ecossistema de bibliotecas cliente amadureceu para "descoberta primeiro" como padrão: hoje é comum configurar uma integração OAuth só com a URL do `issuer`, e a biblioteca busca o resto sozinha — um padrão que só virou mainstream bem depois de 2018.

> **Nota de laboratório**: implementado em [`rfc7592/`](../../rfc7592/README.md), [`rfc7523/`](../../rfc7523/README.md) e [`rfc9449/`](../../rfc9449/README.md) — nos três, o AS publica `/.well-known/oauth-authorization-server`, com as URLs montadas a partir do `Host` da própria requisição (o `issuer` sempre bate com quem está perguntando, de dentro da rede do projeto ou de fora). Nos dois últimos, o client-demo efetivamente **usa** a metadata descoberta para localizar `registration_endpoint`/`token_endpoint`, em vez de só existir como documento passivo; o `rfc9449/` também anuncia `dpop_signing_alg_values_supported`. Os demais labs (`rfc6749/`, `rfc7636/`, `rfc9126/`) continuam sem esse endpoint.
