# RFC 9396 — OAuth 2.0 Rich Authorization Requests (RAR)

[← voltar ao roteiro](../oauth-guide.md)

## 1. Contexto e motivação

O `scope` tradicional é uma lista simples de identificadores string, separados por espaço (`profile email accounts:read`). Funciona bem para permissões grosseiras, mas quebra para autorização **fina e estruturada** — o exemplo clássico, direto do seu contexto FSI: "autorizar um pagamento de exatamente EUR 50,00 para esta conta específica, só desta vez". Não dá para expressar isso como uma string de scope solta. Na prática, ecossistemas de Open Banking (UK Open Banking, Berlin Group NextGenPSD2) precisaram disso **antes** desta RFC existir, e cada um inventou sua própria codificação ad-hoc (às vezes espremendo dados estruturados dentro do próprio nome do scope) — soluções incompatíveis entre si, difíceis de validar, sem padrão comum.

A RFC 9396 resolve isso com um parâmetro novo, **`authorization_details`**, carregando um **array JSON de objetos estruturados** — cada um descrevendo uma autorização específica com campos arbitrários, próprios do tipo de autorização em questão.

## 2. Terminologia e papéis

Nenhum papel novo. Introduz:
- **`authorization_details`** — parâmetro novo (authorization request e/ou token request), array JSON de "objetos de detalhe de autorização".
- **Objeto de detalhe** — cada um tem um `type` obrigatório (string que identifica a semântica daquele objeto — ex.: `"payment_initiation"` — **não** padronizado genericamente pela RFC; cada ecossistema/perfil regulatório define seus próprios tipos) mais campos específicos daquele tipo.
- Campos comuns, opcionais, reutilizáveis por qualquer tipo: `locations` (quais resource servers — mesmo espírito do `resource` da RFC 8707, só que por objeto), `actions`, `datatypes`, `identifier`, `privileges`.

## 3. Fluxo

Não é um grant novo — é um parâmetro a mais no fluxo já existente (tipicamente Authorization Code):

```
GET /authorize?response_type=code&client_id=...
  &authorization_details=[{
    "type": "payment_initiation",
    "actions": ["initiate"],
    "locations": ["https://api.banco.exemplo.com/pagamentos"],
    "instructedAmount": {"currency": "EUR", "amount": "50.00"},
    "creditorAccount": {"iban": "BR00000000000000000000000"}
  }]

AS mostra uma tela de consentimento refletindo ESSE detalhe especifico —
nao um scope generico "payments", literalmente "autorizar pagamento de
EUR 50,00 para esta conta"

Usuario aprova -> AS emite o token, ecoando authorization_details (possivelmente
reduzido) na resposta do /token, para o client confirmar exatamente o que foi concedido
```

## 4. Parâmetros e endpoints normativos

Nenhum endpoint novo — estende a authorization request e a token request/response existentes.
- `authorization_details`: array de objetos, cada um com `type` obrigatório + campos específicos do tipo + campos comuns opcionais (`locations`, `actions`, `datatypes`, `identifier`, `privileges`).
- A **resposta** do token endpoint também devolve `authorization_details`, ecoando exatamente o que foi concedido — não só um scope aproximado.
- Descoberta via **RFC 8414**: `authorization_details_types_supported`, listando quais `type` o AS entende.

## 5. Segurança já tratada na própria RFC 9396

- **Telas de consentimento muito mais precisas**: o usuário vê "autorizar pagamento de EUR 50 para esta conta", não um scope opaco — conecta direto com a preocupação de consentimento informado/phishing que já vimos lá na RFC 6819.
- **O AS deve validar e pode reduzir** `authorization_details` — mesma disciplina já vista com `scope` e com `resource` (RFC 8707): nunca aceitar cegamente o que o client pede.
- **É o último degrau de uma escada que já percorremos o roteiro inteiro**: minimizar escopo (RFC 6750) → restringir audience (RFC 8707) → agora, precisão no nível de **uma transação específica**, não uma classe de capacidade.
- Como `authorization_details` pode carregar dados sensíveis estruturados (IBAN, valor exato) direto na requisição, isso reforça ainda mais por que combinar com **PAR** (escondendo do browser) e **JAR** (assinando para integridade) importa aqui — a combinação natural de alta garantia.

## 6. Relação com outras RFCs

- Evolução direta do `scope` — mesmo papel conceitual (o que está sendo concedido), agora estruturado em vez de string plana.
- Combina naturalmente com **RFC 9126 (PAR)** e **RFC 9101 (JAR)** — a trinca PAR + JAR + RAR é exatamente o padrão avançado do FAPI 2.0 para casos como iniciação de pagamento, amarrando tudo que vimos nas categorias 3 e 6 deste roteiro.
- `locations` ecoa o mesmo conceito do `resource` da **RFC 8707**, só que por objeto de detalhe, não por token inteiro.
- Descoberta via **RFC 8414** (`authorization_details_types_supported`).
- Fecha, junto com a RFC 8707, o fio de "least privilege" que atravessou o roteiro inteiro: de escopo amplo (RFC 6749) a escopo mínimo (RFC 6750) a audience restrita (RFC 8707) a transação específica (RFC 9396).

## 7. O que mudou desde a publicação (2023)

- RFC recente, motivada por pressão regulatória real em ecossistemas de Open Banking, que já precisavam disso havia anos e resolviam de formas proprietárias e incompatíveis antes da padronização.
- O FAPI 2.0 trata RAR como a ferramenta disponível (não universalmente obrigatória como o PKCE virou) sempre que o caso de uso exige esse nível de precisão — iniciação de pagamento sendo o exemplo canônico.
- No seu contexto FSI, é provavelmente o capítulo com aplicação profissional mais direta de todo o roteiro.

> **Nota de laboratório**: nenhum lab construído ainda para esta RFC — o cenário natural seria estender algum lab existente com um `authorization_details` de "iniciação de pagamento" fictícia, mostrando a tela de consentimento refletindo o valor/conta específicos, em vez de um scope genérico.
