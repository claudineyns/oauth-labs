# RFC 7662 — OAuth 2.0 Token Introspection

[← voltar ao roteiro](../oauth-guide.md)

## 1. Contexto e motivação

Quando o `access_token` é **opaco** (uma string aleatória, como em todos os labs deste projeto até aqui), o resource server não tem como, sozinho, saber se ele é válido, qual escopo carrega, ou a quem foi emitido — ele precisa perguntar a alguém. Antes desta RFC, isso era proprietário de cada AS (o mesmo tipo de lacuna que motivou a RFC 7009 para revogação, e a RFC 8414 para descoberta): sem um jeito interoperável do resource server validar um token opaco contra qualquer AS compatível.

A RFC 7662 formaliza um **endpoint de introspecção**: o resource server apresenta o token, o AS responde com um JSON estruturado dizendo se está ativo e, se estiver, seus metadados (escopo, client, usuário, expiração...). É a terceira peça que completa o ciclo de vida do token, ao lado da RFC 6749 (emissão) e da RFC 7009 (revogação): **emitir, validar, revogar**.

## 2. Terminologia e papéis

Nenhum papel novo — mas a RFC usa o termo **"protected resource"** para quem chama a introspecção, reforçando que o público-alvo pretendido é o resource server, não qualquer parte.

## 3. Fluxo

```
POST /introspect
Authorization: Basic <credenciais do resource server, registradas para este fim>

token=<o token a verificar>
&token_type_hint=access_token   (opcional — mesma logica de dica da RFC 7009)
```

Resposta — **sempre 200**, mesmo para token inválido:

```json
{
  "active": true,
  "scope": "profile email",
  "client_id": "s6BhdRkqt3",
  "username": "alice",
  "token_type": "Bearer",
  "exp": 1787510000,
  "iat": 1787506400,
  "sub": "alice",
  "aud": "https://rs.exemplo.com",
  "iss": "https://as.exemplo.com"
}
```

Se o token não existe, expirou ou foi revogado: `{"active": false}` — e **nenhum outro campo** deveria acompanhar isso.

## 4. Parâmetros e endpoints normativos

- **Introspection endpoint** — novo, descoberto via RFC 8414 como `introspection_endpoint`.
- `token` (obrigatório), `token_type_hint` (opcional, `access_token` ou `refresh_token` — a RFC é genérica quanto ao tipo, ver item 5).
- **Autenticação do chamador é obrigatória** — o endpoint precisa estar protegido; não é aberto a qualquer parte.
- Resposta: `active` (obrigatório) + campos opcionais quando ativo — `scope`, `client_id`, `username`, `token_type`, `exp`, `iat`, `nbf`, `sub`, `aud`, `iss`, `jti`. Não por acaso, muitos desses nomes espelham claims padrão de JWT (RFC 7519) — o mesmo vocabulário semântico serve tanto para token opaco quanto para JWT.

## 5. Segurança já tratada na própria RFC 7662

- **O endpoint precisa estar protegido** — introspecção revela informação sensível sobre um token (escopo, usuário, client) e não deveria estar aberta a chamadores arbitrários ou não autenticados. Isso conecta direto com uma pergunta que já discutimos nesta conversa: introspecção **não é** pensada para "o próprio portador do token perguntar sobre si mesmo" — é para o **resource server**, que recebeu o token de outra parte, validá-lo perante quem o emitiu.
- **`active: false` revela o mínimo possível** — a RFC recomenda que, para token inválido, a resposta traga só esse campo, sem mais nada — mesmo princípio anti-oráculo que já vimos na RFC 7009 (ali via sempre-200; aqui via campo `active` minimalista quando falso).
- TLS obrigatório, como em qualquer endpoint que manipula material de token.
- **Custo operacional**: como a introspecção tipicamente acontece a cada requisição recebida pelo resource server (a menos que haja cache local), ela cria uma dependência de rede e um possível vetor de sobrecarga no AS se muitos RSs introspectarem com frequência — implantações costumam mitigar com cache local de curta duração, balanceando contra a atualidade da informação de revogação.

## 6. Relação com outras RFCs

- Fecha o trio de gerenciamento de ciclo de vida com **RFC 6749** (emissão) e **RFC 7009** (revogação) — emitir, revogar, e agora validar.
- É exatamente o que os resource servers de **todos os labs deste projeto** ainda não fazem: cada `rfc*/resource-server` valida o `access_token` lendo **diretamente** do mesmo Redis que o AS escreve — só funciona porque é o mesmo laboratório. Um resource server de verdade, desacoplado, chamaria `/introspect` no AS em vez disso.
- Descoberta via **RFC 8414** como `introspection_endpoint`.
- Contraste direto com a próxima RFC do roteiro, **9068 (JWT Profile for Access Tokens)**: se o AS emite tokens em formato JWT em vez de opaco, o resource server pode validar **localmente**, por assinatura, sem round-trip de rede nenhum — introspecção e token-como-JWT são as duas estratégias concorrentes para o mesmo problema de fundo ("como o RS sabe que o token é válido").
- `token_type_hint` reaproveita exatamente o mesmo padrão de dica opcional já visto na RFC 7009 — mesmo desenho, RFCs irmãs.

## 7. O que mudou desde a publicação (2015)

- Spec estável e essencialmente universal onde quer que tokens opacos sejam usados — companheira natural de qualquer implantação que não use JWT autocontido.
- A ascensão de access tokens em formato JWT (formalizada depois pela RFC 9068, e adotada por convenção de mercado até antes disso) reduziu a **necessidade** de introspecção em cenários de alto throughput (evita o round-trip por requisição) — mas introspecção continua essencial sempre que o status de revogação em tempo real importa mais do que evitar aquele round-trip, ou quando o token é mantido opaco de propósito (tamanho menor, nenhuma informação vazando do próprio conteúdo do token).
- Um padrão híbrido comum hoje: JWT para o caso geral (validação local, rápida) **mais** uma checagem de revogação só quando a operação exige garantia extra — um meio-termo que não era bem o desenho original de 2015, mas surgiu como prática.
