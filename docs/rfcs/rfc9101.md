# RFC 9101 — The OAuth 2.0 Authorization Framework: JWT-Secured Authorization Request (JAR)

[← voltar ao roteiro](../oauth-guide.md)

## 1. Contexto e motivação

A requisição de autorização tradicional (RFC 6749 §4.1.1) manda cada parâmetro como um par chave-valor solto na query string — sem assinatura, sem verificação de integridade. Nada garante ao AS que esses parâmetros chegaram exatamente como o client os montou: um intermediário de rede, uma extensão de browser maliciosa, ou uma cadeia de redirecionamento manipulada poderiam, em tese, alterar um parâmetro individual (trocar `scope=profile` por `scope=profile+admin`, por exemplo) sem que isso deixe rastro algum.

A RFC 9101 (JAR) resolve isso de um jeito diferente da RFC 9126 (PAR): em vez de esconder os parâmetros do browser, ela **empacota todos num único JWT assinado pelo client** — o "Request Object" — e manda esse JWT como um parâmetro só. Qualquer adulteração quebra a assinatura e o AS rejeita. A integridade vem de criptografia, não do canal de transporte.

## 2. Terminologia e papéis

Nenhum papel novo. Introduz:
- **Request Object** — um JWT cujas claims **são** os parâmetros da authorization request (`response_type`, `client_id`, `redirect_uri`, `scope`, `state`, `code_challenge`...) somadas às claims padrão de JWT (`iss` = client_id, `aud` = identificador do AS, `exp`).
- **`request`** — parâmetro que carrega o Request Object **por valor** (o JWT compacto, direto na URL).
- **`request_uri`** — parâmetro que carrega o Request Object **por referência** (uma URL que o *próprio AS* busca para obter o JWT).

> **Cuidado com o nome**: esse `request_uri` da RFC 9101 é conceitualmente diferente do `request_uri` da RFC 9126 (PAR) — aqui é uma URL hospedada pelo *client*, que o AS busca; na RFC 9126 é uma referência opaca gerada pelo *AS* depois de receber um push. Os dois nomes colidem, mas representam mecanismos distintos (embora combináveis — ver item 6).

## 3. Fluxo

**Por valor** (`request`):
```
1. Client monta um JWT com claims = todos os parametros da authorization request + iss, aud, exp
2. Client assina o JWT com uma chave registrada no AS
3. Client → User-Agent: GET /authorize?client_id=...&request=<JWT compacto>
4. AS valida a assinatura (chave do client, via jwks/jwks_uri registrados), confere exp/aud/iss,
   extrai os parametros das claims do JWT (nao da query string solta)
5. Segue com login/consentimento normalmente, usando os parametros ja verificados
```

**Por referência** (`request_uri`):
```
1-2. mesma construcao do JWT
3. Client hospeda o JWT numa URL propria (ex.: https://client.exemplo/reqs/abc123)
4. Client → User-Agent: GET /authorize?client_id=...&request_uri=https://client.exemplo/reqs/abc123
5. AS busca o JWT nessa URL, entao valida assinatura/claims como acima
```

## 4. Parâmetros e endpoints normativos

Nenhum endpoint novo — diferente da RFC 9126, a 9101 reaproveita o `/authorize` inteiramente, só adicionando dois parâmetros possíveis: `request` e `request_uri`.

- Claims do Request Object: `iss`, `aud`, `exp` (padrão JWT) + todos os parâmetros normais da authorization request como claims adicionais.
- Descoberta da chave de assinatura do client: via `jwks` (inline) ou `jwks_uri` (buscado pelo AS) — parte do metadata de registro do client (RFC 7591, categoria 4).
- O AS deve validar a assinatura, verificar `exp`, e idealmente conferir `aud` — e, para o modo por referência, **restringir de onde busca** (ver item 5).

## 5. Segurança já tratada na própria RFC 9101

- **Integridade por assinatura**: mesmo que o canal de transporte não seja confiável, adulteração quebra a assinatura. É uma garantia mais forte e mais geral que a da PAR — a PAR confia porque o canal é autenticado; a JAR **prova** criptograficamente, independente das propriedades do canal.
- **Replay**: `exp` (e opcionalmente `nbf`/`jti`, se o AS quiser rastrear uso único) limitam por quanto tempo e quantas vezes um Request Object capturado poderia ser reaproveitado.
- **Risco de SSRF no modo por referência**: como é o **próprio AS** que busca a URL informada em `request_uri`, um client malicioso (ou um valor não devidamente vinculado ao client registrado) poderia induzir o AS a fazer requisições a URLs arbitrárias/internas. Mitigação recomendada: o AS só busca `request_uri` de hosts/padrões pré-registrados por client.
- **JAR sozinha não dá confidencialidade** — o JWT (JWS) é assinado, não criptografado; qualquer um que veja o `request`/`request_uri` ainda lê `scope`, `redirect_uri` etc. em texto claro, só não consegue adulterar sem detecção. Para confidencialidade também, o Request Object pode ser adicionalmente **criptografado** (JWE) — combinação comum em perfis FAPI.

## 6. Relação com outras RFCs

- Companheira direta da **RFC 9126 (PAR)**, capítulo anterior — e aqui vale a combinação mais importante do roteiro até agora: **empurrar um Request Object assinado via PAR**. O client monta o JWT (JAR), empurra via `POST /par` (PAR), recebe de volta o `request_uri` opaco da RFC 9126, e usa isso no `/authorize`. Resultado: os parâmetros ficam **escondidos do browser** (confidencialidade via PAR) **e** verificavelmente autênticos (integridade via JAR) ao mesmo tempo — as duas RFCs foram desenhadas para compor.
- Chave de assinatura do client vem do metadata de **RFC 7591 (Dynamic Client Registration)** — categoria 4 do roteiro.
- Paralelo conceitual com **RFC 7523** (autenticação de client via `private_key_jwt`) — mesma ideia (JWT assinado pela chave do client provando autenticidade), aplicada a um propósito diferente (autenticar o client no token endpoint, não proteger a authorization request).
- Descoberta via **RFC 8414**: campos como `request_parameter_supported`, `request_uri_parameter_supported`, `require_signed_request_object`.
- Fortemente usada (e frequentemente exigida) em perfis **FAPI** — normalmente já combinada com PAR, exatamente o padrão descrito acima.

## 7. O que mudou desde a publicação (2021)

- Spec relativamente recente e estável, mas seguiu uma trajetória de adoção diferente da do PKCE: **não virou obrigatória universalmente** via RFC 9700 — continua sendo uma ferramenta de "alta garantia", adotada seletivamente onde a organização precisa de integridade mais forte (setor financeiro, por exemplo), não um baseline geral como PKCE se tornou.
- A combinação PAR + JAR se consolidou como o padrão de fato em implementações FAPI 2.0 — reforça que essas duas RFCs se entendem melhor como um par do que isoladamente.

> **Nota de laboratório**: nenhum lab construído ainda para esta RFC — o cenário natural seria estender o `rfc9126/` (que já tem PAR) para também assinar o Request Object antes de empurrá-lo, mostrando as duas proteções combinadas na prática.
