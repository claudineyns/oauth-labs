# RFC 7591 — OAuth 2.0 Dynamic Client Registration Protocol

[← voltar ao roteiro](../oauth-guide.md)

## 1. Contexto e motivação

Em todo capítulo e em todo laboratório deste projeto até aqui, registro de client foi tratado como um passo manual, fora de banda: alguém configura `client_id`/`client_secret`/`redirect_uri` no AS antes de qualquer fluxo acontecer (nos nossos labs, isso é literalmente um script de seed escrevendo direto no Redis). Isso funciona bem para um conjunto pequeno e fixo de apps conhecidos, mas não escala quando:

- O software do client é distribuído a usuários finais que depois o apontam para **o próprio AS** de escolha deles (ex.: um client de e-mail/chat genérico que suporta "traga seu próprio servidor").
- Uma organização quer onboarding self-service de integrações de terceiros (portal de desenvolvedor) sem depender de um humano provisionando credencial manualmente a cada pedido.
- Uma plataforma SaaS multi-tenant precisa provisionar programaticamente um client novo por cliente/tenant.

A RFC 7591 resolve isso com um **endpoint de registro**: o client (ou quem estiver provisionando-o) faz um `POST` com a metadata desejada, e o AS cria o registro, devolvendo `client_id` (e `client_secret`, se aplicável) — transformando o que era um processo manual num chamada de API.

## 2. Terminologia e papéis

Nenhum papel novo. Introduz:
- **Client Registration Endpoint** — endpoint novo, `POST` para criar um registro.
- **Client Metadata** — o conjunto de campos descritivos do client: `redirect_uris`, `client_name`, `grant_types`, `response_types`, `token_endpoint_auth_method`, `jwks`/`jwks_uri`, `scope`, `contacts`, `tos_uri`, `policy_uri`, `software_id`/`software_version`. Muitos desses nomes já apareceram ao longo do roteiro como coisas "registradas previamente" — esta RFC é onde esse registro em si vira uma chamada de API, em vez de um passo administrativo manual.
- **Initial Access Token** (opcional, depende da implantação) — alguns ASs exigem que quem chama o endpoint de registro já possua algum tipo de credencial, para impedir spam/abuso de registro. Não é exigido pela RFC em si, mas explicitamente antecipado como padrão comum de implantação.
- **Software Statement** — um JWT **assinado por um terceiro de confiança** (ex.: o próprio publicador do software, ou uma autoridade de federação), atestando afirmações sobre o software sendo registrado. Permite que o AS confie em campos como "este é realmente o app oficial do Fornecedor X" sem depender só da palavra de quem está chamando o endpoint.

## 3. Fluxo

```
1. Client (ou quem o provisiona) → AS: POST /register
   Content-Type: application/json
   Authorization: Bearer <initial_access_token>   (opcional, depende da implantacao)
   {
     "redirect_uris": ["https://client.exemplo.org/callback"],
     "client_name": "Meu App",
     "grant_types": ["authorization_code", "refresh_token"],
     "response_types": ["code"],
     "token_endpoint_auth_method": "client_secret_basic",
     "scope": "profile email"
   }

2. AS valida a metadata pedida, cria o registro, gera client_id (+ client_secret, se confidencial)

3. AS → Client: 201 Created
   {
     "client_id": "s6BhdRkqt3",
     "client_secret": "cf136dc3c1fc93f31185e5885805d",
     "client_id_issued_at": 2893256800,
     "client_secret_expires_at": 0,
     "registration_access_token": "reg-23410913-abewfq.123483",
     "registration_client_uri": "https://as.exemplo.com/register/s6BhdRkqt3",
     ...(ecoa a metadata aceita, possivelmente ajustada pelo AS)...
   }
```

O `registration_access_token` + `registration_client_uri` devolvidos aqui são exatamente a credencial que a RFC companheira, **RFC 7592**, usa depois para ler/atualizar/apagar esse registro específico — a 7591 cobre só a **criação**.

## 4. Parâmetros e endpoints normativos

- **Client Registration Endpoint** — novo, descoberto via RFC 8414 como `registration_endpoint`.
- **Detalhe que chama atenção**: diferente de quase todo outro endpoint deste roteiro (que usa `application/x-www-form-urlencoded`), o registro usa **`application/json`** — uma exceção deliberada, já que a metadata tem campos aninhados/arrays (`redirect_uris`, `jwks`) que não se prestam bem a form-encoding.
- Campos de request mais relevantes: `redirect_uris` (array, obrigatório se o client usa grants baseados em redirect), `token_endpoint_auth_method`, `grant_types`, `response_types`, `client_name`, `scope` (o **teto** do que o client poderá pedir depois, não o que é concedido em cada requisição), `jwks_uri`/`jwks`, `software_statement`.
- Response: `client_id` (obrigatório), `client_secret` (se confidencial), `client_id_issued_at`, `client_secret_expires_at` (`0` = nunca expira), `registration_access_token`, `registration_client_uri`, além da metadata ecoada.
- Erros no mesmo padrão OAuth: `invalid_redirect_uri`, `invalid_client_metadata`, `invalid_software_statement`, `unapproved_software_statement`.

## 5. Segurança já tratada na própria RFC 7591

- **Registro aberto sem controle é um risco real**: se qualquer um pode registrar um client novo sem nenhum portão (sem initial access token, sem aprovação), fica trivial para um atacante forjar `client_id`s arbitrários — útil para phishing (registrar um client com `client_name`/`logo_uri` enganosos, exibidos na tela de consentimento) ou simplesmente para poluir o registro de clients. A RFC discute (§3, não-normativamente) que implantações **deveriam** considerar algum tipo de autorização antes de permitir o registro — token de acesso inicial, aprovação manual, ou restringir a um conjunto fechado de partes confiáveis — deixando o mecanismo exato a critério de cada implantação.
- **Software Statement mitiga o problema de "quem é você de verdade"**: como os campos de metadata são inteiramente auto-declarados por quem chama o endpoint, um AS que queira garantia mais forte pode exigir um `software_statement` assinado por terceiro confiável antes de aceitar certas afirmações como verdadeiras.
- **`registration_access_token` precisa ser protegido como qualquer credencial bearer** (mesmas preocupações da RFC 6750) — quem o possui pode gerenciar (e, com a RFC 7592, apagar) aquele registro específico.
- **Validação de `redirect_uri` continua se aplicando normalmente** — registro dinâmico não relaxa a exigência de exact-match da RFC 6749/RFC 9700 no momento da autorização; o que for registrado aqui vira exatamente o valor conferido depois.

## 6. Relação com outras RFCs

- Companheira direta da **RFC 7592**, próximo capítulo do roteiro — que estende esta com leitura/atualização/exclusão do registro (usando o `registration_access_token` + `registration_client_uri` que a 7591 devolve).
- Descoberta via **RFC 8414** como `registration_endpoint`.
- É exatamente o que os labs deste projeto **não fazem hoje**: `rfc6749/`, `rfc7636/` e `rfc9126/` registram o client de demonstração fora de banda, via script de seed escrevendo direto no Redis — o padrão manual que esta RFC existe para substituir por uma API de verdade.
- `jwks_uri`/`jwks` registrados aqui são exatamente o que a **RFC 9101 (JAR)** e a **RFC 7523** (autenticação de client via JWT, próxima seção do roteiro) usam para validar artefatos assinados do client — é aqui que essas chaves passam a existir associadas a um `client_id`.
- `token_endpoint_auth_method` registrado aqui determina qual método de autenticação de client se aplica (`client_secret_basic`, `private_key_jwt`, `none` para clients públicos, `tls_client_auth` para mTLS) — conecta com a RFC 7523 e a RFC 8705, ainda por vir.

## 7. O que mudou desde a publicação (2015)

- Spec estável e fundacional, mas adoção de registro **totalmente aberto** (sem nenhum portão) continua relativamente rara em produção — exatamente pelos riscos que a própria RFC já sinaliza. A maioria das implantações que suportam RFC 7591 combinam com initial access token ou aprovação manual, ou restringem a contextos de federação/enterprise.
- Mais comum em ecossistemas onde registro dinâmico resolve um problema real de fato: contextos de OpenID Connect Federation, alguns ecossistemas IoT/apps nativos, e cada vez mais em contextos adjacentes a FAPI, onde software statements dão a âncora de confiança necessária para integrações financeiras reguladas.
- O formato geral (POST JSON → client_id/client_secret + credenciais de gerenciamento) permaneceu estável e virou modelo para outras APIs de "auto-registro" em specs adjacentes.

> **Nota de laboratório**: implementado em três labs, cada um com um `token_endpoint_auth_method` diferente. Em [`rfc7592/`](../../rfc7592/README.md) — `client_secret_basic`; sem script de seed nem `.demo-client.env`; o AS expõe `POST /register`, e o client-demo se registra sob demanda (ação manual do usuário — ver RFC 7592 abaixo). Em [`rfc7523/`](../../rfc7523/README.md) — `private_key_jwt`: o corpo carrega `jwks` (a chave pública do client) em vez de receber um `client_secret` de volta. Em [`rfc9449/`](../../rfc9449/README.md) — `none` (client público): nem `client_secret` nem `jwks` — o sender-constraining fica inteiramente a cargo do DPoP, não da autenticação do client.
