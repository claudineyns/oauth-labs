# RFC 7009 — OAuth 2.0 Token Revocation

## 1. Contexto e motivação

A RFC 6749 define como um client obtém um token. A RFC 6750 define como ele o usa para acessar um resource server. Nenhuma das duas, porém, define uma forma padronizada e interoperável de **desfazer** isso — de dizer explicitamente ao authorization server "este token específico não deve mais ser aceito, a partir de agora". Antes da RFC 7009, publicada também em 2013, cada authorization server que quisesse oferecer revogação precisava inventar seu próprio endpoint proprietário, sem nenhuma garantia de que um client genérico soubesse como chamá-lo — e a maioria simplesmente não oferecia nada, deixando o único mecanismo de "morte" de um token ser a expiração natural pelo TTL.

Essa lacuna importa mais do que parece à primeira vista, e vale detalhar os dois cenários motivadores centrais que justificam a existência desta RFC:

**Cenário 1 — logout explícito do usuário.** Quando um usuário clica em "sair" num client, o comportamento ingênuo (e, sem revogação, o único disponível) é o client simplesmente apagar o token do seu próprio armazenamento local — cookie, localStorage, keychain do dispositivo. Isso é *esquecimento do lado do client*, não *invalidação do lado do servidor*. O token, tecnicamente, continua completamente válido no authorization server e no resource server até expirar naturalmente. Se esse mesmo token vazar depois (backup do dispositivo, log acidental, dump de memória), ele continua utilizável por um atacante até o TTL expirar — mesmo que o usuário tenha, na sua percepção, "saído da conta" há muito tempo. Isso é particularmente grave para refresh tokens, cujo TTL é tipicamente medido em dias ou semanas, não minutos.

**Cenário 2 — resposta a comprometimento suspeito.** Se um refresh token vaza (por exemplo, através de um dispositivo comprometido, um log de erro mal configurado, ou um ataque de reuso detectado como discutido no capítulo da RFC 9700), a única resposta eficaz é invalidá-lo imediatamente — não esperar o TTL natural passar, que pode ser dias. Sem um endpoint padronizado de revogação, essa resposta rápida dependia inteiramente de mecanismos proprietários e não interoperáveis de cada AS.

A RFC 7009 fecha essa lacuna com uma proposta deliberadamente simples: um único endpoint novo, o **revocation endpoint**, que recebe uma requisição síncrona pedindo a invalidação de um token específico. A simplicidade do design (uma única requisição, uma resposta quase sempre idêntica) é uma escolha consciente — como veremos na seção de segurança, boa parte do valor desta RFC está no que ela decide **não revelar** na resposta, tanto quanto no que ela invalida.

## 2. Terminologia e papéis

Nenhum papel novo é introduzido. A contribuição conceitual da RFC 7009 é elevar **revogação** à categoria de ação de primeira classe do protocolo — antes dela, o único jeito de um token "morrer" no OAuth 2.0 puro (RFC 6749/6750) era por expiração natural do TTL; não havia verbo para "matar um token agora, por decisão explícita". Vale notar o paralelo com sistemas de certificados X.509: assim como um certificado tem uma data de expiração natural mas também pode ser revogado antes disso via CRL/OCSP quando a chave é comprometida, um token OAuth tem TTL natural mas agora também tem um mecanismo de revogação antecipada equivalente.

## 3. Fluxo — uma única requisição, com nuances importantes na resposta

O fluxo é deliberadamente simples e síncrono: o client se autentica perante o authorization server e informa qual token deve ser revogado.

```
POST /revoke HTTP/1.1
Host: as.exemplo.com
Content-Type: application/x-www-form-urlencoded
Authorization: Basic czZCaGRSa3F0MzpnWDFmQmF0M2JW

token=45ghiukldjahdnhzdauz&token_type_hint=refresh_token
```

A resposta em caso de sucesso é **`200 OK` com corpo vazio** — e aqui está o detalhe normativo mais importante de toda a especificação, que merece ser dito com todas as letras: essa resposta `200` é retornada **independentemente** de o token informado existir, já estar expirado, ou já ter sido revogado anteriormente. Do ponto de vista do client, "eu pedi para revogar um token que nunca existiu" e "eu pedi para revogar um token válido que acabou de morrer" são operações indistinguíveis na resposta — ambas retornam exatamente o mesmo `200 OK` vazio. A única classe de erro que a RFC define é para requisições **malformadas** (parâmetro `token` ausente, por exemplo) ou para **falha de autenticação do client** — nesses casos, e apenas nesses, o AS retorna um erro (tipicamente `400` para requisição malformada, ou o erro de autenticação apropriado do token endpoint).

Essa decisão de design — que será detalhada na seção 5 — não é acidental nem uma simplificação preguiçosa; é uma mitigação deliberada contra um vetor de ataque específico, e entender esse raciocínio é mais valioso do que decorar o formato da requisição.

## 4. Parâmetros e endpoints normativos

- **Revocation endpoint** — endpoint novo, cuja URI é definida pelo authorization server (convencionalmente `/revoke`, mas sem exigência de nome fixo na RFC). Anos depois, com a publicação da RFC 8414 (Authorization Server Metadata), esse endpoint se tornou descobrível de forma padronizada através do campo `revocation_endpoint` no documento de metadados — eliminando a necessidade de configuração manual do client com a URL exata.
- **`token`** (obrigatório) — o valor do token a ser revogado. Pode ser um access token ou um refresh token; a RFC não distingue sintaticamente entre os dois no corpo da requisição, o que exige que o AS seja capaz de identificar de qual tipo se trata (daí o parâmetro seguinte, que serve apenas de otimização, não de exigência estrutural).
- **`token_type_hint`** (opcional) — os valores definidos são `access_token` e `refresh_token`. É importante entender que este parâmetro é **apenas uma dica de otimização de busca**, não uma declaração vinculante: se o AS armazena access tokens e refresh tokens em índices ou tabelas separados, o hint evita ter que consultar ambos; mas se o hint informado não corresponder ao tipo real do token (por exemplo, o client erra e informa `access_token` quando na verdade é um `refresh_token`), o AS **deve** tentar o outro tipo antes de desistir e retornar sucesso vazio de qualquer forma. Um AS que rejeitasse a requisição só porque o hint "não bateu" estaria implementando a especificação incorretamente.
- **Autenticação do client** — segue exatamente as mesmas regras já estabelecidas para o token endpoint na RFC 6749: um client confidencial deve se autenticar (tipicamente via `client_secret` em Basic Auth, como no exemplo acima); um client público deve, no mínimo, apresentar seu `client_id`, e o AS deve validar que o token apresentado para revogação pertence de fato àquele client — um client não pode revogar o token de outro client apenas conhecendo o valor do token.
- **Semântica de cascata (§2.1 da RFC)** — este é o ponto mais sutil e mais relevante na prática, e vale destacar com precisão o que a RFC efetivamente diz: revogar um **access token** não implica, necessariamente, revogar o **refresh token** associado a ele — isso fica a critério de política do AS. Revogar um **refresh token**, porém, **deveria** (recomendação forte, não obrigação absoluta na letra da RFC, mas universalmente adotada na prática) também invalidar todo access token que tenha sido derivado dele. O racional é simples: se a revogação de um refresh token não derrubasse também os access tokens já emitidos a partir dele, a operação teria um "meio-efeito" enganoso — o cliente pensaria que revogou o acesso, mas um access token filho continuaria plenamente funcional até expirar sozinho, possivelmente minutos ou horas depois.

## 5. Segurança já tratada na própria RFC 7009 — análise aprofundada

### 5.1 `200 OK` sempre, mesmo para token inexistente ou já revogado — o motivo do "anti-oráculo"

Esta é a decisão de design mais importante da especificação, e vale explicar o ataque que ela evita com um exemplo concreto. Imagine que o AS retornasse, em vez do `200` uniforme, uma resposta diferenciada — digamos, `404 Not Found` para "este token não existe" versus `200 OK` para "revogado com sucesso". Um atacante que tivesse capturado parcialmente um token (por exemplo, via um ataque de canal lateral, um log truncado, ou uma tentativa de adivinhação/força bruta contra um espaço de tokens mal dimensionado) poderia usar o endpoint de revogação como **oráculo**: enviar candidatos a token e observar qual resposta volta, inferindo se aquele valor específico é um token válido existente no sistema, mesmo sem nunca ter conseguido *usar* o token de fato. Isso transformaria um endpoint pensado para logout/limpeza em uma ferramenta de reconhecimento para o atacante — exatamente o tipo de vazamento de informação lateral que a RFC 6750 já evita ao não detalhar `error_description` para clients que sequer tentaram se autenticar corretamente (o mesmo princípio de "não dar ao atacante um oráculo de validação gratuito" aparece repetidas vezes na família de RFCs de segurança OAuth).

A resposta uniforme fecha esse vetor por completo: não importa se o token nunca existiu, já expirou naturalmente, ou já havia sido revogado antes — a resposta é sempre idêntica, e um atacante não ganha nenhuma informação distinguível ao testar valores contra o endpoint.

### 5.2 Autenticação obrigatória do client

Sem essa exigência, o revocation endpoint seria um vetor óbvio de negação de serviço: qualquer parte, sem relação alguma com o token, poderia revogar o token de qualquer outra pessoa apenas conhecendo (ou adivinhando) o valor — bastaria enviar `token=<valor capturado ou adivinhado>` sem nenhuma credencial. A exigência de autenticação do client, e a validação de que o token pertence àquele client específico, fecha esse vetor: revogar o token de terceiros deixa de ser possível sem também comprometer as credenciais daquele client.

### 5.3 Cascata refresh → access token recomendada

Já discutido na seção 4 — vale reforçar aqui por que é uma questão de segurança, não apenas de conveniência de UX: sem a cascata, um usuário (ou um sistema automatizado de resposta a incidente) que revoga um refresh token comprometido teria uma falsa sensação de que o acesso foi cortado, quando na verdade um access token filho — de posse do mesmo atacante que comprometeu o refresh token, ou de qualquer parte que o tenha capturado independentemente — continuaria válido até seu próprio TTL natural expirar.

### 5.4 TLS obrigatório

Como em todo endpoint que manipula token ou credencial de autenticação do client, o revocation endpoint exige TLS — sem isso, tanto o `client_secret` (na autenticação) quanto o próprio valor do token a ser revogado trafegariam em texto claro, e um atacante capaz de interceptar essa requisição obteria exatamente o token que o dono estava tentando invalidar, antes mesmo que a revogação surtisse efeito.

## 6. Relação com outras RFCs

- Completa o ciclo de vida do token iniciado pela **RFC 6749** (emissão) e continuado pela **RFC 6750** (uso) — a RFC 7009 é, nesse ciclo, o "desligar" explícito.
- Tornou-se descobrível de forma padronizada via **RFC 8414** (Authorization Server Metadata), como o campo `revocation_endpoint` no documento de metadados do AS.
- É complementar — não sobreposta — à **RFC 7662 (Token Introspection)**, fora do escopo direto deste roteiro mas útil mencionar a diferença de papel: introspecção responde à pergunta "este token ainda é válido, e quais são suas claims/atributos?"; revogação executa a ação "invalide este token agora". As duas coexistem tipicamente como endpoints irmãos no mesmo authorization server, servindo propósitos complementares (consulta versus ação).
- A recomendação de **rotação de refresh token com detecção de reuso**, discutida em profundidade no capítulo anterior (RFC 9700), depende estruturalmente da revogação em cascata desta RFC: detectar que um refresh token foi reusado é só metade da mitigação — a outra metade é ter, por trás dessa detecção, um mecanismo de revogação rápido e eficaz capaz de matar toda a família de tokens comprometida antes que o dano se espalhe.

## 7. O que mudou desde a publicação (2013)

- A RFC em si permanece estável e amplamente implementada, sem revisões relevantes desde a publicação — ao contrário de outras áreas do OAuth, revogação não teve nenhuma controvérsia de design que exigisse retrabalho.
- O que mudou ao redor dela, não nela mesma: passou de "endpoint proprietário, oferecido só por quem se importava" para campo padrão e esperado no documento de discovery (RFC 8414) de qualquer authorization server moderno — hoje, a ausência de um `revocation_endpoint` publicado é vista como lacuna de maturidade, não como opção neutra de design.
- Com a chegada da rotação de refresh token com detecção de reuso (RFC 9700, 2025), a revogação deixou de ser vista apenas como um "recurso de conveniência para logout" e passou a ser **infraestrutura de segurança ativa**: a velocidade e a confiabilidade com que a revogação em cascata funciona é, literalmente, o que determina a eficácia da resposta a um sinal de comprometimento detectado.
- Tokens sender-constrained (DPoP ou mTLS, discutidos no capítulo da RFC 9700) reduzem — mas não eliminam — a urgência de revogação como *resposta a roubo puro*: se posse do token sozinho já não basta para usá-lo (porque falta a prova de posse da chave associada), um token roubado em trânsito perde grande parte do seu valor para o atacante mesmo sem revogação imediata. Ainda assim, a revogação continua essencial para dois cenários que independem de roubo: logout legítimo do usuário e retirada explícita de consentimento — nenhum dos dois é resolvido por sender-constraining, porque em ambos o token *era* legitimamente utilizável até aquele momento.

## 8. Relação com o laboratório deste projeto

Diferente da RFC 6819 e da RFC 9700, a RFC 7009 **tem** implementação prática direta neste projeto: o laboratório `rfc7636/` (que primariamente demonstra PKCE, mas incorpora também Token Revocation como parte do mesmo Authorization Server) expõe um endpoint `/revoke` funcional, com revogação em cascata baseada no conceito de **família de tokens**.

O mecanismo, em `rfc7636/authorization-server/src/index.js`, funciona assim: toda vez que um par access token + refresh token é emitido (seja no login inicial, seja numa rotação subsequente), ambos são associados a um `family_id` comum, gerado uma única vez por concessão (`genFamilyId()`, em `pkce.js`) e mantido como um *set* no Redis (`family:<id>` contendo as chaves `access_token:...` e `refresh_token:...` daquela família). Quando o `/revoke` recebe um `refresh_token`, o handler busca o `family_id` associado, lista todos os membros daquele set, revoga cada um deles, e então apaga o set inteiro — implementando exatamente a "cascata refresh → access" que a seção 4 desta RFC recomenda, mas generalizada para qualquer token que já tenha compartilhado a mesma linhagem de emissão, não apenas o par imediato.

Na interface do lab, o botão "Revogar refresh_token (cascata)" no dashboard do client demo dispara essa chamada; o efeito observável é que, logo em seguida, qualquer tentativa de "Chamar Resource Server" com o access token daquela mesma família retorna `401 invalid_token` — provando visualmente que o access token morreu por tabela, mesmo nunca tendo sido revogado diretamente. O log de eventos do lab (`./containers/logs.sh events`) também deixa visível, na prática, o detalhe da seção 5.1 deste capítulo: a resposta do `/revoke` é sempre `200`, independentemente de o token existir ou de quem seja o dono — o log mostra a requisição e a resposta uniforme lado a lado, sem nunca revelar mais informação do que a especificação permite.

## Exemplo em Java (JDK 21, sem frameworks)

Os exemplos a seguir usam apenas `java.net.http.HttpClient` (cliente) e `com.sun.net.httpserver.HttpServer` (servidor), ambos embutidos no JDK — sem nenhuma dependência externa. Onde uma resposta precisar ser montada ou lida em JSON (nos erros de protocolo, por exemplo), os exemplos referenciam o utilitário `SimpleJson`, definido no Capítulo 1 (RFC 6749) deste livro, em vez de redefinir a lógica de serialização aqui.

### Exemplo 1 — cliente fazendo a requisição de revogação

```java
import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.util.Base64;
import java.nio.charset.StandardCharsets;

public final class RevocationClient {

    private final HttpClient http = HttpClient.newHttpClient();
    private final URI revocationEndpoint;
    private final String clientId;
    private final String clientSecret;

    public RevocationClient(URI revocationEndpoint, String clientId, String clientSecret) {
        this.revocationEndpoint = revocationEndpoint;
        this.clientId = clientId;
        this.clientSecret = clientSecret;
    }

    /**
     * Revoga um token (access ou refresh) — RFC 7009 §2.1.
     * token_type_hint e' opcional; ajuda o AS a otimizar a busca, mas o AS
     * deve tentar o outro tipo se o hint nao bater (RFC 7009 §2.1).
     */
    public void revogar(String token, String tokenTypeHint) throws Exception {
        String credenciais = Base64.getEncoder().encodeToString(
                (clientId + ":" + clientSecret).getBytes(StandardCharsets.UTF_8));

        String corpo = "token=" + java.net.URLEncoder.encode(token, StandardCharsets.UTF_8)
                + (tokenTypeHint != null
                    ? "&token_type_hint=" + java.net.URLEncoder.encode(tokenTypeHint, StandardCharsets.UTF_8)
                    : "");

        HttpRequest requisicao = HttpRequest.newBuilder(revocationEndpoint)
                .header("Content-Type", "application/x-www-form-urlencoded")
                .header("Authorization", "Basic " + credenciais)
                .POST(HttpRequest.BodyPublishers.ofString(corpo))
                .build();

        HttpResponse<String> resposta = http.send(requisicao, HttpResponse.BodyHandlers.ofString());

        // RFC 7009: sucesso e' sempre 200, corpo vazio — independentemente de
        // o token existir, ja estar expirado, ou ja ter sido revogado antes.
        // So' ha erro para requisicao malformada ou falha de autenticacao do
        // client (tipicamente 400, com corpo JSON de erro OAuth padrao).
        if (resposta.statusCode() == 200) {
            System.out.println("Revogacao processada (o AS nunca revela se o "
                    + "token de fato existia ou pertencia a este client).");
        } else {
            // Corpo de erro, quando existe, segue o formato OAuth padrao
            // {"error": "...", "error_description": "..."} — usar o
            // utilitario SimpleJson (Capitulo 1, RFC 6749) para interpretar.
            var campos = SimpleJson.parseFlat(resposta.body());
            System.err.println("Falha na revogacao: " + campos.getOrDefault("error", "desconhecido"));
        }
    }
}
```

### Exemplo 2 — servidor: handler do endpoint `/revoke` com resposta uniforme (anti-oráculo)

Implementa, com `com.sun.net.httpserver.HttpServer`, o comportamento normativo central da RFC: autenticar o client, tentar revogar (respeitando cascata refresh → access), e retornar sempre `200` vazio em caso de requisição bem-formada — nunca vazando se o token existia.

```java
import com.sun.net.httpserver.HttpExchange;
import com.sun.net.httpserver.HttpHandler;
import java.io.IOException;
import java.nio.charset.StandardCharsets;
import java.util.Map;
import java.util.Set;
import java.util.concurrent.ConcurrentHashMap;

public final class RevokeHandler implements HttpHandler {

    // token -> family_id (simulando o Redis do lab rfc7636/, aqui em memoria)
    private final Map<String, String> tokenParaFamilia = new ConcurrentHashMap<>();
    private final Map<String, Set<String>> membrosDaFamilia = new ConcurrentHashMap<>();
    private final ClientAuthenticator autenticador;

    public RevokeHandler(ClientAuthenticator autenticador) {
        this.autenticador = autenticador;
    }

    @Override
    public void handle(HttpExchange exchange) throws IOException {
        String corpo = new String(exchange.getRequestBody().readAllBytes(), StandardCharsets.UTF_8);
        Map<String, String> parametros = parseFormUrlEncoded(corpo);

        // Autenticacao do client e' obrigatoria — RFC 7009 §2.1. Falha aqui
        // e' o UNICO caso (junto com requisicao malformada) que retorna erro
        // real, nao o 200 uniforme.
        String clientIdAutenticado = autenticador.autenticarOuNull(exchange);
        if (clientIdAutenticado == null) {
            enviarErro(exchange, 401, "invalid_client");
            return;
        }

        String token = parametros.get("token");
        if (token == null || token.isBlank()) {
            enviarErro(exchange, 400, "invalid_request");
            return;
        }
        // token_type_hint (parametros.get("token_type_hint")) e' apenas dica
        // de otimizacao — nesta implementacao simplificada, nao muda o
        // comportamento porque o lookup por family_id ja cobre os dois casos.

        revogarComCascata(token);

        // RFC 7009 §2.2: 200 OK, corpo vazio, SEMPRE que a requisicao for
        // bem-formada e o client estiver autenticado — mesmo que `token`
        // nunca tenha existido ou ja estivesse revogado. Isto e' deliberado:
        // evita transformar o endpoint num oraculo de validacao de tokens.
        exchange.sendResponseHeaders(200, -1);
        exchange.close();
    }

    private void revogarComCascata(String token) {
        String familyId = tokenParaFamilia.remove(token);
        if (familyId == null) {
            return; // token desconhecido: nao ha nada a fazer, mas a resposta e' 200 do mesmo jeito
        }
        // Revogar um refresh_token derruba toda a familia (access tokens
        // derivados inclusos) — RFC 7009 §2.1, cascata recomendada.
        Set<String> membros = membrosDaFamilia.remove(familyId);
        if (membros != null) {
            membros.forEach(tokenParaFamilia::remove);
        }
    }

    private void enviarErro(HttpExchange exchange, int status, String erro) throws IOException {
        // Reaproveita o utilitario SimpleJson (definido no Capitulo 1, RFC 6749)
        // para montar o corpo JSON de erro no formato OAuth padrao.
        String json = SimpleJson.object(Map.of("error", erro));
        byte[] bytes = json.getBytes(StandardCharsets.UTF_8);
        exchange.getResponseHeaders().add("Content-Type", "application/json");
        exchange.sendResponseHeaders(status, bytes.length);
        try (var os = exchange.getResponseBody()) {
            os.write(bytes);
        }
    }

    private Map<String, String> parseFormUrlEncoded(String corpo) {
        Map<String, String> resultado = new java.util.HashMap<>();
        for (String par : corpo.split("&")) {
            if (par.isBlank()) continue;
            String[] kv = par.split("=", 2);
            String chave = java.net.URLDecoder.decode(kv[0], StandardCharsets.UTF_8);
            String valor = kv.length > 1 ? java.net.URLDecoder.decode(kv[1], StandardCharsets.UTF_8) : "";
            resultado.put(chave, valor);
        }
        return resultado;
    }

    /** Abstrai a autenticacao do client (Basic Auth ou client_id de client publico). */
    public interface ClientAuthenticator {
        String autenticarOuNull(HttpExchange exchange);
    }
}
```

### Exemplo 3 — nota sobre `token_type_hint` e o dever de tentar o outro tipo

Um trecho isolado, para deixar explícito o detalhe normativo mais frequentemente implementado de forma incorreta: o hint nunca deve ser tratado como filtro que rejeita a requisição se "não bater".

```java
/**
 * Ilustra a regra da RFC 7009 §2.1: token_type_hint e' so' uma otimizacao de
 * busca. Se o hint informado nao encontrar o token no armazenamento
 * correspondente, o AS DEVE tentar o outro tipo antes de desistir — nunca
 * deve retornar erro so' porque o hint "nao bateu" (isso vazaria informacao
 * e violaria a semantica de "sempre 200" da secao 5.1 deste capitulo).
 */
public final class TokenLookupComHint {

    public interface TokenStore {
        boolean existeComoAccessToken(String token);
        boolean existeComoRefreshToken(String token);
        void revogarAccessToken(String token);
        void revogarRefreshToken(String token);
    }

    private final TokenStore store;

    public TokenLookupComHint(TokenStore store) {
        this.store = store;
    }

    public void revogarRespeitandoHint(String token, String hintOuNull) {
        String primeiraTentativa = "refresh_token".equals(hintOuNull) ? "refresh" : "access";

        if (primeiraTentativa.equals("refresh")) {
            if (store.existeComoRefreshToken(token)) {
                store.revogarRefreshToken(token);
                return;
            }
            // Hint dizia refresh_token, mas nao encontrado la — tenta access_token
            // antes de desistir, como a RFC exige.
            if (store.existeComoAccessToken(token)) {
                store.revogarAccessToken(token);
            }
            // Se nao encontrar em nenhum dos dois, nao ha erro a reportar —
            // a resposta ao cliente sera 200 de qualquer forma (secao 5.1).
        } else {
            if (store.existeComoAccessToken(token)) {
                store.revogarAccessToken(token);
                return;
            }
            if (store.existeComoRefreshToken(token)) {
                store.revogarRefreshToken(token);
            }
        }
    }
}
```
