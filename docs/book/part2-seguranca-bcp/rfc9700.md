# RFC 9700 — Best Current Practice for OAuth 2.0 Security (BCP 240)

## 1. Contexto e motivação

RFC 9700, publicada em janeiro de 2025, é uma **BCP** (Best Current Practice) — uma categoria de documento IETF distinta tanto de uma spec de protocolo (como a RFC 6749) quanto de um documento puramente informativo (como a RFC 6819). Uma BCP não define mensagens ou parâmetros novos; ela **consolida consenso operacional** sobre como usar um protocolo já existente com segurança, e o faz com a mesma força normativa de linguagem (`MUST`, `MUST NOT`, `SHOULD`) que uma spec de protocolo usaria. É esse detalhe que separa a RFC 9700 da RFC 6819: onde a 6819 apenas sugeria e catalogava, a 9700 manda.

A origem deste documento é longa e vale contar, porque explica por que ele carrega tanto peso de autoridade coletiva. Antes de virar RFC, o conteúdo circulou por quase uma década como um *Internet-Draft* de nome informal `draft-ietf-oauth-security-topics`, atualizado incrementalmente por praticamente vinte revisões entre 2016 e 2024. Cada revisão incorporava lições de ataques documentados em produção, discussões do grupo de trabalho OAuth da IETF, e a experiência coletiva de operadores de authorization servers em escala — não é o trabalho de um único autor sentado numa mesa, é o resultado de um processo de atrito contínuo entre teoria e exploração real por praticamente todo o tempo de vida do OAuth 2.0 em produção massiva.

O efeito prático de virar RFC 9700 é que dezenas de recomendações que a RFC 6819 fazia como sugestão informal ("SHOULD", ou nem isso — apenas prosa descritiva) aqui viram **obrigação normativa explícita**. Isto não é uma mudança cosmética de redação: é a diferença entre "considere fazer X" e "uma implementação não conforme com esta BCP faz X errado, ponto". Para um arquiteto avaliando ou auditando um authorization server de terceiros, ou decidindo requisitos para um AS próprio, a RFC 9700 é hoje a referência de linha de base — o que ela exige é, para efeitos práticos, o piso mínimo aceitável de segurança OAuth em 2025 em diante.

Vale destacar também o parentesco desta RFC com o esforço de consolidação **OAuth 2.1** — um draft que reescreve a RFC 6749 + RFC 6750 + PKCE num único documento, já incorporando exatamente os mandatos que a 9700 formaliza aqui. Não é coincidência: a 9700 é, na prática, **o capítulo de segurança do OAuth 2.1** — quem entender profundamente este documento já entende a maior parte do que muda entre "OAuth 2.0 como definido em 2012" e "OAuth como se pratica com seriedade em 2025".

Uma nota importante para quem lê este capítulo antes de ter processado tudo que ele sintetiza: a RFC 9700 pressupõe familiaridade com PKCE (RFC 7636), mTLS aplicado a tokens (RFC 8705), DPoP (RFC 9449) e Resource Indicators (RFC 8707) — mas este capítulo foi escrito para ser autocontido. Cada mandato abaixo é explicado com o suficiente de contexto para fazer sentido mesmo que você ainda não tenha lido os capítulos dedicados a essas outras RFCs; quando chegar a eles, este capítulo vai se tornar ainda mais nítido em retrospecto, porque terá o "porquê" já internalizado antes do "como".

## 2. Terminologia e papéis

Nenhum papel novo. A contribuição terminológica real da RFC 9700 é endurecer — não redefinir — a distinção entre client **confidential** e **public** que já vinha da RFC 6749. Vale relembrar essa distinção com precisão, porque a maioria dos mandatos deste capítulo nasce diretamente da fragilidade estrutural do lado "public" dessa fronteira: um client confidencial roda em um ambiente que ele controla e pode manter um segredo (um servidor backend, por exemplo); um client público — uma SPA rodando no navegador, um app mobile, um app desktop distribuído ao usuário final — não tem como manter segredo algum de forma confiável, porque o binário ou o código-fonte do client está, por definição, nas mãos de quem poderia querer extrair esse segredo.

A RFC 9700 também introduz, sem lhe dar um nome formal de "papel", uma nova categoria de decisão de design: **sender-constraining** — a ideia de que um token deveria estar amarrado criptograficamente a quem o solicitou, de forma que posse do token sozinho (o modelo *bearer* puro da RFC 6750) deixe de ser suficiente para usá-lo. Isso não é um papel, mas é um conceito novo que perpassa vários dos mandatos de tokens abaixo.

## 3. Conteúdo normativo — os mandatos, agrupados e explicados a fundo

Como BCP, o documento não introduz mensagens novas — ele restringe e endurece o que já existe. O que segue não é apenas a lista de mandatos, mas uma discussão de *por que* cada um deixou de ser opcional.

### 3.1 Grant types: dois banidos, um universalizado

**Implicit Grant (`response_type=token`) — `MUST NOT` ser usado.**

O Implicit Grant devolvia o access token diretamente no fragmento (`#`) da URL de redirecionamento, sem passar por uma troca server-to-server via token endpoint. A racional original (2012) era acomodar clients em JavaScript puro rodando no navegador, que na época não tinham como fazer uma segunda requisição autenticada de forma prática sem CORS maduro. O problema estrutural: um token no fragmento da URL fica exposto a vazamento via histórico do navegador, via extensões instaladas, via qualquer script de terceiro que rode na mesma página (o fragmento é acessível via `window.location.hash` a qualquer JavaScript da página, não só ao client legítimo), e não existe nenhuma prova de posse do client na entrega — qualquer parte que intercepte o redirecionamento tem o token completo, pronto para uso imediato. Não há mitigação parcial aqui: o design é substituído inteiramente pelo Authorization Code Grant com PKCE, que hoje funciona perfeitamente bem para SPAs graças a CORS e `fetch` maduros — a justificativa original do Implicit Grant simplesmente deixou de existir.

**Resource Owner Password Credentials (ROPC) — `MUST NOT` ser usado.**

ROPC pede ao usuário para digitar usuário e senha diretamente no client, que os repassa ao token endpoint. O problema estrutural (já apontado, com mitigação paliativa, na RFC 6819) é que isso treina o usuário a confiar suas credenciais primárias a qualquer client que peça — destruindo a premissa central de segurança do OAuth, que é justamente o usuário *nunca* revelar sua senha a um client de terceiro, apenas ao authorization server. Diferente do Implicit Grant, aqui não há um substituto direto de "mesma conveniência, design melhor" — a mensagem da RFC 9700 é que se um client precisa de ROPC, o design do sistema como um todo está errado, e a solução é repensar a arquitetura (client confiável de primeira parte deveria ter uma via de autenticação direta com o AS, não mascarada de OAuth).

**PKCE — obrigatório para TODO client no Authorization Code Grant, independentemente do tipo.**

Esta é talvez a mudança de maior alcance prático do documento. A RFC 7636 original escopava PKCE como proteção primariamente voltada a clients públicos (a interceptação de code, RFC 6819 §5.1, é mais fácil de explorar contra eles). A RFC 9700 remove essa distinção: mesmo um client confidencial — com `client_secret` — deve usar PKCE em toda requisição de autorização. O racional: PKCE fecha a interceptação de code de forma independente de qualquer outra camada de proteção, e como o custo de implementá-lo é baixo (gerar um par verifier/challenge, dois parâmetros a mais), não há razão para deixar de exigi-lo universalmente só porque um client *também* tem outra camada de defesa. Segurança em profundidade, não segurança condicional.

### 3.2 Redirect e CSRF

**`redirect_uri` — exact string match obrigatório.**

Como discutido no capítulo anterior (RFC 6819 §5.3), qualquer flexibilização (prefixo, wildcard, substring) historicamente se revelou explorável para redirecionar o authorization code (ou, em designs antigos, o access token) para um destino sob controle do atacante. A RFC 9700 encerra a discussão: comparação deve ser string-a-string exata contra o valor registrado, sem exceção. Isso vale mesmo quando o client legitimamente precisa de múltiplos callbacks — nesse caso, cada um deve ser cadastrado explicitamente como uma entrada distinta e exata, nunca inferido por padrão.

**`state` continua recomendado; `code_verifier` do PKCE pode reforçar (mas não substitui) a proteção CSRF.**

Um ponto sutil que a RFC 9700 esclarece e que vale destacar: como o `code_verifier` do PKCE é gerado pelo client antes da requisição de autorização e só é revelado na troca final por token, ele *poderia*, em teoria, servir como uma segunda camada de vínculo entre a requisição original e a resposta — mas **somente se o client também vincular esse verifier à sessão do navegador daquele usuário específico** (por exemplo, guardando-o num cookie de sessão). PKCE sozinho, sem esse vínculo explícito à sessão, não substitui o papel do `state`: ele prova que quem está trocando o code por token é quem gerou o par verifier/challenge original, mas não prova, por si só, que essa troca está acontecendo na mesma sessão de navegador que iniciou o fluxo — que é exatamente o que o ataque de CSRF de login (RFC 6819 §5.2) explora.

**Ataques de "mix-up".**

Quando um client interage com mais de um authorization server (cenário comum em arquiteturas multi-tenant ou multi-provedor), um atacante pode induzir o client a acreditar que uma resposta veio do AS legítimo A quando na verdade veio de um AS malicioso ou comprometido B, levando o client a enviar o code (ou credenciais de troca) para o destino errado. A RFC 9700 recomenda mitigar isso com identificação explícita de qual AS emitiu a resposta — mecanismo formalizado com mais detalhe pela RFC 9207 (AS Issuer Identification, fora do escopo deste roteiro, mas vale saber que existe e resolve exatamente este problema).

### 3.3 Tokens

**Refresh token rotation — obrigatória, com detecção de reuso recomendada.**

O mandato tem duas camadas, e é importante não confundi-las:

1. **Rotação em si**: cada uso de um refresh token para obter um novo access token deve invalidar o refresh token usado e emitir um novo em seu lugar. O laboratório `rfc7636/` deste projeto já implementa esta camada.
2. **Detecção de reuso** (recomendação mais forte, ainda não presente no lab): se um refresh token *já invalidado* (porque já foi rotacionado uma vez) for apresentado de novo, isso é sinal inequívoco de que alguém mais, além do client legítimo, está de posse de uma cópia antiga do token — ou o client atual perdeu uma corrida de concorrência (bug), ou um atacante roubou uma cópia anterior e está tentando usá-la. Como não há como distinguir os dois casos com certeza, a mitigação recomendada é tratar qualquer reuso como comprometimento confirmado e **revogar toda a família de tokens** descendente daquele refresh token original — todo access token e todo refresh token subsequente gerado a partir dele, não apenas o token reapresentado.

Essa segunda camada é o que a RFC 9700 chama, em espírito, de tornar o refresh token um mecanismo de **detecção ativa de roubo**, não apenas de renovação de sessão: o AS não está apenas confiando que o refresh token está seguro, está *verificando continuamente* que só uma cópia dele está em circulação a qualquer momento.

**Tokens sender-constrained (DPoP ou mTLS) — recomendados onde viável.**

A RFC 6750 já apontava, como fraqueza estrutural, que um access token *bearer* — puramente por posse — dá acesso a qualquer parte que o apresente, sem prova adicional de que é o client legítimo apresentando. A RFC 9700 eleva essa preocupação de "considerar no futuro" para recomendação ativa hoje, especialmente para clients públicos (que não têm `client_secret` para se autenticar de outra forma) e cenários de alto valor (dados financeiros, PII sensível). Os dois mecanismos que atendem essa recomendação — DPoP (RFC 9449, prova de posse via par de chaves gerado pelo client, sem precisar de infraestrutura de certificados) e mTLS (RFC 8705, vínculo do token ao certificado de cliente usado na conexão TLS) — têm capítulos dedicados neste livro; aqui basta reter que "sender-constrained" quer dizer, em qualquer um dos dois casos, que um token roubado em trânsito ou em repouso (sem o material criptográfico associado) é inútil para o atacante.

**Restrição de audience/escopo.**

Reforça diretamente a preocupação de "confused deputy" já catalogada na RFC 6819 (§5.6 do capítulo anterior): um token emitido com a intenção de ser usado no Resource Server A não deveria ser aceito pelo Resource Server B. A RFC 9700 recomenda que o AS restrinja explicitamente a audiência de cada token emitido — mecanismo que ganha forma concreta na RFC 8707 (Resource Indicators), tratada em capítulo próprio deste livro.

**Vida curta e uso único para authorization codes; tempos de expiração curtos para access tokens.**

Reforço do que já era prática recomendada desde a RFC 6749/6819 — a RFC 9700 apenas formaliza como mandato o que a experiência de mais de uma década já havia consolidado como consenso: quanto menor a janela de validade de um artefato que trafega por um canal exposto (o authorization code, no redirecionamento), menor o dano possível de uma interceptação bem-sucedida.

### 3.4 Autenticação do client

A RFC 9700 expressa preferência clara por métodos de autenticação de client **assimétricos** — `private_key_jwt` (RFC 7523, o client assina uma asserção JWT com uma chave privada que nunca trafega pela rede) ou mTLS (RFC 8705) — em vez de `client_secret` estático transmitido a cada requisição de token. O racional é direto: um segredo compartilhado estático que precisa ser enviado repetidamente pela rede é, estruturalmente, mais fácil de vazar (interceptação, log acidental, exposição em configuração) e mais fácil de atacar por força bruta (é um valor fixo que pode ser tentado offline indefinidamente se vazar um hash dele) do que uma assinatura criptográfica gerada sob demanda com uma chave que nunca precisa deixar o ambiente do client.

### 3.5 Apps nativos

A requisição de autorização de um app nativo (mobile ou desktop) **não deve** ser feita dentro de uma *webview* embutida no próprio app — deve abrir o navegador do sistema operacional (Chrome Custom Tabs no Android, `ASWebAuthenticationSession`/Safari View Controller no iOS, ou o navegador padrão em desktop). O racional: uma webview embutida está sob controle total do app que a hospeda — ele pode inspecionar o DOM, injetar JavaScript, capturar o que o usuário digita (incluindo a senha no formulário de login do AS), e não oferece nenhuma das garantias de isolamento de sessão/cookies que o navegador do sistema oferece (por exemplo, reaproveitar uma sessão já autenticada no navegador para permitir *single sign-on* silencioso). Este mandato é formalizado com mais detalhe pela RFC 8252 (OAuth 2.0 for Native Apps), fora do escopo direto deste roteiro, mas a RFC 9700 o reforça como parte do conjunto obrigatório de boas práticas.

## 4. Parâmetros e endpoints normativos

Nenhum endpoint novo é criado por esta RFC. O efeito prático mais próximo de "novidade protocolar" é que ela promove `code_challenge` e `code_challenge_method` — originalmente parâmetros da RFC 7636, opcionais e restritos a clients públicos — à condição de parâmetros que devem estar presentes em **toda** requisição de autorização, independentemente do tipo de client. Um authorization server em conformidade com a RFC 9700 deveria, na prática, rejeitar ou alertar sobre qualquer requisição de autorização que omita PKCE, mesmo vinda de um client confidencial.

## 5. Segurança — este documento inteiro É a seção de segurança

Diferente dos outros capítulos deste livro, aqui não existe uma seção separada "5. Segurança" com conteúdo adicional além do que já foi discutido na seção 3: como BCP, a RFC 9700 apresenta ameaça e mitigação obrigatória juntas, ponto a ponto, ao longo de todo o documento — não há um "conteúdo de protocolo" e depois uma "reflexão de segurança" à parte. O documento inteiro é, estruturalmente, uma seção de segurança.

## 6. Relação com outras RFCs

- Constrói diretamente sobre a **RFC 6819** — pega dezenas de recomendações informais de lá e as torna obrigatórias, como discutido ao longo deste capítulo.
- Torna a **RFC 7636 (PKCE)** universal, removendo a restrição original a clients públicos.
- Deprecia formalmente 2 dos 4 grant types originais da **RFC 6749** (Implicit Grant e ROPC).
- Recomenda ativamente **RFC 8705 (mTLS)** e **RFC 9449 (DPoP)** para sender-constraining de tokens.
- Reforça a preocupação de audience que a **RFC 8707 (Resource Indicators)** resolve com um mecanismo concreto.
- É, na prática, o capítulo de segurança do **OAuth 2.1** (o draft de consolidação que reescreve RFC 6749 + 6750 + PKCE).
- Relacionada, fora do escopo direto deste roteiro: RFC 9207 (AS Issuer Identification, mitigação de ataques de mix-up) e RFC 8252 (OAuth 2.0 for Native Apps, guidance detalhado de webview).

## 7. O que essa RFC representa no arco do tempo

Diferente dos capítulos que tratam de RFCs mais antigas, aqui a pergunta habitual "o que mudou desde a publicação" se inverte: esta RFC é recente (2025) e é justamente o marco que **consolida** mais de dez anos de mudança incremental (2012–2024) em um único documento normativo. Antes dela, "as boas práticas" viviam fragmentadas — parte num draft de segurança de vida longa que só especialistas acompanhavam revisão a revisão, parte em blog posts de equipes de segurança de grandes provedores, parte em catálogos como a RFC 6819, e boa parte apenas na experiência tácita de quem operava authorization servers em produção e via os ataques acontecerem.

O que já se percebe evoluindo **além** dela, e vale ter no radar: perfis de segurança setoriais como o **FAPI** (Financial-grade API, da OpenID Foundation) já tornam **obrigatório** — não apenas recomendado — o que a RFC 9700 apenas sugere: sender-constraining (DPoP ou mTLS) sempre presente, não condicional a "onde viável"; PAR (Pushed Authorization Requests) e JAR (JWT-Secured Authorization Request) sempre usados, movendo os parâmetros de autorização para fora da URL exposta ao navegador; RAR (Rich Authorization Requests) para autorização de granularidade fina, além do modelo simples de escopo. Para um contexto FSI (financial services), vale internalizar que a RFC 9700 é o **piso mínimo** de 2025 em diante — não o teto de maturidade possível — e que especificações como FAPI 2.0 partem exatamente daqui para exigir mais.

## 8. Relação com os laboratórios deste projeto

A RFC 9700 não tem laboratório dedicado — como BCP, ela não introduz protocolo novo para implementar, apenas endurece o uso do que já existe. Suas exigências, porém, já aparecem parcialmente distribuídas pelos laboratórios construídos até aqui, e vale mapear explicitamente o que está feito e o que ainda é lacuna: PKCE (agora universal, não mais só para clients públicos) está implementado no lab `rfc7636/`; a rotação de refresh token também está lá, mas a **detecção de reuso com revogação em cascata** — a camada mais avançada do mandato de tokens — ainda não está implementada em nenhum lab deste projeto, e é o gap mais evidente a se fechar caso um laboratório específico venha a ser construído para esta RFC. DPoP (sender-constraining) tem seu próprio capítulo e, quando o lab correspondente existir, será `rfc9449/`. Enquanto isso não acontece, o exemplo de código abaixo ilustra em Java puro exatamente essa lacuna — rotação com detecção de reuso — como referência conceitual de como ela funcionaria.

## Exemplo em Java (JDK 21, sem frameworks)

### Exemplo 1 — PKCE: geração do par verifier/challenge e verificação (`S256`)

Ilustra o mecanismo que a RFC 9700 torna obrigatório para **todo** client, não apenas os públicos. O `code_verifier` é uma string aleatória de alta entropia; o `code_challenge` é o hash SHA-256 dele, codificado em Base64 URL-safe sem padding — exatamente como especificado pela RFC 7636, aqui usando somente `java.security.MessageDigest` do próprio JDK.

```java
import java.security.MessageDigest;
import java.security.NoSuchAlgorithmException;
import java.security.SecureRandom;
import java.util.Base64;
import java.nio.charset.StandardCharsets;

public final class Pkce {

    private static final SecureRandom RNG = new SecureRandom();

    /** Gera um code_verifier de 256 bits de entropia (RFC 7636 §4.1). */
    public static String gerarCodeVerifier() {
        byte[] bytes = new byte[32];
        RNG.nextBytes(bytes);
        return Base64.getUrlEncoder().withoutPadding().encodeToString(bytes);
    }

    /** Deriva o code_challenge a partir do verifier, metodo S256 (obrigatorio;
     *  "plain" existe na RFC 7636 mas nao deveria ser oferecido na pratica). */
    public static String derivarCodeChallenge(String codeVerifier) {
        try {
            MessageDigest sha256 = MessageDigest.getInstance("SHA-256");
            byte[] hash = sha256.digest(codeVerifier.getBytes(StandardCharsets.US_ASCII));
            return Base64.getUrlEncoder().withoutPadding().encodeToString(hash);
        } catch (NoSuchAlgorithmException e) {
            // SHA-256 e' garantido presente em qualquer JDK conforme; isto
            // nunca deveria disparar, mas o checked exception exige o catch.
            throw new IllegalStateException("SHA-256 indisponivel no JDK", e);
        }
    }

    /**
     * Lado do Authorization Server: na troca final do code por token, recebe
     * o code_verifier em texto puro e confere se ele deriva o mesmo
     * code_challenge que foi apresentado na requisicao de autorizacao original.
     */
    public static boolean verificar(String codeVerifierRecebido, String codeChallengeOriginal) {
        String recalculado = derivarCodeChallenge(codeVerifierRecebido);
        // Comparacao em tempo constante: o challenge nao e' secreto (trafegou
        // em claro na URL de autorizacao), mas o habito de comparar valores
        // criptograficos assim evita repetir o erro onde importa.
        return MessageDigest.isEqual(
                recalculado.getBytes(StandardCharsets.US_ASCII),
                codeChallengeOriginal.getBytes(StandardCharsets.US_ASCII));
    }
}
```

### Exemplo 2 — rotação de refresh token com detecção de reuso e revogação em cascata

Este exemplo implementa em memória exatamente a lacuna apontada na seção 8: não apenas rotacionar (invalidar o antigo, emitir um novo), mas **detectar reuso de um refresh token já invalidado** e, ao detectar, revogar toda a família de tokens descendente. A ideia de "família" é a mesma usada no laboratório `rfc7636/` (lá em Redis; aqui, em memória, para fins didáticos).

```java
import java.security.SecureRandom;
import java.util.Base64;
import java.util.Set;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.CopyOnWriteArraySet;

public final class RefreshTokenRotation {

    private static final SecureRandom RNG = new SecureRandom();

    /** Estado de um refresh token: a familia a que pertence e se ja foi usado. */
    private record Estado(String familyId, boolean usado) {}

    private final ConcurrentHashMap<String, Estado> tokens = new ConcurrentHashMap<>();
    // Todos os refresh tokens (validos ou ja usados) que pertenceram a cada familia,
    // para permitir revogacao em cascata quando reuso e' detectado.
    private final ConcurrentHashMap<String, Set<String>> membrosDaFamilia = new ConcurrentHashMap<>();
    private final Set<String> tokensRevogados = new CopyOnWriteArraySet<>();

    private String gerar() {
        byte[] b = new byte[24];
        RNG.nextBytes(b);
        return Base64.getUrlEncoder().withoutPadding().encodeToString(b);
    }

    /** Emissao inicial (ex: primeiro login) — cria uma nova familia. */
    public String emitirNovo() {
        String familyId = gerar();
        String refreshToken = gerar();
        tokens.put(refreshToken, new Estado(familyId, false));
        membrosDaFamilia.put(familyId, new CopyOnWriteArraySet<>(Set.of(refreshToken)));
        return refreshToken;
    }

    /**
     * Troca um refresh token por um novo (rotacao). Se o token apresentado ja
     * tiver sido usado antes, e' sinal de reuso — RFC 9700 §3 (tokens):
     * revoga toda a familia e sinaliza comprometimento ao chamador.
     *
     * @return o novo refresh token, ou Optional.empty() se reuso foi detectado
     *         (a familia inteira foi revogada como consequencia).
     */
    public java.util.Optional<String> rotacionar(String refreshTokenApresentado) {
        Estado estadoAtual = tokens.get(refreshTokenApresentado);

        if (estadoAtual == null || tokensRevogados.contains(refreshTokenApresentado)) {
            // Token desconhecido ou ja revogado: nada a rotacionar.
            return java.util.Optional.empty();
        }

        if (estadoAtual.usado()) {
            // REUSO DETECTADO: alguem apresentou um refresh token que ja
            // havia sido trocado por um novo anteriormente. Nao ha como
            // distinguir com certeza "bug de concorrencia no client legitimo"
            // de "atacante usando uma copia roubada" — a postura segura e'
            // tratar como comprometimento e revogar a familia inteira.
            revogarFamilia(estadoAtual.familyId());
            registrarAlertaSeguranca(refreshTokenApresentado, estadoAtual.familyId());
            return java.util.Optional.empty();
        }

        // Uso legitimo (primeira vez): marca o atual como usado e emite um novo
        // na mesma familia.
        tokens.put(refreshTokenApresentado, new Estado(estadoAtual.familyId(), true));
        String novoToken = gerar();
        tokens.put(novoToken, new Estado(estadoAtual.familyId(), false));
        membrosDaFamilia.get(estadoAtual.familyId()).add(novoToken);
        return java.util.Optional.of(novoToken);
    }

    private void revogarFamilia(String familyId) {
        Set<String> membros = membrosDaFamilia.getOrDefault(familyId, Set.of());
        tokensRevogados.addAll(membros);
        // Numa implementacao real: revogar tambem, em cascata, todo access
        // token emitido a partir de qualquer refresh token desta familia
        // (mesmo mecanismo do endpoint /revoke da RFC 7009 — ver proximo capitulo).
    }

    private void registrarAlertaSeguranca(String token, String familyId) {
        System.err.println("ALERTA: reuso de refresh_token detectado, familia "
                + familyId + " revogada por completo");
    }

    public boolean estaRevogado(String refreshToken) {
        return tokensRevogados.contains(refreshToken);
    }
}
```

### Exemplo 3 — exact-match de `redirect_uri` reforçado com verificação de esquema para apps nativos

Complementa o Exemplo 2 do capítulo anterior (RFC 6819) acrescentando a checagem específica que a RFC 9700 recomenda para apps nativos: além do exact-match, validar que o esquema da URI não é um esquema customizado genérico compartilhável por múltiplos apps no mesmo dispositivo, a menos que o AS também valide "app-links" verificados (fora do escopo deste exemplo simplificado).

```java
import java.net.URI;
import java.util.Set;

public final class RedirectUriValidatorReforcado {

    private final Set<String> uriRegistradas;
    private final boolean clientEhAppNativo;

    public RedirectUriValidatorReforcado(Set<String> uriRegistradas, boolean clientEhAppNativo) {
        this.uriRegistradas = Set.copyOf(uriRegistradas);
        this.clientEhAppNativo = clientEhAppNativo;
    }

    public boolean ehValido(String redirectUriRecebida) {
        URI uri;
        try {
            uri = URI.create(redirectUriRecebida).normalize();
        } catch (IllegalArgumentException e) {
            return false;
        }

        // RFC 9700: exact match, sempre — sem excecao para nenhum tipo de client.
        if (!uriRegistradas.contains(uri.toString())) {
            return false;
        }

        if (clientEhAppNativo && uri.getScheme() != null) {
            String esquema = uri.getScheme().toLowerCase();
            // "https" com dominio verificado (App Links/Universal Links) e'
            // preferivel a um esquema customizado (ex: "meuapp://") que
            // multiplos apps no mesmo dispositivo poderiam reivindicar —
            // RFC 8252 (OAuth for Native Apps) e RFC 6819 §5.1 discutem essa
            // ambiguidade de sistema operacional com mais profundidade.
            if (!esquema.equals("https")) {
                System.err.println("AVISO: redirect_uri de app nativo usa esquema "
                        + "customizado '" + esquema + "' — prefira https com "
                        + "App Links/Universal Links verificados quando possivel");
            }
        }

        return true;
    }
}
```
