# RFC 6819 — OAuth 2.0 Threat Model and Security Considerations

## 1. Contexto e motivação

A RFC 6749 nasceu deliberadamente enxuta. Ela descreve um *framework* de autorização — quatro concessões, um punhado de endpoints, um vocabulário mínimo — e empurra para fora do documento normativo praticamente toda decisão que separa uma implementação segura de uma implementação ingênua e explorável. Isso não é um defeito de redação: é uma escolha de design consciente dos autores, que preferiram um núcleo estável e extensível a uma spec monolítica que tentasse antecipar todo ataque possível. O preço dessa escolha é que alguém precisa, em algum lugar, escrever o documento complementar que enumera "e se isto der errado?". Esse documento é a RFC 6819, publicada em janeiro de 2013, poucos meses depois da RFC 6749/6750.

É importante posicionar corretamente o que ela é e o que ela não é. A RFC 6819 tem status **Informational** — não é uma especificação de protocolo, não define uma única mensagem nova, não introduz um parâmetro sequer. Ela é, em essência, um exercício de *threat modeling* formal aplicado retroativamente a um protocolo que já existia: descreve a arquitetura OAuth 2.0 sob a ótica de "quais são os ativos valiosos aqui, quem pode atacá-los, por onde, e o que mitiga cada ataque". O gênero não é exclusivo do OAuth — é o mesmo tipo de exercício que se faz com STRIDE, com DREAD, com qualquer metodologia de análise de ameaças de sistemas distribuídos — mas aplicado com granularidade fina à arquitetura específica de authorization code, tokens portáveis e redirecionamentos via user-agent que o OAuth 2.0 introduziu.

Por que isso importa tanto hoje, mais de uma década depois? Porque a RFC 6819 se tornou, na prática, **o catálogo de ameaças mais citado e mais influente de todo o ecossistema OAuth**. Não é exagero dizer que quase toda extensão de segurança publicada depois dela resolve uma ameaça específica que já estava documentada aqui, em prosa, anos antes de existir uma RFC dedicada à mitigação formal. PKCE (RFC 7636) resolve a interceptação de authorization code que a 6819 já descrevia informalmente. Resource Indicators (RFC 8707) resolve a confusão de audience/"confused deputy" que a 6819 já apontava como risco estrutural. A própria RFC 9700 — o assunto do próximo capítulo — é, essencialmente, esta RFC reescrita em tom normativo: ela pega dezenas das recomendações "deveria fazer" daqui e as transforma em "deve fazer obrigatoriamente", à luz de mais de uma década de exploração real em produção.

Vale também entender por que a RFC 6819 nunca foi atualizada, e por que isso não a torna obsoleta. Um catálogo de ameaças é, por natureza, um retrato de um momento — mas a arquitetura fundamental que ele analisa (redirecionamento via navegador, troca de code por token, tokens bearer portáveis) não mudou desde 2013. As ameaças estruturais continuam as mesmas; o que mudou foi o consenso sobre qual mitigação é obrigatória versus opcional, e isso é exatamente o papel que a RFC 9700 assumiu treze anos depois.

## 2. Terminologia e papéis

A RFC 6819 não introduz nenhum papel novo — ela reaproveita integralmente o vocabulário da RFC 6749: *resource owner*, *client*, *authorization server*, *resource server*. O que ela introduz é vocabulário de *threat modeling* propriamente dito, que vale a pena destrinchar porque estrutura toda a leitura do documento:

- **Ativo (*asset*)** — algo de valor que precisa ser protegido. No OAuth, os ativos centrais são: as credenciais do resource owner (senha, sessão de login no AS), o `client_secret` (segredo do client confidencial), o *authorization code* (curta duração, mas trocável por token), o *access token* e o *refresh token* (o ativo de maior duração e maior "poder de compra" — um refresh token comprometido pode gerar access tokens indefinidamente até ser revogado), e os próprios dados do resource owner expostos pelo resource server.
- **Ameaça (*threat*)** — um evento ou ação que pode comprometer um ativo. A RFC organiza as ameaças por *onde* elas ocorrem na arquitetura, não por *que tipo* de ataque são — uma escolha metodológica que faz sentido porque o OAuth é, antes de tudo, uma coreografia entre partes distribuídas, e cada ponto da coreografia (o navegador do usuário, o canal de redirecionamento, o armazenamento do client, o armazenamento do AS) tem uma superfície de ataque distinta.
- **Contramedida (*countermeasure*)** — a mitigação recomendada para cada ameaça, normalmente expressa como "SHOULD" ou como recomendação de design, quase nunca como "MUST" (lembre-se: é um documento Informational, não tem poder normativo de spec).
- **Nível de impacto e probabilidade** — embora a RFC não use uma matriz de risco formal (tipo DREAD com pontuação numérica), ela qualifica cada ameaça em termos de quão fácil é executá-la e quão grave é o dano — um vocabulário implícito de risco que aparece na profundidade da discussão dedicada a cada item.

Um ponto sutil que vale reter: a RFC 6819 trata o **navegador do usuário (user-agent)** quase como um quinto papel implícito na análise de ameaças, mesmo que a RFC 6749 não o eleve à categoria de papel formal. Isso faz sentido porque boa parte das ameaças mais graves do catálogo — CSRF, vazamento via `Referer`, comprometimento por malware no dispositivo, phishing na tela de consentimento — dependem inteiramente do comportamento e das garantias (ou falta delas) do navegador como intermediário do redirecionamento.

## 3. Estrutura do documento — não há fluxo, há um mapa de superfície de ataque

Como já adiantado, não existe um "fluxo de protocolo" para descrever aqui — a contribuição da RFC é estrutural, não procedural. Ela segue a arquitetura clássica de um documento de threat modeling:

- **§3 — Arquitetura recapitulada.** Redesenha o diagrama de sequência do Authorization Code Grant (e dos demais grants da RFC 6749) especificamente para servir de mapa de referência à análise que segue. Cada seta do diagrama — requisição de autorização, redirecionamento com code, troca de code por token, chamada ao resource server com o token — vira um ponto de ancoragem para as ameaças listadas depois.
- **§4 — Proteções já embutidas na RFC 6749/6750.** Antes de listar o que pode dar errado, o documento resume o que a spec-base já exige ou recomenda: TLS obrigatório nos endpoints que carregam credenciais e tokens, expiração de token, validação de `redirect_uri` (ainda sem especificar *como* validar — esse detalhe fica para depois), escopo como mecanismo de limitação de dano. Essa seção existe para deixar claro que o catálogo que segue não está reinventando a segurança do zero — está identificando as lacunas que sobram *depois* dessas proteções de base.
- **§5 — O catálogo de ameaças propriamente dito**, organizado por alvo:
  - **§5.1 — Ameaças ao client.** Falsificação de client, roubo de `client_secret`, malware no dispositivo do usuário capturando tokens em trânsito ou em repouso.
  - **§5.2 — Ameaças ao authorization server.** Comprometimento do endpoint de autorização, phishing da tela de login/consentimento, ataques ao armazenamento de tokens e segredos.
  - **§5.3 — Ameaças ao resource owner.** Engenharia social para induzir consentimento indevido, clickjacking na UI de autorização, vazamento de credenciais de login.
  - **§5.4 — Ameaças ao resource server.** Replay de token, aceitação de token emitido para outro público (confused deputy), validação insuficiente de escopo.
- **§6 — Recomendações consolidadas**, que voltam a percorrer o mesmo território de §5 mas já na forma de "o que fazer a respeito", servindo de ponte para o que, treze anos depois, se tornaria a RFC 9700.

Essa arquitetura em duas passadas (primeiro o ativo/ameaça, depois a mitigação) é o motivo pelo qual a RFC 6819, apesar de longa, funciona bem como referência de consulta: dado um sintoma ou uma dúvida de design ("meu client precisa validar X?"), é possível ir direto à seção que trata do ativo em risco.

## 4. Parâmetros e endpoints normativos

Nenhum. Vale repetir com ênfase porque é fácil, ao ler um documento tão detalhado, presumir que ele define algo protocolar — não define. A RFC 6819 não cria nenhum endpoint, não adiciona nenhum parâmetro à requisição de autorização ou à requisição de token, não define um único código de erro novo. Toda a análise é sobre a arquitetura *já existente* da RFC 6749/6750. Isso contrasta diretamente com o próximo capítulo (RFC 9700), que também não define protocolo novo, mas que — por ser uma BCP e não um documento puramente informativo — assume tom prescritivo com força de "MUST"/"MUST NOT" mesmo sem inventar mensagens novas.

## 5. Ameaças e mitigações mais relevantes do catálogo (§5) — análise aprofundada

O catálogo completo tem dezenas de itens numerados. O que segue é uma seleção comentada das ameaças que mais moldaram o resto do ecossistema — não um resumo raso, mas uma discussão de cada uma com o cenário de exploração completo e o porquê estrutural da mitigação.

### 5.1 Interceptação do authorization code

**O cenário.** O authorization code trafega pelo canal menos controlado de todo o fluxo: o redirecionamento via navegador, tipicamente uma URL completa (`redirect_uri?code=...&state=...`) que passa por, no mínimo, o histórico do navegador e potencialmente por proxies, logs de servidor web e — em mobile, o caso mais grave — pelo próprio sistema operacional na forma de um *custom URI scheme* (`meuapp://callback?code=...`).

Em Android e iOS anteriores a mecanismos mais rígidos de verificação de domínio (App Links / Universal Links), múltiplos aplicativos podiam se registrar para o *mesmo* esquema de URI customizado. O sistema operacional, ao receber o redirecionamento, não tem garantia de entregá-lo ao app legítimo — um app malicioso instalado no mesmo dispositivo, registrado com o esquema idêntico, pode receber a interceptação e capturar o code antes (ou em vez) do client verdadeiro. Uma vez de posse do code, o atacante só precisa completar a troca por token — e se o client for público (sem `client_secret`, caso comum em mobile), não há nenhuma segunda barreira.

**Por que isso é grave especificamente para clients públicos.** Um client confidencial que perde um code interceptado ainda está parcialmente protegido, porque a troca final exige o `client_secret` que só ele possui. Um client público não tem esse escudo — o code sozinho é suficiente para completar o roubo. É exatamente esta assimetria que a RFC 6819 identifica como estrutural, sem ainda ter uma solução formal para propor.

**A mitigação que a própria RFC já insinua.** O texto da 6819 já sugere, em prosa, vincular a requisição de autorização inicial à troca final de code por token — de forma que um atacante que só intercepte o code (sem ter iniciado o fluxo) não consiga completá-lo. Essa ideia, ainda informal aqui, é **literalmente** a espinha dorsal do PKCE (RFC 7636), publicado três anos depois: o client gera um segredo local (`code_verifier`), envia um hash dele (`code_challenge`) na requisição de autorização, e só o `code_verifier` original — nunca exposto no canal de redirecionamento — permite trocar o code por token. Um atacante que capture o code no meio do caminho não tem o verifier e a troca falha.

### 5.2 CSRF no endpoint de redirecionamento (login CSRF via authorization code)

**O cenário.** Sem um mecanismo de correlação entre a requisição de autorização que o client iniciou e a resposta que ele recebe, um atacante pode montar o seguinte ataque: ele mesmo inicia um fluxo de autorização legítimo (autenticando-se com a *sua própria* conta), captura o authorization code resultante, e induz a vítima — via um link malicioso, um `<img>` oculto, um formulário auto-submit — a acessar o `redirect_uri` do client com *esse* code anexado. Se o client aceitar o code sem validar que ele corresponde à sessão que a vítima realmente iniciou, o resultado é que a conta da vítima no client fica vinculada à conta do atacante no resource server — um ataque de fixação de sessão/conta que pode ser usado, por exemplo, para plantar dados sob controle do atacante que depois a vítima acredita serem seus.

**A mitigação.** O parâmetro `state`, opaco e gerado pelo client antes de iniciar o fluxo, vinculado à sessão do navegador da vítima (tipicamente guardado num cookie de sessão do client). Ao receber o retorno no `redirect_uri`, o client compara o `state` recebido com o que ele próprio gravou para aquela sessão — se não bater, a requisição é rejeitada. O laboratório deste projeto já implementa essa validação de `state`.

Vale marcar uma nuance que a RFC 6819 já antecipa e que a RFC 9700 viria a detalhar melhor: o `state` protege contra CSRF **somente se for validado contra algo vinculado à sessão do navegador** — gerar um `state` aleatório mas não guardá-lo em lugar nenhum para comparar depois é uma implementação incompleta que dá falsa sensação de segurança.

### 5.3 Open redirector via `redirect_uri` mal validado

**O cenário.** Se o authorization server aceita qualquer `redirect_uri` que "comece com" ou "contenha" o valor registrado pelo client — validação por prefixo, por substring, ou pior, por wildcard —, um atacante pode manipular o parâmetro `redirect_uri` na requisição de autorização para apontar para um destino sob seu controle que ainda "bate" com a regra frouxa. Exemplos clássicos de bypass de validação por prefixo: registrar `https://client.exemplo.com/callback` e o atacante conseguir usar `https://client.exemplo.com/callback.atacante.com/` ou `https://client.exemplo.com@atacante.com/callback` (abuso de sintaxe de URI com userinfo) ou ainda `https://client.exemplo.com/callback/../../atacante`. O efeito prático: o authorization code (ou, em fluxos mais antigos, até o access token via Implicit Grant) é entregue a um endpoint do atacante, não ao client legítimo.

**Por que a validação "flexível" é tentadora e por que ela é sempre um erro.** Times de desenvolvimento frequentemente querem suportar múltiplos subcaminhos de callback (`/callback`, `/callback/mobile`, `/callback/web`) sem cadastrar cada um explicitamente, e por isso implementam validação por prefixo "por conveniência". A RFC 6819 já sinaliza isso como recomendação (não obrigação) de usar comparação estrita. É só treze anos depois, na RFC 9700, que o **exact match** se torna mandato universal (`MUST`) — o mesmo raciocínio de "conveniência abre brecha" se repete tantas vezes na história da segurança do OAuth que vale a pena grifar aqui: qualquer flexibilização de uma regra de comparação de URI tem, historicamente, se revelado explorável.

### 5.4 Vazamento de token via `Referer`, logs ou histórico do navegador

**O cenário.** Se o access token (ou o authorization code) aparece na query string de uma URL, ele fica exposto a três vetores de vazamento que nada têm a ver com o protocolo OAuth em si: (1) o cabeçalho `Referer` enviado pelo navegador para qualquer recurso de terceiro embutido na página seguinte (imagens, scripts, iframes) carrega a URL completa, incluindo a query string; (2) logs de servidor web tipicamente registram a URL completa da requisição, inclusive parâmetros de query, em texto plano, muitas vezes retidos por meses; (3) o histórico do navegador retém a URL indefinidamente, acessível a qualquer pessoa com acesso físico ao dispositivo ou a extensões de navegador maliciosas.

Este item da 6819 é o fundamento direto de por que a **RFC 6750** desaconselha explicitamente carregar o *access token* na query string (permitindo apenas como último recurso, com ressalvas), e prefere o cabeçalho `Authorization: Bearer`. O mesmo raciocínio, aplicado ao *authorization code* — que inevitavelmente viaja na query string do `redirect_uri`, já que não há alternativa de protocolo para isso — é o motivo de o code ter vida curtíssima (minutos, uso único) em vez de qualquer TTL mais longo: o vazamento *vai* acontecer estruturalmente (é a natureza do canal), a mitigação é reduzir a janela de validade a quase zero.

### 5.5 Reuso do authorization code

**O cenário.** Um authorization code já trocado por token com sucesso é apresentado de novo ao token endpoint. Duas leituras possíveis: ou é um erro de implementação do client (bug, retry duplicado por timeout), ou é um sinal de que o code vazou e um segundo ator (o atacante) está tentando completar a troca depois do client legítimo já ter feito isso.

**A mitigação.** Rejeitar peremptoriamente qualquer segunda tentativa de troca do mesmo code — não apenas ignorá-la silenciosamente, mas tratá-la como evento de segurança. A RFC 6819 já recomenda que, ao detectar reuso, o authorization server deveria revogar retroativamente todos os tokens já emitidos a partir daquele code, sob a premissa de que se o code foi reapresentado é porque pode ter havido duas partes de posse dele — e não há como saber com certeza qual delas era a legítima. O laboratório deste projeto já implementa o code como recurso de uso único (removido do armazenamento assim que trocado).

### 5.6 "Confused deputy" / substituição de token entre resource servers

**O cenário.** Um access token emitido pelo authorization server com a intenção de ser aceito apenas pelo Resource Server A é apresentado — e aceito — pelo Resource Server B. Isso acontece quando o token não carrega (ou o RS não valida) nenhuma informação de "para qual audiência este token foi emitido", e quando múltiplos resource servers confiam cegamente em qualquer token assinado/válido pelo mesmo authorization server, sem checar se aquele token específico foi de fato destinado a eles. O nome "confused deputy" vem do padrão clássico de segurança de sistemas: um agente com autoridade legítima (o RS, que confia no AS) é enganado a exercer essa autoridade em benefício de um pedido que não deveria atender.

Este é um dos itens do catálogo com a trajetória histórica mais longa dentro do próprio roteiro deste livro: a RFC 6819 já o identifica como risco estrutural em 2013; a **RFC 8707 (Resource Indicators)**, anos depois, oferece o mecanismo formal de mitigação (o parâmetro `resource`, que permite ao client declarar — e ao AS registrar no próprio token — para qual resource server aquele token específico é válido); e a **RFC 9700** reforça a recomendação como parte do endurecimento geral de restrição de audience/escopo.

### 5.7 Clickjacking na tela de consentimento

**O cenário.** A tela onde o resource owner decide "autorizar" ou "negar" o acesso do client pode ser embutida, via `<iframe>`, dentro de uma página controlada pelo atacante — tornada invisível ou disfarçada de outro elemento de UI (um botão de "jogo", um "play" de vídeo). O usuário pensa que está clicando em algo inofensivo, mas na verdade seu clique atinge o botão "Autorizar" da tela de consentimento posicionado exatamente sob o cursor.

**A mitigação**, hoje trivial de implementar mas que a RFC 6819 já recomendava explicitamente em 2013: o authorization server deve enviar o cabeçalho `X-Frame-Options: DENY` (ou o equivalente moderno via `Content-Security-Policy: frame-ancestors 'none'`) em toda resposta da tela de autorização/consentimento, impedindo que ela seja embutida em iframe de terceiros.

### 5.8 Força bruta contra `client_secret`

**O cenário.** Clients públicos, por definição, não têm `client_secret` — mas mesmo clients confidenciais mal configurados (segredo curto, sem rate limiting no endpoint de token, sem lockout após tentativas falhas) ficam expostos a ataques de força bruta ou dicionário contra o segredo. A RFC 6819 usa este item para reforçar uma tensão que já vinha da própria RFC 6749: a distinção confidential/public nunca foi uma garantia binária de segurança — é uma classificação de *capacidade* de manter segredo, e mesmo dentro da categoria "confidencial" há uma escala enorme de robustez efetiva.

**A mitigação.** Segredos de entropia adequada (nunca senhas memorizáveis por humanos), rate limiting agressivo no endpoint de token, e — o caminho que a RFC 9700 viria a preferir estruturalmente — migrar para autenticação assimétrica (assinatura com chave privada, `private_key_jwt` ou mTLS) em vez de depender de um segredo compartilhado estático que precisa trafegar em toda requisição de token.

### 5.9 Comprometimento do armazenamento do authorization server

**O cenário.** Um vazamento de banco de dados, backup ou dump de memória do authorization server expõe `client_secret`s, access tokens e refresh tokens armazenados sem proteção adequada — tipicamente em texto plano, quando deveriam estar ao menos com hash (para segredos que só precisam ser *verificados*, nunca reapresentados) ou criptografados em repouso (para tokens que precisam ser recuperados para validação).

Este item merece destaque porque é o único do catálogo cuja mitigação depende inteiramente de práticas de infraestrutura e operação — nada que o protocolo OAuth em si consiga resolver. É também o motivo pelo qual "confiar no AS" é uma decisão de arquitetura tão pesada: comprometer o AS compromete transitivamente todo client e todo resource server que dependem dele.

## 6. Relação com outras RFCs

A RFC 6819 funciona como a base conceitual de praticamente todo o resto do roteiro de segurança deste livro:

- **RFC 7636 (PKCE)** resolve diretamente a ameaça de interceptação de authorization code (§5.1 acima).
- **RFC 8707 (Resource Indicators)** resolve a ameaça de confused deputy/substituição de token entre resource servers (§5.6 acima).
- **RFC 9700 (BCP)** é, em essência, esta mesma análise revisitada treze anos depois — pega dezenas de recomendações "deveria" catalogadas aqui e as promove a "deve" obrigatório, à luz de mais de uma década de exploração real documentada.
- Complementa diretamente a **RFC 6749/6750** — assume o papel de "e se algo der errado?" que as specs de protocolo, deliberadamente, não cobrem.
- Deu origem, mais tarde, a análises de ameaça mais específicas que ficam fora do escopo deste roteiro mas merecem nota: ataques de **"mix-up"** entre múltiplos authorization servers (quando um client fala com mais de um AS e pode ser enganado sobre qual deles respondeu a uma dada requisição), endereçados formalmente pela RFC 9207 (AS Issuer Identification).

## 7. O que mudou desde a publicação (2013)

- A RFC nunca foi revisada — permanece, textualmente, um retrato de ameaças de mais de uma década atrás. Isso não a invalida: a arquitetura fundamental que ela analisa não mudou, e a maioria das ameaças catalogadas continua tão relevante hoje quanto em 2013.
- Muitas mitigações que aqui eram apenas "recomendadas" viraram **obrigatórias** na RFC 9700: PKCE universal (não mais restrito a clients públicos), exact-match de `redirect_uri`, rotação de refresh token.
- Ameaças ligadas ao ROPC (Resource Owner Password Credentials), que aqui recebiam apenas mitigação paliativa (recomendações de uso restrito, TLS obrigatório, sem armazenamento de senha), hoje são resolvidas de forma mais radical: a RFC 9700 simplesmente deprecia o grant type inteiro (`MUST NOT` ser usado) em vez de tentar mitigar riscos em torno de um design considerado estruturalmente falho.
- Classes de ameaça inteiramente novas surgiram depois e não podiam constar num documento de 2013: ataques específicos de manipulação de JWT (`alg=none`, confusão entre chave simétrica e assimétrica em validação de assinatura), phishing de device code (só relevante depois da RFC 8628, publicada em 2019), e ataques de *downgrade* de PKCE (forçar um client a negociar sem PKCE quando ele o suportaria) — nenhuma dessas categorias existia no vocabulário de ameaças de 2013.

## 8. Relação com os laboratórios deste projeto

A RFC 6819 não tem — nem poderia ter — um laboratório dedicado: é um documento analítico, sem protocolo próprio para implementar. Mas suas mitigações aparecem, na prática, espalhadas por vários laboratórios já construídos neste projeto: a validação de `state` e o code de uso único já estão no lab base da RFC 6749; a mitigação de interceptação de code via PKCE está implementada no lab `rfc7636/`; a revogação em cascata que mitiga o dano de um refresh token comprometido está também no `rfc7636/` (e será aprofundada no capítulo da RFC 7009, a seguir). Ler este capítulo antes de mexer em qualquer um desses laboratórios ajuda a enxergar *por que* cada uma dessas peças de código existe — cada uma delas é a resposta direta a uma ameaça específica catalogada aqui.

## Exemplo em Java (JDK 21, sem frameworks)

Os exemplos abaixo são didáticos — ilustram, em Java puro (sem Spring, sem bibliotecas de terceiros), os mecanismos de mitigação discutidos acima. Não são código de produção: faltam tratamento de concorrência real de nível industrial, persistência durável, e configuração de TLS, que num sistema real ficariam a cargo da infraestrutura.

### Exemplo 1 — geração de `state` com `SecureRandom` e comparação em tempo constante

Mitiga a ameaça de CSRF no endpoint de redirecionamento (§5.2). Dois pontos merecem atenção: o gerador de aleatoriedade precisa ser criptograficamente seguro (nunca `java.util.Random`), e a comparação do `state` recebido contra o `state` esperado precisa ser em tempo constante — comparar strings com `String.equals` pode, em tese, vazar informação por *timing* (a comparação de `String.equals` interrompe no primeiro byte diferente), o que é uma prática ruim para qualquer comparação de valor sensível, mesmo que aqui o `state` não seja secreto (é apenas imprevisível) — o hábito de comparação constante-tempo evita repetir o erro em outros lugares onde o valor comparado *é* sensível (como um token).

```java
import java.security.SecureRandom;
import java.security.MessageDigest;
import java.util.Base64;
import java.util.concurrent.ConcurrentHashMap;
import java.util.Map;

/**
 * Gera e valida o parametro `state` (RFC 6819 secao 5.2 — mitigacao de CSRF
 * no endpoint de redirecionamento).
 */
public final class StateProtection {

    // SecureRandom, NUNCA java.util.Random: precisa ser imprevisivel para um
    // atacante, nao apenas "bem distribuido" estatisticamente.
    private static final SecureRandom RNG = new SecureRandom();

    // Em producao isto seria um store com TTL (Redis, por exemplo) atrelado
    // a sessao do navegador. Aqui, um mapa em memoria basta para ilustrar.
    private final Map<String, String> statePorSessao = new ConcurrentHashMap<>();

    /** Gera um `state` opaco de 256 bits e o vincula a sessao do usuario. */
    public String gerarEArmazenar(String sessionId) {
        byte[] bytes = new byte[32]; // 256 bits de entropia
        RNG.nextBytes(bytes);
        String state = Base64.getUrlEncoder().withoutPadding().encodeToString(bytes);
        statePorSessao.put(sessionId, state);
        return state;
    }

    /**
     * Valida o `state` recebido no redirect contra o que foi gravado para
     * aquela sessao. Comparacao em tempo constante via MessageDigest.isEqual
     * — evita que o tempo de resposta vaze quantos bytes iniciais batem.
     */
    public boolean validar(String sessionId, String stateRecebido) {
        String stateEsperado = statePorSessao.remove(sessionId); // uso unico
        if (stateEsperado == null || stateRecebido == null) {
            return false;
        }
        byte[] a = stateEsperado.getBytes(java.nio.charset.StandardCharsets.UTF_8);
        byte[] b = stateRecebido.getBytes(java.nio.charset.StandardCharsets.UTF_8);
        // MessageDigest.isEqual ja e' implementado para nao dar "early exit"
        // no primeiro byte diferente, ao contrario de Arrays.equals/String.equals.
        return MessageDigest.isEqual(a, b);
    }
}
```

### Exemplo 2 — comparação exata (não por prefixo) de `redirect_uri`

Mitiga a ameaça de open redirector via validação flexível (§5.3). O erro mais comum em implementações reais é usar `startsWith` ou `contains` "para suportar múltiplos subcaminhos" — o exemplo abaixo mostra a forma correta (comparação de URI normalizada e exata contra uma lista de valores registrados) e comenta explicitamente por que a alternativa "conveniente" é perigosa.

```java
import java.net.URI;
import java.util.Set;

public final class RedirectUriValidator {

    private final Set<String> uriRegistradas; // valores EXATOS cadastrados pelo client

    public RedirectUriValidator(Set<String> uriRegistradas) {
        this.uriRegistradas = Set.copyOf(uriRegistradas);
    }

    /**
     * RFC 6819 §5.3 / RFC 9700: comparacao deve ser exata (string a string,
     * apos normalizacao minima), nunca por prefixo ou substring.
     *
     * Exemplo do que NAO fazer (comentado de proposito, para servir de
     * contraste didatico):
     *
     *   // ERRADO: abre brecha para "https://client.com/callback.evil.com/"
     *   // return redirectUri.startsWith(uriRegistrada);
     *
     *   // ERRADO: abre brecha para "https://client.com/callback/../../evil"
     *   // return redirectUri.contains(uriRegistrada);
     */
    public boolean ehValido(String redirectUriRecebida) {
        URI normalizada = normalizar(redirectUriRecebida);
        if (normalizada == null) {
            return false;
        }
        // Comparacao EXATA da forma normalizada contra o conjunto registrado.
        return uriRegistradas.contains(normalizada.toString());
    }

    private URI normalizar(String bruta) {
        try {
            // URI.normalize() resolve "." e ".." no path, mas NAO substitui
            // a necessidade de comparacao exata depois — normalizar apenas
            // evita falsos negativos triviais (ex: barra final redundante
            // deve ser tratada como parte do cadastro, nao "normalizada para
            // sumir", ou a validacao fica frouxa de novo).
            return URI.create(bruta).normalize();
        } catch (IllegalArgumentException e) {
            return null; // URI malformada: rejeita, nunca tenta "consertar".
        }
    }
}
```

### Exemplo 3 — authorization code de uso único (detecção de reuso)

Mitiga a ameaça descrita em §5.5. A ideia central: remover o code do armazenamento **atomicamente** no momento da primeira troca bem-sucedida, e tratar uma segunda apresentação como evento de segurança (não apenas como "código inválido" — o AS deveria, numa implementação real, revogar retroativamente qualquer token já emitido a partir daquele code).

```java
import java.util.concurrent.ConcurrentHashMap;
import java.util.Map;

public final class AuthorizationCodeStore {

    private record CodeInfo(String clientId, String username, long expiraEm) {}

    private final Map<String, CodeInfo> codigos = new ConcurrentHashMap<>();

    public void emitir(String code, String clientId, String username) {
        codigos.put(code, new CodeInfo(clientId, username,
                System.currentTimeMillis() + 60_000)); // 60s de vida, uso unico
    }

    /**
     * Troca o code por informacoes de sessao — remove atomicamente do mapa.
     * `Map.remove` retorna null se a chave ja nao existir, o que cobre tanto
     * "nunca existiu" quanto "ja foi trocado antes" com uma unica chamada
     * atomica (sem race condition entre "checar" e "remover").
     */
    public CodeInfo trocarPorTokenOuNull(String code) {
        CodeInfo info = codigos.remove(code);
        if (info == null) {
            // RFC 6819 §5.5: reuso ou code inexistente. Numa implementacao
            // real, aqui e' o gatilho para revogar em cascata qualquer token
            // ja emitido a partir deste code, pois a segunda apresentacao
            // e' sinal de possivel comprometimento.
            registrarEventoSuspeito(code);
            return null;
        }
        if (info.expiraEm() < System.currentTimeMillis()) {
            return null; // expirado: tambem rejeita, sem distinguir o motivo ao chamador
        }
        return info;
    }

    private void registrarEventoSuspeito(String code) {
        // Em producao: alerta de seguranca, nao apenas um log de debug.
        System.err.println("ALERTA: tentativa de reuso de authorization code detectada");
    }
}
```

### Exemplo 4 — cabeçalho anti-clickjacking na tela de consentimento

Mitiga a ameaça descrita em §5.7, usando apenas `com.sun.net.httpserver.HttpServer` (embutido no JDK, sem dependência externa) para ilustrar onde o cabeçalho deveria ser adicionado.

```java
import com.sun.net.httpserver.HttpExchange;
import com.sun.net.httpserver.HttpHandler;

public final class TelaConsentimentoHandler implements HttpHandler {

    @Override
    public void handle(HttpExchange exchange) throws java.io.IOException {
        // RFC 6819 §5.7: impede que esta tela seja embutida em <iframe> de
        // um site atacante para induzir "clickjacking" sobre o botao Autorizar.
        exchange.getResponseHeaders().add("X-Frame-Options", "DENY");
        exchange.getResponseHeaders().add(
                "Content-Security-Policy", "frame-ancestors 'none'");

        String html = "<html><body><h1>Autorizar acesso?</h1>"
                + "<form method=\"POST\"><button>Autorizar</button></form>"
                + "</body></html>";
        byte[] corpo = html.getBytes(java.nio.charset.StandardCharsets.UTF_8);
        exchange.getResponseHeaders().add("Content-Type", "text/html; charset=utf-8");
        exchange.sendResponseHeaders(200, corpo.length);
        try (var os = exchange.getResponseBody()) {
            os.write(corpo);
        }
    }
}
```
