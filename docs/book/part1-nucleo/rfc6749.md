# RFC 6749 — The OAuth 2.0 Authorization Framework

## 1. Contexto e motivação

### 1.1 O anti-padrão de senha

Antes do OAuth existir como especificação formal, a forma corriqueira de um aplicativo de terceiros acessar dados de um usuário em outro serviço era o que a comunidade batizou de **anti-padrão de senha** (*password anti-pattern*): o usuário simplesmente entregava sua senha do serviço-alvo (webmail, rede social, banco) diretamente ao aplicativo terceiro, que a armazenava e a usava para se autenticar "como se fosse" o usuário.

Esse modelo tem uma lista longa de problemas estruturais, não incidentais:

- **Acesso irrestrito.** A senha não carrega noção de escopo. Um app que só precisa ler a lista de contatos ganha, de fato, os mesmos poderes de qualquer login legítimo do usuário — trocar a senha, ler mensagens privadas, excluir a conta.
- **Impossível revogar seletivamente.** Se o usuário quiser cortar o acesso de um app específico sem afetar os demais, a única ferramenta disponível é trocar a própria senha — o que derruba *todos* os apps de uma vez, inclusive os que o usuário queria manter.
- **A senha passa a existir em outro lugar.** Cada app terceiro que guarda a senha do usuário é mais um ponto de vazamento possível. Um incidente de segurança nesse app terceiro compromete diretamente a conta original — não apenas os dados que o app deveria acessar.
- **Nenhuma trilha de auditoria útil.** Do ponto de vista do serviço original, uma requisição autenticada com a senha do usuário é indistinguível de uma requisição feita pelo próprio usuário logado no navegador. Não há como saber "isso veio do app X" nem revogar apenas aquele agente.
- **Incentiva o usuário a normalizar o phishing.** Se a prática legítima é "digite sua senha do Google neste app de terceiros", o usuário perde a capacidade de distinguir isso de um golpe de phishing — o próprio ecossistema erode a defesa que deveria ensinar.

### 1.2 A ideia central: autorização delegada

O OAuth 2.0 resolve esse problema trocando o modelo mental de "autenticação emprestada" por **autorização delegada**: o resource owner (o usuário) concede ao client (o app terceiro) um **token de acesso** — uma credencial derivada, de escopo e validade limitados, emitida por um terceiro de confiança (o authorization server) — sem que o client jamais veja ou manipule a senha original do usuário.

Três propriedades decorrem diretamente dessa mudança de modelo:

1. **Escopo explícito.** O token carrega (ou está associado no AS a) um conjunto de permissões que o resource owner aprovou explicitamente — "ler perfil", "listar repositórios", "iniciar uma transferência até R$ 500", etc. O client nunca herda mais poder do que o concedido.
2. **Revogação granular.** O resource owner pode revogar o acesso de um client específico (via painel do AS, por exemplo "Aplicativos conectados à sua conta") sem afetar a senha da conta nem os outros clients autorizados.
3. **Auditoria e atribuição.** O AS sabe, a cada token emitido, para qual client, com qual escopo, e por vezes até em nome de qual resource owner ele foi emitido — permitindo logs, métricas e políticas de segurança por client.

Vale enfatizar que o OAuth 2.0 é um framework de **autorização**, não de **autenticação**. Ele resolve "o client X pode acessar o recurso Y em nome do usuário Z, com este escopo?" — não "quem é o usuário Z?". Confundir os dois é um erro histórico recorrente (por exemplo, usar um access token como prova de identidade do usuário no client) que a própria comunidade precisou corrigir mais tarde com uma camada adicional — o OpenID Connect —, que fica deliberadamente fora do escopo deste livro (que trata apenas de OAuth puro).

### 1.3 De OAuth 1.0 para OAuth 2.0 — o que mudou e por quê

A RFC 6749 substitui formalmente a especificação anterior, RFC 5849 (OAuth 1.0), e a mudança mais visível é filosófica: o OAuth 1.0 exigia que **cada requisição** ao resource server fosse assinada criptograficamente (HMAC-SHA1 sobre uma string canônica construída a partir do método HTTP, URL e parâmetros, com um `client_secret` e um `token_secret` como chaves). Isso tinha uma vantagem real — a requisição carregava sua própria prova de integridade e de posse, mesmo trafegando sobre HTTP puro — mas um custo de implementação alto: bibliotecas cliente precisavam replicar exatamente o algoritmo de canonicalização (uma fonte enorme de bugs de interoperabilidade), e cada linguagem/plataforma precisava de uma biblioteca de assinatura dedicada.

O OAuth 2.0 troca essa complexidade por uma aposta diferente: **TLS obrigatório** em todo endpoint que transporta credenciais ou tokens, combinado com **bearer tokens** simples (definidos separadamente na RFC 6750) — uma string opaca que, uma vez capturada, dá acesso a quem a possuir, sem assinatura por requisição. Essa troca é deliberada e está documentada na própria RFC 6749 (§ Introduction): simplicidade de implementação em troca de depender inteiramente do transporte (TLS) para proteção contra interceptação, e de tempo de vida curto para conter o dano de uma eventual captura.

Essa decisão de design é a raiz de praticamente toda a evolução posterior do ecossistema OAuth. A ausência de "prova de posse por requisição" é exatamente o que os mecanismos de *sender-constraining* — RFC 8705 (mTLS) e RFC 9449 (DPoP), tratados mais adiante neste livro — foram desenhados para reintroduzir, de forma mais moderna, para os cenários que exigem essa garantia extra.

### 1.4 Um framework, não um protocolo único

Um ponto de leitura importante, e que costuma gerar confusão em quem chega do mundo mais rígido de protocolos como Kerberos ou SAML: a RFC 6749 se autodenomina explicitamente um **framework** de autorização, não um protocolo fechado. Ela define uma família de fluxos (*grant types*) para cenários distintos, deixa portas abertas para extensão (novos `grant_type`, novos `response_type`, parâmetros adicionais), e delega deliberadamente uma quantidade grande de decisões de segurança concretas para especificações companheiras — a RFC 6819 (Threat Model, contemporânea) e, mais de uma década depois, a RFC 9700 (Best Current Practice), que revisita e restringe boa parte do que a 6749 deixou como "opção válida".

Essa característica de "esqueleto extensível" é ao mesmo tempo a força do OAuth 2.0 (permitiu nascer PKCE, DPoP, Resource Indicators, RAR, todos como extensões aditivas sem quebrar a RFC original) e a fonte de boa parte das implementações inseguras encontradas em produção — porque a RFC, isolada, não impõe as mitigações que hoje são consideradas obrigatórias.

## 2. Terminologia e papéis

### 2.1 Os quatro papéis

- **Resource Owner** — a entidade capaz de conceder acesso a um recurso protegido. Tipicamente uma pessoa física (o usuário final), mas pode ser uma entidade não-humana em cenários de automação (por exemplo, um sistema que autoriza outro sistema a agir por ele — embora aí frequentemente se recorra ao Client Credentials Grant, onde não há resource owner distinto do client, como veremos).
- **Client** — a aplicação que solicita acesso a um recurso protegido em nome do resource owner (ou, no caso do Client Credentials Grant, em nome de si mesma). É importante notar que "client" na terminologia OAuth é um papel, não uma camada de arquitetura: o mesmo processo pode acumular, em fluxos diferentes, o papel de client em uma integração e de resource server em outra.
- **Authorization Server (AS)** — o servidor que emite access tokens ao client após autenticar com sucesso o resource owner e obter sua autorização. O AS é o único componente que precisa conhecer a credencial primária do resource owner (senha, segundo fator, etc.).
- **Resource Server (RS)** — o servidor que hospeda os recursos protegidos e é capaz de aceitar e validar access tokens para servir requisições. Note que a RFC 6749 não especifica *como* o RS valida o token contra o AS (introspecção via RFC 7662, JWT autocontido via RFC 9068, um cache local, etc.) — isso fica, propositalmente, fora do escopo desta RFC.

Em implementações pequenas (como o próprio laboratório deste projeto), AS e RS podem ser processos totalmente separados que compartilham apenas um armazenamento (Redis, no caso do lab) como fonte de verdade sobre tokens válidos. Em arquiteturas maiores, é comum o AS ser um produto dedicado (Keycloak, Auth0, Okta, um IdP corporativo) e o RS ser cada microsserviço de negócio que aceita tokens emitidos por ele — validando-os via introspecção remota ou localmente, se forem JWTs auto-verificáveis.

### 2.2 Tipos de client: confidential vs. public

Essa é provavelmente a dimensão mais consequente da terminologia da RFC 6749, porque determina diretamente qual grant type é apropriado e qual superfície de ataque o client apresenta:

- **Confidential client** — capaz de manter um `client_secret` (ou outra credencial de autenticação) em segredo, de forma persistente e fora do alcance de um atacante que só tenha acesso ao dispositivo/rede do resource owner. O exemplo canônico é um servidor backend tradicional: o `client_secret` fica em uma variável de ambiente ou vault, nunca chega ao navegador.
- **Public client** — não tem como manter nenhum segredo de forma confiável, porque o binário/bundle do client é distribuído para o próprio dispositivo do resource owner (e, portanto, pode ser decompilado, inspecionado com um proxy, ou lido em texto claro). Exemplos: uma SPA rodando inteiramente no navegador, um app mobile nativo, um script de linha de comando (CLI) instalado localmente.

A RFC 6749 já reconhece essa distinção no corpo do texto (§2.1), mas é importante entender a implicação prática: **um `client_secret` "embutido" em um app público não é um segredo** — é, na melhor das hipóteses, um identificador ofuscado. Historicamente, muitas SPAs e apps mobile "confidenciais na configuração, públicos na realidade" embutiram client secrets em JavaScript ou em APKs, dando a falsa sensação de terem um client autenticado. A RFC 9700 (item 6 deste livro) formaliza essa lição e recomenda tratar qualquer client sem armazenamento seguro de segredo como público, período — com PKCE como mitigação obrigatória (e não apenas recomendada) do Authorization Code Grant nesse caso.

### 2.3 Perfis de client

A RFC 6749 (§2.1) também descreve três perfis de implantação, que na prática mapeiam para a distinção confidential/public acima:

- **Web application** — roda inteiramente em um servidor web; o resource owner acessa via navegador, mas o client_secret e os tokens ficam no backend. Confidential por natureza.
- **User-agent-based application** — o código do client é baixado para dentro de um user-agent (navegador) e roda lá (o caso clássico de SPA). Public por natureza, já que todo o código e estado é visível/manipulável no dispositivo do usuário.
- **Native application** — instalado e executado diretamente no dispositivo do resource owner (app mobile, desktop). Também public, pelo mesmo motivo — mesmo que o binário seja "compilado", engenharia reversa e interceptação de tráfego local (proxy no próprio device) tornam qualquer segredo embutido inseguro.

### 2.4 Client identifier e client secret

O `client_id` é um identificador único do client perante o AS — não é secreto (pode aparecer em URLs, no código-fonte de uma SPA, em logs) e serve apenas para o AS saber "qual configuração de client é essa" (redirect_uri registrada, grants permitidos, escopos permitidos). O `client_secret`, quando existe, é a credencial de autenticação do client junto ao AS — só faz sentido para clients confidenciais, e a RFC 6749 (§2.3.1) recomenda que ele seja transmitido preferencialmente via HTTP Basic Authentication no token endpoint (o que o laboratório deste projeto implementa, além de aceitar as credenciais no corpo como alternativa — mais adiante detalhado na seção 4).

## 3. Fluxos (Grant Types)

A RFC 6749 define quatro grant types nativos, mais um mecanismo de extensão para grants customizados (§4.5, via o parâmetro `grant_type` com um valor de URI absoluta definido por outra especificação — é assim, por exemplo, que a RFC 7523/7521 define grants baseados em JWT/SAML assertions, e como a própria RFC 8693 Token Exchange se encaixa no framework).

**Nota de atualização, antecipando o item 7 deste capítulo**: a RFC 9700 (2025) deprecia formalmente o Implicit Grant e o Resource Owner Password Credentials Grant. Ambos são descritos abaixo por completude histórica e porque ainda aparecem em sistemas legados que um arquiteto pode encontrar em produção — mas não devem ser adotados em projetos novos.

### 3.1 Authorization Code Grant (§4.1) — o fluxo central

Este é o fluxo mais importante do OAuth 2.0, desenhado especificamente para clients confidenciais (e, com a adição posterior de PKCE — RFC 7636 —, também seguro para clients públicos). A sequência completa:

```
(1) Client → User-Agent:  redireciona o navegador para
      GET /authorize?response_type=code&client_id=...&redirect_uri=...&scope=...&state=...

(2) AS ↔ User-Agent:      autentica o resource owner (login) e apresenta
                           a tela de consentimento (quais escopos o client está pedindo)

(3) AS → User-Agent → Client:  redireciona de volta para
      redirect_uri?code=AUTH_CODE&state=...

(4) Client → AS (back-channel):  POST /token
      grant_type=authorization_code&code=AUTH_CODE&redirect_uri=...&client_id=...&client_secret=...

(5) AS → Client:           { access_token, token_type, expires_in, refresh_token?, scope }
```

A propriedade de segurança central deste desenho é que **o access token nunca passa pelo user-agent/navegador** — apenas o `code`, um valor intermediário de vida curtíssima (a RFC recomenda no máximo 10 minutos; o laboratório deste projeto usa 60 segundos) e de **uso único** (o AS deve invalidá-lo assim que trocado por tokens, mesmo que a troca tenha falhado — porque um code que aparece duas vezes é evidência forte de replay ou vazamento). Como o `code` sozinho não vale nada sem o `client_secret` correspondente (no passo 4), mesmo que um atacante o intercepte no passo 3 (por exemplo, através de um redirect_uri mal validado, um app de terceiros malicioso no mesmo dispositivo, ou logs de navegação), ele não consegue completar a troca — a menos que também tenha comprometido o client confidencial, o que é um cenário de ameaça bem mais severo.

É exatamente essa dependência de "o atacante não tem o `client_secret`" que quebra para clients públicos — e é o motivo de existir o PKCE (RFC 7636, próximo capítulo deste livro): ele substitui a necessidade de um segredo estático de longo prazo por um segredo efêmero gerado a cada tentativa de autorização.

Um detalhe frequentemente ignorado: o `redirect_uri` deve ser enviado tanto no passo 1 (authorization request) quanto no passo 4 (token request), e o AS deve conferir que os dois **coincidem exatamente**. Essa checagem cruzada é uma segunda linha de defesa contra a interceptação do code — mesmo que o atacante consiga capturar o `code` retornado a um `redirect_uri` diferente do originalmente registrado, a troca no passo 4 falha se ele não souber reproduzir o mesmo `redirect_uri` usado na autorização.

### 3.2 Implicit Grant (§4.2) — *deprecado pela RFC 9700*

O Implicit Grant existia para resolver um problema de uma época específica: SPAs rodando inteiramente no navegador não tinham como executar o passo 4 do Authorization Code Grant sem expor o `client_secret` em JavaScript (visível a qualquer um que abrisse o DevTools). A "solução" foi eliminar essa troca: o AS devolvia o `access_token` **diretamente no fragmento da URL de redirect** (a parte depois de `#`, que por design nunca é enviada ao servidor em uma requisição HTTP subsequente, permanecendo só no navegador):

```
GET /authorize?response_type=token&client_id=...&redirect_uri=...&scope=...&state=...
→ redirect_uri#access_token=...&token_type=Bearer&expires_in=3600&state=...
```

Os problemas deste desenho, hoje bem documentados (RFC 6819 já os antecipava; RFC 9700 os usa como justificativa formal de depreciação):

- O access token trafega pela **URL do navegador**, ficando exposto a: histórico de navegação, extensões de browser, qualquer script de terceiros rodando na mesma página, e ao header `Referer` se a página seguinte não tomar cuidado.
- Não há passo de troca back-channel, então **não há autenticação do client** nesse fluxo — qualquer app que conheça o `client_id` (não secreto, por definição) pode iniciar o fluxo.
- Como o token vem embutido na URL redirecionada por um user-agent, é mais fácil de um atacante induzir o navegador a entregar o token a um `redirect_uri` diferente do esperado, se a validação do AS for frouxa.
- Não há emissão de refresh_token nesse fluxo original (o navegador precisaria repetir a interação completa do usuário quando o token expirasse) — o que na prática levava implementações a usar tokens de vida mais longa, piorando o impacto de um vazamento.

A solução moderna e definitiva é Authorization Code + PKCE, mesmo em SPAs: o navegador não precisa mais de um `client_secret` porque o PKCE usa um segredo efêmero gerado por sessão de autorização (o `code_verifier`), eliminando a razão de existir do Implicit Grant.

### 3.3 Resource Owner Password Credentials — ROPC (§4.3) — *deprecado pela RFC 9700*

Neste fluxo, o resource owner entrega usuário e senha **diretamente ao client**, que os envia ao token endpoint em troca de tokens:

```
Client → AS: POST /token
  grant_type=password&username=...&password=...&client_id=...&client_secret=...&scope=...
```

O problema é evidente e literal: este é exatamente o anti-padrão de senha descrito na seção 1.1, apenas formalizado dentro do OAuth. O client vê e manipula a senha primária do usuário — reintroduzindo todos os riscos que o framework nasceu para eliminar. A própria RFC 6749 já o cercava de ressalvas ("SHOULD only be used when there is a high degree of trust between the resource owner and the client"), reservando-o essencialmente para clients de primeira parte (first-party) — por exemplo, o próprio app oficial de um banco autenticando o usuário em seu backend.

Mesmo nesse cenário restrito, o ROPC tem uma limitação estrutural que o BCP posterior aponta: ele é incompatível por design com qualquer mecanismo de autenticação que não seja usuário/senha simples — MFA interativo, biometria, WebAuthn, redirecionamento a um IdP corporativo — porque não há passo de redirecionamento ao AS onde essas interações poderiam acontecer. Isso, sozinho, já o tornava inadequado à medida que MFA se tornou padrão de mercado, independentemente da questão de confiança.

### 3.4 Client Credentials Grant (§4.4)

Este é o único grant nativo sem resource owner distinto: o próprio client se autentica com suas credenciais para obter um token que representa a si mesmo, não um usuário. É o padrão para comunicação **machine-to-machine** (M2M) — por exemplo, um serviço de backend que chama uma API de outro serviço, um job em batch, uma integração server-to-server:

```
Client → AS: POST /token
  grant_type=client_credentials&client_id=...&client_secret=...&scope=...

AS → Client: { access_token, token_type, expires_in, scope }
```

Note na RFC (§4.4.3) uma regra fácil de esquecer: um `refresh_token` **não deve** ser emitido neste grant. A justificativa é direta — como não há resource owner nem sessão de usuário para "renovar", o client sempre pode simplesmente chamar o token endpoint novamente com as mesmas credenciais quando precisar de um novo access token. Emitir um refresh_token aqui só adicionaria um segredo de longa duração extra para proteger, sem benefício real. O laboratório deste projeto respeita essa regra (`withRefresh: false` no grant `client_credentials`, ver seção final deste capítulo).

Client Credentials é, por natureza, restrito a clients confidenciais — um client público não tem como manter um `client_secret`, e portanto não tem uma identidade própria e verificável a apresentar neste grant. Em arquiteturas mais modernas (ver RFC 9700 e as extensões do item 6 deste livro), esse grant também é o alvo natural de reforço via mTLS (RFC 8705) para autenticação de client baseada em certificado, em vez de segredo compartilhado.

### 3.5 Refresh Token (§6) — mecanismo transversal

O refresh token não é um grant type por si só — é um mecanismo que atravessa os grants que envolvem resource owner (Authorization Code e, historicamente, ROPC): o AS pode, opcionalmente, emitir um `refresh_token` junto com o `access_token`. Esse refresh_token é usado depois para obter novos access tokens **sem repetir a interação com o resource owner** (sem novo login, sem nova tela de consentimento):

```
Client → AS: POST /token
  grant_type=refresh_token&refresh_token=...&client_id=...&client_secret=...
```

**Rotacionar ou manter o refresh token na renovação?** A própria RFC 6749 (§6) já trata disso: é facultativo do AS. Se a resposta da renovação incluir um novo `refresh_token`, o client deve descartar o antigo e passar a usar apenas o novo a partir dali; se o campo vier ausente na resposta, o client mantém o refresh_token que já tinha — a ausência do campo já é, por si, o sinal de "nada mudou, continue usando o mesmo". Isso é importante porque um client mal implementado que *sempre* espera um novo refresh_token e descarta o campo quando ausente perderia a capacidade de se renovar novamente.

A RFC 9700, mais de uma década depois, aperta essa recomendação: rotação a cada uso passa a ser fortemente recomendada (especialmente para clients públicos), combinada com **detecção de reuso** — se um refresh_token já rotacionado (portanto inválido) for apresentado novamente, isso é evidência de que ele foi roubado e clonado, e o AS deveria revogar toda a família de tokens derivada dele, não apenas rejeitar a tentativa isolada. O laboratório deste projeto já adota rotação incondicional a cada uso (o handler do grant `refresh_token` sempre deleta o token antigo do Redis e emite um novo — ver seção final).

Também vale registrar o escopo do refresh_token na renovação: a RFC 6749 (§6) permite que o client solicite um `scope` mais restrito do que o originalmente concedido (nunca mais amplo) — um mecanismo de "downscoping" que muitas implementações client sequer exploram, mas que é útil para aderir ao princípio de menor privilégio quando o client sabe, no momento da renovação, que só precisará de um subconjunto das permissões originais.

### 3.6 Extensibilidade: grants customizados

A RFC 6749 (§4.5 e §8.3) reserva formalmente o espaço de valores de `grant_type` para extensão: qualquer valor que seja uma URI absoluta é tratado como um grant customizado definido por outra especificação, permitindo que o ecossistema cresça sem modificar o núcleo. Exemplos notáveis que um arquiteto financeiro encontra em produção: RFC 7523 (JWT Bearer Grant, `urn:ietf:params:oauth:grant-type:jwt-bearer` — comum em integrações de assertions SAML/JWT emitidas por um IdP corporativo) e RFC 8693 (Token Exchange, `urn:ietf:params:oauth:grant-type:token-exchange` — usado para troca de tokens entre domínios de confiança, delegação e "on-behalf-of" em arquiteturas de microsserviços). Ambas ficam fora do escopo direto deste livro, mas é útil saber que o mecanismo de extensão existe desde a RFC original.

## 4. Parâmetros e endpoints normativos

### 4.1 Authorization endpoint (§3.1)

É o endpoint que interage com o resource owner através do user-agent (tipicamente um navegador). É aqui, e somente aqui, que credenciais primárias do usuário (senha, segundo fator) devem ser inseridas — nunca no client. A RFC exige que este endpoint suporte o método HTTP GET (e pode, opcionalmente, suportar POST) e que os parâmetros sejam serializados na query string, mesmo que a implementação renderize a interação subsequente (tela de login, tela de consentimento) via POST de formulário — que é exatamente como o laboratório deste projeto implementa (`GET /authorize` monta a tela de login; `POST /authorize` processa a decisão do usuário).

### 4.2 Token endpoint (§3.2)

É o canal back-channel (client-para-AS, direto, sem o navegador no meio) usado para trocar um `code`, `refresh_token` ou credenciais de client por tokens. A RFC exige TLS e o método HTTP POST, com o corpo serializado como `application/x-www-form-urlencoded` (§4.1.3, §4.3.2, §4.4.2, §6). É neste endpoint que o client se autentica, quando aplicável — a RFC 6749 (§2.3.1) recomenda HTTP Basic Authentication (`client_id` como username, `client_secret` como password, ambos devidamente `percent-encoded` antes do Base64) como método preferencial, mas também permite `client_id`/`client_secret` como parâmetros do corpo, para clients que não conseguem manipular o header `Authorization`.

### 4.3 Redirection endpoint (§3.1.2)

É a URI no próprio client para onde o AS devolve o resultado da autorização (o `code`, no fluxo padrão, ou um erro). Deve ser **registrada previamente** junto ao AS como parte do cadastro do client, e a RFC exige comparação **exata** (não apenas prefixo ou domínio) entre o `redirect_uri` enviado na requisição e o valor registrado — esse ponto é retomado com mais profundidade na seção de segurança (5.1) porque é uma fonte histórica recorrente de vulnerabilidades de open redirect.

### 4.4 Parâmetros-chave da authorization request (§4.1.1)

| Parâmetro | Obrigatório? | Descrição |
|---|---|---|
| `response_type` | Sim | `code` (Authorization Code Grant) ou `token` (Implicit, deprecado) |
| `client_id` | Sim | Identificador público do client, registrado no AS |
| `redirect_uri` | Condicional | Obrigatório se o client tiver múltiplos redirect_uris registrados; recomendado sempre enviar |
| `scope` | Opcional | Lista de escopos separados por espaço; se omitido, o AS decide o padrão (frequentemente o escopo completo registrado, ou nenhum) |
| `state` | Recomendado (na prática, obrigatório) | Valor opaco gerado pelo client, ecoado sem alteração pelo AS no retorno — mecanismo anti-CSRF (ver 5.2) |

### 4.5 Parâmetros-chave da token response (§4.1.4, §5.1)

| Parâmetro | Obrigatório? | Descrição |
|---|---|---|
| `access_token` | Sim | O token propriamente dito |
| `token_type` | Sim | Tipicamente `Bearer` (RFC 6750) |
| `expires_in` | Recomendado | Tempo de vida em segundos, a partir do momento de emissão |
| `refresh_token` | Opcional | Presente conforme política do AS e do grant (ver 3.5) |
| `scope` | Condicional | Obrigatório apenas se o escopo efetivamente concedido difere do solicitado — mas é boa prática sempre incluir, para o client não ter que assumir |

A resposta do token endpoint deve incluir os headers `Cache-Control: no-store` e `Pragma: no-cache` (§5.1) — porque o corpo contém segredos (tokens), e caches HTTP intermediários (proxies corporativos, CDNs) não devem persisti-los.

### 4.6 Erros padronizados (§4.1.2.1, §5.2)

`invalid_request`, `invalid_client`, `invalid_grant`, `unauthorized_client`, `unsupported_grant_type`, `unsupported_response_type`, `invalid_scope`, `access_denied`, `server_error`, `temporarily_unavailable` — devolvidos como parâmetros de **redirect** (erros do authorization endpoint, exceto quando o próprio `redirect_uri` é o problema — nesse caso, o AS deve exibir a mensagem diretamente ao usuário, nunca redirecionar a um destino não verificado) ou como **corpo JSON** com status HTTP apropriado (erros do token endpoint, normalmente `400` ou `401`).

## 5. Segurança já tratada na própria RFC 6749

### 5.1 Open redirector

O `redirect_uri` é, por definição, uma URL para onde o AS envia dados sensíveis (o `code`, no mínimo) de forma automatizada, disparada por uma resposta HTTP de redirecionamento. Se o AS aceitasse qualquer `redirect_uri` fornecido na requisição (ou validasse apenas por prefixo/domínio), um atacante poderia registrar um client legítimo, mas fornecer em tempo de requisição um `redirect_uri` apontando para um domínio próprio — o AS então enviaria o `code` de qualquer resource owner que autorizasse a requisição diretamente ao atacante. Pior ainda: o próprio AS se tornaria um "open redirector" reaproveitável para phishing genérico, mesmo sem relação alguma com OAuth.

A mitigação normativa (§3.1.2.3) é comparação **exata** contra a lista de `redirect_uri`s pré-registrados no cadastro do client — não prefixo, não apenas o domínio, string completa idêntica (incluindo path e query string, se houver). O laboratório deste projeto implementa exatamente essa checagem: `client.redirect_uri !== redirect_uri` rejeita qualquer valor que não seja idêntico byte a byte ao registrado.

### 5.2 CSRF no callback: o parâmetro `state`

Sem alguma proteção, um atacante poderia iniciar o próprio fluxo de autorização (obtendo um `code` seu, legítimo, para sua própria conta) e induzir a vítima a completar o passo de troca desse code no client da vítima — efetivamente "plantando" a própria conta do atacante na sessão da vítima (um ataque de CSRF na etapa de callback, às vezes chamado de "login CSRF" ou "session fixation via OAuth"). O parâmetro `state` mitiga isso: o client gera um valor opaco e imprevisível antes do passo 1, guarda-o associado à sessão local do navegador (cookie de sessão, por exemplo), e confere que o valor devolvido no passo 3 é **exatamente** o mesmo antes de prosseguir com a troca do code. Se um atacante tentar reaproveitar seu próprio `code`/callback contra a sessão da vítima, o `state` que ele apresenta não vai bater com o que está associado à sessão dela.

### 5.3 Interceptação do authorization code

Mesmo com `redirect_uri` e `state` corretos, o `code` ainda trafega por um canal menos controlado que o back-channel (o navegador, possivelmente por redes não confiáveis, apps concorrentes no mesmo dispositivo em plataformas mobile mais antigas que não isolam esquemas de URL customizados). A RFC 6749 mitiga isso com vida útil curtíssima e uso único (o AS invalida o code assim que ele é trocado — ou, mais rigorosamente, assim que uma tentativa de troca acontece, válida ou não). A mitigação mais robusta e específica para esse vetor — especialmente relevante em apps nativos que dependem de custom URI schemes para o redirect — veio depois, com a RFC 7636 (PKCE), tratada no próximo capítulo deste livro.

### 5.4 TLS obrigatório

Todo endpoint que transporta credenciais (`client_secret`, senha do resource owner) ou tokens (`code`, `access_token`, `refresh_token`) deve operar sobre TLS. Isso vale tanto para o authorization endpoint (onde a senha do usuário é digitada) quanto para o token endpoint (onde o `client_secret` e os tokens trafegam). Sem TLS, tanto o modelo bearer (RFC 6750) quanto a autenticação básica de client ficam completamente expostos a qualquer um capaz de observar a rede.

> **Nota de laboratório**: conforme já registrado no capítulo anterior e reiterado aqui, os labs práticos deste projeto rodam deliberadamente em HTTP puro (`http://localhost`), simplificação mantida até o capítulo da RFC 8705 (mTLS), onde TLS real passa a ser o próprio mecanismo em estudo. Até lá, o foco pedagógico é a mecânica de grants e tokens, não a camada de transporte.

### 5.5 Autenticação de client no token endpoint

A RFC 6749 (§2.3) deixa o método de autenticação de client parcialmente aberto, mas recomenda HTTP Basic (client_id/client_secret no header `Authorization`) como preferencial, permitindo alternativamente os mesmos valores no corpo da requisição. Um detalhe de nuance que aparece na prática (e que o laboratório deste projeto trata corretamente): quando a autenticação falha e foi tentada via Basic Auth, a resposta de erro `401` deve incluir o header `WWW-Authenticate: Basic realm="..."` — sinalizando ao client qual esquema de autenticação era esperado, consistente com a semântica geral de HTTP Authentication (RFC 7235).

### 5.6 O que a RFC 6749 deliberadamente deixa em aberto

A RFC 6749 é, por design, um framework "esqueleto": ela documenta as opções e os mecanismos básicos, mas deixa deliberadamente de fora recomendações mais assertivas sobre, por exemplo, obrigatoriedade de PKCE, rotação de refresh tokens, sender-constraining de access tokens, ou validação de escopo em runtime. Essas lacunas foram primeiro catalogadas pela RFC 6819 (Threat Model, contemporânea à 6749) e, mais de uma década depois, endereçadas de forma prescritiva pela RFC 9700 (Best Current Practice) — que efetivamente promove várias "opções" da 6749 a "obrigações" à luz de uma década de exploração em produção.

## 6. Relação com outras RFCs

- **RFC 6750** define como o `access_token` do tipo Bearer, obtido através dos mecanismos descritos nesta RFC, é efetivamente apresentado ao resource server — este documento (6749) só define como o token é *obtido*, nunca como é *usado*. É o assunto do próximo capítulo deste livro.
- **RFC 6819** (Threat Model) cataloga sistematicamente as ameaças específicas de cada grant type descrito aqui, servindo de base analítica para tudo que viria depois.
- **RFC 7636 (PKCE)** foi criada especificamente para eliminar a dependência de `client_secret` no Authorization Code Grant para clients públicos, mitigando a interceptação de code (seção 5.3) sem exigir um segredo estático.
- **RFC 7523 / RFC 8693** exploram o mecanismo de extensão de `grant_type` (seção 3.6) para assertions e token exchange, respectivamente.
- **RFC 8705 (mTLS)** e **RFC 9449 (DPoP)** reforçam tanto a autenticação de client (seção 5.5) quanto o token em si, amarrando-o criptograficamente a quem o solicitou.
- **RFC 8707 (Resource Indicators)** e **RFC 9396 (RAR)** refinam a granularidade do `scope`, respondendo à limitação de que escopos são apenas strings planas sem estrutura.
- **RFC 9700** revisita e restringe as escolhas desta RFC à luz de mais de uma década de exploração em produção — depreciando Implicit e ROPC, e tornando PKCE obrigatório universalmente.
- **OAuth 2.1** (draft, não uma RFC formal até o momento deste livro) efetivamente reescreve este documento incorporando essas correções como obrigatórias em vez de opcionais, consolidando o que a RFC 9700 recomenda em uma única especificação coesa.

## 7. O que mudou desde a publicação (2012)

- **Implicit e ROPC**: de "opções válidas para cenários específicos" para "não usar" (RFC 9700) — a experiência de produção mostrou que os riscos superavam os benefícios em praticamente todos os casos reais.
- **PKCE**: nasceu como mitigação "só para clients públicos" (RFC 7636, 2015) e se tornou "obrigatório para todos os clients, inclusive confidenciais" (RFC 9700, 2025) — defesa em profundidade contra interceptação de code mesmo quando o client tem um segredo.
- **`redirect_uri`**: de comparação flexível (permitida por alguns AS na prática, embora nunca formalmente recomendada) para **exact string match** obrigatório, sem ambiguidade.
- **Bearer tokens simples** (sem sender-constraining): considerados adequados em 2012, hoje vistos como piso mínimo insuficiente para cenários de alta sensibilidade (sistemas financeiros, dados de saúde) — ver RFC 8705 (mTLS) e RFC 9449 (DPoP), tratadas no item 6 deste livro.
- **Refresh token rotation**: de "facultativo, sem orientação forte" para "fortemente recomendado, com detecção de reuso" (RFC 9700).

## Exemplo em Java (JDK 21, sem frameworks)

Os exemplos a seguir usam exclusivamente a biblioteca padrão do JDK 21 — `java.net.http.HttpClient` para chamadas HTTP e um utilitário mínimo de JSON escrito à mão para este livro (sem Jackson, Gson, nem qualquer outra dependência externa). Este utilitário — `SimpleJson` — é definido aqui, no primeiro capítulo, e os capítulos seguintes deste livro apenas o referenciam, sem redefini-lo.

**Nota importante**: este é um parser deliberadamente ingênuo, feito só para fins didáticos deste livro. Ele não trata aninhamento, arrays, nem escaping completo de JSON. **Em código de produção, use sempre uma biblioteca JSON real** (Jackson, Gson, ou a que já for padrão no seu stack) — nunca um parser artesanal como este.

```java
// SimpleJson.java — utilitário mínimo para os exemplos deste livro (JDK puro, sem bibliotecas externas).
// Uso didático apenas: em produção, use uma biblioteca JSON real (ex: Jackson, Gson).
final class SimpleJson {
    private SimpleJson() {}

    static String object(Map<String, ?> fields) {
        StringBuilder sb = new StringBuilder("{");
        var it = fields.entrySet().iterator();
        while (it.hasNext()) {
            var e = it.next();
            sb.append('"').append(e.getKey()).append("\":");
            Object v = e.getValue();
            if (v instanceof Number || v instanceof Boolean) sb.append(v);
            else sb.append('"').append(String.valueOf(v).replace("\"", "\\\"")).append('"');
            if (it.hasNext()) sb.append(',');
        }
        return sb.append('}').toString();
    }

    // Parser deliberadamente ingênuo: só serve para os exemplos deste livro,
    // assume JSON plano (sem aninhamento) com chaves/valores string, número ou booleano.
    static Map<String, String> parseFlat(String json) {
        Map<String, String> map = new LinkedHashMap<>();
        Matcher m = Pattern.compile("\"(.*?)\"\\s*:\\s*(\"(.*?)\"|[0-9.]+|true|false)").matcher(json);
        while (m.find()) {
            String key = m.group(1);
            String value = m.group(3) != null ? m.group(3) : m.group(2);
            map.put(key, value);
        }
        return map;
    }
}
```

### Exemplo 1 — Montando a URL da authorization request (§4.1.1)

O primeiro passo do Authorization Code Grant é redirecionar o navegador do resource owner para o authorization endpoint do AS, com os parâmetros corretamente codificados como query string. Note o uso de `URLEncoder` (obrigatório: `client_id`, `redirect_uri` e `scope` podem conter caracteres que precisam de percent-encoding) e a geração de um `state` opaco e imprevisível — aqui, via `SecureRandom`, nunca via `Random` comum, porque o `state` é um mecanismo de segurança (anti-CSRF, seção 5.2 deste capítulo), não um identificador qualquer.

```java
import java.net.URLEncoder;
import java.nio.charset.StandardCharsets;
import java.security.SecureRandom;
import java.util.Base64;

final class AuthorizationRequestBuilder {

    private static final SecureRandom RNG = new SecureRandom();

    // Gera um valor opaco, imprevisível, para o parametro state (RFC 6749 5.2 / 4.1.1).
    // Por que SecureRandom e nao Random: state precisa ser imprevisivel para um atacante,
    // senao a protecao anti-CSRF pode ser burlada por forca bruta ou adivinhacao.
    static String newState() {
        byte[] raw = new byte[24];
        RNG.nextBytes(raw);
        return Base64.getUrlEncoder().withoutPadding().encodeToString(raw);
    }

    static String build(String authorizeEndpoint, String clientId, String redirectUri,
                         String scope, String state) {
        String enc = "UTF-8";
        return authorizeEndpoint
                + "?response_type=code"
                + "&client_id=" + urlEncode(clientId)
                + "&redirect_uri=" + urlEncode(redirectUri)
                + "&scope=" + urlEncode(scope)
                + "&state=" + urlEncode(state);
    }

    private static String urlEncode(String value) {
        return URLEncoder.encode(value, StandardCharsets.UTF_8);
    }

    public static void main(String[] args) {
        String state = newState();
        String url = build(
                "http://localhost:3001/authorize",
                "client-demo",
                "http://localhost:3000/callback",
                "profile",
                state);

        // Em uma aplicacao web real, o client guardaria `state` associado a sessao
        // do navegador (ex: cookie de sessao no servidor) ANTES de redirecionar,
        // para poder conferir a igualdade quando o AS chamar de volta o redirect_uri.
        System.out.println("Redirecionar o navegador para: " + url);
        System.out.println("State a guardar na sessao local: " + state);
    }
}
```

### Exemplo 2 — Trocando o authorization code por tokens (§4.1.3)

Depois que o AS redireciona de volta ao `redirect_uri` com `?code=...&state=...`, o client (no backend, fora do alcance do navegador) confere o `state` e faz a troca back-channel no token endpoint. Note o `Content-Type: application/x-www-form-urlencoded` (exigido pela RFC, §4.1.3) e a autenticação do client via HTTP Basic — o método preferencial segundo a RFC 6749 §2.3.1.

```java
import java.net.URI;
import java.net.URLEncoder;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.nio.charset.StandardCharsets;
import java.util.Base64;
import java.util.Map;

final class TokenExchange {

    private static final HttpClient HTTP = HttpClient.newHttpClient();

    // Troca um authorization code por access_token (+ refresh_token, se emitido).
    // grant_type=authorization_code -- RFC 6749 4.1.3.
    static Map<String, String> exchangeAuthorizationCode(
            String tokenEndpoint, String clientId, String clientSecret,
            String code, String redirectUri) throws Exception {

        String body = "grant_type=authorization_code"
                + "&code=" + enc(code)
                + "&redirect_uri=" + enc(redirectUri);

        return post(tokenEndpoint, clientId, clientSecret, body);
    }

    // Uso do refresh_token para obter um novo access_token sem repetir o login
    // do resource owner -- RFC 6749 6. O client deve estar preparado para
    // receber (ou nao) um novo refresh_token na resposta: se vier, descarta o
    // antigo; se nao vier, continua usando o que ja tinha.
    static Map<String, String> refresh(
            String tokenEndpoint, String clientId, String clientSecret,
            String refreshToken) throws Exception {

        String body = "grant_type=refresh_token"
                + "&refresh_token=" + enc(refreshToken);

        return post(tokenEndpoint, clientId, clientSecret, body);
    }

    private static Map<String, String> post(String tokenEndpoint, String clientId,
            String clientSecret, String formBody) throws Exception {

        // Autenticacao de client via HTTP Basic (RFC 6749 2.3.1) -- metodo
        // preferencial. client_id e client_secret sao concatenados com ':' e
        // codificados em Base64; o RFC exige que cada um seja percent-encoded
        // ANTES da concatenacao, para evitar ambiguidade se algum contiver ':'.
        String basicAuth = Base64.getEncoder().encodeToString(
                (enc(clientId) + ":" + enc(clientSecret)).getBytes(StandardCharsets.UTF_8));

        HttpRequest request = HttpRequest.newBuilder()
                .uri(URI.create(tokenEndpoint))
                .header("Authorization", "Basic " + basicAuth)
                .header("Content-Type", "application/x-www-form-urlencoded")
                .POST(HttpRequest.BodyPublishers.ofString(formBody, StandardCharsets.UTF_8))
                .build();

        HttpResponse<String> response = HTTP.send(request, HttpResponse.BodyHandlers.ofString());

        if (response.statusCode() != 200) {
            // Corpo de erro do token endpoint e sempre JSON: {"error":"...","error_description":"..."}
            Map<String, String> error = SimpleJson.parseFlat(response.body());
            throw new IllegalStateException("token endpoint respondeu "
                    + response.statusCode() + ": " + error.get("error")
                    + " -- " + error.get("error_description"));
        }

        return SimpleJson.parseFlat(response.body());
    }

    private static String enc(String value) {
        return URLEncoder.encode(value, StandardCharsets.UTF_8);
    }

    public static void main(String[] args) throws Exception {
        // Exemplo de uso apos o navegador retornar ?code=...&state=... para o
        // redirect_uri do client (conferencia do state omitida aqui por brevidade
        // -- ver Exemplo 1 sobre por que ela e obrigatoria).
        Map<String, String> tokens = exchangeAuthorizationCode(
                "http://localhost:3001/token",
                "client-demo",
                "s3cr3t",
                "AUTH_CODE_RECEBIDO_NO_CALLBACK",
                "http://localhost:3000/callback");

        System.out.println("access_token:  " + tokens.get("access_token"));
        System.out.println("expires_in:    " + tokens.get("expires_in"));
        System.out.println("refresh_token: " + tokens.get("refresh_token"));

        // Mais tarde, quando o access_token expirar:
        Map<String, String> renewed = refresh(
                "http://localhost:3001/token", "client-demo", "s3cr3t",
                tokens.get("refresh_token"));
        System.out.println("novo access_token: " + renewed.get("access_token"));
    }
}
```

### Exemplo 3 — Client Credentials Grant (§4.4): comunicação machine-to-machine

Sem resource owner, sem redirect, sem code — apenas o client se autenticando diretamente no token endpoint. Este é o padrão típico para um serviço backend chamar outro serviço backend, sem usuário humano na equação.

```java
import java.net.URI;
import java.net.URLEncoder;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.nio.charset.StandardCharsets;
import java.util.Base64;
import java.util.Map;

final class ClientCredentialsExample {

    private static final HttpClient HTTP = HttpClient.newHttpClient();

    static Map<String, String> requestServiceToken(
            String tokenEndpoint, String clientId, String clientSecret, String scope)
            throws Exception {

        String body = "grant_type=client_credentials&scope="
                + URLEncoder.encode(scope, StandardCharsets.UTF_8);

        String basicAuth = Base64.getEncoder().encodeToString(
                (clientId + ":" + clientSecret).getBytes(StandardCharsets.UTF_8));

        HttpRequest request = HttpRequest.newBuilder()
                .uri(URI.create(tokenEndpoint))
                .header("Authorization", "Basic " + basicAuth)
                .header("Content-Type", "application/x-www-form-urlencoded")
                .POST(HttpRequest.BodyPublishers.ofString(body, StandardCharsets.UTF_8))
                .build();

        HttpResponse<String> response = HTTP.send(request, HttpResponse.BodyHandlers.ofString());

        Map<String, String> parsed = SimpleJson.parseFlat(response.body());
        if (response.statusCode() != 200) {
            throw new IllegalStateException("falha ao obter token de servico: " + parsed);
        }

        // Nota (RFC 6749 4.4.3): este grant nao emite refresh_token -- se o
        // access_token expirar, o client simplesmente repete esta chamada com
        // as mesmas credenciais. Nao ha sessao de resource owner para "renovar".
        return parsed;
    }

    public static void main(String[] args) throws Exception {
        Map<String, String> tokens = requestServiceToken(
                "http://localhost:3001/token", "servico-backend", "outro-segredo", "service");
        System.out.println("access_token (M2M): " + tokens.get("access_token"));
    }
}
```

### Relação com o laboratório deste projeto

O laboratório `rfc6749/` deste projeto (em Node.js/Express) implementa exatamente os mecanismos descritos neste capítulo, em três processos separados que se comunicam apenas via HTTP e um Redis compartilhado como fonte de verdade dos tokens: o `authorization-server` expõe `/authorize` (GET renderiza a tela de login, POST processa a decisão do resource owner e emite o `code` de uso único) e `/token` (que trata `authorization_code`, `refresh_token` e `client_credentials` no mesmo handler, validando `grant_types` permitidos por client); o `resource-server` valida o bearer token recebido; e o `client-demo` desempenha o papel de client confidencial, guardando o `client_secret` inteiramente no backend. A rotação incondicional de refresh token a cada uso (seção 3.5 deste capítulo) já está implementada — `redis.del(refresh_token:...)` seguido de emissão de um novo — assim como a validação exata de `redirect_uri` (seção 5.1) e a checagem cruzada `client_id`/`redirect_uri` entre o passo de autorização e o de troca do code (seção 3.1).
