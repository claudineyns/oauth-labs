# RFC 6750 — Bearer Token Usage

## 1. Contexto e motivação

### 1.1 A lacuna deixada pela RFC 6749

A RFC 6749 define, com detalhe considerável, como um `access_token` é **obtido** — os grant types, os endpoints, os parâmetros. Mas ela deixa deliberadamente de fora uma pergunta igualmente central: uma vez em posse do token, como o client o **usa** para efetivamente acessar um recurso protegido? Essa lacuna é o escopo exclusivo da RFC 6750, publicada no mesmo dia (outubro de 2012) que a 6749, como uma companion spec dedicada.

A RFC 6750 formaliza o tipo de token mais comum do OAuth 2.0 — na prática, o único que a RFC 6749 realmente exercita em seus exemplos: o **bearer token**.

### 1.2 A definição central: posse é acesso

Um bearer token é uma credencial na qual **qualquer parte que o possua pode usá-la**, sem precisar provar posse de nenhuma chave criptográfica associada, sem assinar a requisição, sem qualquer prova adicional de que é o legítimo destinatário original do token. Na prática: "quem tem o token, tem o acesso" — a analogia clássica na literatura é a de um **cheque ao portador** (*bearer check*): quem apresenta o papel ao banco recebe o valor, independentemente de ser ou não o titular original da conta.

Essa definição é a contrapartida direta de uma escolha de design já discutida no capítulo anterior deste livro: o OAuth 1.0 (RFC 5849) exigia que cada requisição fosse assinada criptograficamente com HMAC-SHA1, amarrando cada chamada a uma chave que o atacante precisaria roubar separadamente da simples observação do tráfego. O OAuth 2.0 removeu essa exigência em favor de simplicidade de implementação — e a RFC 6750 é, em certo sentido, **o preço dessa simplicidade**: como não há prova de posse por requisição, **toda a segurança do modelo recai sobre como o token é transportado, armazenado e sobre seu tempo de vida** — nunca sobre o protocolo de uso em si.

Esse é o ponto mais importante a reter deste capítulo, e vale repetir com todas as letras: bearer = simples de implementar, simples de interoperar, mas **roubável e livremente reutilizável por qualquer um que o capture**, até que expire ou seja revogado. Não há "assinatura errada" que um resource server possa detectar — um token roubado é, do ponto de vista do RS, indistinguível de um token usado pelo seu dono legítimo.

### 1.3 Por que esse modelo foi aceitável em 2012 (e por que hoje é visto como piso mínimo)

Em 2012, a aposta era razoável: TLS já era amplamente disponível e cada vez mais padrão, os tempos de vida recomendados eram curtos, e a maior parte dos cenários de uso não envolvia os níveis de sensibilidade que hoje justificam controles adicionais (transações financeiras de alto valor, dados de saúde, acesso a infraestrutura crítica). Anos de exploração em produção, no entanto, revelaram vetores de roubo de token que TLS por si só não neutraliza completamente — vazamento por logs mal configurados, XSS em SPAs que armazenam tokens acessíveis a JavaScript, proxies corporativos mal configurados fazendo TLS termination e logando corpos de requisição, tokens capturados em ambientes de desenvolvimento/homologação com configuração mais frouxa que vazam para produção, entre outros.

É exatamente essa lacuna estrutural — "posse = acesso, sem mais nada" — que, uma década depois, motivou o desenvolvimento de mecanismos de ***sender-constraining***: a RFC 8705 (OAuth 2.0 Mutual-TLS Client Authentication and Certificate-Bound Access Tokens) e a RFC 9449 (DPoP — Demonstrating Proof of Possession), ambas tratadas no item 6 deste livro. Essas especificações não substituem o bearer token da RFC 6750 — elas o **complementam**, amarrando o token a um material criptográfico que só o legítimo detentor possui (um certificado de cliente mTLS, ou um par de chaves DPoP), de forma que um token capturado por interceptação ou vazamento de log deixa de ser diretamente utilizável por quem o capturou.

### 1.4 O nome importa: por que "Bearer" e não apenas "token"

A RFC 6750 formaliza `Bearer` como o valor literal do campo `token_type` na resposta do token endpoint (RFC 6749 §5.1) e como o *authentication scheme* HTTP usado no header `Authorization`. Esse nome não é cosmético — ele sinaliza explicitamente, para qualquer implementador que leia a especificação, que aquele tipo particular de token não carrega nenhuma prova de posse embutida. Um esquema alternativo (como o `DPoP` introduzido pela RFC 9449) usa um nome diferente precisamente para deixar claro, já no header, que a semântica de segurança é outra — um resource server que só sabe validar `Bearer` não deve aceitar silenciosamente um esquema diferente como se fosse equivalente.

## 2. Terminologia e papéis

Nenhum papel novo é introduzido em relação à RFC 6749 — client, resource server, authorization server e resource owner permanecem exatamente os mesmos, com as mesmas responsabilidades já descritas no capítulo anterior. A RFC 6750 se limita a definir com precisão dois conceitos que a 6749 apenas menciona de passagem:

- **Bearer Token** — o tipo específico de credencial abordado por esta especificação (o valor de `token_type` no token endpoint é literalmente a string `"Bearer"`, case-insensitive por uma errata posterior — ver seção 7).
- **Bearer Token Usage** — o conjunto de regras normativas sobre como um client deve apresentar esse token e como um resource server deve validá-lo (ou rejeitá-lo) em uma requisição.

Um detalhe de nuance frequentemente perdido: a RFC 6750 é inteiramente **agnóstica quanto ao formato interno do token**. Ela não especifica se o `access_token` é um identificador opaco (uma string aleatória que só faz sentido em conjunto com uma tabela de estado no AS/RS — o modelo que o laboratório deste projeto usa, com o token como chave no Redis) ou um token auto-contido e verificável (como um JWT assinado, formalizado mais tarde pela RFC 9068). Ambos são "bearer tokens" do ponto de vista desta RFC — a diferença está inteiramente em como o resource server valida o token, o que fica fora do escopo tanto da 6749 quanto da 6750.

## 3. Fluxo(s) — as 3 formas de transmitir o token (§2)

A RFC define exatamente três métodos pelos quais o client pode apresentar o `access_token` ao resource server. Antes de detalhar cada um, uma regra transversal — e muitas vezes negligenciada em implementações reais — merece destaque: **o client não deve usar mais de um método na mesma requisição**. Se um resource server detectar o token informado em mais de um lugar simultaneamente (por exemplo, tanto no header `Authorization` quanto na query string), a resposta correta é `400 Bad Request` com `error=invalid_request` — nunca aceitar silenciosamente um dos dois e ignorar o outro, e nunca tratar isso como ambiguidade "inofensiva". A razão de ser dessa regra é reduzir a superfície de ataque de confusão: se dois locais pudessem carregar tokens diferentes, um sistema com múltiplas camadas (proxy, gateway, aplicação) poderia inspecionar um e a aplicação final usar outro, abrindo brechas de bypass de autorização.

### 3.1 Authorization Request Header Field (§2.1) — o método recomendado

Este é o método que a RFC explicitamente recomenda e que **todo resource server compatível deve suportar**:

```
GET /recurso HTTP/1.1
Host: api.exemplo.com
Authorization: Bearer mF_9.B5f-4.1JqM
```

A vantagem estrutural deste método é que o header `Authorization` não é, por padrão, persistido em logs de acesso comuns de servidores web (diferente da URL completa, que quase sempre é), não aparece no header `Referer` enviado a terceiros, e não fica no histórico de navegação — reduzindo consideravelmente a superfície de vazamento acidental em comparação aos outros dois métodos.

### 3.2 Form-Encoded Body Parameter (§2.2) — restrito e não recomendado

Este método só é permitido quando **todas** as condições a seguir são satisfeitas: o método HTTP é `POST` (a RFC também permite outros métodos que aceitem corpo, mas na prática é quase sempre POST), o `Content-Type` é integralmente `application/x-www-form-urlencoded`, e o corpo da requisição não contém nenhum outro conteúdo além dos parâmetros form-encoded (ou seja, não pode coexistir com um corpo multipart, um payload JSON, ou qualquer outro formato):

```
POST /recurso HTTP/1.1
Host: api.exemplo.com
Content-Type: application/x-www-form-urlencoded

access_token=mF_9.B5f-4.1JqM&outro_campo=valor
```

A RFC explicitamente qualifica este método como não recomendado, exceto quando o client não tem como manipular headers HTTP diretamente (algumas plataformas/bibliotecas legadas de formulário). Além da limitação evidente (só funciona com POST/PUT e corpo form-encoded), há um risco de log adicional: muitos frameworks de aplicação registram corpos de requisição inteiros em logs de depuração — um hábito bem mais comum do que logar o header `Authorization` — o que amplia a chance de o token vazar por essa via.

### 3.3 URI Query Parameter (§2.3) — desaconselhado explicitamente

Este é o método que a própria RFC trata com a linguagem mais forte de desaconselhamento, embora ainda o defina formalmente (para interoperabilidade com clients legados que não têm alternativa):

```
GET /recurso?access_token=mF_9.B5f-4.1JqM HTTP/1.1
Host: api.exemplo.com
```

Os riscos, todos bem documentados na literatura de segurança web e reiterados na própria RFC (§5): URLs completas (incluindo query string) são rotineiramente gravadas em logs de acesso de servidores web, proxies reversos e balanceadores de carga — muitas vezes por padrão, sem qualquer configuração adicional. URLs também ficam no histórico de navegação do dispositivo do usuário, indefinidamente, acessível a qualquer um com acesso físico ou a um backup do dispositivo. E, criticamente, se a página que recebe essa URL contiver qualquer link para um recurso de terceiros (uma imagem, um script, um link clicável), o header `Referer` da requisição subsequente pode incluir a URL completa da página atual — vazando o token para um domínio completamente alheio ao OAuth. A recomendação prática, reforçada por implementações modernas (ver seção 7), é tratar este método como **inaceitável** em vez de meramente desaconselhado, a menos que exista uma razão de interoperabilidade muito específica e documentada.

*(Os 3 métodos — e a rejeição por uso simultâneo em mais de um local — já estão implementados e testados no laboratório [`rfc6749/resource-server`](../../rfc6749/resource-server/src/index.js) deste projeto, na função `requireBearer`, que extrai o token do header, do corpo ou da query string e rejeita explicitamente quando mais de uma fonte está presente.)*

## 4. Parâmetros e endpoints normativos

A RFC 6750 não define nenhum endpoint novo — ela reaproveita inteiramente os endpoints já definidos pela RFC 6749 (authorization, token, redirection). O que ela define são parâmetros e headers específicos para o momento de **uso** do token contra o resource server:

### 4.1 `token_type = "Bearer"` na resposta do token endpoint

Este é o único ponto de contato direto entre a RFC 6750 e a resposta do token endpoint definida pela RFC 6749 (§5.1): o campo `token_type` deve valer `"Bearer"` (com essa capitalização na emissão, embora a comparação na recepção deva ser case-insensitive — ver seção 7) para sinalizar ao client que ele deve seguir as regras desta RFC ao apresentar o token.

### 4.2 O header de desafio/erro `WWW-Authenticate` (§3)

Este é o mecanismo central pelo qual um resource server comunica, de forma padronizada, tanto um "desafio" inicial (quando nenhum token foi apresentado) quanto um erro específico (quando um token foi apresentado, mas é inválido, expirado, ou insuficiente):

```
WWW-Authenticate: Bearer realm="exemplo", error="invalid_token", error_description="o token expirou"
```

O parâmetro `realm` segue a semântica geral de HTTP Authentication (RFC 7235) — identifica o espaço de proteção ao qual a credencial se aplica, útil quando um mesmo host serve múltiplos domínios de autorização distintos. Os parâmetros `error` e `error_description` são específicos desta RFC e só devem ser incluídos quando há de fato um erro a reportar — nunca em um desafio inicial simples (ver a regra sutil da seção 4.4 abaixo).

### 4.3 Os 3 códigos de erro normativos (§3.1)

| Código | Status HTTP | Significado |
|---|---|---|
| `invalid_request` | 400 | Requisição malformada — por exemplo, token informado em mais de um local (seção 3), ou parâmetro obrigatório ausente/duplicado |
| `invalid_token` | 401 | Token ausente de significado válido: expirado, revogado, malformado, ou emitido por um AS que o RS não reconhece |
| `insufficient_scope` | 403 | O token é válido (autenticação bem-sucedida), mas não carrega o escopo necessário para a operação solicitada (falha de autorização, não de autenticação) — o header de resposta deve incluir um parâmetro `scope` listando o(s) escopo(s) exigido(s) |

A distinção entre `invalid_token` (401) e `insufficient_scope` (403) é semanticamente importante e corresponde exatamente à distinção clássica entre autenticação e autorização: 401 significa "eu não sei quem você é" (ou "sua credencial não é válida"), 403 significa "eu sei quem você é, e você não tem permissão para isso". Um resource server que devolve 401 para uma falha de escopo (ou vice-versa) está entregando uma informação de diagnóstico incorreta ao client — o que pode levar a lógicas de retry equivocadas (por exemplo, tentar renovar o token via refresh_token quando na verdade o problema é que o escopo concedido nunca incluiria a operação, e nenhuma renovação vai resolver isso).

### 4.4 A regra sutil e fácil de esquecer: desafio sem erro

Quando **nenhum** token foi enviado na requisição (o cliente sequer tentou se autenticar), o resource server deve responder `401` com um `WWW-Authenticate` **sem** os parâmetros `error` e `error_description` — apenas `Bearer realm="..."`. A justificativa, embora sutil, é uma boa prática de segurança por design: incluir o motivo detalhado do erro para uma parte que ainda nem tentou se autenticar vaza informação desnecessária (por exemplo, detalhes sobre o esquema de validação interno) a um ator potencialmente hostil que está apenas sondando o endpoint. O erro detalhado (`invalid_token`, `insufficient_scope`) só faz sentido depois que uma tentativa real de autenticação foi feita e falhou por um motivo específico.

## 5. Segurança já tratada na própria RFC 6750 (§5)

A seção de considerações de segurança da RFC 6750 é desproporcionalmente extensa para uma especificação que, à primeira vista, parece "apenas" descrever como colocar um token em um header — e isso é deliberado: como bearer = posse é igual a acesso (seção 1.2), praticamente toda garantia de segurança do sistema depende de como essas recomendações são seguidas.

### 5.1 TLS obrigatório em toda requisição que carrega o token

Diferente da RFC 6749, onde TLS protege primariamente a emissão do token, aqui TLS deve proteger **toda e qualquer requisição subsequente** que carregue o bearer token — não apenas o momento de obtenção. Um bearer token trafegando em texto claro, ainda que apenas uma vez, é funcionalmente equivalente a vazar uma senha: qualquer observador passivo da rede (um Wi-Fi público não criptografado, um proxy corporativo mal configurado, um roteador comprometido) captura uma credencial diretamente utilizável até a expiração do token.

### 5.2 Tempo de vida curto como mitigação central

Como não há mecanismo de revogação instantânea universal embutido no bearer token em si (revogação depende de infraestrutura adicional — uma blocklist consultada pelo RS, ou tokens auto-contidos de vida curta o suficiente para que a janela de exposição seja pequena), a RFC recomenda tempos de vida curtos como a principal ferramenta de contenção de dano: se um token vaza, o estrago está limitado ao que pode ser feito antes da expiração. É por isso que o laboratório deste projeto usa um `ACCESS_TOKEN_TTL` de apenas 5 minutos — deliberadamente curto para tornar visível, na prática, o papel do refresh token (RFC 6749 §6) como o mecanismo que permite sessões longas sem exigir access tokens de vida longa.

### 5.3 Armazenamento: tratar bearer tokens como segredos

Tanto no client quanto no resource server, um bearer token deve ser tratado com o mesmo rigor que uma senha: nunca em texto claro em logs de aplicação, nunca em caches não protegidos, nunca em armazenamento local sem controle de acesso adequado (em uma SPA, por exemplo, `localStorage` é acessível a qualquer script rodando na mesma origem — incluindo um script malicioso injetado via XSS — o que motiva, em arquiteturas mais cuidadosas, guardar tokens em cookies `HttpOnly` geridos pelo backend, fora do alcance de JavaScript).

### 5.4 Nunca colocar o token na URL de página

Esta recomendação reforça diretamente o desaconselhamento do método de query parameter (seção 3.3): além dos riscos já descritos de log e histórico, colocar o token na URL da própria página (não apenas em uma chamada de API) o expõe a qualquer extensão de navegador com permissão de leitura de URL, a ferramentas de analytics que capturam a URL corrente automaticamente, e a qualquer captura de tela ou compartilhamento de tela que inclua a barra de endereço.

### 5.5 Escopo reduzido como limitação de dano

Tokens devem carregar o menor escopo possível para a operação em questão — um princípio de menor privilégio aplicado diretamente ao design do token. Se um token de leitura de perfil vaza, o dano potencial deve se limitar à leitura de perfil, nunca se estender a operações mais sensíveis que o client nem sequer precisava solicitar. Essa recomendação, ainda relativamente genérica na RFC 6750, prenuncia diretamente desenvolvimentos posteriores tratados no item 6 deste livro: a RFC 8707 (Resource Indicators), que amarra o token a um recurso-alvo específico, e a RFC 9396 (Rich Authorization Requests), que permite escopos estruturados e muito mais granulares do que a simples lista de strings da RFC 6749.

> **Nota de laboratório**: como já registrado no capítulo anterior, os labs práticos deste projeto rodam em HTTP puro (`http://localhost`), a despeito da exigência formal de TLS descrita em 5.1 — uma simplificação deliberada, mantida até o capítulo da RFC 8705 (mTLS, item 6 deste livro), onde TLS real passa a ser o próprio mecanismo em estudo. Até lá, o foco pedagógico permanece na mecânica de emissão/uso de tokens, não na camada de transporte.

## 6. Relação com outras RFCs

- A RFC 6750 depende inteiramente da **RFC 6749** para a emissão do token — ela cobre exclusivamente o uso, nunca a obtenção.
- O formato de erro que ela introduz (`WWW-Authenticate` com parâmetros `error`/`error_description`) estabeleceu um padrão que outras extensões do ecossistema OAuth reaproveitaram por analogia, mesmo fora do escopo estrito de bearer tokens.
- **RFC 8705 (mTLS)** e **RFC 9449 (DPoP)** existem justamente para resolver a fraqueza estrutural que a própria RFC 6750 documenta explicitamente em sua seção 5: um bearer token roubado equivale a acesso total até a expiração. Ambas adicionam uma camada de prova de posse por cima do que seria, de outra forma, um bearer token puro — sem alterar o formato básico definido aqui.
- **RFC 9068 (JWT Profile for Access Tokens)** formaliza um formato específico e auto-contido de bearer token (um JWT assinado com claims padronizadas) — a RFC 6750, como já notado na seção 2, é inteiramente agnóstica quanto a esse formato: um token opaco de tabela hash e um JWT assinado são, ambos, "bearer tokens" do ponto de vista desta especificação.
- **RFC 9700 (BCP)** reforça a recomendação de tokens sender-constrained para cenários sensíveis, elevando a uma quase-obrigação prática o que a RFC 6750 já sinalizava como uma limitação conhecida e aceita em 2012.
- **RFC 7662 (Token Introspection)** define um protocolo padronizado para o resource server consultar o authorization server sobre a validade e os metadados de um bearer token opaco — uma peça de infraestrutura complementar que a RFC 6750 pressupõe existir de alguma forma, mas não especifica.

## 7. O que mudou desde a publicação (2012)

- A RFC em si não foi revisada formalmente, mas a prática de mercado evoluiu de forma perceptível: hoje é comum tratar o método de query string (seção 3.3) como **inaceitável** — não apenas desaconselhado — em implementações modernas; muitas APIs financeiras e de alto valor nem sequer o implementam, forçando o client a usar o header `Authorization`.
- Uma errata publicada posteriormente esclareceu que o nome do esquema de autenticação (`Bearer`) deve ser tratado como **case-insensitive** na recepção, seguindo a regra geral de esquemas de autenticação HTTP definida pela RFC 7235 — um resource server rigoroso demais que exigisse exatamente `"Bearer "` (com maiúscula exata) estaria, tecnicamente, fora de conformidade. O resource server do laboratório deste projeto já trata isso corretamente, usando o regex `/^Bearer /i` (a flag `i` torna a checagem case-insensitive) para extrair o token do header.
- O padrão de "considerado seguro o suficiente" mudou substancialmente: em 2012, bearer token puro + TLS era o estado da arte aceitável para praticamente qualquer cenário. Hoje, para APIs financeiras ou de alto valor, a expectativa de mercado (refletida na RFC 9700 e em perfis de segurança setoriais como o FAPI — Financial-grade API, do OpenID Foundation) é sender-constraining via mTLS ou DPoP como padrão, não como exceção — bearer puro passou a ser tratado como piso mínimo aceitável apenas para cenários de baixa sensibilidade.

## Exemplo em Java (JDK 21, sem frameworks)

Os exemplos a seguir reutilizam o utilitário `SimpleJson` já definido no Capítulo 1 (RFC 6749) deste livro — não o redefinimos aqui. Como antes, tudo usa exclusivamente `java.net.http.HttpClient` da biblioteca padrão do JDK 21, sem qualquer framework ou biblioteca externa.

### Exemplo 1 — Enviando o bearer token via header (§2.1, o método recomendado)

```java
import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.util.Map;

final class BearerViaHeader {

    private static final HttpClient HTTP = HttpClient.newHttpClient();

    // Metodo recomendado pela RFC 6750 2.1 -- todo resource server compatível
    // DEVE suportar este metodo. O token nao aparece na URL nem no corpo,
    // reduzindo a chance de vazamento por logs de acesso, historico ou Referer.
    static HttpResponse<String> callProtectedResource(String resourceUrl, String accessToken)
            throws Exception {

        HttpRequest request = HttpRequest.newBuilder()
                .uri(URI.create(resourceUrl))
                .header("Authorization", "Bearer " + accessToken)
                .GET()
                .build();

        return HTTP.send(request, HttpResponse.BodyHandlers.ofString());
    }

    public static void main(String[] args) throws Exception {
        HttpResponse<String> response = callProtectedResource(
                "http://localhost:3002/api/profile", "mF_9.B5f-4.1JqM");

        if (response.statusCode() == 200) {
            Map<String, String> body = SimpleJson.parseFlat(response.body());
            System.out.println("Perfil: " + body);
        } else {
            System.out.println("Falhou com status " + response.statusCode());
            // Ver Exemplo 3 para como interpretar o header WWW-Authenticate aqui.
        }
    }
}
```

### Exemplo 2 — Enviando o bearer token via body e via query (§2.2 e §2.3, não recomendados)

Estes dois métodos são apresentados por completude — a RFC os define, mas desaconselha ambos (o segundo, de forma bem mais enfática). Note que os dois exemplos abaixo **nunca** devem ser combinados com o header `Authorization` na mesma requisição (RFC 6750 §2 proíbe mais de um método simultâneo — ver seção 3 deste capítulo).

```java
import java.net.URI;
import java.net.URLEncoder;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.nio.charset.StandardCharsets;

final class BearerViaBodyOrQuery {

    private static final HttpClient HTTP = HttpClient.newHttpClient();

    // RFC 6750 2.2 -- permitido SOMENTE em POST/PUT com corpo inteiramente
    // application/x-www-form-urlencoded, e sem nenhum outro conteudo no corpo.
    // Nao recomendado: existe para clients que nao conseguem manipular headers.
    static HttpResponse<String> viaFormBody(String resourceUrl, String accessToken)
            throws Exception {

        String body = "access_token=" + URLEncoder.encode(accessToken, StandardCharsets.UTF_8);

        HttpRequest request = HttpRequest.newBuilder()
                .uri(URI.create(resourceUrl))
                .header("Content-Type", "application/x-www-form-urlencoded")
                .POST(HttpRequest.BodyPublishers.ofString(body, StandardCharsets.UTF_8))
                .build();

        return HTTP.send(request, HttpResponse.BodyHandlers.ofString());
    }

    // RFC 6750 2.3 -- desaconselhado explicitamente: a URL completa (com o
    // token) fica sujeita a logs de proxy/servidor, historico do navegador e
    // vazamento via header Referer para terceiros. Usar apenas como ultimo recurso.
    static HttpResponse<String> viaQueryParam(String resourceUrlBase, String accessToken)
            throws Exception {

        String url = resourceUrlBase + "?access_token="
                + URLEncoder.encode(accessToken, StandardCharsets.UTF_8);

        HttpRequest request = HttpRequest.newBuilder()
                .uri(URI.create(url))
                .GET()
                .build();

        return HTTP.send(request, HttpResponse.BodyHandlers.ofString());
    }

    public static void main(String[] args) throws Exception {
        String token = "mF_9.B5f-4.1JqM";

        HttpResponse<String> r1 = viaFormBody("http://localhost:3002/api/profile", token);
        System.out.println("via body: " + r1.statusCode());

        HttpResponse<String> r2 = viaQueryParam("http://localhost:3002/api/profile", token);
        System.out.println("via query: " + r2.statusCode());
    }
}
```

### Exemplo 3 — Interpretando o header `WWW-Authenticate` de erro (§3)

Quando o resource server rejeita a requisição, ele sinaliza o motivo através do header `WWW-Authenticate`. Um client bem-comportado deveria distinguir os três códigos de erro normativos (seção 4.3 deste capítulo) para decidir a ação correta: `invalid_token` sugere tentar obter um novo token (via refresh_token, RFC 6749 §6); `insufficient_scope` sugere que uma renovação simples não resolve — seria necessário um novo fluxo de autorização pedindo o escopo adequado; `invalid_request` sinaliza um bug no próprio client (token enviado em mais de um lugar, por exemplo).

```java
import java.util.LinkedHashMap;
import java.util.Map;
import java.util.regex.Matcher;
import java.util.regex.Pattern;

final class WwwAuthenticateParser {

    // Parser deliberadamente simples para o cabecalho:
    //   WWW-Authenticate: Bearer realm="exemplo", error="invalid_token", error_description="o token expirou"
    // RFC 6750 3 / 3.1. Assume o esquema "Bearer" e parametros key="value" separados por virgula.
    static Map<String, String> parse(String header) {
        Map<String, String> params = new LinkedHashMap<>();
        if (header == null || !header.regionMatches(true, 0, "Bearer", 0, 6)) {
            return params; // nao e um desafio Bearer -- outro esquema, ou ausente
        }

        Matcher m = Pattern.compile("(\\w+)=\"(.*?)\"").matcher(header);
        while (m.find()) {
            params.put(m.group(1), m.group(2));
        }
        return params;
    }

    // Decide a proxima acao do client com base no error retornado (se houver).
    // Ausencia de 'error' com apenas 'realm' = desafio inicial (RFC 6750 3, ver
    // secao 4.4 deste capitulo) -- nenhum token foi enviado, nao ha o que reinterpretar.
    static String suggestAction(Map<String, String> challenge) {
        String error = challenge.get("error");
        if (error == null) {
            return "Nenhum token foi enviado (ou o desafio nao traz detalhes) -- autenticar normalmente.";
        }
        return switch (error) {
            case "invalid_token" -> "Token invalido/expirado -- tentar renovar via refresh_token (RFC 6749 6).";
            case "insufficient_scope" -> "Escopo insuficiente (scope exigido: "
                    + challenge.getOrDefault("scope", "?")
                    + ") -- e necessario um novo consentimento, refresh nao resolve.";
            case "invalid_request" -> "Requisicao malformada -- provavel bug no client (ex: token em mais de um lugar).";
            default -> "Erro desconhecido: " + error;
        };
    }

    public static void main(String[] args) {
        String header = "Bearer realm=\"oauth-rfc6749-lab\", error=\"invalid_token\", "
                + "error_description=\"o token expirou\"";

        Map<String, String> challenge = parse(header);
        System.out.println("Parametros: " + challenge);
        System.out.println("Acao sugerida: " + suggestAction(challenge));

        // Caso do desafio "puro" (nenhum token enviado -- secao 4.4 deste capitulo):
        // sem error/error_description, apenas realm.
        Map<String, String> bareChallenge = parse("Bearer realm=\"oauth-rfc6749-lab\"");
        System.out.println("Desafio simples: " + bareChallenge);
        System.out.println("Acao sugerida: " + suggestAction(bareChallenge));
    }
}
```

### Relação com o laboratório deste projeto

O laboratório `rfc6749/resource-server` deste projeto (Node.js/Express) implementa exatamente os três métodos de transmissão descritos neste capítulo dentro da função `requireBearer`: ela extrai o token do header `Authorization` via regex case-insensitive (`/^Bearer (.+)$/i`, coerente com a errata discutida na seção 7), do corpo form-encoded quando aplicável, e da query string — e rejeita explicitamente com `400 invalid_request` se mais de uma fonte estiver presente na mesma requisição, exatamente como a regra transversal da seção 3 exige. Ele também monta o header `WWW-Authenticate` com os três códigos de erro normativos (`invalid_token`, `insufficient_scope`, e o `invalid_request` do caso de múltiplas fontes), incluindo o parâmetro `scope` na resposta de `insufficient_scope` — e omite `error`/`error_description` no caso de nenhum token ter sido enviado, seguindo à risca a regra sutil da seção 4.4.
