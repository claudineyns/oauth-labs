# RFC 7591 — OAuth 2.0 Dynamic Client Registration Protocol

## 1. Contexto e motivação

Em todo capítulo e em todo laboratório deste livro até este ponto, registro de client foi tratado como um passo **manual, fora de banda**: alguém — um administrador, um script de seed rodando na inicialização do ambiente — configura `client_id`, `client_secret` e `redirect_uris` diretamente no armazenamento do Authorization Server, **antes** de qualquer fluxo OAuth acontecer. Nos labs deste projeto, isso é literalmente um script escrevendo um registro pronto direto no Redis, executado no boot do ambiente.

Esse modelo funciona bem — e continua sendo a escolha certa — quando existe um conjunto pequeno e relativamente estático de clients conhecidos de antemão (o cenário típico de "integração B2B combinada por contrato"). Mas ele deixa de escalar em pelo menos três cenários realistas:

1. **Software distribuído que aponta para um AS de escolha do usuário final.** Pense num client de e-mail, de chat, ou um agregador de "traga sua própria conta" (bring-your-own-server): o mesmo binário de client precisa, em tempo de execução, se registrar contra qualquer Authorization Server que o usuário decida usar — o desenvolvedor do client não tem como pré-negociar credenciais com cada AS existente no mundo.
2. **Onboarding self-service de integrações de terceiros.** Uma plataforma que expõe uma API OAuth-protegida a desenvolvedores externos quer, tipicamente, um portal onde qualquer integrador possa criar um novo client sem depender de um humano do lado do provedor aprovando e digitando credenciais manualmente a cada pedido.
3. **Provisionamento programático multi-tenant.** Uma plataforma SaaS que cria um tenant novo por cliente frequentemente precisa, como parte desse provisionamento automatizado, criar também um (ou vários) client OAuth associado — sem intervenção humana no caminho crítico.

A RFC 7591 (publicada em 2015, junto com a RFC 7592) resolve isso substituindo o processo manual por um **endpoint de registro**: o client (ou o software que o provisiona em nome de um usuário/tenant) faz um `POST` descrevendo a metadata desejada, e o Authorization Server responde criando o registro e devolvendo as credenciais recém-geradas. O que antes era um ticket de suporte ou um script administrativo vira uma chamada de API — com todas as implicações de segurança que isso traz (tratadas em detalhe na §5).

### 1.1 Por que isso não é "menos seguro por definição"

Vale desfazer uma intuição comum: registro dinâmico **não é**, em si, menos seguro que registro manual — é apenas um mecanismo diferente de *como* a credencial chega a existir. Um registro manual malfeito (segredo fraco, redirect_uri mal validado no cadastro) é tão vulnerável quanto um registro dinâmico malfeito. O que muda é a **superfície de ataque**: registro manual tem, implicitamente, um portão humano no caminho (alguém decidiu criar aquele client); registro dinâmico só tem esse portão se a implantação explicitamente o construir (via initial access token, aprovação, ou outro controle — ver §5). A RFC é honesta sobre isso: ela padroniza o mecanismo, mas deixa a decisão de *quem pode chamá-lo* inteiramente a critério de cada implantação.

## 2. Terminologia e papéis

A RFC 7591 não introduz papéis novos além dos já conhecidos (Client, Authorization Server) — introduz um vocabulário específico do próprio processo de registro:

- **Client Registration Endpoint** — o endpoint novo, aceitando `POST`, cuja localização é tipicamente descoberta via o campo `registration_endpoint` do documento de metadata da RFC 8414 (capítulo anterior deste livro).
- **Client Metadata** — o conjunto de campos descritivos que caracterizam um client: `redirect_uris`, `client_name`, `grant_types`, `response_types`, `token_endpoint_auth_method`, `jwks`/`jwks_uri`, `scope`, `contacts`, `tos_uri`, `policy_uri`, `logo_uri`, `client_uri`, `software_id`, `software_version`. Praticamente todos esses nomes já apareceram ao longo do roteiro deste livro como coisas "configuradas previamente" em algum lugar — esta RFC é justamente onde esse ato de configuração vira uma chamada de API, em vez de um passo administrativo silencioso.
- **Initial Access Token** — uma credencial **opcional**, cuja existência e formato ficam inteiramente a critério de cada implantação (a RFC não define seu formato). Serve como portão de entrada: um AS pode exigir que quem chama `POST /register` já possua algum token previamente emitido (por um processo de aprovação separado, por exemplo), impedindo registro totalmente aberto. Não é exigido pela letra da RFC, mas é explicitamente antecipado como padrão comum e recomendado de implantação — a RFC até dedica uma seção não-normativa a discutir esse tipo de controle (ver §5).
- **Software Statement** — um JWT **assinado por um terceiro de confiança** (tipicamente o próprio publicador/fabricante do software, ou uma autoridade de federação), contendo afirmações (claims) sobre o software que está sendo registrado. A ideia central: em vez de o AS confiar cegamente em campos auto-declarados no corpo do `POST` (qualquer um pode escrever `"client_name": "Banco Legítimo S.A."` sem que isso seja verdade), o software statement permite que essas afirmações venham *assinadas* por alguém que o AS já confia previamente — deslocando a âncora de confiança de "o que o requisitante diz" para "o que um terceiro atestou".

### 2.1 O "escopo do registro" vs. "escopo de uma requisição"

Um ponto sutil que vale destacar cedo: o campo `scope` enviado no registro **não é** uma concessão — é o **teto** do que aquele client poderá, no futuro, solicitar em requisições de autorização individuais. Um client registrado com `"scope": "profile email"` não ganha automaticamente esses scopes em todo token emitido; ele só passa a ser **elegível** para pedi-los. A concessão efetiva continua acontecendo fluxo a fluxo, exatamente como descrito no capítulo da RFC 6749. Confundir essas duas coisas — achar que registrar com um scope amplo já concede acesso amplo — é um erro conceitual comum em quem lê a RFC pela primeira vez.

## 3. Fluxo

```
1. Client (ou quem o provisiona em seu nome) -> AS: POST /register
   Content-Type: application/json
   Authorization: Bearer <initial_access_token>   (opcional, depende da implantacao)

   {
     "redirect_uris": ["https://client.exemplo.org/callback"],
     "client_name": "Meu App",
     "grant_types": ["authorization_code", "refresh_token"],
     "response_types": ["code"],
     "token_endpoint_auth_method": "client_secret_basic",
     "scope": "profile email"
   }

2. AS valida a metadata solicitada:
   - redirect_uris sao URIs absolutas, sem fragmento, coerentes com o
     token_endpoint_auth_method (client publico tipicamente nao deveria
     usar client_secret_basic, por exemplo)
   - grant_types e response_types sao mutuamente consistentes
     (ex.: response_types=["code"] implica grant_types deve incluir
     "authorization_code")
   - se initial_access_token for exigido pela implantacao, valida-o
   - se software_statement estiver presente, valida a assinatura contra
     a chave do emissor confiavel

3. AS cria o registro internamente, gera client_id (e client_secret, se o
   client for confidencial) e responde:

   AS -> Client: 201 Created
   Content-Type: application/json

   {
     "client_id": "s6BhdRkqt3",
     "client_secret": "cf136dc3c1fc93f31185e5885805d",
     "client_id_issued_at": 2893256800,
     "client_secret_expires_at": 0,
     "registration_access_token": "reg-23410913-abewfq.123483",
     "registration_client_uri": "https://as.exemplo.com/register/s6BhdRkqt3",
     "redirect_uris": ["https://client.exemplo.org/callback"],
     "client_name": "Meu App",
     "grant_types": ["authorization_code", "refresh_token"],
     "response_types": ["code"],
     "token_endpoint_auth_method": "client_secret_basic",
     "scope": "profile email"
   }
```

Note que a resposta **ecoa** a metadata que foi efetivamente aceita — que pode ser idêntica à solicitada, ou ajustada pelo AS (por exemplo, um AS pode aceitar o registro mas remover um `grant_type` que não suporta, em vez de rejeitar o pedido inteiro; a RFC permite ambos os comportamentos, deixando a critério da implantação qual delas seguir).

O par `registration_access_token` + `registration_client_uri`, devolvido aqui na criação, é exatamente a credencial e a URL que a RFC companheira — **RFC 7592**, próximo capítulo — usa depois para ler, atualizar ou apagar esse registro específico. A 7591 cobre exclusivamente a **criação**; tudo que acontece depois do `201 Created` é território da 7592.

### 3.1 Erros de registro

Os erros seguem o mesmo padrão OAuth de `error` + `error_description` (RFC 6749 §5.2), com códigos específicos deste protocolo:

- `invalid_redirect_uri` — a URI fornecida é inválida ou não atende a alguma exigência da implantação (esquema não permitido, fragmento presente, etc.).
- `invalid_client_metadata` — algum campo de metadata é inválido ou inconsistente (ex.: `token_endpoint_auth_method` que o AS não suporta, conforme anunciado em `token_endpoint_auth_methods_supported` na metadata RFC 8414).
- `invalid_software_statement` — o software statement fornecido não pôde ser validado (assinatura inválida, claims malformadas).
- `unapproved_software_statement` — o software statement é criptograficamente válido, mas o AS optou por não aprovar esse software específico (ex.: uma allowlist de emissores de software statement).

## 4. Parâmetros e endpoints normativos

- **Client Registration Endpoint** — novo, tipicamente descoberto via RFC 8414 como o campo `registration_endpoint` do documento de metadata.
- **Detalhe que chama atenção imediatamente a quem já percorreu os outros capítulos deste livro**: diferente de praticamente todo outro endpoint OAuth coberto até aqui (que usa `application/x-www-form-urlencoded` — `/token`, `/revoke`, `/introspect`), o registro usa **`application/json`**. Essa é uma exceção deliberada da RFC, não um descuido: a metadata do client tem campos naturalmente estruturados — arrays (`redirect_uris`, `grant_types`, `response_types`, `contacts`) e potencialmente objetos aninhados (`jwks`, que é um JSON Web Key Set completo) — que não se prestam bem à codificação achatada de form-urlencoded. É por isso que este capítulo (e o próximo) são os únicos deste livro onde o utilitário `SimpleJson` — definido no Capítulo 1 (RFC 6749) — é genuinamente indispensável para o corpo da requisição, não só da resposta.
- **Campos de request mais relevantes**:
  - `redirect_uris` (array de strings) — obrigatório se o client pretende usar qualquer grant baseado em redirecionamento (`authorization_code`). Cada URI deve ser absoluta e sem fragmento.
  - `token_endpoint_auth_method` — como o client se autenticará no `/token`: `client_secret_basic`, `client_secret_post`, `private_key_jwt`, `client_secret_jwt`, `none` (client público, sem segredo), `tls_client_auth`/`self_signed_tls_client_auth` (RFC 8705, mais adiante no roteiro).
  - `grant_types` — lista de grant types que o client pretende usar (default `["authorization_code"]` se omitido).
  - `response_types` — tipicamente `["code"]`; deve ser consistente com `grant_types` (um client pedindo `response_types: ["code"]` precisa ter `"authorization_code"` em `grant_types`).
  - `client_name`, `client_uri`, `logo_uri`, `contacts`, `tos_uri`, `policy_uri` — campos majoritariamente informativos/de exibição, usados por exemplo numa tela de consentimento para identificar o client ao Resource Owner.
  - `scope` — string separada por espaços, o teto do que o client poderá solicitar depois (ver §2.1).
  - `jwks_uri` / `jwks` — chave pública (ou conjunto de chaves) do client, usada para verificar assinaturas quando `token_endpoint_auth_method` é `private_key_jwt`, ou para verificar Request Objects assinados (RFC 9101). São mutuamente exclusivos — um client não deve fornecer os dois.
  - `software_statement` — o JWT assinado por terceiro, cobrindo (potencialmente) qualquer subconjunto dos campos acima; quando presente, os valores do software statement tipicamente prevalecem sobre valores conflitantes enviados soltos no corpo.
- **Campos de response**: `client_id` (único campo de resposta genuinamente obrigatório), `client_secret` (presente apenas se o client for confidencial), `client_id_issued_at` (timestamp Unix), `client_secret_expires_at` (`0` significa "nunca expira" — um valor positivo é um timestamp Unix de expiração), `registration_access_token`, `registration_client_uri`, além de toda a metadata efetivamente aceita, ecoada de volta.

## 5. Segurança já tratada na própria RFC 7591

- **Registro aberto sem nenhum portão é um risco concreto, não hipotético.** Se qualquer parte não autenticada pode chamar `POST /register` livremente, torna-se trivial para um atacante criar `client_id`s arbitrários em volume. Isso é diretamente explorável para phishing — registrar um client com `client_name` e `logo_uri` deliberadamente enganosos, que serão exibidos numa tela de consentimento legítima do AS, fazendo um usuário confiar num client malicioso porque a *interface* de consentimento parece confiável — ou simplesmente para poluir/sobrecarregar o armazenamento de clients do AS (um vetor de negação de serviço de baixo esforço). A RFC discute isso na sua §3 (de forma não-normativa, deixando a decisão a cada implantação): implementações **deveriam** considerar algum tipo de barreira antes de permitir o registro — um initial access token previamente distribuído por um canal confiável, um passo de aprovação manual pós-registro antes do client se tornar utilizável, ou simplesmente restringir o endpoint a um conjunto fechado de partes já autenticadas por outro mecanismo (mTLS de rede, allowlist de IP, etc.).
- **Software Statement mitiga o problema fundamental de "quem é você de verdade".** Como todos os campos de metadata são, por padrão, inteiramente auto-declarados por quem chama o endpoint, um AS que precise de garantia mais forte sobre a autenticidade de certas afirmações (por exemplo, "este software é realmente o app oficial publicado pelo Fornecedor X", relevante em contextos regulados como Open Banking/FAPI) pode exigir que essas afirmações venham dentro de um software statement assinado por uma autoridade de emissão em quem o AS já confia previamente — deixando de depender da palavra não verificada de quem preenche o formulário de registro.
- **`registration_access_token` precisa de proteção equivalente a qualquer credencial bearer** (as mesmas considerações da RFC 6750 se aplicam integralmente): quem o possui pode gerenciar — e, com a RFC 7592, efetivamente apagar — aquele registro de client específico. Vazamento desse token tem, na prática, um raio de impacto comparável a vazar o próprio `client_secret`.
- **Validação de `redirect_uri` não é relaxada pelo fato do registro ser dinâmico.** É um erro conceitual pensar que "dinâmico" significa "menos rigoroso" — a exigência de correspondência exata entre o `redirect_uri` usado numa requisição de autorização e algum valor previamente registrado (RFC 6749 §3.1.2.3, reforçada pela RFC 9700) se aplica exatamente da mesma forma a um client registrado dinamicamente. O que muda é só *como* aquele valor chegou a existir no armazenamento do AS — a checagem no momento do `/authorize` é idêntica.
- **Confidencialidade do `client_secret` na resposta é uma janela de exposição única.** O `client_secret` só é devolvido **uma vez**, na resposta de criação — nunca novamente em uma consulta subsequente (ver RFC 7592, `GET` explicitamente omite esse campo). Isso significa que o cliente que perde essa resposta original (ex.: falha de rede após o `201`, log truncado) perde o segredo para sempre, exigindo rotação (via `PUT`, RFC 7592) para recuperar acesso — um comportamento operacionalmente relevante, não só teórico.

## 6. Relação com outras RFCs

- **Companheira direta e indissociável da RFC 7592** (próximo capítulo deste livro), publicada na mesma data — a 7592 estende exatamente este protocolo com leitura, atualização e exclusão do registro, usando o `registration_access_token` + `registration_client_uri` que a 7591 devolve na criação. As duas RFCs formam, na prática, um único ciclo de vida partido em dois documentos por conveniência de escopo.
- **Descoberta via RFC 8414** — o `registration_endpoint` é um dos campos do documento de metadata (capítulo anterior); um client que queira descobrir automaticamente onde registrar-se consulta a metadata primeiro.
- **É exatamente o que a maioria dos labs deste projeto ainda não faz**: `rfc6749/`, `rfc7636/` e `rfc9126/` registram o client de demonstração fora de banda, via script de seed escrevendo diretamente no Redis na subida do ambiente — o padrão manual que esta RFC existe precisamente para substituir por uma chamada de API real.
- **`jwks_uri`/`jwks` registrados aqui alimentam diretamente a RFC 9101 (JAR)** e a **RFC 7523** (autenticação de client via JWT assertion, seção adiante do roteiro) — é neste ponto do ciclo de vida que essas chaves passam a existir associadas formalmente a um `client_id` específico no AS.
- **`token_endpoint_auth_method` registrado aqui determina, de forma vinculante, qual método de autenticação de client se aplica** a partir daí: `client_secret_basic`/`client_secret_post` (segredo compartilhado), `private_key_jwt` (RFC 7523), `none` (client público, tipicamente combinado com PKCE — RFC 7636), `tls_client_auth` (mTLS, RFC 8705, ainda por vir no roteiro).
- **RFC 9126 (PAR)** — um client registrado dinamicamente pode, em seguida, ser instruído (via metadata) a sempre empurrar seus parâmetros de autorização antes de redirecionar o Resource Owner; não há dependência direta entre os protocolos, mas ambos convivem naturalmente no mesmo AS.

## 7. O que mudou desde a publicação (2015)

- Spec estável e fundacional, mas a adoção de registro **totalmente aberto** (sem qualquer portão de entrada) permanece relativamente rara em produção — precisamente pelos riscos que a própria RFC já sinaliza na sua seção de considerações de segurança. A esmagadora maioria das implantações que suportam RFC 7591 combinam-na com initial access token, aprovação manual pós-registro, ou restringem o endpoint a contextos fechados de federação/enterprise.
- É mais visível, na prática, em ecossistemas onde registro dinâmico resolve um problema real e não apenas teórico: contextos de **OpenID Connect Federation** (onde a confiança vem de uma cadeia de assinaturas, não de um portal humano), alguns ecossistemas de **IoT e apps nativos** com provisionamento em massa, e crescentemente em contextos adjacentes a **FAPI** (Financial-grade API), onde software statements fornecem exatamente a âncora de confiança forte que integrações financeiras reguladas exigem antes de conceder qualquer credencial.
- O formato geral do protocolo (`POST` JSON → `client_id`/`client_secret` + credenciais de gerenciamento) permaneceu estável desde 2015 e efetivamente virou o **modelo de referência** para outras APIs de "auto-registro" em especificações adjacentes publicadas depois — a forma do request/response praticamente não mudou, mesmo com o ecossistema ao redor evoluindo bastante.

> **Nota de laboratório**: implementado em três labs deste projeto, cada um exercitando um `token_endpoint_auth_method` diferente — uma escolha deliberada para cobrir o espectro de uso real do protocolo. Em [`rfc7592/`](../../../rfc7592/README.md) — `client_secret_basic`: não há script de seed nem `.demo-client.env`; o Authorization Server expõe `POST /register`, e o client-demo se registra **sob demanda**, como ação manual do usuário (botão "Registrar client agora" — ver detalhes no capítulo da RFC 7592 a seguir). Em [`rfc7523/`](../../../rfc7523/README.md) — `private_key_jwt`: o corpo do registro carrega `jwks` (a chave pública do client) em vez de o client receber um `client_secret` de volta, coerente com autenticação baseada em assinatura JWT em vez de segredo compartilhado. Em [`rfc9449/`](../../../rfc9449/README.md) — `none` (client público): nem `client_secret` nem `jwks` são trocados; o sender-constraining do token fica inteiramente a cargo do DPoP (RFC 9449), não da autenticação do client no `/token`.

## Exemplo em Java (JDK 21, sem frameworks)

Os exemplos usam `java.net.http.HttpClient` e o utilitário `SimpleJson` (`SimpleJson.object(Map)` para serializar o corpo, `SimpleJson.parseFlat(String)` para ler a resposta), ambos definidos no Capítulo 1 (RFC 6749) deste livro. Note que este é o **único** endpoint, entre todos os labs do projeto, cujo corpo de requisição é JSON — todo o resto usa `application/x-www-form-urlencoded`.

### 7.1 Registrar um client novo com `POST /register`

```java
import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.net.http.HttpRequest.BodyPublishers;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

/**
 * Registra dinamicamente um novo client no Authorization Server (RFC 7591).
 * Diferente de /token, /revoke, /introspect (form-urlencoded), este endpoint
 * usa application/json — a metadata tem campos naturalmente estruturados
 * (arrays como redirect_uris) que nao se prestam a form-encoding achatado.
 */
public class ClientRegistrationClient {

    private final HttpClient http = HttpClient.newHttpClient();
    private final String registrationEndpoint;

    public ClientRegistrationClient(String registrationEndpoint) {
        this.registrationEndpoint = registrationEndpoint;
    }

    public Map<String, String> registrar(String redirectUri, String clientName) throws Exception {
        // Monta a metadata desejada. redirect_uris e um array — e exatamente
        // por causa de campos assim que o corpo precisa ser JSON, nao
        // form-urlencoded (que so representa pares chave-valor escalares).
        Map<String, Object> metadata = new LinkedHashMap<>();
        metadata.put("redirect_uris", List.of(redirectUri));
        metadata.put("client_name", clientName);
        metadata.put("grant_types", List.of("authorization_code", "refresh_token"));
        metadata.put("response_types", List.of("code"));
        metadata.put("token_endpoint_auth_method", "client_secret_basic");
        metadata.put("scope", "profile email");

        String corpoJson = SimpleJson.object(metadata);

        HttpRequest request = HttpRequest.newBuilder()
                .uri(URI.create(registrationEndpoint))
                .header("Content-Type", "application/json")
                .header("Accept", "application/json")
                // Se a implantacao exigir initial_access_token, seria aqui:
                // .header("Authorization", "Bearer " + initialAccessToken)
                .POST(BodyPublishers.ofString(corpoJson))
                .build();

        HttpResponse<String> response = http.send(request, HttpResponse.BodyHandlers.ofString());

        if (response.statusCode() != 201) {
            // Erros seguem o padrao OAuth: error + error_description no corpo,
            // ex.: invalid_redirect_uri, invalid_client_metadata,
            // invalid_software_statement, unapproved_software_statement.
            throw new IllegalStateException(
                    "Registro falhou: HTTP " + response.statusCode() + " - " + response.body());
        }

        return SimpleJson.parseFlat(response.body());
    }
}
```

### 7.2 Ler de volta as credenciais e a URI de gerenciamento

```java
import java.util.Map;

/**
 * Extrai e organiza os campos criticos da resposta de registro. O
 * client_secret so aparece AQUI, uma unica vez — nao e devolvido de novo
 * em nenhuma consulta subsequente (ver RFC 7592, capitulo seguinte: o GET
 * de gerenciamento omite deliberadamente esse campo).
 */
public class RegistroRecemCriado {

    public final String clientId;
    public final String clientSecret;          // pode ser null (client publico)
    public final String registrationAccessToken;
    public final String registrationClientUri;
    public final long clientSecretExpiresAt;   // 0 = nunca expira

    public RegistroRecemCriado(Map<String, String> resposta) {
        this.clientId = resposta.get("client_id");
        this.clientSecret = resposta.get("client_secret"); // ausente => client publico
        this.registrationAccessToken = resposta.get("registration_access_token");
        this.registrationClientUri = resposta.get("registration_client_uri");

        String expiresAt = resposta.get("client_secret_expires_at");
        this.clientSecretExpiresAt = expiresAt != null ? Long.parseLong(expiresAt) : 0L;

        if (clientId == null) {
            throw new IllegalStateException("Resposta de registro sem client_id — resposta invalida");
        }
        if (registrationAccessToken == null || registrationClientUri == null) {
            // Sem esse par, e impossivel gerenciar o registro depois (RFC 7592)
            // — o client precisaria de um novo registro do zero se os perder.
            System.err.println("Aviso: AS nao devolveu credenciais de gerenciamento (RFC 7592)");
        }
    }

    public void persistirComoSegredo() {
        // PONTO DE ATENCAO DIDATICO: client_secret e registration_access_token
        // sao credenciais de alto valor (secao 5 deste capitulo) e devem ser
        // guardadas com o mesmo cuidado que qualquer segredo de longa duracao
        // — nunca logadas em texto claro, nunca versionadas em codigo-fonte.
        System.out.println("client_id: " + clientId);
        System.out.println("client_secret: [omitido do log deliberadamente]");
        System.out.println("registration_client_uri: " + registrationClientUri);
    }
}
```

### 7.3 Exemplo completo de uso

```java
public class RegistroExemplo {
    public static void main(String[] args) throws Exception {
        // registration_endpoint tipicamente descoberto via RFC 8414
        // (metadata.get("registration_endpoint")), aqui hardcoded por brevidade.
        String registrationEndpoint = "http://localhost:3301/register";

        ClientRegistrationClient registrador = new ClientRegistrationClient(registrationEndpoint);
        var resposta = registrador.registrar(
```
