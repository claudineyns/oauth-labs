# RFC 8414 — OAuth 2.0 Authorization Server Metadata

## 1. Contexto e motivação

Todo protocolo de integração cliente-servidor enfrenta, mais cedo ou mais tarde, o mesmo problema de fundo: como o cliente sabe *onde* falar com o servidor? Em OAuth 2.0 "puro" (RFC 6749), a resposta original era simplesmente "fora de banda" — o desenvolvedor do client lê a documentação do provedor, copia manualmente as URLs de `/authorize` e `/token` para um arquivo de configuração, e torce para que elas não mudem. Essa abordagem sobrevive razoavelmente bem quando existe **um** provedor fixo e conhecido (o client foi escrito especificamente para ele), mas começa a ranger nas costuras assim que o ecossistema cresce em qualquer uma destas direções:

- **Bibliotecas OAuth genéricas.** Uma biblioteca cliente que pretenda suportar "qualquer Authorization Server compatível" não pode hardcodar URL nenhuma — ela precisa de um mecanismo em tempo de execução para aprender a topologia do AS específico que está sendo integrado.
- **Crescimento orgânico de endpoints.** RFC 6749 definiu só `/authorize` e `/token`. Depois vieram `/revoke` (RFC 7009), `/introspect` (RFC 7662), `/device_authorization` (RFC 8628), `/par` (RFC 9126), e a lista não para de crescer. Sem um documento central, cada nova capacidade exigiria seu próprio mecanismo de descoberta ad hoc, ou pior, mais um parâmetro de configuração manual que alguém vai esquecer de preencher.
- **Multi-tenancy e ambientes federados.** Em cenários com múltiplos "issuers" lógicos atrás da mesma infraestrutura (ex.: um AS multi-tenant, um por cliente/organização), cada tenant pode ter endpoints ligeiramente diferentes — path prefixado por tenant, conjunto de scopes distinto, algoritmos de assinatura habilitados diferentes. Configuração estática por tenant é operacionalmente inviável em escala.
- **Rotação e migração de infraestrutura.** Qualquer mudança de URL no AS — uma migração de domínio, uma reorganização de path, a introdução de um load balancer com path diferente — quebra, silenciosamente, toda configuração estática espalhada pelos clients. Não há como avisar "atualizem suas configurações" de forma centralizada quando a configuração é, por definição, distribuída.

A RFC 8414 (publicada em 2018, mas formalizando uma prática já comum informalmente) resolve isso com um **documento de descoberta**: um único JSON, publicado numa URL *well-known* padronizada, que descreve de uma vez todos os endpoints e capacidades relevantes do AS. Em vez de N configurações manuais (uma por endpoint, replicada em cada client), existe **um** ponto de verdade que qualquer client pode consultar em tempo de execução.

Vale explicitar a genealogia: esse padrão não nasceu com a 8414. O OpenID Connect Discovery — que expõe `/.well-known/openid-configuration` — é anterior e já resolvia exatamente esse problema para o mundo OIDC. A RFC 8414 é, essencialmente, a extração desse mesmo padrão para o OAuth 2.0 "puro", sem exigir a pilha OIDC inteira (sem exigir `id_token`, sem exigir um `userinfo_endpoint`, sem as claims de identidade). Isso significa que muita gente que já lida com OIDC reconhece a 8414 imediatamente — os nomes de campo são, em grande parte, os mesmos, e não por acaso: a RFC 8414 foi desenhada deliberadamente para que os dois documentos pudessem, na prática, ser o **mesmo objeto JSON** quando um AS suporta ambos os protocolos (um AS que também é OpenID Provider tipicamente publica o mesmo conteúdo, ou um superconjunto dele, em ambos os paths well-known).

## 2. Terminologia e papéis

A RFC 8414 não introduz nenhum papel novo em relação ao vocabulário OAuth já estabelecido (Resource Owner, Client, Authorization Server, Resource Server) — ela introduz apenas conceitos ligados ao próprio mecanismo de descoberta:

- **Authorization Server Metadata** — o documento JSON em si: um conjunto de pares chave-valor descrevendo endpoints, capacidades e políticas suportadas pelo AS.
- **Well-Known URI** — o mecanismo de localização do documento, definido pela RFC 8615 (*Well-Known Uniform Resource Identifiers*), da qual a 8414 é consumidora. O caminho padronizado é `/.well-known/oauth-authorization-server`.
- **`issuer`** — de longe o campo mais importante do documento, e o único genuinamente obrigatório. É uma URL (sem *fragment*, tipicamente sem *query*) que identifica o AS de forma única e global. Esse valor não é decorativo: ele precisa bater, byte a byte, com qualquer lugar onde o AS se identifica como emissor — o claim `iss` de um JWT (RFC 9068, tokens JWT introspectáveis), o `aud` esperado de um Request Object assinado (RFC 9101), ou o valor usado para localizar o próprio documento de metadata (ver §5 abaixo — essa auto-referência é o cerne da mitigação de mix-up attack).

### 2.1 A regra de composição do path well-known

Um detalhe que confunde bastante gente na primeira leitura, porque é contraintuitivo comparado a outras convenções de URL: quando o `issuer` **tem um path** (por exemplo, um AS multi-tenant publicado em `https://as.exemplo.com/tenant1`), o segmento `.well-known/oauth-authorization-server` é **inserido antes** do path do issuer, não anexado depois dele.

```
issuer:                https://as.exemplo.com/tenant1
well-known CORRETO:    https://as.exemplo.com/.well-known/oauth-authorization-server/tenant1
well-known ERRADO:     https://as.exemplo.com/tenant1/.well-known/oauth-authorization-server
```

Essa regra existe porque `.well-known` é, por definição da RFC 8615, um path reservado no **nível da origem** (scheme + host + porta) — não algo que se relativiza a um subpath arbitrário. A justificativa prática é operacional: um servidor HTTP típico já tem uma rota fixa para tudo que começa com `/.well-known/`, independentemente de quantos tenants ou subpaths existam depois. Se a convenção fosse "anexar depois", cada tenant precisaria de sua própria rota `.well-known` configurada separadamente — voltando ao mesmo problema de escala que a RFC tenta resolver. Um AS de tenant único, sem path no `issuer` (o caso mais comum, e o caso do lab deste livro), não precisa se preocupar com essa regra: o well-known fica simplesmente em `https://as.exemplo.com/.well-known/oauth-authorization-server`.

### 2.2 Metadata "genuína" vs. metadata "descritiva"

Vale uma distinção conceitual que a RFC deixa implícita: alguns campos do documento são **descritivos** (informam algo que já é verdade independentemente do documento — ex.: `token_endpoint`, que é só "onde bater"), enquanto outros são **normativos sobre política** (`require_pushed_authorization_requests: true`, por exemplo, muda o comportamento exigido do client). Um client bem-comportado deve tratar campos de política com o mesmo peso que teria uma exigência hardcoded — ignorá-los porque "são só metadata" é um erro de interpretação comum em implementações apressadas.

## 3. Fluxo

Não é, estritamente falando, um "fluxo" OAuth no sentido de trocar código de autorização por token — é uma consulta HTTP simples, pública, sem estado e sem autenticação:

```
GET /.well-known/oauth-authorization-server HTTP/1.1
Host: as.exemplo.com

HTTP/1.1 200 OK
Content-Type: application/json

{
  "issuer": "https://as.exemplo.com",
  "authorization_endpoint": "https://as.exemplo.com/authorize",
  "token_endpoint": "https://as.exemplo.com/token",
  "registration_endpoint": "https://as.exemplo.com/register",
  "revocation_endpoint": "https://as.exemplo.com/revoke",
  "introspection_endpoint": "https://as.exemplo.com/introspect",
  "jwks_uri": "https://as.exemplo.com/jwks.json",
  "scopes_supported": ["profile", "email", "offline_access"],
  "response_types_supported": ["code"],
  "grant_types_supported": ["authorization_code", "refresh_token", "client_credentials"],
  "token_endpoint_auth_methods_supported": ["client_secret_basic", "private_key_jwt"],
  "code_challenge_methods_supported": ["S256"],
  "pushed_authorization_request_endpoint": "https://as.exemplo.com/par",
  "require_pushed_authorization_requests": false,
  "device_authorization_endpoint": "https://as.exemplo.com/device_authorization"
}
```

O consumidor típico deste documento não é um humano lendo no browser (embora isso também funcione, já que é um GET público) — é código de biblioteca cliente que, na inicialização, busca esse JSON uma vez, faz cache dele por um período razoável, e a partir daí resolve `token_endpoint`/`authorization_endpoint`/etc. dinamicamente em vez de tê-los hardcoded. É esse padrão — "configure só o issuer, a biblioteca descobre o resto" — que se tornou o modo dominante de configurar integrações OAuth/OIDC em produção bem depois de 2018 (ver §7).

### 3.1 O que acontece quando o documento não existe

A RFC não prescreve um comportamento único para "AS não publica metadata" — mas na prática, um client que recebe `404 Not Found` na URL well-known tem duas saídas legítimas: (a) cair de volta para configuração manual dos endpoints (o modo "pré-8414", ainda plenamente válido), ou (b) tratar isso como erro fatal de integração, se o client foi desenhado para depender inteiramente de descoberta. Ambas são escolhas de implementação, não normas da RFC.

## 4. Parâmetros e endpoints normativos

- **A well-known URI é o próprio "endpoint"** — não há verbo além de `GET`, não há autenticação (o documento é público por design — ver §5), e a resposta é sempre `application/json`.
- **`issuer`** — único campo genuinamente **obrigatório** em todo o documento. Todos os demais são opcionais na letra da RFC, ainda que praticamente universais na prática (nenhum AS sério publica um documento de metadata sem `token_endpoint`, por exemplo, mesmo que tecnicamente a RFC permitisse).
- Campos que aparecem ao longo de praticamente todo o roteiro deste livro, cada um sendo a forma "descoberta" de algo que, em RFCs anteriores, era configuração manual:
  - `authorization_endpoint`, `token_endpoint` — os dois endpoints fundacionais (RFC 6749).
  - `jwks_uri` — onde buscar as chaves públicas do AS para validar assinaturas (usado por RFC 9068, RFC 9101, JWT-based client auth).
  - `scopes_supported` — lista informativa (não normativa em termos de enforcement) dos scopes que o AS reconhece.
  - `response_types_supported`, `grant_types_supported` — quais fluxos o AS de fato implementa; um client pode usar isso para decidir, em runtime, se um determinado grant type está disponível antes de tentar usá-lo.
  - `token_endpoint_auth_methods_supported` — quais métodos de autenticação de client o `/token` aceita (`client_secret_basic`, `client_secret_post`, `private_key_jwt`, `none`, `tls_client_auth` — RFC 8705).
  - `code_challenge_methods_supported` — como o AS anuncia suporte a PKCE (RFC 7636) e com quais métodos de transformação (tipicamente só `S256`; `plain` é desencorajado e alguns ASs nem o anunciam mesmo aceitando-o por retrocompatibilidade).
  - `revocation_endpoint` (RFC 7009), `introspection_endpoint` (RFC 7662), `device_authorization_endpoint` (RFC 8628), `pushed_authorization_request_endpoint` + `require_pushed_authorization_requests` (RFC 9126), `request_parameter_supported`/`request_uri_parameter_supported`/`require_signed_request_object` (RFC 9101), `registration_endpoint` (RFC 7591 — capítulo seguinte deste livro).
- Campos adicionais comuns na prática, ainda que fora do escopo estrito dos labs deste projeto: `service_documentation`, `ui_locales_supported`, `op_policy_uri`, `op_tos_uri`, `revocation_endpoint_auth_methods_supported`, `introspection_endpoint_auth_methods_supported` (cada endpoint secundário pode ter seu **próprio** conjunto de métodos de autenticação suportados, potencialmente diferente do `/token`).

Esse documento é, na prática, o índice vivo que amarra quase todo endpoint introduzido pelas RFCs deste roteiro — é o "mapa do tesouro" que substitui a necessidade de ler documentação estática de integração.

### 4.1 Extensibilidade

A RFC define explicitamente que novos campos podem ser registrados no **IANA "OAuth Authorization Server Metadata" registry** sem exigir uma revisão da RFC 8414 em si — é assim que campos de RFCs posteriores (PAR, JAR, DPoP) puderam ser adicionados ao vocabulário do documento sem qualquer mudança na 8414 original. Um client robusto deve, portanto, **ignorar silenciosamente** campos desconhecidos em vez de tratá-los como erro — o documento é projetado para crescer.

## 5. Segurança já tratada na própria RFC 8414

- **Validação do `issuer` é a mitigação central de mix-up attack.** Ao buscar metadata em `https://{host}/.well-known/oauth-authorization-server`, o campo `issuer` devolvido no corpo **deve** bater exatamente — mesmo scheme, mesmo host, mesma porta (se explícita), sem barra final divergente — com o valor efetivamente consultado. Sem essa checagem, um client poderia ser induzido (por DNS spoofing, por um proxy malicioso, por um AS comprometido reaproveitado em outro contexto) a aceitar um documento de metadata que na verdade descreve um AS diferente do pretendido, redirecionando silenciosamente todo o fluxo de autorização para infraestrutura sob controle de um atacante. Essa é exatamente a mesma família de preocupação tratada com mais profundidade no capítulo da RFC 9700 (identificação inequívoca do emissor como defesa contra mix-up attacks) — a validação do `issuer` no documento de metadata é, historicamente, uma das primeiras instâncias concretas dessa mitigação no ecossistema OAuth.
- **TLS é obrigatório** para buscar o documento em qualquer implantação de produção. Um documento de metadata adulterado em trânsito (ataque man-in-the-middle sobre HTTP puro) poderia redirecionar o client inteiro para endpoints controlados por um atacante — trocar `token_endpoint` por uma URL maliciosa é, em essência, um vetor de personificação completa do AS, capaz de capturar `client_secret`, códigos de autorização, ou tokens inteiros. (Os labs deste projeto rodam em HTTP puro deliberadamente, como simplificação didática — ver a Parte de mTLS/RFC 8705 para quando TLS entra na conversa de forma explícita.)
- **Cache não deve ser cego nem eterno.** A RFC não prescreve uma política de cache específica (não há `Cache-Control` normativo definido pela 8414 em si), mas alerta para os dois riscos opostos: cache **desatualizado demais** pode quebrar integração silenciosamente quando o AS migra endpoints; cache de um documento **comprometido** (obtido uma vez sob condições adversas, depois reutilizado indefinidamente) prolonga a janela de um redirecionamento malicioso muito além do momento do ataque original. Um TTL razoável (minutos a poucas horas, revalidado periodicamente) é a prática comum, ainda que não normatizada em número exato.
- **Ausência de autenticação para buscar o documento é proposital, não uma omissão.** O documento de metadata funciona como uma âncora de confiança pública — similar a uma chave pública, ou ao próprio certificado TLS do servidor: ele existe justamente para ser lido por qualquer um, sem barreira, para *bootstrapar* confiança antes de qualquer outra interação acontecer. O efeito colateral é que qualquer parte — incluindo um atacante fazendo reconhecimento — pode ver exatamente quais capacidades o AS suporta (quais grant types, quais métodos de auth, se PAR é obrigatório). Isso é considerado risco de reconhecimento de baixo impacto, não uma vulnerabilidade em si: a informação exposta é, por natureza, a mesma que qualquer integrador legítimo precisaria descobrir de qualquer forma.
- **Confusão de porta/scheme como variante sutil do mix-up.** Um detalhe menos óbvio: `https://as.exemplo.com` e `https://as.exemplo.com:443` podem ser semanticamente equivalentes para um navegador, mas a comparação de string do `issuer` deve ser feita de forma canônica e consistente — implementações ingênuas que comparam strings brutas sem normalizar porta padrão podem, em teoria, criar uma janela de bypass da validação. A RFC não detalha algoritmo de canonicalização; delega ao bom senso de comparação de URLs já estabelecido por outras especificações (RFC 3986).

## 6. Relação com outras RFCs

- **Modelo direto do OpenID Connect Discovery** (`/.well-known/openid-configuration`), que é anterior e continua sendo o "primo" mais rico em campos (inclui `userinfo_endpoint`, `id_token_signing_alg_values_supported`, claims de identidade). A 8414 é, deliberadamente, a versão "OAuth puro" do mesmo padrão — compatível o suficiente para que um AS que suporte ambos os protocolos frequentemente publique conteúdo idêntico ou sobreposto nos dois paths well-known.
- **É o mecanismo de descoberta para praticamente todo endpoint já coberto neste roteiro**: RFC 7009 (`revocation_endpoint`), RFC 7662 (`introspection_endpoint`), RFC 8628 (`device_authorization_endpoint`), RFC 9126 (`pushed_authorization_request_endpoint` + a flag de exigência), RFC 9101 (flags de suporte a Request Object).
- **Complementa diretamente RFC 7591/7592 (próximos dois capítulos)** — um client que descobre as capacidades do AS via 8414 pode se registrar dinamicamente de forma informada: por exemplo, só pedir `token_endpoint_auth_method: "private_key_jwt"` se `token_endpoint_auth_methods_supported` de fato listar esse valor, evitando um registro fadado a falhar depois na hora de autenticar no `/token`.
- **Conecta diretamente com a preocupação de mix-up attack da RFC 9700** através da validação do `issuer` — este capítulo cobre o mecanismo (o campo, a comparação de string); o capítulo da 9700 cobre o *raciocínio de ameaça* mais amplo por trás dessa exigência.
- **RFC 9449 (DPoP)**, tratada mais adiante no roteiro, estende o vocabulário de metadata com `dpop_signing_alg_values_supported` — mais um exemplo do documento crescendo organicamente sem exigir revisão da 8414 original.

## 7. O que mudou desde a publicação (2018)

- A especificação em si é estável e hoje **essencialmente universal** — praticamente todo Authorization Server de produção séria publica esse documento; deixou de ser um "extra opcional" e virou expectativa de baseline mínima de qualquer integração OAuth nova.
- O conjunto de campos que o documento pode descrever cresceu organicamente conforme cada RFC companheira foi publicada (PAR em 2021, e mais adiante DPoP) — o mecanismo de extensibilidade via registro IANA (§4.1) permitiu essa evolução sem precisar de um novo padrão de descoberta a cada nova capacidade adicionada ao ecossistema.
- **O ecossistema de bibliotecas cliente amadureceu para "descoberta primeiro" como modo padrão de configuração.** Bibliotecas OAuth/OIDC modernas tipicamente pedem só a URL do `issuer` como entrada de configuração, e resolvem todo o resto (endpoints, algoritmos suportados, chaves) automaticamente a partir do documento de metadata — um padrão de configuração que só se tornou dominante bem depois de 2018, à medida que a adoção da RFC (e da prática equivalente em OIDC) se espalhou.
- Em ambientes de nuvem gerenciados (identity-as-a-service), o documento de metadata frequentemente é o **único artefato de configuração** exposto ao integrador — o provedor nem sempre documenta endpoints individuais em texto livre, esperando que o integrador consuma o JSON diretamente.

> **Nota de laboratório**: implementado em [`rfc7592/`](../../../rfc7592/README.md), [`rfc7523/`](../../../rfc7523/README.md) e [`rfc9449/`](../../../rfc9449/README.md) — nos três, o Authorization Server publica `/.well-known/oauth-authorization-server`, com as URLs montadas dinamicamente a partir do cabeçalho `Host` da própria requisição recebida (o `issuer` sempre bate exatamente com quem está perguntando, seja de dentro da rede interna do projeto — via `oauth7592-as:3301` — ou de fora, via `localhost:3301`). Nos dois últimos labs, o client-demo efetivamente **usa** a metadata descoberta para localizar `registration_endpoint`/`token_endpoint` em tempo de execução, em vez de existir só como documento passivo consultável por curl; o `rfc9449/` também anuncia `dpop_signing_alg_values_supported`. Os demais labs do projeto (`rfc6749/`, `rfc7636/`, `rfc9126/`) continuam sem esse endpoint, usando configuração fora de banda — o contraste entre os dois modos, lado a lado no mesmo projeto, é deliberado.

## Exemplo em Java (JDK 21, sem frameworks)

Os exemplos a seguir usam exclusivamente `java.net.http.HttpClient` (embutido no JDK desde a versão 11) e o utilitário `SimpleJson`, definido no Capítulo 1 (RFC 6749) deste livro, para parse do documento de metadata. Nenhuma biblioteca externa é usada — nem para HTTP, nem para JSON.

### 7.1 Buscar e fazer parse do documento de metadata

```java
import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.time.Duration;
import java.util.Map;

/**
 * Busca o documento de Authorization Server Metadata (RFC 8414) a partir
 * do issuer informado, aplicando a regra de composicao de path da RFC 8615
 * (well-known e inserido ANTES do path do issuer, nao depois).
 */
public class MetadataFetcher {

    private final HttpClient http = HttpClient.newBuilder()
            .connectTimeout(Duration.ofSeconds(5))
            .build();

    /**
     * @param issuer ex.: "https://as.exemplo.com" ou "https://as.exemplo.com/tenant1"
     */
    public Map<String, String> fetchMetadata(String issuer) throws Exception {
        URI issuerUri = URI.create(issuer);
        String origin = issuerUri.getScheme() + "://" + issuerUri.getAuthority();
        String issuerPath = issuerUri.getPath(); // "" ou "/tenant1"

        // Regra RFC 8615 + 8414: .well-known entra ANTES do path do issuer.
        String wellKnownUrl = origin + "/.well-known/oauth-authorization-server" + issuerPath;

        HttpRequest request = HttpRequest.newBuilder()
                .uri(URI.create(wellKnownUrl))
                .header("Accept", "application/json")
                .GET()
                .build();

        HttpResponse<String> response = http.send(request, HttpResponse.BodyHandlers.ofString());

        if (response.statusCode() != 200) {
            // Sem metadata publicada: o integrador decide se cai para
            // configuracao manual ou trata como erro fatal (a RFC nao normatiza).
            throw new IllegalStateException(
                    "Nao foi possivel obter metadata: HTTP " + response.statusCode());
        }

        // SimpleJson.parseFlat assume um objeto JSON "raso" (sem aninhamento) —
        // suficiente para os campos escalares do documento de metadata que
        // este exemplo consome. Arrays como scopes_supported exigiriam um
        // parser mais completo, fora do escopo didatico deste exemplo.
        return SimpleJson.parseFlat(response.body());
    }
}
```

### 7.2 Validar que o `issuer` bate com o host consultado (mitigação de mix-up)

```java
import java.net.URI;
import java.util.Map;

/**
 * Implementa a validacao central de seguranca da RFC 8414 (secao 5 deste
 * capitulo): o campo "issuer" devolvido no corpo DEVE bater exatamente com
 * a URL que foi consultada. Pular esta checagem abre a porta para um
 * ataque de mix-up — o client passaria a confiar em endpoints (token_endpoint,
 * authorization_endpoint) de um Authorization Server diferente do pretendido.
 */
public class IssuerValidator {

    public static void validar(String issuerEsperado, Map<String, String> metadata) {
        String issuerRecebido = metadata.get("issuer");

        if (issuerRecebido == null) {
            // "issuer" e o UNICO campo obrigatorio do documento (RFC 8414 §3.2).
            // A ausencia dele torna o documento inteiro nao confiavel.
            throw new SecurityException("Documento de metadata sem campo 'issuer' obrigatorio");
        }

        // Comparacao exata de string, nao apenas "mesmo host". Um issuer com
        // path (multi-tenant) precisa bater ATE o path, nao so scheme+host.
        // Barra final divergente ja e o suficiente para reprovar (RFC nao
        // define normalizacao implicita de barra final).
        URI esperado = URI.create(issuerEsperado);
        URI recebido = URI.create(issuerRecebido);

        boolean bateSchemeHostPorta =
                esperado.getScheme().equalsIgnoreCase(recebido.getScheme())
                && esperado.getAuthority().equalsIgnoreCase(recebido.getAuthority());
        boolean batePath = normalizarPath(esperado.getPath()).equals(normalizarPath(recebido.getPath()));

        if (!bateSchemeHostPorta || !batePath) {
            throw new SecurityException(
                    "Possivel mix-up attack: issuer esperado='" + issuerEsperado
                    + "' mas documento declara issuer='" + issuerRecebido + "'");
        }
    }

    private static String normalizarPath(String path) {
        if (path == null || path.isEmpty()) return "";
        return path.endsWith("/") ? path.substring(0, path.length() - 1) : path;
    }
}
```

### 7.3 Uso combinado — descoberta seguida de resolução de endpoint

```java
import java.util.Map;

/**
 * Exemplo de uso ponta a ponta: descobre a metadata, valida o issuer, e so
 * entao resolve o token_endpoint a partir do documento — em vez de ter essa
 * URL hardcoded na configuracao do client. E este o padrao "descoberta
 * primeiro" que o ecossistema de bibliotecas OAuth adotou como default
 * (secao 7 deste capitulo).
 */
public class DescobertaExemplo {

    public static void main(String[] args) throws Exception {
        String issuer = "http://localhost:3301"; // igual ao lab rfc7592/

        MetadataFetcher fetcher = new MetadataFetcher();
        Map<String, String> metadata = fetcher.fetchMetadata(issuer);

        IssuerValidator.validar(issuer, metadata);

        String tokenEndpoint = metadata.get("token_endpoint");
        String registrationEndpoint = metadata.get("registration_endpoint");

        if (tokenEndpoint == null) {
            throw new IllegalStateException("AS nao anuncia token_endpoint — integracao impossivel");
        }

        System.out.println("issuer confirmado: " + metadata.get("issuer"));
        System.out.println("token_endpoint descoberto: " + tokenEndpoint);
```
