# RFC 7592 — OAuth 2.0 Dynamic Client Registration Management Protocol

## 1. Contexto e motivação

A RFC 7591, tratada no capítulo anterior, resolve exatamente um problema: como criar um registro de client dinamicamente, via API, em vez de fora de banda. Mas criação é só o primeiro momento do ciclo de vida de qualquer entidade que persiste — depois de criado, um registro de client inevitavelmente precisa ser **lido** (para exibir num painel de administração, por exemplo), **atualizado** (o `redirect_uri` mudou porque o app migrou de domínio; é hora de rotacionar o `client_secret` por política; um novo `grant_type` precisa ser habilitado) e, eventualmente, **apagado** (o client foi descomissionado e não deve mais existir).

A RFC 7591, sozinha, não define nenhuma dessas três operações — ela devolve `registration_access_token` e `registration_client_uri` na resposta de criação, mas não especifica formalmente o que fazer com eles depois. É exatamente essa lacuna que a **RFC 7592** fecha, publicada **na mesma data** que a 7591 (ambas de julho de 2015) — não por coincidência: as duas foram desenhadas em conjunto como duas metades de um único ciclo de vida, apenas divididas em documentos separados por conveniência de escopo e para permitir que uma implantação suporte só criação (7591) sem necessariamente suportar gerenciamento self-service ao vivo (7592), se assim preferir.

Cenários concretos que motivam esta RFC, além dos já citados:

- **Migração de infraestrutura do lado do client.** Um app migra de domínio ou reestrutura suas rotas de callback; sem um mecanismo de atualização padronizado, a única saída seria abrir um novo registro do zero e desativar o antigo manualmente — perdendo a continuidade de `client_id` que outros sistemas (logs, auditoria, integrações downstream) podem depender.
- **Portais self-service de gerenciamento.** Uma organização que já oferece registro dinâmico (7591) naturalmente quer, no mesmo portal, permitir que o próprio integrador veja e edite a configuração do client que criou — sem depender de suporte técnico para cada ajuste pequeno.
- **Baixa formal de um client descomissionado.** Deixar tokens simplesmente expirarem sozinhos não é o mesmo que dar baixa formal no registro: um client apagado explicitamente não pode mais, por exemplo, ser usado para *criar novos* tokens via `client_credentials` ou `authorization_code`, mesmo que algum token antigo ainda não tenha expirado (ver §5 sobre a relação, não automática, entre apagar o registro e revogar tokens já emitidos).

## 2. Terminologia e papéis

A RFC 7592 não introduz nenhum papel novo, nem nenhum conceito genuinamente novo em termos de vocabulário — ela reaproveita integralmente o que a RFC 7591 já definiu: `registration_access_token` (a credencial) e `registration_client_uri` (a localização), ambos devolvidos exclusivamente na resposta de criação da 7591, são exatamente a credencial e a URL que esta RFC usa para todas as operações subsequentes sobre aquele registro específico.

Vale destacar uma distinção estrutural importante entre os dois documentos de metadata envolvidos neste ecossistema:

- **`registration_endpoint`** (RFC 7591) é uma capacidade **geral** do Authorization Server — um único endpoint, o mesmo para qualquer client que queira se registrar, descoberto genericamente via RFC 8414.
- **`registration_client_uri`** (RFC 7592) é **específico por instância de client** — uma URL diferente para cada registro individual, que só existe (e só é conhecida) depois que aquele client específico foi criado. Não há, nem poderia haver, um campo de metadata RFC 8414 genérico apontando para "o" `registration_client_uri`, porque não existe um único — existe um por client.

Essa distinção é o motivo pelo qual a RFC 7592 não aparece na lista de campos descobertos via `/.well-known/oauth-authorization-server` (capítulo da RFC 8414) — não é uma omissão, é uma consequência necessária da própria natureza da informação.

## 3. Fluxo — três operações sobre `registration_client_uri`

Todas as três operações são autenticadas exclusivamente por `Authorization: Bearer <registration_access_token>` — não há outro mecanismo de autenticação previsto pela RFC para este conjunto de endpoints (nem `client_secret_basic`, nem mTLS específico deste protocolo; o token bearer é, deliberadamente, a única credencial reconhecida aqui).

### 3.1 Leitura (`GET`)

```
GET /register/s6BhdRkqt3 HTTP/1.1
Authorization: Bearer reg-23410913-abewfq.123483

HTTP/1.1 200 OK
Content-Type: application/json

{
  "client_id": "s6BhdRkqt3",
  "client_id_issued_at": 2893256800,
  "redirect_uris": ["https://client.exemplo.org/callback"],
  "client_name": "Meu App",
  "grant_types": ["authorization_code", "refresh_token"],
  "response_types": ["code"],
  "token_endpoint_auth_method": "client_secret_basic",
  "scope": "profile email",
  "registration_client_uri": "https://as.exemplo.com/register/s6BhdRkqt3",
  "registration_access_token": "reg-23410913-abewfq.123483"
}
```

Um detalhe de segurança relevante que a especificação deixa implícito, mas que toda implementação séria observa na prática: a resposta do `GET` **omite o `client_secret`**. O segredo foi devolvido uma única vez, no momento da criação (RFC 7591); a partir daí, nenhuma consulta subsequente o revela de novo — mesmo para o dono legítimo do `registration_access_token`. Se o `client_secret` for perdido, a única saída é rotacioná-lo via `PUT` (§3.2), não recuperá-lo via `GET`.

### 3.2 Atualização (`PUT` — substituição completa, não patch parcial)

```
PUT /register/s6BhdRkqt3 HTTP/1.1
Authorization: Bearer reg-23410913-abewfq.123483
Content-Type: application/json

{
  "client_id": "s6BhdRkqt3",
  "redirect_uris": ["https://client.exemplo.org/novo-callback"],
  "client_name": "Meu App",
  "grant_types": ["authorization_code", "refresh_token"],
  "response_types": ["code"],
  "token_endpoint_auth_method": "client_secret_basic",
  "scope": "profile email"
}

HTTP/1.1 200 OK
Content-Type: application/json

{
  "client_id": "s6BhdRkqt3",
  "redirect_uris": ["https://client.exemplo.org/novo-callback"],
  "client_name": "Meu App",
  "grant_types": ["authorization_code", "refresh_token"],
  "response_types": ["code"],
  "token_endpoint_auth_method": "client_secret_basic",
  "scope": "profile email",
  "registration_access_token": "reg-NOVO-token-98765.abcdef",
  "registration_client_uri": "https://as.exemplo.com/register/s6BhdRkqt3"
}
```

O ponto normativo mais importante — e o que mais gera confusão prática — é que a semântica do `PUT` aqui é **substituição completa do recurso**, no sentido HTTP mais estrito do verbo, e não um `PATCH` parcial. Isso significa que o client precisa reenviar **toda** a metadata que deseja manter, não apenas o campo que mudou. Um corpo de `PUT` que omite `token_endpoint_auth_method` não significa "não altere esse campo" — na prática (dependendo de como a implantação trata omissão), pode significar "reverta para o default", ou ser rejeitado como metadata incompleta. A responsabilidade de recuperar o estado atual completo (via `GET` prévio) e só então editar o campo desejado antes de reenviar tudo é do client — a RFC não protege contra um `PUT` malfeito que apaga configuração por omissão acidental (ver §5).

O segundo ponto normativo relevante: a resposta a um `PUT` bem-sucedido **pode** vir com um `registration_access_token` **novo**, diferente do que foi usado na própria requisição. Isso não é um bug nem uma coincidência — é uma opção explícita de design da RFC (§2.2): o AS pode rotacionar essa credencial a cada atualização, como defesa em profundidade. Se isso acontecer, o client **precisa** passar a usar o token novo a partir daquele momento — o token antigo deixa de ser válido para chamadas futuras.

### 3.3 Exclusão (`DELETE`)

```
DELETE /register/s6BhdRkqt3 HTTP/1.1
Authorization: Bearer reg-23410913-abewfq.123483

HTTP/1.1 204 No Content
```

Sem corpo de resposta. O código `204 No Content` confirma que o registro foi removido; chamadas subsequentes de `GET`/`PUT`/`DELETE` para o mesmo `registration_client_uri` devem, a partir daí, responder com algo equivalente a "não encontrado" ou "não autorizado" (a RFC não prescreve qual dos dois exatamente — implementações variam entre `401`/`403` e `404`, cada escolha com uma implicação de information disclosure ligeiramente diferente).

## 4. Parâmetros e endpoints normativos

- **Não há um endpoint genérico novo anunciado no documento de metadata da RFC 8414** — como discutido em §2, `registration_client_uri` é específico por client, não uma capacidade geral e uniforme do AS.
- **Métodos HTTP**: `GET` (ler o estado atual), `PUT` (atualizar — substituição completa), `DELETE` (apagar permanentemente). Não há `POST` neste conjunto de endpoints (criação já aconteceu via RFC 7591) nem `PATCH` (a RFC não define atualização parcial como alternativa ao `PUT`).
- **Autenticação**: exclusivamente `Bearer <registration_access_token>` em toda chamada, sem exceção — inclusive no `GET`, que muita gente presume (erroneamente) ser "só leitura, menos sensível". Não é: ler a configuração completa de um client (redirect_uris, scopes, métodos de auth) já é, em si, informação sensível o bastante para exigir a mesma credencial das operações destrutivas.
- **Códigos de status relevantes**: `200 OK` (GET e PUT bem-sucedidos, ambos com corpo), `204 No Content` (DELETE bem-sucedido, sem corpo), `401 Unauthorized` (token ausente ou inválido), `403 Forbidden` (token válido mas sem permissão sobre este registro específico — situação que, na prática, um AS bem implementado tende a tratar de forma indistinguível de "não encontrado", para não vazar a existência de um `client_id` a quem não deveria sabê-la).

## 5. Segurança já tratada na própria RFC 7592

- **O `registration_access_token` é uma credencial de altíssimo valor — arguivelmente mais sensível que o próprio `client_secret`.** Quem o possui pode ler a configuração completa do client (incluindo, potencialmente, ver que um `client_secret` existe e quando expira — ainda que não seu valor), **modificar** `redirect_uris` (o que efetivamente redireciona, do ponto de vista do AS, para onde ele está disposto a entregar authorization codes e tokens em nome desse client) e **apagar** o registro inteiro. A RFC é explícita: essa credencial merece proteção pelo menos equivalente à de um `client_secret`; alguns argumentam que merece proteção *maior*, porque o dano de um vazamento não se limita a personificar o client numa troca de token — permite reconfigurar silenciosamente o comportamento do client do ponto de vista do AS, ou eliminá-lo de vez.
- **A semântica de substituição completa do `PUT` é, na prática, um risco operacional tão relevante quanto qualquer risco puramente criptográfico.** Como não existe um `PATCH` parcial, um client que reenvia um objeto de metadata incompleto — por exemplo, esquecendo de incluir um `redirect_uri` secundário que ainda está em uso ativo em outro ambiente — corre o risco real de **apagar silenciosamente** configuração de segurança já existente: resetar `token_endpoint_auth_method` para um valor default menos restritivo, ou perder uma entrada válida de `redirect_uris` sem qualquer aviso ou confirmação. A mitigação prática (não normativa, mas amplamente recomendada) é sempre fazer um `GET` imediatamente antes de qualquer `PUT`, editar o objeto completo recebido, e só então reenviá-lo — nunca construir o corpo do `PUT` "do zero" a partir de memória do que se pretendia originalmente.
- **Apagar o registro do client não garante, por si só, que tokens já emitidos parem de funcionar.** Este é um ponto de nuance frequentemente mal-entendido: `DELETE /register/{id}` remove o **registro** (a entidade "client" no armazenamento do AS) — mas access tokens e refresh tokens já emitidos anteriormente para aquele client podem, dependendo estritamente de como a implementação do AS foi construída, continuar tecnicamente válidos até expirarem naturalmente, a menos que o AS explicitamente encadeie a exclusão do registro com uma revogação em massa dos tokens associados (RFC 7009). A RFC 7592 não exige esse encadeamento — é uma prática recomendada de implementação madura, não uma obrigação normativa do protocolo. Um AS que queira uma baixa verdadeiramente completa precisa implementar essa ligação deliberadamente.
- **A rotação do `registration_access_token` a cada `PUT` é uma defesa em profundidade opcional**, seguindo o mesmo princípio já visto para refresh tokens no capítulo da RFC 6749/RFC 9700: mesmo que o token antigo tenha vazado em algum momento entre duas atualizações, rotacioná-lo a cada `PUT` limita a janela de validade útil de uma credencial comprometida sem exigir nenhuma ação extra do lado do client (além de, claro, passar a usar o valor novo devolvido).
- **Enumeração de `client_id` via tentativa-e-erro é uma preocupação lateral, mas real.** Como `registration_client_uri` inclui o `client_id` na própria URL (`/register/{clientId}`), um AS que responda de forma diferenciável a "client_id existe mas token errado" (`403`) versus "client_id não existe" (`404`) está, ainda que sutilmente, vazando quais `client_id`s são válidos a quem tenta adivinhar. Implementações cuidadosas tendem a normalizar essa resposta.

## 6. Relação com outras RFCs

- **Companheira direta e indissociável da RFC 7591** (capítulo anterior deste livro) — a 7591 cria, a 7592 gerencia, usando exatamente as credenciais que a 7591 já devolve na resposta de criação. Foram publicadas juntas precisamente por serem as duas metades inseparáveis de um único ciclo de vida de registro.
- **Conecta diretamente com a RFC 7009 (Token Revocation)**, tratada em capítulo anterior deste roteiro: apagar um registro de client deveria, por política de implementação madura (não por exigência normativa formal entre os dois protocolos), levar à revogação em cadeia de qualquer token pendente daquele client. São problemas adjacentes mas distintos — revogar um **token** individual versus dar baixa formal num **client** inteiro — e uma implantação bem projetada tipicamente trata a segunda ação como gatilho para a primeira, mesmo que os textos normativos de ambas as RFCs não exijam essa ligação explicitamente.
- **O `registration_access_token` em si é, funcionalmente, um bearer token nos termos exatos da RFC 6750** — as mesmas considerações de transporte seguro, de não vazamento em logs, de proteção equivalente a qualquer outra credencial de portador se aplicam integralmente, ainda que o propósito específico desse token (gerenciar um registro, não acessar um recurso protegido) seja exclusivo deste par de RFCs.
- **Diferente de `registration_endpoint`, `registration_client_uri` não é descoberto genericamente via RFC 8414** — como já discutido em §2, é inerentemente específico por instância de client, incompatível com a natureza de "capacidade geral do AS" que o documento de metadata descreve.

## 7. O que mudou desde a publicação (2015)

- Publicada junto com a RFC 7591, manteve-se igualmente estável ao longo dos anos; sua taxa de adoção acompanha de perto a da 7591 — onde há criação dinâmica de clients, o gerenciamento via 7592 é o complemento natural e esperado, embora nem toda implantação escolha suportar as duas simetricamente.
- É comum, na prática, encontrar implantações que suportam **só** a criação (7591) e tratam atualização/exclusão como um processo administrativo fora de banda (um humano intervindo diretamente no armazenamento, ou um processo de suporte) — nesses casos, o gerenciamento self-service ao vivo previsto pela 7592 é tratado como *hardening opcional*, não como requisito obrigatório de toda integração dinâmica. Isso reflete, em parte, a superfície de risco adicional que expor gerenciamento ao vivo introduz (§5) — algumas organizações preferem deliberadamente manter esse controle mais próximo, mesmo tendo adotado registro dinâmico para a criação.
- Sem mudança significativa de uso desde a publicação — continua sendo uma peça relativamente nicho do ecossistema OAuth (comparada à onipresença de RFC 6749 ou mesmo de PKCE), mas estável e bem definida, mais visível em contextos de federação e portais self-service corporativos, sempre lado a lado com a 7591.

> **Nota de laboratório**: implementado em [`rfc7592/`](../../../rfc7592/README.md) — o Authorization Server expõe `GET`/`PUT`/`DELETE` em `/register/:clientId`, todos autenticados pelo `registration_access_token` recebido na criação (RFC 7591). O `GET` omite deliberadamente o `client_secret` da resposta, exatamente como discutido em §3.1; o `PUT` rotaciona o `registration_access_token` a cada chamada bem-sucedida, exatamente como discutido em §3.2 e §5. No client-demo, o próprio ato de registro é uma **ação manual do usuário** ("Registrar client agora" na home) — nenhuma outra funcionalidade (login, chamadas machine-to-machine, ou a própria seção de gerenciamento) fica disponível até essa ação ser concluída. Uma vez registrado, a home exibe a seção "Gerenciar registro" com três ações espelhando exatamente os três verbos desta RFC: "Consultar (GET)" mostra a metadata atual (sem o segredo); "Atualizar (PUT)" reenvia a metadata completa com um `client_name` alterado e exibe o `registration_access_token` recém-rotacionado na resposta; "Apagar (DELETE)" remove o registro e devolve a aplicação inteira ao estado "não registrado" — exigindo um novo registro manual do zero. Um teste didático sugerido pelo próprio README do lab: executar "Apagar (DELETE)" e, em seguida, tentar "Executar chamada machine-to-machine" — o `/token` responde com `invalid_client`, demonstrando concretamente que apagar o registro efetivamente invalida o client para **novas** emissões de token (ainda que, como discutido em §5, isso não seja garantia automática de que tokens antigos já emitidos parem de funcionar por si só).

## Exemplo em Java (JDK 21, sem frameworks)

Os exemplos usam `java.net.http.HttpClient` e o utilitário `SimpleJson` (`SimpleJson.object(Map)`/`SimpleJson.parseFlat(String)`), definido no Capítulo 1 (RFC 6749) deste livro. Todas as chamadas carregam `Authorization: Bearer <registration_access_token>` — não há outro método de autenticação previsto por esta RFC.

### 7.1 Consultar o registro atual (`GET`)

```java
import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.util.Map;

/**
 * Cliente de gerenciamento de registro (RFC 7592). Todas as operacoes usam
 * o registration_client_uri especifico deste client (devolvido apenas na
 * criacao via RFC 7591) e sao autenticadas com o registration_access_token
 * correspondente — nunca com client_secret_basic ou qualquer outro metodo
 * de autenticacao de client usado no /token.
 */
public class RegistrationManagementClient {

    private final HttpClient http = HttpClient.newHttpClient();

    /**
     * GET: le a configuracao atual do client. Repare que o client_secret
     * NUNCA volta aqui — foi devolvido uma unica vez, na criacao (RFC 7591).
     * Se foi perdido, a unica saida e rotacionar via PUT, nao recuperar via GET.
     */
    public Map<String, String> consultar(String registrationClientUri, String registrationAccessToken)
            throws Exception {
        HttpRequest request = HttpRequest.newBuilder()
                .uri(URI.create(registrationClientUri))
                .header("Authorization", "Bearer " + registrationAccessToken)
                .header("Accept", "application/json")
                .GET()
                .build();

        HttpResponse<String> response = http.send(request, HttpResponse.BodyHandlers.ofString());

        if (response.statusCode() != 200) {
            throw new IllegalStateException(
                    "Consulta ao registro falhou: HTTP " + response.statusCode());
        }
        return SimpleJson.parseFlat(response.body());
    }
}
```

### 7.2 Atualizar o registro (`PUT` — substituição completa, nunca patch)

```java
import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.net.http.HttpRequest.BodyPublishers;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class RegistrationUpdater {

    private final HttpClient http = HttpClient.newHttpClient();

    /**
     * PUT: ATENCAO — este e um replace completo do recurso, nao um PATCH
     * parcial (secao 3.2 deste capitulo). O corpo precisa conter TODA a
     * metadata que se deseja manter, nao so o campo alterado. Por isso este
     * metodo exige que o chamador passe a configuracao atual completa (tipicamente
     * obtida via um GET imediatamente anterior) e so entao aplica a mudanca
     * desejada em cima dela — nunca construa o corpo do zero.
     */
    public Map<String, String> atualizar(
            String registrationClientUri,
            String registrationAccessToken,
            Map<String, String> configuracaoAtualCompleta,
            String novoRedirectUri) throws Exception {

        // Parte da config JA EXISTENTE (obtida via GET previo) e so altera
        // o campo desejado — nunca monta um objeto novo do zero, sob risco
        // de apagar silenciosamente campos que nao foram tocados aqui.
        Map<String, Object> corpo = new LinkedHashMap<>();
        corpo.put("client_id", configuracaoAtualCompleta.get("client_id"));
        corpo.put("redirect_uris", List.of(novoRedirectUri));
        corpo.put("client_name", configuracaoAtualCompleta.get("client_name"));
        corpo.put("grant_types", List.of("authorization_code", "refresh_token"));
        corpo.put("response_types", List.of("code"));
        corpo.put("token_endpoint_auth_method", configuracaoAtualCompleta.get("token_endpoint_auth_method"));
        corpo.put("scope", configuracaoAtualCompleta.get("scope"));

        String corpoJson = SimpleJson.object(corpo);

        HttpRequest request = HttpRequest.newBuilder()
                .uri(URI.create(registrationClientUri))
                .header("Authorization", "Bearer " + registrationAccessToken)
                .header("Content-Type", "application/json")
                .PUT(BodyPublishers.ofString(corpoJson))
                .build();

        HttpResponse<String> response = http.send(request, HttpResponse.BodyHandlers.ofString());

        if (response.statusCode() != 200) {
            throw new IllegalStateException(
                    "Atualizacao do registro falhou: HTTP " + response.statusCode());
        }

        Map<String, String> resposta = SimpleJson.parseFlat(response.body());

        // PONTO CRITICO: o AS pode rotacionar o registration_access_token a
        // cada PUT bem-sucedido (secao 3.2 / 5 deste capitulo — comportamento
        // efetivamente usado pelo lab rfc7592/). O token usado NESTA chamada
        // pode ja nao servir para a PROXIMA — o chamador precisa persistir
        // o valor novo antes de fazer qualquer outra operacao.
        String tokenRotacionado = resposta.get("registration_access_token");
        if (tokenRotacionado != null && !tokenRotacionado.equals(registrationAccessToken)) {
            System.out.println("registration_access_token foi rotacionado — atualize o valor armazenado");
        }

        return resposta;
    }
}
```

### 7.3 Apagar o registro (`DELETE`)

```java
import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;

public class RegistrationDeleter {

    private final HttpClient http = HttpClient.newHttpClient();

    /**
     * DELETE: remove permanentemente o registro. Resposta esperada e 204 sem
     * corpo. IMPORTANTE (secao 5 deste capitulo): isto NAO garante, por si
     * so, que tokens ja emitidos para este client parem de funcionar — a
     * menos que o Authorization Server encadeie explicitamente uma revogacao
     * em massa (RFC 7009) a este DELETE. E uma pratica recomendada de
     * implementacao, nao uma obrigacao normativa da RFC 7592.
     */
    public void apagar(String registrationClientUri, String registrationAccessToken) throws Exception {
        HttpRequest request = HttpRequest.newBuilder()
                .uri(URI.create(registrationClientUri))
                .header("Authorization", "Bearer " + registrationAccessToken)
                .DELETE()
                .build();

        HttpResponse<String> response = http.send(request, HttpResponse.BodyHandlers.ofString());

        if (response.statusCode() != 204) {
            throw new IllegalStateException(
                    "Exclusao do registro falhou: HTTP " + response.statusCode());
        }
        // Sem corpo a processar. A partir daqui, este client_id deixa de ser
        // aceito no /token para NOVAS emissoes (invalid_client), replicando
        // o comportamento observavel no lab rfc7592/.
    }
}
```

### 7.4 Uso combinado — ciclo de vida completo

```java
import java.util.Map;

/**
 * Demonstra o ciclo de vida completo de gerenciamento sobre um registro ja
 * existente (criado previamente via RFC 7591, capitulo anterior): consulta,
 * atualizacao com rotacao de credencial, e exclusao final.
 */
public class CicloDeVidaExemplo {
    public static void main(String[] args) throws Exception {
        // Valores tipicamente obtidos da resposta de criacao (RFC 7591) e
        // persistidos pelo client — aqui hardcoded so para fins didaticos.
        String registrationClientUri = "http://localhost:3301/register/abcdef0123456789";
        String registrationAccessToken = "reg-token-inicial-devolvido-na-criacao";

        var gerenciador = new RegistrationManagementClient();
        Map<String, String> atual = gerenciador.consultar(registrationClientUri, registrationAccessToken);
        System.out.println("Configuracao atual: " + atual);
        // Note: atual.get("client_secret") sera sempre null aqui — o GET
        // nunca devolve o segredo de volta (secao 3.1 deste capitulo).

        var atualizador = new RegistrationUpdater();
        Map<String, String> resposta = atualizador.atualizar(
                registrationClientUri,
                registrationAccessToken,
                atual,
                "http://localhost:3300/novo-callback");

        // A partir daqui, o token de gerenciamento pode ter mudado —
        // sempre use o valor mais recente devolvido pela ultima chamada.
        String tokenAtual = resposta.getOrDefault("registration_access_token", registrationAccessToken);

        var removedor = new RegistrationDeleter();
        removedor.apagar(registrationClientUri, tokenAtual);
        System.out.println("Registro apagado — client nao pode mais obter novos tokens");
    }
}
```
