# RFC 9396 — OAuth 2.0 Rich Authorization Requests (RAR)

## 1. Contexto e motivação

O `scope` tradicional (RFC 6749) é uma lista simples de identificadores string, separados por espaço (`profile email accounts:read`). Esse modelo funciona bem para permissões grosseiras e relativamente estáveis — "este client pode ler perfil", "este client pode ler saldo de conta" — mas quebra estruturalmente quando a autorização precisa ser **fina, estruturada e específica de uma transação**. O exemplo canônico, direto do seu contexto FSI: "autorizar um pagamento de exatamente EUR 50,00 para esta conta específica, só desta vez, não um pagamento de qualquer valor para qualquer conta". Não existe forma razoável de expressar isso como uma string de scope solta — mesmo tentativas criativas (`payments:initiate:eur:50.00:BR00...`) esbarram rapidamente em limites práticos: strings de scope não têm gramática, não têm tipos, não têm validação estrutural, e crescem sem limite conforme mais dimensões precisam ser codificadas (moeda, valor, conta, data-limite, finalidade).

Na prática, ecossistemas regulados de Open Banking (UK Open Banking, Berlin Group NextGenPSD2, e outros) **precisaram** resolver esse problema antes desta RFC existir — a pressão regulatória para "iniciação de pagamento com consentimento granular" não esperou o IETF. O resultado foi que cada ecossistema inventou sua própria codificação ad-hoc, tipicamente:

- Espremendo dados estruturados dentro do próprio nome do scope (frágil, difícil de parsear com segurança, limites de tamanho de string HTTP);
- Ou transportando um objeto de "detalhes do consentimento" fora do fluxo OAuth padrão, por um canal proprietário paralelo (quebrando a portabilidade entre AS de fornecedores diferentes, e forçando cada client a implementar integração específica por país/ecossistema).

Ambas as abordagens são incompatíveis entre si, difíceis de validar de forma genérica, e sem nenhum padrão comum entre implementações — exatamente o tipo de fragmentação que uma especificação IETF existe para resolver.

A RFC 9396 resolve isso introduzindo um parâmetro novo, **`authorization_details`**, carregando um **array JSON de objetos estruturados** — cada um descrevendo uma autorização específica, com campos arbitrários próprios do tipo de autorização em questão, mas com uma pequena moldura comum reutilizável entre tipos.

### Por que um array, e não um objeto único?

O uso de um **array** (em vez de um único objeto de detalhe) permite que uma única requisição de autorização carregue múltiplas autorizações independentes ao mesmo tempo — por exemplo, "iniciar este pagamento de EUR 50" **e** "ler o extrato dos últimos 90 dias", como dois objetos distintos no mesmo array, cada um com seu próprio `type` e seus próprios campos. Isso evita ter que inventar um esquema artificial de "múltiplos tipos misturados dentro de um objeto só" e mantém cada autorização estruturalmente isolada e independentemente validável.

## 2. Terminologia e papéis

Nenhum papel novo. Introduz:

- **`authorization_details`** — parâmetro novo, utilizável tanto na authorization request quanto (em certos fluxos, como Client Credentials) diretamente na token request. Valor: array JSON de "objetos de detalhe de autorização".
- **Objeto de detalhe de autorização** — cada elemento do array tem:
  - **`type`** (obrigatório) — string que identifica a semântica daquele objeto específico (ex.: `"payment_initiation"`). Crucialmente, **a RFC 9396 não padroniza nenhum valor genérico de `type`** — ela define só a moldura (o "envelope"). Cada ecossistema, perfil regulatório ou implantação específica é quem define seus próprios tipos e o significado de cada campo associado (o Berlin Group, por exemplo, define seus próprios tipos para iniciação de pagamento europeia; um AS interno de um banco brasileiro definiria os seus, adaptados a PIX/TED/boleto).
  - **Campos específicos do tipo** — arbitrários, definidos por quem especifica aquele `type` (no exemplo de pagamento: `instructedAmount`, `creditorAccount`, etc.).
  - **Campos comuns opcionais, reutilizáveis por qualquer tipo** (a RFC os define para promover alguma interoperabilidade mínima entre tipos diferentes):
    - `locations` — quais resource servers este objeto de detalhe se destina; mesmo espírito do parâmetro `resource` da RFC 8707 (capítulo anterior), só que aplicado por **objeto de detalhe individual**, não pelo token inteiro.
    - `actions` — quais ações são autorizadas (ex.: `["initiate"]`, `["read"]`).
    - `datatypes` — quais tipos de dado estão em jogo (útil sobretudo para autorizações de leitura, ex.: `["balances", "transactions"]`).
    - `identifier` — um identificador de uma instância específica de recurso (ex.: o ID de uma conta específica).
    - `privileges` — um refinamento adicional de nível de privilégio dentro daquele tipo.

### `authorization_details` coexiste com `scope`?

Sim — a RFC não deprecia `scope`. Uma requisição pode carregar `scope` (para autorizações grosseiras e estáveis, como "acesso ao perfil") **e** `authorization_details` (para a parte fina e específica de transação, como o pagamento) simultaneamente. Cabe a cada implantação decidir como as duas se combinam na tela de consentimento e na avaliação de política do AS — a RFC não define uma regra universal de precedência entre os dois.

## 3. Fluxo

Não é um grant novo — é um parâmetro adicional que se encaixa no fluxo já existente (tipicamente Authorization Code, mas nada impede uso em outros grants onde fizer sentido, como Client Credentials para autorizações machine-to-machine estruturadas):

```
GET /authorize?response_type=code&client_id=...
  &authorization_details=[{
    "type": "payment_initiation",
    "actions": ["initiate"],
    "locations": ["https://api.banco.exemplo.com/pagamentos"],
    "instructedAmount": {"currency": "BRL", "amount": "120.00"},
    "creditorAccount": {"iban": "BR00000000000000000000000"}
  }]

AS mostra uma tela de consentimento refletindo ESSE detalhe especifico —
nao um scope generico "payments", literalmente algo como
"autorizar pagamento de BRL 120,00 para esta conta especifica"

Usuario aprova -> AS emite o token, ecoando authorization_details
(possivelmente REDUZIDO em relacao ao pedido original) na resposta
do /token, para o client confirmar exatamente o que foi concedido
```

### Por que o AS pode "reduzir" o que foi pedido, e por que isso importa

Um ponto normativo central, fácil de subestimar: o AS **não é obrigado** a conceder exatamente o que foi pedido em `authorization_details`. Ele pode reduzir (por exemplo, se o usuário aprovar um valor menor numa tela de consentimento interativa, ou se uma política do AS limitar o valor máximo por transação de um certo tipo de client). A resposta do `/token` **ecoa o que foi efetivamente concedido**, não uma confirmação vazia de "ok, aceito o que você pediu". Isso é uma mudança de disciplina importante em relação ao `scope` tradicional, onde muitas implementações históricas simplesmente devolviam o mesmo `scope` pedido sem necessariamente confirmar explicitamente o que foi de fato concedido caso a caso.

Isso implica uma responsabilidade adicional para o client: **ele deve inspecionar o `authorization_details` devolvido na resposta do token, não assumir cegamente que recebeu exatamente o que pediu**. Um client bem implementado que pediu autorização para EUR 100 e recebeu de volta uma autorização reduzida para EUR 50 precisa tratar essa diferença explicitamente (por exemplo, informando o usuário, ou abortando a operação se a redução tornar a transação sem sentido).

### Caso de borda: `authorization_details` inválido ou tipo desconhecido

Se o AS não reconhece um `type` pedido (não está em sua lista de tipos suportados — descoberta via `authorization_details_types_supported`, RFC 8414), a RFC espera que o AS rejeite a requisição com um erro apropriado, em vez de silenciosamente ignorar aquele objeto de detalhe específico e prosseguir sem ele — silenciosamente descartar autorização pedida seria uma falha de segurança "silenciosa" (o client acredita que pediu algo e recebeu confirmação implícita, quando na verdade não recebeu nada).

### Caso de borda: token de recurso único vs. múltiplos `locations`

Assim como o `resource` da RFC 8707 pode gerar um token multi-audience, um único objeto de `authorization_details` pode ter `locations` com múltiplos resource servers. A mesma tensão entre "um token poderoso falando com vários RSs" e "tokens mais restritos, um por RS" se aplica aqui, e a decisão de política cabe à implantação — a RFC não resolve essa tensão de forma universal, só fornece o vocabulário.

## 4. Parâmetros e endpoints normativos

Nenhum endpoint novo — estende tanto a authorization request quanto a token request/response existentes.

- **`authorization_details`** (pedido): array de objetos, cada um com `type` obrigatório + campos específicos do tipo + campos comuns opcionais (`locations`, `actions`, `datatypes`, `identifier`, `privileges`).
- **`authorization_details`** (resposta do `/token`): também devolvido, ecoando exatamente (ou de forma reduzida — ver seção 3) o que foi efetivamente concedido — não apenas um scope aproximado ou uma confirmação vazia.
- **Descoberta via RFC 8414**: `authorization_details_types_supported`, listando quais valores de `type` aquele AS especificamente entende e sabe processar. Um client que pretende usar RAR deve, em princípio, checar esse campo de descoberta antes de assumir que um `type` específico será aceito por um AS desconhecido.
- **Introspecção (RFC 7662)**: uma resposta de introspecção de um token vinculado a `authorization_details` também deve expor esse campo, permitindo que um resource server (ou um AS diferente, num cenário de token exchange) veja exatamente qual autorização estruturada aquele token carrega — não só um `scope` genérico.

## 5. Segurança já tratada na própria RFC 9396

### Telas de consentimento muito mais precisas

O ganho mais imediato e tangível: o usuário vê, na tela de consentimento, algo como "autorizar pagamento de BRL 120,00 para esta conta específica", em vez de um scope opaco tipo `payments:write` que não comunica nada sobre o valor ou destinatário real da transação. Isso conecta diretamente com a preocupação de consentimento informado (e o risco de phishing por consentimento genérico demais) já discutida no capítulo da RFC 6819 — um usuário que aprova "acesso a pagamentos" de forma genérica está, na prática, dando um cheque em branco; um usuário que aprova "pagar BRL 120 para esta conta" está aprovando algo que pode efetivamente entender e conferir.

### O AS deve validar e pode reduzir — nunca aceitar cegamente

Mesma disciplina já vista com `scope` (RFC 6749/6750) e com `resource` (RFC 8707, capítulo anterior): o AS nunca deve aceitar cegamente o que o client pede em `authorization_details` — precisa validar contra a política daquele client, daquele usuário, e daquele tipo de autorização, podendo reduzir o que é efetivamente concedido (seção 3).

### O último degrau de uma escada de least privilege

É importante enxergar RAR não como uma peça isolada, mas como o **último degrau de uma escada de granularidade** que este roteiro percorreu inteiro:

1. **Escopo amplo** (RFC 6749) — o mecanismo básico de "o que este client pode fazer", frequentemente grosseiro na prática (`read`, `write`).
2. **Escopo mínimo por convenção** (RFC 6750 e a prática de least privilege discutida desde então) — disciplina de nomear e conceder scopes o mais estreitos possível, mas ainda por convenção, não por garantia estrutural.
3. **Restrição de audience** (RFC 8707, capítulo anterior) — garantia estrutural de **para quem** o token vale, resolvendo confused deputy independentemente de nomenclatura de scope.
4. **Detalhe no nível de uma transação específica** (RFC 9396, este capítulo) — não apenas "o que" e "para quem", mas **exatamente qual transação**, com seus parâmetros concretos (valor, conta, data), verificável pelo próprio resource server no momento de executar a ação.

Cada degrau resolve uma limitação estrutural que o degrau anterior não conseguia cobrir sozinho — RAR é onde essa escada termina, no nível mais fino que o protocolo oferece antes de sair do domínio de "autorização" e entrar no domínio de "lógica de negócio da transação em si".

### Combinação natural com PAR e JAR

Como `authorization_details` pode carregar dados sensíveis estruturados diretamente na requisição (IBAN, valor exato, possivelmente até finalidade da transação), isso reforça por que combinar com:

- **PAR (RFC 9126)** — para não expor esses dados sensíveis no browser (query string de uma requisição GET de redirecionamento), movendo o conteúdo completo para uma chamada backend-to-backend.
- **JAR (RFC 9101)** — para assinar a requisição inteira, garantindo integridade (nenhum campo, incluindo o `authorization_details`, pode ser adulterado em trânsito sem invalidar a assinatura).

A combinação PAR + JAR + RAR é, na prática, o padrão de referência para cenários de alta garantia como iniciação de pagamento — e é exatamente o conjunto que o FAPI 2.0 recomenda para esses casos.

## 6. Relação com outras RFCs

- Evolução direta do `scope` tradicional — mesmo papel conceitual (comunicar o que está sendo concedido), agora estruturado em JSON tipado em vez de uma string plana separada por espaços.
- Combina naturalmente com **RFC 9126 (PAR)** e **RFC 9101 (JAR)** — a trinca PAR + JAR + RAR é exatamente o padrão avançado do FAPI 2.0 para casos como iniciação de pagamento, amarrando construções vistas nas partes anteriores deste roteiro (PAR/JAR, categorias de segurança avançada da requisição) ao mecanismo de autorização fina apresentado aqui.
- `locations` ecoa diretamente o conceito de `resource` da **RFC 8707** (capítulo anterior), só que aplicado por objeto de detalhe individual, não pelo token inteiro — a mesma ideia de restrição de audience, só que com granularidade mais fina.
- Descoberto via **RFC 8414** (`authorization_details_types_supported`).
- Fecha, junto com a RFC 8707, o fio de least privilege que atravessa o roteiro inteiro: de escopo amplo (RFC 6749) a escopo mínimo por convenção (RFC 6750) a audience estruturalmente restrita (RFC 8707) a transação específica (RFC 9396) — ver a escada detalhada na seção 5.

## 7. O que mudou desde a publicação (2023)

- RFC recente, motivada por pressão regulatória real em ecossistemas de Open Banking, que já precisavam desse nível de granularidade havia vários anos e resolviam de formas proprietárias e mutuamente incompatíveis antes da padronização — a RFC 9396 chega, em certo sentido, formalizando uma necessidade que o mercado já tinha suprido de forma fragmentada.
- O **FAPI 2.0 trata RAR como uma ferramenta disponível** (não universalmente obrigatória, diferente do PKCE, que o FAPI 2.0 tornou praticamente onipresente) — usada sempre que o caso de uso exige esse nível de precisão, sendo iniciação de pagamento o exemplo canônico e mais citado.
- No seu contexto FSI, é provavelmente o capítulo com **aplicação profissional mais direta** de todo o roteiro: qualquer sistema de iniciação de pagamento, ou qualquer cenário de "consentimento granular por transação" em serviços financeiros regulados, converge para este mecanismo.

> **Nota de laboratório**: nenhum lab construído ainda para esta RFC neste projeto. O cenário natural seria estender algum lab existente com um `authorization_details` de "iniciação de pagamento" fictícia, mostrando a tela de consentimento refletindo o valor/conta específicos (em vez de um scope genérico do tipo `payments:write`), e o resource server validando o `type` e os campos concretos daquele objeto antes de autorizar a execução da transação. Os exemplos de código abaixo são, portanto, standalone.

## Exemplo em Java (JDK 21, sem frameworks)

Usamos `java.net.http.HttpClient` para montar a requisição e o utilitário `SimpleJson`, definido no Capítulo 1 (RFC 6749) deste livro, para as partes planas do JSON — com uma extensão mínima e local para lidar com o array/objetos aninhados que `authorization_details` exige (o `SimpleJson` do Capítulo 1 é deliberadamente simples e cobre só JSON "flat").

> **Nota didática**: assim como nos capítulos anteriores, o parsing manual abaixo é só para expor o mecanismo do protocolo. Em produção, use uma biblioteca JSON madura (Jackson, Gson, ou equivalente) para qualquer estrutura JSON aninhada real — o `SimpleJson` deste livro é deliberadamente mínimo, para fins didáticos.

### 1. Montando `authorization_details` para iniciação de pagamento

```java
import java.net.URLEncoder;
import java.nio.charset.StandardCharsets;

public class AuthorizationDetailsBuilder {

    /**
     * Monta manualmente o array JSON de authorization_details para um
     * unico objeto de "iniciacao de pagamento" — type e um valor definido
     * pelo ECOSSISTEMA/perfil regulatorio, NAO pela RFC 9396 em si (que so
     * define o envelope comum: type + locations/actions/datatypes/
     * identifier/privileges).
     *
     * Isto substitui um scope plano como "payments:write" por uma
     * descricao estruturada e especifica da transacao concreta.
     */
    static String montarPagamentoUnico(String moeda, String valor,
                                         String ibanDestino, String resourceServerUrl) {
        return "[{"
                + "\"type\":\"payment_initiation\","
                + "\"actions\":[\"initiate\"],"
                + "\"locations\":[\"" + resourceServerUrl + "\"],"
                + "\"instructedAmount\":{"
                +     "\"currency\":\"" + moeda + "\","
                +     "\"amount\":\"" + valor + "\""
                + "},"
                + "\"creditorAccount\":{"
                +     "\"iban\":\"" + ibanDestino + "\""
                + "}"
                + "}]";
    }

    /**
     * Codifica o array JSON como valor de query string, para uso numa
     * authorization request via GET. Em cenarios reais de alta garantia
     * (dados sensiveis como IBAN e valor exato no proprio parametro),
     * prefira combinar com PAR (RFC 9126) para nao expor isso no browser —
     * ver discussao na secao 5 deste capitulo.
     */
    static String montarUrlAutorizacaoComRar(String authorizationEndpoint, String clientId,
                                               String redirectUri, String state,
                                               String authorizationDetailsJson) {
        return authorizationEndpoint
                + "?response_type=code"
                + "&client_id=" + urlEncode(clientId)
                + "&redirect_uri=" + urlEncode(redirectUri)
                + "&state=" + urlEncode(state)
                + "&authorization_details=" + urlEncode(authorizationDetailsJson);
    }

    private static String urlEncode(String valor) {
        return URLEncoder.encode(valor, StandardCharsets.UTF_8);
    }
}
```

### 2. Parseando e validando `authorization_details` no resource server

```java
import java.util.List;
import java.util.regex.Matcher;
import java.util.regex.Pattern;

public class ValidadorAuthorizationDetails {

    /**
     * Parser MINIMO e ilustrativo para o unico formato que este exemplo
     * precisa entender (um objeto de payment_initiation dentro do array).
     * NAO e um parser JSON de proposito geral — para isso, use uma
     * biblioteca real em producao (ver nota didatica no topo).
     */
    record DetalhePagamento(String type, String moeda, String valor, String iban,
                             List<String> locations) {}

    static DetalhePagamento parsearPrimeiroDetalhePagamento(String authorizationDetailsJson) {
        String tipo = extrairCampo(authorizationDetailsJson, "\"type\"\\s*:\\s*\"([^\"]+)\"");
        String moeda = extrairCampo(authorizationDetailsJson, "\"currency\"\\s*:\\s*\"([^\"]+)\"");
        String valor = extrairCampo(authorizationDetailsJson, "\"amount\"\\s*:\\s*\"([^\"]+)\"");
        String iban = extrairCampo(authorizationDetailsJson, "\"iban\"\\s*:\\s*\"([^\"]+)\"");
        return new DetalhePagamento(tipo, moeda, valor, iban, List.of());
    }

    private static String extrairCampo(String json, String regex) {
        Matcher m = Pattern.compile(regex).matcher(json);
        return m.find() ? m.group(1) : null;
    }

    /**
     * O passo de seguranca central deste capitulo, do lado do resource
     * server: antes de EXECUTAR a transacao, confirmar type + cada campo
     * especifico — nao basta que o token "tenha algum scope de pagamento",
     * o RS precisa validar que ESTA transacao concreta (valor, conta) e
     * exatamente o que foi autorizado, nao uma inferida a partir de um
     * scope generico.
     */
    static boolean autorizadoParaExecutarEstaTransacao(DetalhePagamento detalhe,
                                                         String valorRequisitado,
                                                         String moedaRequisitada,
                                                         String ibanRequisitado) {
        if (!"payment_initiation".equals(detalhe.type())) {
            return false; // tipo errado — este token nao autoriza pagamento algum
        }
        // Comparacao EXATA de valor/moeda/conta — nada de "valor menor ou
        // igual" implicito aqui; o objeto de detalhe concedido e o teto
        // exato desta autorizacao especifica (o AS ja pode ter reduzido o
        // pedido original antes de conceder — secao 3).
        return detalhe.moeda().equals(moedaRequisitada)
                && detalhe.valor().equals(valorRequisitado)
                && detalhe.iban().equals(ibanRequisitado);
    }
}
```

### 3. Comparando `scope` plano vs. `authorization_details` estruturado

```java
public class ComparacaoScopeVsRar {

    /**
     * Ilustra, lado a lado, a diferenca de expressividade entre o modelo
     * antigo (scope) e o modelo desta RFC (authorization_details) para o
     * MESMO caso de uso: autorizar um pagamento especifico.
     */
    static void demonstrarDiferenca() {
        // Modelo antigo (RFC 6749): scope plano, sem estrutura nenhuma —
        // autoriza uma CLASSE de acao ("iniciar pagamentos"), nao uma
        // transacao especifica. O resource server, ao ver esse scope,
        // nao tem como saber QUAL pagamento foi de fato consentido pelo
        // usuario — teria que confiar em algum canal fora de banda.
        String scopeAntigo = "payments:initiate";

        // Modelo desta RFC: JSON estruturado, autoriza uma TRANSACAO
        // especifica e verificavel — o resource server pode (e deve)
        // conferir type + campos concretos antes de executar, sem
        // depender de nenhum canal fora de banda.
        String authorizationDetailsNovo = AuthorizationDetailsBuilder.montarPagamentoUnico(
                "BRL", "120.00", "BR00000000000000000000000",
                "https://api.banco.exemplo.com/pagamentos");

        System.out.println("scope (RFC 6749):            " + scopeAntigo);
        System.out.println("authorization_details (RFC 9396): " + authorizationDetailsNovo);
    }
}
```
