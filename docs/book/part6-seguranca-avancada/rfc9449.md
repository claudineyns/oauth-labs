# RFC 9449 — OAuth 2.0 Demonstrating Proof of Possession (DPoP)

## 1. Contexto e motivação

Mesmo problema de fundo do capítulo anterior (RFC 8705, mTLS): bearer token roubado é acesso total até a expiração, fraqueza que a RFC 6750 já registrava como fora de seu próprio escopo desde o capítulo 2 deste roteiro. Mas mTLS tem um custo de infraestrutura real — PKI completa, gestão de ciclo de vida de certificado de cliente, e o problema recorrente de terminação de TLS quebrando o vínculo quando há um gateway no meio do caminho, como vimos em detalhe no capítulo anterior.

O DPoP propõe uma alternativa **deliberadamente mais leve**: sender-constraining implementado inteiramente na **camada de aplicação**, usando um par de chaves assimétrico comum — sem PKI, sem certificado, sem CA, sem cadeia de confiança nenhuma — que funciona sobre HTTPS normal e sobrevive a qualquer proxy no meio do caminho, porque **nada depende da conexão TLS em si**, só de um objeto assinado (um JWT) enviado como header HTTP comum, ao lado de qualquer requisição.

Isso torna o DPoP particularmente atraente para exatamente as categorias de client onde o mTLS mais dói:

- **SPAs no browser** — já têm acesso à Web Crypto API, que consegue gerar pares de chave e assinar sem nunca expor a chave privada ao JavaScript da página (chaves não-extraíveis, `extractable: false`).
- **Apps mobile** — já têm acesso a keystores seguros (Android Keystore, iOS Secure Enclave) para gerar e usar pares de chave sem exportar a chave privada.
- **CLIs e ferramentas de desenvolvedor** — já geram pares de chave locais para outros fins (SSH, por exemplo) e não têm ciclo de vida de certificado X.509 para gerenciar.

Nenhuma dessas categorias tradicionalmente gerencia certificados de cliente — exigir mTLS delas seria adicionar uma peça de infraestrutura nova e cara. DPoP reaproveita algo que muitas delas já sabem fazer (gerar e usar um par de chaves) e adiciona só a disciplina de assinar uma prova nova a cada chamada.

### Por que uma prova por requisição, e não uma vez por token?

Esse é o ponto mais frequentemente mal entendido do DPoP na primeira leitura: a prova DPoP **não é assinada uma vez, quando o token é emitido** — ela é assinada **de novo, a cada requisição HTTP individual**, tanto ao obter o token quanto ao usá-lo depois no resource server. Isso parece redundante à primeira vista (por que assinar de novo se a chave é a mesma?), mas é exatamente o que permite ao servidor aplicar uma janela de frescor bem apertada e detectar replay de forma muito mais rígida do que seria possível com uma única prova reaproveitada — ver seção 5.

## 2. Terminologia e papéis

Nenhum papel novo. Introduz:

- **DPoP proof** — um JWT assinado a cada requisição individual, carregando `htm` (método HTTP em maiúsculas), `htu` (URI de destino, **sem** query string nem fragmento), `iat` (timestamp de criação), `jti` (identificador único por prova, nunca reaproveitado) e, no **header** do próprio JWT (não no payload), a chave pública do client embutida como JWK (`jwk`).
- **Header HTTP `DPoP`** — carrega essa prova, tanto na requisição ao token endpoint (provando posse da chave que vai ser vinculada ao token que está sendo emitido) quanto em cada requisição subsequente ao resource server (provando, de novo, posse da mesma chave, a cada chamada).
- **Esquema de autorização `DPoP`** — tokens vinculados a DPoP usam `Authorization: DPoP <token>`, não `Authorization: Bearer <token>`. Isso é deliberado: o esquema no header já denuncia, para qualquer observador da mensagem (incluindo logs, proxies, ferramentas de depuração), que aquele token exige uma prova de posse para ser aceito — não é "só mais um bearer".
- **`ath`** (access token hash) — quando a prova acompanha uma chamada ao resource server (não ao token endpoint), carrega o hash SHA-256 (Base64URL) do próprio access token apresentado junto, amarrando explicitamente a prova àquele token específico.
- **`jkt`** (JWK Thumbprint, RFC 7638) — thumbprint canônico da chave pública, calculado a partir dos membros obrigatórios do JWK (varia por tipo de chave — para EC: `crv`, `kty`, `x`, `y`; para RSA: `e`, `kty`, `n`), ordenados alfabeticamente, serializados sem espaços, SHA-256, Base64URL. Aparece na claim `cnf.jkt` do access token emitido — mesma estrutura de extensão `cnf` que a RFC 8705 já usava com `x5t#S256`, só que aqui o que é vinculado é uma chave pública crua, não um certificado.
- **`typ: dpop+jwt`** — o header do JWT de prova se autodeclara como prova DPoP, não um JWT genérico. Mesmo princípio de autodeclaração de tipo já visto em `typ: at+jwt` (RFC 9068): evita que uma prova DPoP seja aceita em um contexto onde qualquer outro JWT seria válido, ou vice-versa.

### Por que a chave pública viaja no header do JWT, e não é pré-registrada?

Diferente de `private_key_jwt` (RFC 7523) ou de JWKS pré-registrado, o DPoP **não exige registro prévio de chave nenhuma**. A chave pública viaja embutida em cada prova (`jwk` no header). Isso é o que torna o DPoP utilizável por clients totalmente públicos, sem nenhum passo de provisionamento de chave: o client simplesmente gera um par de chaves na primeira vez que precisa, e a chave pública "se apresenta" na primeira prova que ele envia. O vínculo de confiança não vem de "o AS já conhecia essa chave" — vem de "o AS emitiu o token vendo, naquele exato momento, uma prova de posse daquela chave, e vinculou o thumbprint dela ao token resultante". A partir daí, qualquer uso subsequente do token precisa reapresentar prova da mesma chave.

## 3. Fluxo

**1. Client gera um par de chaves** (uma vez, guardado localmente — Web Crypto API não-extraível no browser, keystore seguro no mobile, ou um arquivo de chave local numa CLI).

**2. Requisição de token, com prova DPoP:**
```
POST /token
DPoP: <JWT: header={typ:"dpop+jwt", alg, jwk:<chave publica>},
            payload={htm:"POST", htu:"https://as.exemplo.com/token", iat, jti}>
grant_type=...&code=...

AS valida a prova:
  - assinatura bate com o jwk embutido no proprio header da prova
  - typ = dpop+jwt
  - htm/htu conferem com esta requisicao exata
  - iat dentro de uma janela de frescor aceitavel
  - jti nao foi visto antes (nesta janela)

AS emite o access_token com token_type=DPoP, vinculado:
  cnf.jkt = thumbprint (RFC 7638) dessa chave publica
```

**3. Requisição de recurso, com uma prova NOVA (fresca por requisição) + o token vinculado:**
```
GET /api/recurso
Authorization: DPoP <access_token>      — esquema "DPoP", nao "Bearer"
DPoP: <JWT: header={jwk: mesma chave publica},
            payload={htm:"GET", htu:"https://rs.exemplo.com/api/recurso",
                     iat, jti, ath:<hash do access_token>}>

RS valida, nesta ordem:
  1) o access_token em si (introspeccao ou verificacao local do JWT) -> confirma cnf.jkt = X
  2) assinatura da prova bate com o jwk do proprio header da prova
  3) thumbprint desse jwk == cnf.jkt do token (precisa bater)
  4) htm/htu conferem com esta requisicao exata
  5) iat dentro da janela de frescor
  6) jti nao foi reaproveitado (dentro de uma janela de rastreio)
  7) ath bate com o hash do access_token apresentado nesta mesma chamada
```

A diferença mecânica central em relação ao mTLS (capítulo anterior): em vez de amarrar o token a uma **conexão** (identidade de certificado TLS), o DPoP amarra o token a uma **chave usada para assinar uma prova nova a cada requisição individual** — sem exigência nenhuma de camada de transporte. Isso significa que o vínculo sobrevive a qualquer proxy, load balancer ou gateway no meio do caminho, porque a prova é só mais um header HTTP comum, visível e intacto de ponta a ponta — nada equivalente ao problema de "terminação de TLS quebra mTLS" existe aqui.

### Caso de borda: renovação de token (`refresh_token`)

Quando um client troca um `refresh_token` por um novo `access_token`, a requisição ao token endpoint também precisa vir acompanhada de uma prova DPoP — e o AS deve confirmar que essa prova usa **a mesma chave** já vinculada ao `refresh_token` originalmente (via `cnf.jkt` associado ao registro do `refresh_token`, não só do `access_token`). Sem essa checagem na renovação, um `refresh_token` roubado (que tipicamente não é ele mesmo enviado ao resource server, então não se beneficiaria diretamente do `ath`) ainda poderia ser trocado por um `access_token` novo por quem não tem a chave privada original — exatamente o mesmo raciocínio do caso de borda equivalente na RFC 8705.

### Caso de borda: troca de chave no meio de uma sessão

Nada na RFC proíbe um client de gerar uma chave nova (por exemplo, ao reinstalar, ou por rotação periódica de segurança). Mas isso invalida qualquer token já vinculado à chave antiga — o client precisa passar por um novo fluxo de obtenção de token (ou renovação, se ainda tiver um `refresh_token` — mas aí esbarra na checagem do parágrafo anterior). Na prática, a maioria dos clients gera a chave uma vez e a mantém pela vida útil da instalação/sessão.

## 4. Parâmetros e endpoints normativos

- **Header `DPoP`** — novo, carrega a prova compacta (JWT serializado), tanto na requisição de token quanto na de recurso.
- **Esquema `Authorization: DPoP <token>`** — substitui `Bearer` para tokens vinculados assim; visível diretamente na mensagem HTTP, sem precisar inspecionar o token em si para saber que exige prova.
- `token_type` na resposta do token endpoint vira `"DPoP"`, não `"Bearer"` — outro sinal explícito, desta vez na resposta de emissão.
- Descoberto via RFC 8414: `dpop_signing_alg_values_supported`, listando quais algoritmos de assinatura o AS aceita para provas DPoP (tipicamente `ES256` é o mais recomendado por gerar assinaturas menores que RSA, mas a RFC não exige um algoritmo específico).
- Erro característico no resource server: token DPoP apresentado sem prova válida/correspondente → `401` com header `WWW-Authenticate: DPoP ...` e um código de erro como `error="invalid_dpop_proof"`, seguindo o mesmo formato de erro que a RFC 6750 já definia para `WWW-Authenticate: Bearer`, adaptado ao novo esquema.
- O header da prova deve trazer `typ: dpop+jwt` — se ausente ou com outro valor, a prova deve ser rejeitada mesmo que a assinatura seja válida (proteção contra confusão de tipo de token, mesmo princípio de `typ: at+jwt` na RFC 9068).
- Um servidor de autorização também pode emitir um **nonce** de servidor (header `DPoP-Nonce`) que o client deve ecoar na claim `nonce` da próxima prova — mecanismo opcional adicional contra certas formas de replay antecipado ("pré-computar" provas offline); não é obrigatório em toda implantação, mas está previsto na RFC para AS que queiram essa camada extra.

## 5. Segurança já tratada na própria RFC 9449

### Proteção contra replay via `jti` + janela curta de `iat`

Como cada requisição exige uma prova nova, o servidor pode aplicar uma janela de frescor bem apertada (rejeitar provas com `iat` de mais de alguns segundos/poucos minutos atrás) e rastrear os `jti`s vistos recentemente (tipicamente num cache com TTL curto, como Redis) — proteção de replay muito mais rígida do que a de um único bearer token de vida longa, já que uma prova capturada por um atacante (de um log, de um proxy comprometido) fica inútil quase imediatamente, tanto pela janela de tempo quanto pelo `jti` já consumido.

### `htm`/`htu` amarram a prova à requisição exata

Uma prova feita para uma chamada específica (combinação de método HTTP + URL, sem query nem fragmento) não serve para nenhuma outra — mesmo que capturada a tempo (dentro da janela de frescor), não pode ser reaproveitada para chamar um endpoint diferente ou usar um método HTTP diferente no mesmo endpoint.

### `ath` amarra a prova ao token específico

Impede que um atacante que tenha capturado, separadamente, um access_token válido **e** alguma prova DPoP não relacionada (de outra chamada, de outro token, potencialmente até de outro client com a mesma chave — cenário artificial, mas ilustra o ponto) consiga combinar os dois. A prova precisa referenciar explicitamente o hash do token específico com que está sendo usada — sem `ath` correto, a prova não vale para aquele token, mesmo sendo uma prova DPoP legítima e recente.

### A chave privada nunca sai do client

Mesma garantia central do mTLS/`private_key_jwt`: só a prova (uma assinatura sobre um payload pequeno) trafega pela rede, nunca a chave privada em si. Clients em browser podem usar chaves não-extraíveis via Web Crypto API — mesmo um script malicioso injetado na mesma página (via alguma vulnerabilidade de XSS, por exemplo) não consegue exfiltrar a chave privada propriamente dita, porque o próprio browser recusa a operação de exportação. Isso não é proteção total, porém: um script malicioso rodando no mesmo contexto **ainda pode pedir ao browser para assinar provas arbitrárias** enquanto tiver acesso à página — DPoP protege contra roubo/replay de token capturado na rede ou em um log, não contra um runtime de client totalmente comprometido, que consegue abusar da própria API de assinatura em tempo real.

### Comparação com mTLS em termos de revogação

DPoP não tem equivalente aos controles de revogação em nível de PKI que o mTLS herda naturalmente (listas de revogação de certificado, controles de CA, verificação OCSP). Se uma chave DPoP for comprometida, não existe um mecanismo padronizado de "lista de chaves revogadas" — a mitigação prática é a vida curta do access_token e a recusa em renovar `refresh_token`s vinculados a uma chave suspeita (decisão operacional do AS, não normatizada pela RFC). Para a ameaça específica que motivou a RFC — "token roubado da rede ou de um log" — DPoP é igualmente eficaz ao mTLS, a um custo de infraestrutura muito menor; mas não é um substituto direto para todos os controles que uma PKI completa oferece.

## 6. Relação com outras RFCs

- Irmã direta/alternativa da **RFC 8705 (mTLS)**, capítulo anterior — mesmo objetivo (sender-constraining contra a fraqueza de bearer da RFC 6750), mecanismo diferente (prova assinada na camada de aplicação vs. certificado na camada de transporte TLS). A RFC 9700 recomenda qualquer um dos dois, sem preferência estrutural.
- `cnf.jkt` em access tokens JWT é a instância específica do DPoP do mesmo ponto de extensão `cnf` que a RFC 9068 definiu e que a RFC 8705 já usava (com `x5t#S256`) — mesma estrutura de claim, mecanismos de vínculo diferentes.
- `typ: dpop+jwt` espelha exatamente o mesmo princípio de autodeclaração de tipo do `typ: at+jwt` da RFC 9068.
- Descoberto via `dpop_signing_alg_values_supported` da RFC 8414.
- Particularmente adequado a clients públicos (SPAs, mobile, CLI) que já geram uma chave efêmera localmente — resolve a lacuna de autenticação forte para esse tipo de client (que não pode guardar um `client_secret` com segurança) já discutida nos capítulos da RFC 6749 e da RFC 9700, sem exigir `client_secret` nem PKI.
- No seu contexto FSI: **FAPI 2.0 trata DPoP como um dos dois mecanismos aceitáveis de sender-constraining** (ao lado de mTLS) no perfil baseline — implantações que não têm PKI de client madura tendem a preferir DPoP por esse motivo.

## 7. O que mudou desde a publicação (2023)

- Uma das RFCs mais recentes deste roteiro — adoção crescendo ativamente, sobretudo em arquiteturas com muito SPA/mobile, onde o custo de PKI do mTLS sempre foi mal ajustado à realidade operacional desses clients.
- Cada vez mais vista como recomendação padrão para sender-constraining em implantações novas que ainda não têm infraestrutura de mTLS, dado o custo operacional bem menor de "gerar um par de chaves" comparado a "operar uma PKI de client".
- Suporte de ferramentas amadureceu rápido desde a publicação — integração com Web Crypto API em bibliotecas OAuth de front-end, e SDKs mobile incorporando geração/uso de chave DPoP nativamente.

> **Nota de laboratório**: implementado em [`rfc9449/`](../../rfc9449/README.md) — confirmando a observação acima, roda inteiramente em HTTP puro, sem quebrar a simplificação de TLS deliberadamente adiada até a RFC 8705. O client é público (sem `client_secret`, sem JWKS pré-registrada — a chave viaja embutida em cada prova, como descrito na seção 2). Curiosamente, o lab usa chaves **RSA com `alg: RS256`** para as provas (não EC/`ES256`, que é a escolha mais comum na prática por gerar assinaturas menores) — a RFC não exige um algoritmo específico, só que ele apareça em `dpop_signing_alg_values_supported`. Todo `access_token`/`refresh_token` carrega `cnf_jkt`; o AS valida a prova na emissão (inclusive conferindo, na renovação, que a prova vem da mesma chave já vinculada ao `refresh_token` — exatamente o caso de borda discutido na seção 3), e o RS valida na chamada ao recurso.
>
> Os logs de montagem (`logs.sh client`) e de validação passo a passo (`logs.sh as`/`logs.sh rs`) foram um requisito explícito deste lab — cada checagem (assinatura, `typ`, `htm`/`htu`, janela de `iat`, `jti`, `ath`, thumbprint vs. `cnf.jkt`) é logada individualmente pelo módulo `dpop.js` (compartilhado entre AS e RS para a validação, e usado pelo client para a montagem), com o motivo exato de rejeição quando falha — por exemplo, `"htu nao confere com a requisicao"` ou `"prova ja utilizada antes — replay detectado via jti"`. Dois botões de ataque na UI do lab exercitam exatamente as proteções da seção 5: usar o token como `Bearer` simples (sem prova — corretamente rejeitado, já que o `token_type` é `DPoP`) e reenviar a mesma prova capturada (replay — corretamente rejeitado pela checagem de `jti`).

## Exemplo em Java (JDK 21, sem frameworks)

Usamos `java.security.*` (para o par de chaves EC e assinatura), `java.net.http.HttpClient` e `java.util.Base64`. Para serialização/parsing JSON simples, reaproveitamos o utilitário `SimpleJson`, definido no Capítulo 1 (RFC 6749) deste livro.

> **Nota didática importante**: assim como no capítulo anterior, montar e assinar um JWT "na mão" abaixo é só para fins didáticos, para expor exatamente os passos que uma prova DPoP exige. Em produção, use uma biblioteca JOSE validada (ex.: Nimbus JOSE+JWT) tanto para assinar quanto para validar — parsing manual de JSON dentro de um JWT em produção é uma fonte comum de vulnerabilidades sutis (confusão de algoritmo, canonicalização incorreta de JSON, etc.).

### 1. Gerando o par de chaves EC (P-256)

```java
import java.security.KeyPair;
import java.security.KeyPairGenerator;
import java.security.interfaces.ECPublicKey;
import java.security.spec.ECGenParameterSpec;

public class ChaveDpop {

    /**
     * P-256 (secp256r1) é a curva mais comumente usada para provas DPoP,
     * combinada com o algoritmo de assinatura ES256 — assinaturas bem
     * menores que RSA equivalente, o que importa porque a prova viaja
     * inteira em um header HTTP a CADA requisição.
     */
    static KeyPair gerarParDeChaves() throws Exception {
        KeyPairGenerator gerador = KeyPairGenerator.getInstance("EC");
        gerador.initialize(new ECGenParameterSpec("secp256r1"));
        return gerador.generateKeyPair();
    }

    /**
     * Extrai as coordenadas x/y da chave pública EC, em Base64URL sem
     * padding — os campos que compõem um JWK de chave EC (RFC 7518 §6.2).
     */
    static String[] coordenadasXY(ECPublicKey chavePublica) {
        var ponto = chavePublica.getW();
        int tamanhoCampo = (chavePublica.getParams().getCurve().getField()
                .getFieldSize() + 7) / 8; // 32 bytes para P-256

        return new String[] {
            java.util.Base64.getUrlEncoder().withoutPadding()
                .encodeToString(paraBytesTamanhoFixo(ponto.getAffineX(), tamanhoCampo)),
            java.util.Base64.getUrlEncoder().withoutPadding()
                .encodeToString(paraBytesTamanhoFixo(ponto.getAffineY(), tamanhoCampo))
        };
    }

    private static byte[] paraBytesTamanhoFixo(java.math.BigInteger valor, int tamanho) {
        byte[] bruto = valor.toByteArray();
        byte[] resultado = new byte[tamanho];
        int copiarDe = Math.max(0, bruto.length - tamanho);
        int copiarPara = Math.max(0, tamanho - bruto.length);
        System.arraycopy(bruto, copiarDe, resultado, copiarPara, bruto.length - copiarDe);
        return resultado;
    }
}
```

### 2. Montando e assinando a prova DPoP, calculando `jkt`

```java
import java.security.Signature;
import java.security.interfaces.ECPrivateKey;
import java.security.interfaces.ECPublicKey;
import java.security.MessageDigest;
import java.util.Base64;
import java.util.LinkedHashMap;
import java.util.Map;
import java.util.UUID;

public class ProvaDpop {

    /**
     * Monta o JWK (público) da chave EC, como um mapa ORDENADO — a ordem
     * importa para o calculo do thumbprint (RFC 7638), que exige os
     * membros obrigatorios em ordem alfabetica antes de fazer o hash.
     */
    static Map<String, String> montarJwkPublico(ECPublicKey chavePublica) {
        String[] xy = ChaveDpop.coordenadasXY(chavePublica);
        // Ordem alfabetica dos membros obrigatorios: crv, kty, x, y
        Map<String, String> jwk = new LinkedHashMap<>();
        jwk.put("crv", "P-256");
        jwk.put("kty", "EC");
        jwk.put("x", xy[0]);
        jwk.put("y", xy[1]);
        return jwk;
    }

    /**
     * jkt (RFC 7638): SHA-256 sobre a serializacao JSON canonica (membros
     * ordenados, sem espacos) dos campos obrigatorios do JWK, em Base64URL.
     * E o valor que o AS embute em cnf.jkt no token, e que qualquer
     * validador recalcula a partir do jwk apresentado numa prova para
     * conferir contra o token.
     */
    static String calcularJkt(Map<String, String> jwkOrdenado) throws Exception {
        String json = SimpleJson.object(new LinkedHashMap<>(jwkOrdenado));
        MessageDigest sha256 = MessageDigest.getInstance("SHA-256");
        byte[] hash = sha256.digest(json.getBytes(java.nio.charset.StandardCharsets.UTF_8));
        return Base64.getUrlEncoder().withoutPadding().encodeToString(hash);
    }

    /**
     * Monta e assina uma prova DPoP NOVA para uma requisicao especifica.
     * accessToken, se informado, ativa o claim ath (uso ao chamar o
     * resource server; ausente na requisicao ao token endpoint).
     */
    static String montarEAssinarProva(KeyPair par, String htm, String htu,
                                        String accessToken) throws Exception {
        ECPublicKey chavePublica = (ECPublicKey) par.getPublic();
        ECPrivateKey chavePrivada = (ECPrivateKey) par.getPrivate();
        Map<String, String> jwk = montarJwkPublico(chavePublica);

        // Header do JWT: typ autodeclarado + alg + a chave publica embutida
        Map<String, Object> header = new LinkedHashMap<>();
        header.put("typ", "dpop+jwt");
        header.put("alg", "ES256");
        header.put("jwk", jwk);
        String headerJson = montarJsonComObjetoAninhado(header);
        String headerB64 = Base64.getUrlEncoder().withoutPadding()
                .encodeToString(headerJson.getBytes(java.nio.charset.StandardCharsets.UTF_8));

        long iat = System.currentTimeMillis() / 1000;
        String jti = UUID.randomUUID().toString();

        Map<String, String> payload = new LinkedHashMap<>();
        payload.put("htm", htm);
        payload.put("htu", htu);
        payload.put("iat", String.valueOf(iat));
        payload.put("jti", jti);
        if (accessToken != null) {
            // ath: hash do access_token apresentado nesta mesma chamada —
            // amarra a prova aquele token especifico (secao 5).
            MessageDigest sha256 = MessageDigest.getInstance("SHA-256");
            byte[] hashToken = sha256.digest(
                    accessToken.getBytes(java.nio.charset.StandardCharsets.UTF_8));
            payload.put("ath", Base64.getUrlEncoder().withoutPadding().encodeToString(hashToken));
        }
        String payloadJson = SimpleJson.object(new LinkedHashMap<>(payload));
        String payloadB64 = Base64.getUrlEncoder().withoutPadding()
                .encodeToString(payloadJson.getBytes(java.nio.charset.StandardCharsets.UTF_8));

        String assinandoSobreEsteConteudo = headerB64 + "." + payloadB64;

        // ES256 = ECDSA sobre SHA-256 — a chave privada NUNCA sai deste
        // metodo: so a assinatura resultante e retornada.
        Signature assinatura = Signature.getInstance("SHA256withECDSA");
        assinatura.initSign(chavePrivada);
        assinatura.update(assinandoSobreEsteConteudo.getBytes(java.nio.charset.StandardCharsets.UTF_8));
        byte[] assinaturaDer = assinatura.sign();
        // Nota: Signature.sign() com ECDSA produz DER; JWS exige o formato
        // R||S de tamanho fixo (JOSE) — conversao omitida aqui por brevidade,
        // mas obrigatoria numa implementacao real (mais um motivo para usar
        // uma biblioteca JOSE em producao, que ja faz essa conversao).
        String assinaturaB64 = Base64.getUrlEncoder().withoutPadding().encodeToString(assinaturaDer);

        return assinandoSobreEsteConteudo + "." + assinaturaB64;
    }

    // Serializacao minima s[o para permitir um objeto aninhado (jwk) dentro
    // do header — SimpleJson.object (Cap. 1) assume valores string/flat;
    // esta variante e um complemento local, so para este exemplo.
    private static String montarJsonComObjetoAninhado(Map<String, Object> mapa) {
        StringBuilder sb = new StringBuilder("{");
        boolean primeiro = true;
        for (var entrada : mapa.entrySet()) {
            if (!primeiro) sb.append(",");
            primeiro = false;
            sb.append("\"").append(entrada.getKey()).append("\":");
            if (entrada.getValue() instanceof Map<?, ?> aninhado) {
                @SuppressWarnings("unchecked")
                Map<String, String> m = (Map<String, String>) aninhado;
                sb.append(SimpleJson.object(new LinkedHashMap<>(m)));
            } else {
                sb.append("\"").append(entrada.getValue()).append("\"");
            }
        }
        return sb.append("}").toString();
    }
}
```

### 3. Validando `jkt` contra `cnf.jkt` do token (resource server)

```java
import java.util.Map;

public class ValidadorDpop {

    /**
     * Passo central de validacao no resource server: o thumbprint da chave
     * usada NESTA prova precisa bater com o cnf.jkt vinculado ao token.
     * Sem essa igualdade, o token nao serve para esta chamada, mesmo com
     * assinatura da prova valida e token em si nao expirado.
     */
    static boolean chaveDaProvaConfereComToken(Map<String, String> jwkDaProva,
                                                 String jktEsperadoDoToken) throws Exception {
        String jktCalculado = ProvaDpop.calcularJkt(
                new java.util.LinkedHashMap<>(jwkDaProva));
        return jktCalculado.equals(jktEsperadoDoToken);
    }

    /**
     * ath: confere que a prova foi feita especificamente para o
     * access_token apresentado nesta chamada (nao para outro token).
     */
    static boolean athConfereComToken(String athDaProva, String accessTokenApresentado)
            throws Exception {
        var sha256 = java.security.MessageDigest.getInstance("SHA-256");
        byte[] hash = sha256.digest(
                accessTokenApresentado.getBytes(java.nio.charset.StandardCharsets.UTF_8));
        String athEsperado = java.util.Base64.getUrlEncoder().withoutPadding()
                .encodeToString(hash);
        return athEsperado.equals(athDaProva);
    }

    /**
     * htm/htu: a prova so vale para o metodo+URI exatos desta requisicao.
     * htu NUNCA inclui query string ou fragmento (RFC 9449 §4.2).
     */
    static boolean htmHtuConferem(String htmDaProva, String htuDaProva,
                                    String metodoRequisicaoAtual, String uriRequisicaoAtual) {
        return htmDaProva.equals(metodoRequisicaoAtual)
                && htuDaProva.equals(uriRequisicaoAtual);
    }
}
```
