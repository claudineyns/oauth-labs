# RFC 8705 — OAuth 2.0 Mutual-TLS Client Authentication and Certificate-Bound Access Tokens

## 1. Contexto e motivação

Esta RFC define **duas coisas distintas**, e vale insistir na separação logo de início porque é comum vê-las confundidas em discussões informais:

1. **mTLS como método de autenticação de client** no token endpoint — o client se autentica apresentando um certificado X.509 durante o próprio handshake TLS, em vez de (ou além de) qualquer credencial transportada dentro da requisição HTTP. É uma alternativa assimétrica ao `client_secret`, ocupando o mesmo espaço de decisão que `private_key_jwt` (RFC 7523 §2.2): "como o AS sabe que é realmente este client falando?" — só que a prova é feita na camada de transporte (TLS), não dentro do corpo da requisição.
2. **Certificate-bound access tokens** — independentemente de como o client se autenticou, o AS pode amarrar (*bind*) o access token emitido ao certificado X.509 usado na conexão em que o token foi obtido. Um token vinculado assim só é aceito pelo resource server se a **mesma** identidade de certificado for reapresentada na conexão que efetivamente usa o token.

A primeira metade resolve "quem é o client". A segunda resolve um problema completamente diferente e mais fundamental, que atravessa este roteiro inteiro desde o capítulo da RFC 6750: **bearer token roubado = acesso total até a expiração**, porque um bearer token é, por definição, uma credencial "quem tiver, pode usar" (*possession-based*). A RFC 6750 já registrava esse risco residual como algo que fica fora do escopo dela — ficou como uma dívida técnica explícita, que a RFC 8705 (e a RFC 9449, no capítulo seguinte) vêm pagar.

É perfeitamente possível usar as duas metades de forma independente:

- **mTLS só para autenticação de client, sem token vinculado** — o client prova quem é usando certificado, mas o access_token resultante continua sendo um bearer comum. Reduz o risco de personificação do client (ninguém sem a chave privada consegue se passar por ele no token endpoint), mas não protege o token depois de emitido.
- **Token vinculado a certificado, com client autenticado por outro método** — teoricamente possível, mas raro na prática: a vinculação normalmente nasce naturalmente da própria conexão mTLS que já está sendo usada para autenticar o client, então a maioria das implantações reais faz as duas coisas **juntas**, porque é onde mora o valor real: autenticar via mTLS *e* vincular o token resultante ao mesmo certificado, numa única conexão.

### Por que mTLS e não só "confiar no client_secret"?

Vale reforçar o contraste com o modelo mais simples (`client_secret_basic`/`client_secret_post`, RFC 6749): um segredo compartilhado, transmitido a cada requisição, que precisa ser guardado por ambos os lados (client e AS) e que, se vazar de qualquer um dos dois lados (log, repositório, banco de dados do AS comprometido), permite personificação completa do client até ser rotacionado. Um certificado X.509 com chave privada nunca sai do client (fica em HSM, keystore protegido, ou pelo menos um arquivo de chave local) — o AS nunca vê nem guarda a chave privada, só a chave pública embutida no certificado. É a mesma vantagem estrutural que `private_key_jwt` já trazia; mTLS só move essa prova para a camada de transporte.

## 2. Terminologia e papéis

Nenhum papel novo — client, AS e RS continuam os mesmos. Conceitos novos:

- **`tls_client_auth`** — método de autenticação de client em que o certificado apresentado no handshake é validado por uma cadeia de confiança **PKI tradicional**: o AS verifica que o certificado foi emitido por uma CA (ou cadeia de CAs) em que ele confia, normalmente também checando um campo esperado do subject/SAN contra o `client_id` registrado. É o modelo natural para ambientes corporativos que já operam uma PKI interna (comum em bancos, exatamente o seu contexto FSI).
- **`self_signed_tls_client_auth`** — o client apresenta um certificado **autoassinado** (sem cadeia de CA nenhuma). O AS não valida cadeia; em vez disso, compara a chave pública do certificado apresentado contra uma chave pública **pré-registrada** para aquele `client_id`, fora de banda, no momento do registro do client. É estruturalmente idêntico, em espírito de confiança, ao modelo de JWKS pré-registrado do `private_key_jwt` — a diferença é só o empacotamento (certificado X.509 vs. JWK cru).
- **Certificate-bound access token** — um access_token (opaco ou JWT) associado a um certificado X.509 específico. A associação pode viver:
  - **Server-side**, para tokens opacos: o AS guarda, junto ao registro interno do token, o thumbprint do certificado que o gerou; a introspecção (RFC 7662) expõe isso.
  - **Embutida no próprio token**, para JWT access tokens (RFC 9068): claim `cnf` (confirmation), com membro `x5t#S256` contendo o thumbprint.
- **Thumbprint do certificado (`x5t#S256`)** — SHA-256 sobre a codificação **DER** do certificado X.509 completo, codificado em Base64URL sem padding. É determinístico: o mesmo certificado sempre produz o mesmo thumbprint, permitindo comparação simples byte-a-byte do hash em vez de comparar certificados inteiros.

### Onde o certificado "mora" durante a requisição

Um ponto frequentemente mal entendido: o certificado **não** é enviado como um header HTTP nem como parâmetro do corpo. Ele é parte do handshake TLS em si — o servidor solicita (`CertificateRequest`) e o client responde com sua cadeia de certificados como parte do protocolo TLS, antes mesmo da primeira linha HTTP ser trocada. Isso implica algo operacionalmente importante: **qualquer coisa que termine o TLS antes do AS/RS** (um load balancer, um API gateway, um proxy reverso) precisa, de alguma forma, repassar a informação do certificado do client para a aplicação — porque a aplicação, rodando atrás desse ponto de terminação, nunca vê o handshake TLS original.

## 3. Fluxo

**Autenticação do client via mTLS, no token endpoint:**

```
Handshake TLS: client apresenta certificado X.509
               (validado via cadeia de CA — tls_client_auth —
                ou via chave pré-registrada — self_signed_tls_client_auth)

POST /token   (sobre essa mesma conexão mTLS)
grant_type=...&client_id=...
              — sem client_secret, sem client_assertion:
                o certificado apresentado no handshake É a credencial
```

**Emissão do token vinculado** (automática, quando o AS suporta o recurso e o client foi autenticado ou pelo menos identificado via mTLS):

```
Ao emitir o access_token, o AS calcula x5t#S256 = Base64URL(SHA-256(DER(certificado)))
e vincula:
  - token opaco: thumbprint guardado no registro interno do token, no AS
  - token JWT:   embutido como claim cnf: { "x5t#S256": "<thumbprint>" }
```

**Validação no resource server, no uso do token:**

```
Client → RS: mesma disciplina mTLS (apresenta o certificado de novo, nesta nova conexão)
             + Authorization: Bearer <token vinculado>

RS:
  1) valida o token normalmente (introspecção RFC 7662, ou verificação local se for JWT)
  2) calcula o thumbprint do certificado apresentado NESTA conexão específica
  3) compara com o thumbprint vinculado ao token (cnf.x5t#S256, ou resposta de introspecção)
  4) thumbprint diferente (ou ausente) → rejeita, mesmo que o token em si seja "válido"
```

O passo 4 é a propriedade de segurança central deste mecanismo inteiro: **possuir a string do bearer token deixa de ser suficiente**. É preciso também controlar a chave privada correspondente ao certificado, para conseguir reestabelecer uma conexão mTLS válida com aquele mesmo certificado — algo que um atacante que só roubou o token (de um log, de um proxy mal configurado, de um cache) não tem como fazer.

### Caso de borda: renovação de token (`refresh_token`)

Quando um client usa um `refresh_token` para obter um novo `access_token`, a requisição ao token endpoint também passa pela mesma conexão mTLS. A RFC recomenda que o AS confira que o certificado apresentado nesta renovação é **o mesmo** que originou o `refresh_token` (ou pelo menos um certificado ainda válido e associado ao mesmo client) — do contrário, um `refresh_token` roubado (mesmo sem token vinculado ele mesmo, já que `refresh_token`s tipicamente não trafegam para o resource server) ainda poderia ser trocado por um `access_token` novo por quem não tem a chave privada original. Vincular também a renovação fecha essa lacuna.

### Caso de borda: múltiplos certificados válidos para o mesmo client

Nada na RFC impede um AS de aceitar mais de um certificado registrado para o mesmo `client_id` (útil durante rotação de certificado, ver seção 5). Cabe à implantação decidir a política — a RFC não normatiza um mecanismo de "múltiplos certificados simultaneamente válidos", deixando isso como decisão operacional de cada AS.

## 4. Parâmetros e endpoints normativos

- **Nenhum endpoint novo.** Estende a autenticação do token endpoint com dois métodos novos, registráveis via `token_endpoint_auth_method` no registro dinâmico de client (RFC 7591): `tls_client_auth` e `self_signed_tls_client_auth`.
- **Metadados de registro do client** — quando `tls_client_auth` é usado, o registro do client pode carregar campos adicionais indicando qual atributo do certificado deve ser conferido contra qual valor esperado (ex.: DN do subject, ou uma SAN específica) — a RFC define um pequeno vocabulário de campos para isso (`tls_client_auth_subject_dn` e variantes), permitindo ao AS saber exatamente o que comparar no certificado apresentado.
- **Resposta de introspecção (RFC 7662)** ganha um membro `cnf` com `x5t#S256` quando o token introspectado está vinculado a certificado — é assim que um resource server que usa introspecção (em vez de validar um JWT localmente) descobre o thumbprint esperado.
- **JWT access tokens (RFC 9068)** carregam `cnf.x5t#S256` diretamente no payload, quando vinculados — resource servers que validam o JWT localmente (sem round-trip de introspecção) leem o thumbprint direto do próprio token.
- **Descoberta via RFC 8414**: `tls_client_certificate_bound_access_tokens` (booleano, indicando suporte a tokens vinculados) e os dois métodos novos aparecendo em `token_endpoint_auth_methods_supported`. Também pode existir um endpoint alternativo dedicado a mTLS (`mtls_endpoint_aliases`), para AS que hospedam o token endpoint "normal" (sem exigir certificado de client) e uma variante mTLS-only em uma URL distinta — útil quando nem todo cliente do AS usa mTLS.

## 5. Segurança já tratada na própria RFC 8705

### Fechamento da lacuna de bearer token

Fecha exatamente a fraqueza estrutural que a RFC 6750 já registrava como fora de escopo desde o início deste roteiro: bearer token roubado deixa de bastar sem a chave privada correspondente ao certificado. Esse é, de longe, o ganho de segurança mais importante desta RFC.

### Terminação de TLS quebra tudo

Este é o ponto operacional mais citado (e mais frequentemente esquecido) da RFC: **se um proxy, load balancer ou API gateway termina a conexão TLS antes da requisição chegar ao AS/RS**, a aplicação nunca vê o certificado real do client — o handshake mTLS aconteceu entre o client e o gateway, não entre o client e a aplicação. Isso quebra silenciosamente qualquer verificação de `cnf.x5t#S256`, a menos que o certificado seja repassado por um canal explicitamente confiável — tipicamente um header HTTP (`X-Client-Cert` ou similar) contendo o certificado ou seu thumbprint, que a aplicação só aceita porque existe uma segunda camada de confiança entre gateway e aplicação (por exemplo, mTLS *também* entre gateway e backend, ou uma rede estritamente isolada). Sem esse cuidado, um atacante que conseguisse falar diretamente com a aplicação (contornando o gateway) poderia forjar esse header e personificar qualquer certificado.

Esse é um ponto arquitetural real, não teórico: provedores de nuvem e gateways de API adicionaram, ao longo do tempo, suporte específico para "passthrough de mTLS" (encaminhar o handshake original até o backend) ou para "encaminhamento de certificado via header confiável" justamente por causa dessa fricção repetida em implantações reais.

### Rotação de certificado

Como o token está amarrado a um certificado específico (via thumbprint), quando o client renova ou troca seu certificado (expiração natural, comprometimento suspeito, troca de CA), **qualquer token já emitido e vinculado ao certificado antigo se torna inutilizável** — o thumbprint apresentado na próxima conexão não vai mais bater. Na prática, isso raramente é um problema porque access tokens tendem a ter vida curta (minutos), então a rotação de certificado naturalmente "varre" tokens antigos sem precisar de um mecanismo explícito de "migração de vínculo". Para `refresh_token`s de vida mais longa, uma implantação cuidadosa precisa antecipar esse efeito: trocar o certificado de um client efetivamente revoga (silenciosamente) todos os `refresh_token`s vinculados ao certificado anterior.

### Modelo de confiança do `self_signed_tls_client_auth`

Sem cadeia de CA, o AS depende inteiramente de ter pré-registrado a chave pública exata esperada para aquele `client_id`, por um canal de registro que ele confia (fora de banda, geralmente no momento do onboarding do client). Se esse pré-registro for feito de forma frouxa (aceitar qualquer certificado que o client mandar por e-mail, por exemplo, sem verificação adicional de identidade), a "autenticação" vira teatro — a mesma disciplina de confiança prévia que já vimos com JWKS estático na RFC 7523.

### Certificados expirados ou revogados

A RFC não define, ela mesma, como o AS deve tratar validação de revogação (CRL, OCSP) — isso é delegado à infraestrutura PKI subjacente, do mesmo jeito que qualquer verificação TLS "normal" trataria. Uma implantação que usa `tls_client_auth` precisa ter uma política operacional clara sobre isso (checar OCSP a cada handshake? confiar apenas em CRLs atualizadas periodicamente?) — é uma responsabilidade que sai do escopo direto da RFC 8705 e cai inteiramente sobre a camada TLS/PKI da implantação.

## 6. Relação com outras RFCs

- Resolve diretamente a fraqueza que a **RFC 6750** já sinalizava como fora de escopo desde o capítulo 2 deste roteiro — um bom fechamento de ciclo para quem seguiu o roteiro em ordem.
- Estende a **RFC 9068** (JWT access tokens) via `cnf.x5t#S256`, e a **RFC 7662** (introspecção) via o membro `cnf` na resposta — ambos os pontos de extensão já haviam sido antecipados nos capítulos correspondentes deste roteiro.
- Método de autenticação de client alternativo ao **`private_key_jwt`** (RFC 7523 §2.2): os dois são baseados em chave assimétrica (sem segredo estático compartilhado), mas mTLS reaproveita infraestrutura de PKI/TLS já existente, enquanto `private_key_jwt` usa JWS/JWKS — sem exigir handshake TLS especial. A RFC 9700 recomenda qualquer um dos dois sobre `client_secret` estático, sem preferir um especificamente; a escolha é de implantação, conforme a infraestrutura já disponível (uma organização com PKI corporativa madura tende a mTLS; uma sem PKI tende a `private_key_jwt`).
- Irmã direta da **RFC 9449 (DPoP)**, próximo capítulo — as duas são mecanismos de *sender-constraining*, resolvendo o mesmo problema (roubo de bearer token) por caminhos diferentes: mTLS amarra o token à camada de **transporte** (exige PKI completa e infraestrutura mTLS, mais pesado, mas reaproveita controles de PKI já maduros como revogação de certificado); DPoP amarra o token à camada de **aplicação** (mais leve, sem PKI nenhuma, funciona sobre HTTPS comum, sem sofrer com a complicação de terminação de mTLS em gateways).
- Descoberta via **RFC 8414** através dos novos campos de metadata.

## 7. O que mudou desde a publicação (2020)

- Spec estável, cada vez mais **exigida** (não só recomendada) em setores de alta garantia. No seu contexto FSI, vale reter: **FAPI 2.0 trata sender-constraining (mTLS OU DPoP) como praticamente obrigatório** no perfil baseline, não como hardening opcional — não é mais "se vocês quiserem", é requisito de conformidade em muitos perfis regulatórios de open banking.
- A armadilha operacional de "terminação de TLS no gateway quebra mTLS" virou um problema bem documentado conforme mais organizações tentaram implantar isso na prática. Provedores de nuvem (AWS ALB/NLB, vários API gateways populares) adicionaram suporte específico a "passthrough de mTLS" ou "encaminhamento de certificado via header confiável", justamente para essa fricção repetida.
- A **RFC 9449 (DPoP)**, próximo capítulo, nasceu em boa parte porque a exigência de infraestrutura do mTLS (PKI completa, configuração cuidadosa de gateway, gestão de ciclo de vida de certificado de cliente) é pesada para muitas implantações — especialmente SPAs e apps mobile, onde gerenciar um certificado de cliente é operacionalmente incômodo (rotação, distribuição segura, revogação). DPoP costuma ser descrito como "a alternativa mais leve ao mTLS para sender-constraining".

Diferente de todos os capítulos anteriores do roteiro, este é o primeiro que exigiria genuinamente TLS real (certificados de cliente, possivelmente uma CA pequena para emiti-los) para fazer sentido — rompendo deliberadamente a simplificação de HTTP puro mantida em todos os labs até aqui (ver decisão de manter TLS adiado até este capítulo). ## Exemplo em Java (JDK 21, sem frameworks)

Os exemplos a seguir usam somente `java.security.*`, `javax.net.ssl.*` e `java.net.http.HttpClient` — nada de bibliotecas externas. Para os campos JSON de saída (quando necessário), reaproveitamos o utilitário `SimpleJson`, definido no Capítulo 1 (RFC 6749) deste livro.

> **Nota didática importante**: os exemplos abaixo usam `KeyStore`/`SSLContext` do próprio JDK para o handshake TLS em si (isso é produção-grade — é exatamente como uma aplicação Java real faria mTLS). Já o cálculo manual do thumbprint (`x5t#S256`) e a comparação com uma claim `cnf` de um JWT são feitos "na mão" apenas para fins didáticos, para expor o mecanismo. Em produção, a extração e validação de claims de um JWT (incluindo verificação de assinatura, `exp`, `aud`, etc.) deve usar uma biblioteca JOSE validada (ex.: Nimbus JOSE+JWT) — nunca parsing manual de JSON de um JWT em produção.

### 1. Cliente HTTP com certificado mTLS (`tls_client_auth`)

Configura um `HttpClient` para apresentar um certificado de cliente (com sua chave privada) durante o handshake TLS, ao chamar o token endpoint.

```java
import javax.net.ssl.KeyManagerFactory;
import javax.net.ssl.SSLContext;
import javax.net.ssl.TrustManagerFactory;
import java.io.FileInputStream;
import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.security.KeyStore;
import java.time.Duration;

public class ClienteMtls {

    /**
     * Monta um HttpClient que apresenta um certificado de cliente (X.509 +
     * chave privada) durante o handshake TLS — a prova de identidade do
     * client, no lugar de client_secret, acontece aqui, na camada de
     * transporte, ANTES de qualquer byte HTTP ser trocado.
     */
    static HttpClient criarClienteComCertificado(
            String keystorePath, char[] keystoreSenha,
            String truststorePath, char[] truststoreSenha) throws Exception {

        // KeyStore do CLIENT: contém o certificado X.509 do client + sua
        // chave privada correspondente. E a chave privada nunca sai deste
        // processo — só a assinatura implícita do handshake TLS viaja.
        KeyStore keyStore = KeyStore.getInstance("PKCS12");
        try (var in = new FileInputStream(keystorePath)) {
            keyStore.load(in, keystoreSenha);
        }
        KeyManagerFactory kmf = KeyManagerFactory.getInstance(
                KeyManagerFactory.getDefaultAlgorithm());
        kmf.init(keyStore, keystoreSenha);

        // TrustStore: quais CAs este client confia PARA VALIDAR O SERVIDOR
        // (o "outro lado" do mTLS — o client também precisa confiar no
        // certificado do AS, como em qualquer TLS normal).
        KeyStore trustStore = KeyStore.getInstance("PKCS12");
        try (var in = new FileInputStream(truststorePath)) {
            trustStore.load(in, truststoreSenha);
        }
        TrustManagerFactory tmf = TrustManagerFactory.getInstance(
                TrustManagerFactory.getDefaultAlgorithm());
        tmf.init(trustStore);

        SSLContext sslContext = SSLContext.getInstance("TLSv1.3");
        sslContext.init(kmf.getKeyManagers(), tmf.getTrustManagers(), null);

        return HttpClient.newBuilder()
                .sslContext(sslContext)
                .connectTimeout(Duration.ofSeconds(10))
                .build();
    }

    /**
     * POST /token autenticado por mTLS: repare que NÃO há client_secret nem
     * client_assertion no corpo — o certificado apresentado no handshake
     * (configurado acima) É a credencial do client.
     */
    static HttpResponse<String> requisitarToken(HttpClient client, String tokenEndpoint,
                                                 String clientId, String code,
                                                 String redirectUri) throws Exception {
        String corpo = "grant_type=authorization_code"
                + "&client_id=" + clientId
                + "&code=" + code
                + "&redirect_uri=" + redirectUri;

        HttpRequest request = HttpRequest.newBuilder()
                .uri(URI.create(tokenEndpoint))
                .header("Content-Type", "application/x-www-form-urlencoded")
                .POST(HttpRequest.BodyPublishers.ofString(corpo))
                .build();

        return client.send(request, HttpResponse.BodyHandlers.ofString());
    }
}
```

### 2. Calculando o thumbprint `x5t#S256` de um certificado

Do lado do resource server (ou de um validador standalone), calcula o SHA-256 sobre a codificação DER do certificado — exatamente o que o AS calculou ao emitir o token, e o que precisa bater com a claim `cnf.x5t#S256` recebida.

```java
import java.security.MessageDigest;
import java.security.cert.Certificate;
import java.security.cert.CertificateFactory;
import java.util.Base64;
import java.io.FileInputStream;

public class ThumbprintCertificado {

    /**
     * x5t#S256 (RFC 8705 §3.1): SHA-256 sobre a codificação DER do
     * certificado inteiro, em Base64URL sem padding. Determinístico — o
     * mesmo certificado sempre produz o mesmo thumbprint, permitindo
     * comparação simples de string em vez de comparar certificados inteiros.
     */
    static String calcularX5tS256(Certificate certificado) throws Exception {
        byte[] der = certificado.getEncoded(); // getEncoded() já retorna DER p/ X.509
        MessageDigest sha256 = MessageDigest.getInstance("SHA-256");
        byte[] hash = sha256.digest(der);
        return Base64.getUrlEncoder().withoutPadding().encodeToString(hash);
    }

    static Certificate carregarCertificadoDoKeystore(String path, char[] senha,
                                                       String alias) throws Exception {
        var keyStore = java.security.KeyStore.getInstance("PKCS12");
        try (var in = new FileInputStream(path)) {
            keyStore.load(in, senha);
        }
        return keyStore.getCertificate(alias);
    }

    // Alternativa: a partir de bytes PEM/DER recebidos por outro canal
    // (ex.: header de um gateway que repassa o certificado do client —
    // ver a discussão de "terminação de TLS quebra mTLS" na seção 5).
    static Certificate carregarCertificadoDePem(byte[] pemBytes) throws Exception {
        CertificateFactory cf = CertificateFactory.getInstance("X.509");
        return cf.generateCertificate(new java.io.ByteArrayInputStream(pemBytes));
    }
}
```

### 3. Validando um access token JWT com `cnf.x5t#S256` (resource server)

Extrai a claim `cnf.x5t#S256` de um JWT (parsing manual, só didático — ver nota acima) e compara com o thumbprint do certificado apresentado nesta conexão TLS.

```java
import java.util.Base64;
import java.util.Map;

public class ValidadorTokenVinculado {

    /**
     * Extrai o payload (segunda parte) de um JWT compacto e localiza
     * cnf.x5t#S256. Parsing manual, só didático — em produção, valide
     * assinatura/exp/aud/etc. com uma biblioteca JOSE antes de sequer olhar
     * para claims de negócio.
     */
    static String extrairThumbprintEsperado(String jwtCompacto) {
        String[] partes = jwtCompacto.split("\\.");
        if (partes.length != 3) {
            throw new IllegalArgumentException("JWT malformado");
        }
        String payloadJson = new String(
                Base64.getUrlDecoder().decode(partes[1]),
                java.nio.charset.StandardCharsets.UTF_8);

        // parseFlat aqui é ilustrativo — um payload de JWT real tem
        // estrutura aninhada (cnf é um objeto dentro do payload); um parser
        // de produção precisaria de suporte a objetos aninhados, que o
        // SimpleJson (utilitário do Capítulo 1) não cobre por ser
        // deliberadamente simples. Adaptar conforme a estrutura real.
        Map<String, String> payload = SimpleJson.parseFlat(payloadJson);
        return payload.get("cnf.x5t#S256"); // ilustrativo — depende do parser usado
    }

    /**
     * O passo de segurança central da RFC 8705: token só é aceito se o
     * thumbprint do certificado NESTA conexão bater com o vinculado ao token.
     */
    static boolean tokenValidoParaEstaConexao(String thumbprintEsperado,
                                                String thumbprintDaConexaoAtual) {
        if (thumbprintEsperado == null) {
            // Token não é vinculado a certificado — decisão de política:
            // uma implantação que EXIGE sender-constraining deve rejeitar
            // aqui, não tratar como "válido sem vínculo".
            return false;
        }
        // Comparação de thumbprints — strings já normalizadas (Base64URL),
        // então comparação direta é suficiente (evite MessageDigest.isEqual
        // aqui não ser necessário: não estamos comparando segredos, e sim
        // valores públicos e determinísticos).
        return thumbprintEsperado.equals(thumbprintDaConexaoAtual);
    }
}
```
