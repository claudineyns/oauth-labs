# RFC 8707 — Resource Indicators for OAuth 2.0

## 1. Contexto e motivação

Este é o capítulo onde fechamos, com profundidade, a pergunta que ficou em aberto desde o capítulo da RFC 6819: **a segmentação clara de nomes de scope por recurso já não resolveria o problema de "confused deputy" sozinha, sem precisar de um mecanismo dedicado de audience?**

### A análise completa: scope segregado resolve o problema?

Considere o cenário canônico de confused deputy em OAuth: um token emitido com `scope=accounts:read` (pensado, no momento da emissão, para ser usado contra a API de contas) é apresentado — por engano do client, por um proxy mal configurado, ou por má-fé de um atacante que o interceptou — à API de pagamentos. A pergunta que a RFC 6819 deixou em aberto informalmente é: se os nomes de scope forem bem segregados (`accounts:read` nunca significando nada em nenhum outro serviço), isso já não bastaria?

**No caso concreto isolado, sim, funciona**: a API de pagamentos, ao checar se o token apresentado tem `payments:read` ou `payments:write`, não vai encontrar nenhum desses scopes — porque o token só tem `accounts:read` — e rejeita a chamada. Nomenclatura limpa de scope, sozinha, evita essa ação indevida específica.

O problema é que essa proteção depende inteiramente de **disciplina de implementação em cada resource server individual**, não de uma garantia estrutural do protocolo. Vamos decompor por que isso é uma diferença importante, não só uma nuance acadêmica:

**(a) Nada no protocolo obriga um resource server a checar o nome de scope específico dele.** Um serviço mal implementado — por bug de regex numa checagem de scope, por uma checagem frouxa do tipo "aceita qualquer scope que comece com o prefixo `read`", ou, pior ainda, por só conferir `active: true` numa resposta de introspecção sem sequer olhar o campo `scope` retornado — aceita o token mesmo com nomenclatura perfeitamente segregada. A proteção nunca foi do protocolo: foi do código específico de quem escreveu aquele resource server, e código específico tem bugs, tem pressa de deadline, e não é auditado com a mesma disciplina em toda uma organização.

**(b) A unicidade global de nomes de scope é, na prática, um problema de governança organizacional — não um problema técnico resolvido pelo protocolo.** Numa organização grande, com dezenas ou centenas de times construindo APIs ao longo de vários anos, garantir que ninguém nunca reaproveite um nome de scope (seja por coincidência, seja copiando um serviço existente como ponto de partida e esquecendo de renomear) é uma disciplina que **degrada com o tempo**. Não existe um registro central de scopes que o protocolo exija ou valide — é convenção pura, sujeita a toda a entropia normal de organizações grandes: rotatividade de equipe, documentação desatualizada, pressão de prazo.

**(c) Confused deputy não é só "o escopo errado foi concedido" — é "a parte errada aceitou essa credencial".** Este é o ponto mais sutil e o mais importante de reter: mesmo um token com scope **corretamente nomeado** e **corretamente checado** pelo resource server pode, ainda assim, ser aceito por um resource server que **não deveria**, estruturalmente, receber tokens daquele tipo. Exemplo concreto: um ambiente de staging, menos confiável que produção (talvez rodando código de um branch de feature ainda não revisado), que por coincidência de arquitetura compartilhada também expõe um endpoint que checa `accounts:read` — e aceita, porque o scope bate, mesmo que esse ambiente jamais devesse estar processando tokens de produção. Nomenclatura de scope distingue **"o que pode ser feito"** (a ação/permissão), mas não distingue **"com quem o token pode falar"** (o destinatário pretendido) — são dois eixos ortogonais, e scope só cobre um deles.

**Conclusão da análise**: segmentação de nomes de scope é uma mitigação real, vale a pena manter como defesa em profundidade, e reduz consideravelmente o risco prático. Mas não é um substituto estrutural para uma restrição de audience, exatamente porque depende de disciplina de nomenclatura e de implementação correta em **absolutamente todo** resource server do ecossistema, em vez de uma garantia reforçada pelo próprio protocolo — uma garantia que não depende de como os scopes foram nomeados, nem de quão disciplinado foi o time que implementou aquele resource server específico. É exatamente essa lacuna estrutural que a RFC 8707 fecha, introduzindo um sinal explícito, no próprio pedido, de qual recurso o token deve servir — sinal que depois "pousa" na claim `aud` do token, verificável de forma padronizada por qualquer resource server, independentemente de como seus scopes foram nomeados.

## 2. Terminologia e papéis

Nenhum papel novo. Introduz:

- **`resource`** — parâmetro novo, de valor **URI absoluta** (sem fragmento), identificando o resource server que o client pretende usar com o token resultante daquela requisição específica.
- **Resource Indicator** — o nome que a RFC dá a essa declaração explícita, feita pelo client no momento do pedido: "este token é para conversar com **este** destinatário, e não com qualquer outro que aceite o mesmo scope".

### Por que URI, e não um identificador arbitrário?

A escolha de usar uma URI absoluta (tipicamente a própria base URL do resource server, ex. `https://api.exemplo.com/pagamentos`) em vez de um identificador opaco arbitrário tem duas vantagens práticas: (1) reaproveita um formato que o ecossistema HTTP já entende e já valida (sintaxe de URI é padronizada, RFC 3986); (2) frequentemente já corresponde a algo que o resource server já sabe reconhecer sobre si mesmo (sua própria base URL), simplificando a checagem de audience do lado do RS — comparar a claim `aud` recebida contra "minha própria URI conhecida" é uma operação direta.

## 3. Fluxo

```
GET /authorize?response_type=code&client_id=...
    &resource=https://api.exemplo.com/pedidos&scope=...

ou, no token endpoint (qualquer grant, incluindo client_credentials):

POST /token
grant_type=...&resource=https://api.exemplo.com/pedidos&...

AS valida se o client tem permissao de obter token para ESSE resource, com ESSE scope
AS emite o token restrito aquele resource (aud = o resource pedido, ou uma lista, se multiplo)
```

O parâmetro `resource` pode aparecer **mais de uma vez** na mesma requisição, se o client quiser (ou precisar) de um token válido para vários recursos simultaneamente. A RFC deixa como decisão de implantação o que o AS faz nesse caso:

- **Emitir um único token multi-audience** — `aud` vira uma lista com todos os recursos pedidos, e cada resource server precisa checar se **seu próprio** identificador está presente na lista (não checar igualdade estrita, e sim pertencimento).
- **Recusar por ambiguidade** — alguns AS, especialmente em perfis de alta garantia (FAPI, por exemplo), preferem restringir a **um único** `resource` por token, simplificando a checagem de audience do lado do RS para uma comparação de igualdade direta, e reduzindo a superfície de um token "poderoso demais" que fala com múltiplos serviços simultaneamente.

### Caso de borda: `resource` ausente

Quando o client não informa `resource` nenhum, o comportamento cai para o que o AS já fazia antes desta RFC existir — normalmente emitir um token sem restrição explícita de audience (ou com uma audience padrão pré-configurada por client/scope, dependendo da implantação). A RFC não obriga que `resource` seja sempre exigido; ela introduz o mecanismo, e cabe a cada AS (ou a um perfil de segurança específico, como FAPI) decidir se torna esse parâmetro obrigatório.

### Caso de borda: `resource` pedido mas não autorizado para aquele client

O AS deve validar se o client em questão está de fato autorizado a obter tokens para aquele `resource` específico — um client registrado para falar apenas com a API de contas não deveria conseguir simplesmente pedir `resource=https://api.exemplo.com/pagamentos` e receber um token válido para pagamentos só porque pediu. Essa validação é responsabilidade do AS (ver seção 5) — sem ela, o parâmetro `resource` seria apenas decorativo, sem nenhum reforço real de segurança.

### Caso de borda: `resource` e `scope` interagindo

Um mesmo client pode ter diferentes scopes válidos para diferentes recursos (ex.: `accounts:read` faz sentido para `resource=https://api.exemplo.com/contas`, mas não para `resource=https://api.exemplo.com/pagamentos`). O AS precisa avaliar a combinação `(client, resource, scope)` como um todo — não apenas `(client, scope)` isoladamente, como fazia antes desta RFC. Isso pode exigir uma tabela de política mais rica no AS (matriz client × resource × scope permitido), mas é exatamente o ganho de granularidade que a RFC entrega.

## 4. Parâmetros e endpoints normativos

Nenhum endpoint novo — estende tanto a requisição de autorização (RFC 6749 §4.1.1) quanto a requisição de token, com o parâmetro `resource`, repetível.

- **Também utilizável na RFC 8693 (Token Exchange)** — que já usava exatamente esse mesmo parâmetro `resource` antes desta RFC existir formalmente. A RFC 8707 generaliza o parâmetro (que nasceu ligado ao Token Exchange) para os grants padrão do núcleo OAuth (Authorization Code, Client Credentials, etc.), não só para cenários de troca de token.
- **Descoberta via RFC 8414**: campo de metadata do AS indicando suporte ao parâmetro (ex. algo equivalente a `resource_parameter_supported` em implementações que expõem esse detalhe de descoberta).
- **Não há um novo formato de resposta** — o efeito do parâmetro aparece indiretamente, na claim `aud` do token emitido (JWT, RFC 9068) ou no campo `aud` de uma resposta de introspecção (RFC 7662), nunca como um campo próprio na resposta do próprio `/token`.

## 5. Segurança já tratada na própria RFC 8707

- **O AS deve validar** se o client está autorizado a obter token para o `resource` pedido, com aquele `scope` específico — a RFC é explícita que o AS não deve simplesmente aceitar qualquer `resource` que o client informe e ecoar de volta sem checagem. Sem essa validação do lado do AS, o parâmetro vira só uma sugestão do client, sem reforço de segurança nenhum.
- **Recomenda fortemente que resource servers validem a audience** dos tokens que recebem — este é o ponto onde a decisão tomada no momento do pedido (`resource`) precisa efetivamente "pousar" em algum lugar verificável e concreto: a claim `aud` de um JWT access token (RFC 9068), ou o campo `aud` de uma resposta de introspecção (RFC 7662). Um AS que suporta `resource` mas cujos resource servers nunca checam `aud` está implementando só metade do mecanismo — a metade que não protege nada sozinha.
- Reforça, de forma **estrutural** (não dependente de disciplina de nomenclatura de scope, nem de qualidade de implementação de cada RS individual), exatamente a proteção que a análise da seção 1 mostrou que a segmentação de scope, sozinha, não conseguia garantir de forma confiável em toda uma organização.
- **Vazamento de topologia interna**: um efeito colateral a se ter em mente — o valor de `resource` frequentemente revela a URL real de um serviço interno (ex. `https://internal-payments.corp.example.com/api`). Em fluxos onde o parâmetro trafega pelo user-agent (a requisição de autorização, tipicamente redirecionada pelo browser), isso pode expor detalhes de topologia de rede interna que a organização preferiria não tornar públicos. Mitigação natural: combinar com **PAR (RFC 9126)**, que tira o parâmetro do browser inteiramente, movendo-o para uma chamada backend-to-backend direta entre client e AS.

## 6. Relação com outras RFCs

- Resolve diretamente a preocupação de "confused deputy" catalogada informalmente na **RFC 6819**, e reforçada explicitamente pela **RFC 9700** como prática recomendada moderna.
- A claim `aud` da **RFC 9068** (JWT access tokens) e o campo `aud` da resposta de introspecção da **RFC 7662** são exatamente onde a decisão de `resource` desta RFC fica registrada, de forma verificável, no token — a mesma divisão "decisão no pedido vs. efeito registrado no token" que já vimos entre a RFC 8693 (Token Exchange) e a RFC 9068.
- Companheira direta da **RFC 8693 (Token Exchange)**, que já usava esse mesmo parâmetro `resource` antes desta RFC generalizá-lo para os grants padrão do núcleo OAuth.
- Combina naturalmente com a **RFC 9126 (PAR)** para evitar o vazamento de topologia interna discutido na seção 5, tirando o parâmetro `resource` do browser.
- É o penúltimo degrau de uma escada de least privilege que atravessa o roteiro inteiro, e que o próximo capítulo (RFC 9396) fecha: escopo amplo (RFC 6749) → escopo mínimo por convenção (RFC 6750) → **audience estruturalmente restrita** (esta RFC) → detalhe no nível de uma transação específica (RFC 9396, próximo capítulo).
- Fecha o ciclo aberto desde o capítulo da RFC 6819 e revisitado tanto na RFC 8693 (o cenário de gateway como confused deputy) quanto na RFC 9068 (onde a claim `aud` foi definida como ponto de extensão).

## 7. O que mudou desde a publicação (2020)

- Adoção crescente, particularmente em implantações com múltiplos resource servers/microsserviços — exatamente o cenário onde a análise da seção 1 mostra que confiar só em nomenclatura de scope se torna frágil com a escala.
- Em perfis adjacentes a FAPI — que, no seu contexto FSI, já esperam indicação explícita de recurso em vez de depender só de disciplina de nomenclatura de escopo, exatamente como a análise da seção 1 concluiu ser insuficiente sozinha.
- Continua sendo, junto com a RFC 8693, a resposta estrutural moderna ao problema que a RFC 6819 catalogou informalmente mais de uma década antes — um bom exemplo de como o ecossistema OAuth vai fechando lacunas conhecidas há muito tempo com mecanismos formalizados, um RFC de cada vez.

> **Nota de laboratório**: nenhum lab construído ainda para esta RFC neste projeto. Um cenário natural seria estender um lab existente com múltiplos resource servers simulados, mostrando o mesmo `client_id` obtendo tokens com `aud` diferentes conforme o `resource` pedido, e um resource server rejeitando explicitamente um token cuja `aud` não bate com sua própria identidade — exercitando exatamente o mecanismo de confused deputy discutido na seção 1. Os exemplos de código abaixo são, portanto, standalone.

## Exemplo em Java (JDK 21, sem frameworks)

Usamos `java.net.http.HttpClient` para montar as requisições com o parâmetro `resource`, e o utilitário `SimpleJson`, definido no Capítulo 1 (RFC 6749) deste livro, para lidar com o payload do token.

> **Nota didática**: como nos capítulos anteriores desta parte, extrair a claim `aud` de um JWT abaixo é feito com parsing manual só para fins didáticos. Em produção, valide o JWT inteiro (assinatura, `exp`, `nbf`, etc.) com uma biblioteca JOSE antes de examinar qualquer claim de negócio como `aud`.

### 1. Incluindo `resource` na authorization request e no `/token`

```java
import java.net.URI;
import java.net.URLEncoder;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.nio.charset.StandardCharsets;

public class ClienteComResourceIndicator {

    /**
     * Monta a URL de authorization request incluindo resource — a
     * declaracao explicita, feita ja no PEDIDO, de para qual resource
     * server o token resultante deve valer. O parametro pode ser
     * repetido se o client precisar de token multi-audience (o AS decide
     * se aceita ou recusa por ambiguidade — secao 3).
     */
    static String montarUrlAutorizacao(String authorizationEndpoint, String clientId,
                                         String redirectUri, String scope,
                                         String resource, String state,
                                         String codeChallenge) {
        return authorizationEndpoint
                + "?response_type=code"
                + "&client_id=" + urlEncode(clientId)
                + "&redirect_uri=" + urlEncode(redirectUri)
                + "&scope=" + urlEncode(scope)
                + "&resource=" + urlEncode(resource) // URI absoluta do RS pretendido
                + "&state=" + urlEncode(state)
                + "&code_challenge=" + urlEncode(codeChallenge)
                + "&code_challenge_method=S256";
    }

    /**
     * POST /token repetindo o MESMO resource usado na authorization
     * request — praticas recomendadas sugerem consistencia entre os dois
     * pedidos, embora a RFC nao proiba um AS de tratar o resource do
     * /token como a fonte de verdade final.
     */
    static HttpResponse<String> trocarCodePorToken(HttpClient client, String tokenEndpoint,
                                                     String clientId, String code,
                                                     String redirectUri, String codeVerifier,
                                                     String resource) throws Exception {
        String corpo = "grant_type=authorization_code"
                + "&client_id=" + urlEncode(clientId)
                + "&code=" + urlEncode(code)
                + "&redirect_uri=" + urlEncode(redirectUri)
                + "&code_verifier=" + urlEncode(codeVerifier)
                + "&resource=" + urlEncode(resource);

        HttpRequest request = HttpRequest.newBuilder()
                .uri(URI.create(tokenEndpoint))
                .header("Content-Type", "application/x-www-form-urlencoded")
                .POST(HttpRequest.BodyPublishers.ofString(corpo))
                .build();

        return client.send(request, HttpResponse.BodyHandlers.ofString());
    }

    private static String urlEncode(String valor) {
        return URLEncoder.encode(valor, StandardCharsets.UTF_8);
    }
}
```

### 2. Validando `aud` no resource server (mitigação de confused deputy)

```java
import java.util.Base64;
import java.util.List;
import java.util.Map;

public class ValidadorAudience {

    /**
     * Identidade PROPRIA deste resource server especifico — normalmente
     * configurada, nao descoberta dinamicamente. E o valor que este RS
     * exige encontrar na claim aud de qualquer token que aceitar.
     */
    private static final String MINHA_IDENTIDADE_DE_RECURSO =
            "https://api.exemplo.com/pagamentos";

    /**
     * Extrai o payload de um JWT compacto (parsing manual, so didatico —
     * ver nota no topo do capitulo).
     */
    static String extrairPayloadJson(String jwtCompacto) {
        String[] partes = jwtCompacto.split("\\.");
        if (partes.length != 3) {
            throw new IllegalArgumentException("JWT malformado");
        }
        return new String(Base64.getUrlDecoder().decode(partes[1]),
                java.nio.charset.StandardCharsets.UTF_8);
    }

    /**
     * O passo de seguranca central desta RFC, do lado do resource server:
     * antes de aceitar QUALQUER chamada, confirmar que este token foi
     * emitido pensando EXPLICITAMENTE neste resource server — nao aceitar
     * so porque o scope aparenta bater (a licao da secao 1: scope sozinho
     * nao e suficiente).
     *
     * aud pode ser uma unica string ou uma lista (quando o AS emitiu um
     * token multi-audience) — tratamos os dois casos.
     */
    static boolean audienceValidaParaEsteRecurso(List<String> audiencesDoToken) {
        if (audiencesDoToken == null || audiencesDoToken.isEmpty()) {
            // Sem aud nenhuma: politica de seguranca deste RS deve decidir
            // se rejeita (recomendado, se este RS exige resource indicator)
            // ou aceita com uma politica de fallback mais permissiva.
            return false;
        }
        return audiencesDoToken.contains(MINHA_IDENTIDADE_DE_RECURSO);
    }

    /**
     * Fluxo completo simplificado: parseia, extrai aud (aqui ilustrado
     * com um unico valor via SimpleJson.parseFlat; um payload real com
     * aud como array exigiria um parser com suporte a listas, que o
     * SimpleJson didatico do Capitulo 1 nao cobre por simplicidade) e
     * decide se aceita a chamada.
     */
    static boolean validarChamada(String accessTokenJwt) {
        String payloadJson = extrairPayloadJson(accessTokenJwt);
        Map<String, String> payload = SimpleJson.parseFlat(payloadJson);
        String aud = payload.get("aud"); // ilustrativo — adaptar para lista se necessario
        if (aud == null) {
            return false;
        }
        return audienceValidaParaEsteRecurso(List.of(aud));
    }
}
```
