# RFC 9068 — JSON Web Token (JWT) Profile for OAuth 2.0 Access Tokens

## 1. Contexto e motivação

A RFC 6749 deixa o formato do `access_token` deliberadamente indefinido — é uma string opaca, ponto final, e o resource server "simplesmente sabe" como validá-la por algum meio fora do escopo da especificação (tipicamente, um dos dois caminhos que este livro já cobriu: leitura direta de um armazenamento compartilhado, como nos labs deste projeto, ou introspecção via RFC 7662). Essa flexibilidade foi proposital — o OAuth 2.0 nunca quis prescrever formato de token, só o protocolo de obtenção — mas criou um problema real de interoperabilidade ao longo da década seguinte: **vários fornecedores passaram a usar JWT como access token de forma independente, cada um com seu próprio conjunto de claims, sem um vocabulário comum**. Um resource server construído para entender o JWT de um fornecedor não entendia o de outro, mesmo os dois sendo nominalmente "access token em formato JWT" — a mesma tecnologia de base (JWS/JWT, RFC 7515/7519), mas nomes de claim, obrigatoriedades e convenções divergentes o suficiente para inviabilizar reuso de bibliotecas de validação entre ecossistemas.

A RFC 9068 (2021) formaliza a **estrutura** de um JWT quando usado como access token — claims obrigatórias/recomendadas e, principalmente, um valor de `typ` no header que **autodeclara** "isto é especificamente um access token JWT", evitando confusão com outros tipos de JWT circulando pelo mesmo sistema (notavelmente, o ID Token do OpenID Connect, que compartilha boa parte do vocabulário de claims mas tem um propósito semântico completamente diferente).

### 1.1 A diferença entre "JWT como access token" e "JWT como formato universal"

É importante não interpretar esta RFC como "todo access token deveria ser JWT". A própria RFC é explícita que continua sendo uma escolha legítima do AS emitir tokens opacos — o que ela resolve é **quando** o AS decide usar JWT, garantindo que essa escolha produza um artefato interoperável, em vez de mais um formato proprietário reinventado. Em outras palavras: RFC 9068 não é uma RFC sobre "usar JWT", é uma RFC sobre "se você vai usar JWT como access token, faça assim, e não de outro jeito qualquer".

### 1.2 O problema concreto de "confusão de JWT" que motiva o `typ`

Antes de existir um marcador de tipo explícito, um sistema com múltiplos emissores de JWT (o próprio AS emitindo ID Tokens do OIDC **e** access tokens, por exemplo) corre o risco de um componente de validação aceitar por engano um JWT emitido para um propósito diferente do que ele espera. Um ID Token, por design, tem claims como `sub` (o usuário), `aud` (o client_id, não o resource server!), `iss` — muito parecido em forma com um access token JWT, mas com **semântica de audience completamente diferente**: o público-alvo pretendido de um ID Token é o *client* que fez o login, não um resource server de API. Um resource server que, por erro de implementação, aceitasse um ID Token como se fosse um access token válido estaria confiando numa prova de identidade pensada para outro consumidor e outro propósito — uma classe real e documentada de vulnerabilidade ("confusão de tipo de token"/JWT confusion), não uma preocupação teórica.

## 2. Terminologia e papéis

Nenhum papel novo. Introduz:

- **JWT Access Token** — um JWT que segue este perfil específico: conjunto de claims definido, header com `typ` marcado.
- **`typ: at+jwt`** no header — marcador de tipo explícito (o valor completo, quando usado como cabeçalho `Content-Type` de uma requisição HTTP que carregue o token, seria `application/at+jwt`; dentro do header JOSE do próprio JWT, o valor abreviado `at+jwt` é o convencional, seguindo a mesma convenção de tipos estruturados definida pela RFC 8725/RFC 7515).
- **Media Type Structured Syntax Suffix** — o sufixo `+jwt` em `at+jwt` segue a convenção de nomenclatura de tipos de mídia estruturados (RFC 6839), o mesmo padrão que dá nomes como `application/at+jwt` ao invés de simplesmente reaproveitar `application/jwt` genérico para tudo. A ideia é permitir que ferramentas genéricas de processamento de JWT reconheçam "isto é um JWT" (pelo sufixo) e ferramentas específicas de OAuth reconheçam "isto é especificamente um access token" (pelo prefixo `at`).

## 3. "Fluxo" — não há fluxo novo, é um formato aplicado ao que já existe

Esta RFC não define endpoint nem grant novo — ela governa o **formato** do valor que já volta no campo `access_token` da resposta padrão do token endpoint (RFC 6749 §5.1), quando o AS escolhe emitir tokens em JWT em vez de opacos. A resposta do `/token` continua tendo exatamente a mesma forma:

```json
{
  "access_token": "<agora um JWT compacto, em vez de uma string aleatoria>",
  "token_type": "Bearer",
  "expires_in": 300,
  "scope": "profile email"
}
```

A única mudança está **dentro** do valor de `access_token` — antes 48 caracteres hexadecimais aleatórios sem estrutura, agora três segmentos Base64URL separados por ponto (header.payload.assinatura), estruturados conforme as regras abaixo.

### 3.1 Estrutura do header

```json
{
  "typ": "at+jwt",
  "alg": "RS256",
  "kid": "chave-do-as-2026-01"
}
```

O `kid` (Key ID) não é exigido pela RFC 9068 diretamente, mas é praticamente indispensável na prática: como o resource server precisa saber **qual** chave pública usar para verificar a assinatura (o AS tipicamente tem mais de uma chave ao longo do tempo, por rotação), o `kid` funciona como um índice dentro do conjunto de chaves publicado via `jwks_uri` (RFC 8414 + o formato JWK Set da RFC 7517).

### 3.2 Claims exigidas/recomendadas pelo perfil

| Claim | Status | Significado |
|---|---|---|
| `iss` | obrigatória | Identificador do AS — mesmo valor do `issuer` publicado via metadata da RFC 8414 |
| `exp` | obrigatória | Expiração |
| `iat` | obrigatória | Momento de emissão |
| `aud` | obrigatória | Identifica o(s) resource server(s) destinatário(s) — pode ser um array, se o token é destinado a mais de um RS |
| `sub` | obrigatória | De quem o token fala — o resource owner, em grants delegados (Authorization Code); o próprio client, em Client Credentials Grant (onde não há resource owner) |
| `client_id` | obrigatória | Deliberadamente **distinta** de `sub` — num grant delegado, `sub` é o usuário e `client_id` é o app agindo em nome dele; confundir os dois é um erro sutil e recorrente de implementações que tentam "economizar" uma claim |
| `jti` | obrigatória | Identificador único do token — mesmo conceito de unicidade já visto no `client_assertion` da RFC 7523, aplicado agora ao próprio access token |
| `scope` | recomendada | Mesma string espaço-delimitada de sempre |
| `auth_time` | opcional | Quando o resource owner efetivamente se autenticou (não quando o token foi emitido — podem ser momentos bem diferentes, por exemplo num refresh) |
| `acr` | opcional | Authentication Context Class Reference — "com que nível de garantia" a autenticação ocorreu |
| `amr` | opcional | Authentication Methods References — "por quais métodos" (senha, biometria, segundo fator) |

Os três últimos (`auth_time`, `acr`, `amr`) são emprestados conceitualmente do ID Token do OpenID Connect — e essa vizinhança semântica é exatamente o motivo pelo qual o marcador `typ` é tão importante: um access token JWT e um ID Token OIDC podem, na prática, compartilhar boa parte do vocabulário de claims, tornando ainda mais fácil confundir um pelo outro sem um marcador de tipo explícito no header.

### 3.3 Por que `sub` e `client_id` precisam ser claims separadas

Vale insistir neste ponto porque é um erro real e recorrente. Considere um Authorization Code Grant onde Alice autoriza o aplicativo "MeuApp" a acessar sua conta:

- `sub = "alice"` — de quem o token fala, o resource owner que concedeu a autorização.
- `client_id = "meuapp-web"` — quem está de fato segurando o token e fazendo a chamada de API.

Um resource server que precise decidir "este client tem permissão para fazer isto, independente do usuário" (uma checagem de allowlist de aplicações, por exemplo) usa `client_id`. Um resource server que precise decidir "este usuário tem permissão para ver este recurso" usa `sub`. Confundir as duas claims — por exemplo, um RS mal implementado que aplica uma regra de autorização usando `sub` quando deveria usar `client_id` — pode abrir brechas onde a identidade errada é usada para a decisão de autorização errada. Já no Client Credentials Grant (onde não existe resource owner), `sub` costuma ser igual ao próprio `client_id`, porque não há "outro" de quem falar.

## 4. Parâmetros e endpoints normativos

Nenhum endpoint novo. O único parâmetro normativo relevante é de **header do próprio JWT**, não de protocolo HTTP: `typ` deve ser `at+jwt` (ou, em contextos de `Content-Type` HTTP, `application/at+jwt`), e `alg` precisa ser um algoritmo de assinatura de verdade — **nunca `none`**. A RFC reforça explicitamente essa proibição porque `alg: none` é uma das armadilhas mais conhecidas e mais fáceis de introduzir acidentalmente numa implementação de validação de JWT malfeita (uma biblioteca que, ao ver `alg: none`, simplesmente pula a etapa de verificação de assinatura).

### 4.1 O que a RFC não normatiza (e por que isso importa)

A RFC 9068 não define:
- **Qual algoritmo de assinatura usar** (RS256, PS256, ES256 — todos são compatíveis com o perfil, desde que não seja `none` e desde que o RS saiba qual esperar para aquele `iss`/`kid`).
- **Como o resource server descobre a chave pública** — isso é delegado à RFC 8414 (`jwks_uri`) e RFC 7517 (formato JWK).
- **Se o token deve ou não ser criptografado (JWE)** além de assinado (JWS) — deixado como uma opção, não uma exigência (ver seção 5.3).

Essa omissão deliberada é consistente com o espírito geral do ecossistema de RFCs deste livro: cada especificação resolve uma fatia específica do problema, e composição entre elas é o que produz um sistema completo.

## 5. Segurança já tratada na própria RFC 9068

### 5.1 `typ: at+jwt` previne confusão de tipo de token

Sem essa autodeclaração explícita, um resource server (ou uma biblioteca mal implementada, ou um desenvolvedor que copiou código de validação de ID Token achando que servia igualmente para access token) poderia aceitar por engano um JWT emitido para **outro propósito** como se fosse um access token válido — uma classe real de vulnerabilidade histórica ("confusão de JWT"), já discutida na seção 1.2. O `typ` explícito permite ao código de validação do RS checar, **antes de confiar em qualquer outra coisa** (antes mesmo de verificar a assinatura, idealmente, como uma checagem rápida de "isto sequer é o tipo certo de artefato"), se aquele JWT realmente foi emitido para ser um access token.

A ordem de validação recomendada na prática costuma ser: (1) parsear a estrutura, (2) checar `typ` no header, (3) verificar assinatura com a chave correta para o `alg`/`kid` declarados, (4) só então validar as claims de conteúdo (`exp`, `aud`, `iss`, `sub`...). Fazer a checagem de `typ` antes da assinatura é uma otimização de "fail fast" — rejeitar rápido tokens do tipo errado sem gastar o custo de uma verificação criptográfica que de qualquer forma levaria à rejeição por outro motivo.

### 5.2 `aud` restringe quais resource servers podem aceitar o token

Operacionaliza diretamente a preocupação de restrição de audience já discutida na RFC 6819 (o cenário do "confused deputy" — um RS que aceita um token pensado para outro RS, agindo como intermediário involuntário de um ataque) e que a RFC 8707 (Resource Indicators) formaliza do lado da **requisição** (o client pede um token para um recurso específico). A RFC 9068 é o "ponto de pouso" dessa preocupação: é aqui que a decisão de audience fica efetivamente registrada **dentro do próprio token**, como uma claim que qualquer RS pode e deve checar antes de aceitar o token como seu.

Um resource server correto verifica que **o próprio identificador dele** está presente em `aud` (que pode ser uma string única ou um array de valores, quando o token é válido para múltiplos RSs) — e rejeita qualquer token onde isso não seja verdade, mesmo que a assinatura seja perfeitamente válida e o token não tenha expirado. Um token assinado corretamente pelo AS, mas destinado a outro RS, **não é válido para este RS** — a assinatura prova quem emitiu, não para quem foi destinado.

### 5.3 Sem criptografia por padrão — a troca entre legibilidade e confidencialidade

Um JWT access token normalmente é assinado (JWS), não criptografado — suas claims são legíveis em texto (Base64URL, tecnicamente, mas Base64 não é criptografia, é só codificação) por qualquer um que tenha o token, diferente de um token opaco (cujo "significado" fica trancado dentro do AS, inacessível a quem não tem acesso ao armazenamento interno). É uma troca real:

- **Legibilidade/validação local ganha** — o RS não precisa perguntar a ninguém, decodifica e valida sozinho.
- **Confidencialidade do conteúdo perde** — qualquer intermediário que veja o token (um proxy, um log de acesso mal configurado que grava cabeçalhos `Authorization`, o próprio navegador do usuário em certos fluxos) consegue ler `sub`, `scope`, e qualquer outra claim, mesmo sem conseguir *usar* o token (a assinatura impede forjar um novo, mas não impede ler o existente).

A RFC permite (não exige) usar JWE — JSON Web Encryption, o par criptográfico do JWS — por cima da assinatura quando as claims forem sensíveis o suficiente para justificar esse custo adicional. É o mesmo par JWS/JWE já visto no contexto do Request Object da RFC 9101 (JAR), aplicado aqui ao access token em vez de à requisição de autorização.

### 5.4 Revogação fica mais difícil de aplicar em tempo real

Validação local por assinatura significa que o RS confia no token até o `exp`, sem checar de novo com o AS — a mesma troca já apontada no capítulo da RFC 7662: JWT evita o round-trip de rede, mas perde a capacidade do AS dizer "na verdade, acabei de revogar esse token" no meio da vida dele. Se um token JWT com `exp` de 1 hora é comprometido (roubado) 5 minutos depois de emitido, ele continua válido — do ponto de vista de qualquer RS que o valide localmente — pelos 55 minutos restantes, mesmo que o AS já tenha sido informado do comprometimento e queira revogá-lo.

Mitigações práticas, já discutidas de forma mais geral no capítulo da RFC 7662:
- **Tempos de vida curtos** — reduzir a janela de exposição ao custo de refresh mais frequente.
- **Padrão híbrido** — JWT para o caso comum (validação rápida, local) + checagem extra de revogação (introspecção, ou consulta a uma lista de revogação) só em operações de alto valor (transações financeiras, mudanças administrativas irreversíveis).
- **`cnf` (confirmation) e sender-constraining** — amarrar o token a uma chave/certificado específico (RFC 8705 mTLS, RFC 9449 DPoP — ver seção 7) reduz o *impacto* de um token roubado mesmo sem revogação em tempo real, porque o token roubado sozinho não basta para uso — ainda seria necessário possuir a chave/certificado associado.

### 5.5 Nuances adicionais de validação que a prática exige

- **Verificação de `alg` no header nunca deve ser delegada ao próprio token.** Assim como discutido no capítulo da RFC 7523, um resource server deve fixar de antemão quais algoritmos aceita para aquele `iss`/`kid`, nunca "confiar" cegamente no `alg` declarado no header recebido — a mesma classe de ataque de confusão de algoritmo (RS256-para-HS256, ou aceitação acidental de `none`) se aplica aqui integralmente.
- **Tamanho do token cresce em relação ao opaco.** Um access token JWT tipicamente ocupa várias centenas de bytes a mais de um caso opaco de 32-48 caracteres — relevante em cenários com limites estritos de tamanho de cabeçalho HTTP, ou alto volume de tráfego onde esse overhead se acumula.
- **`jti` aqui serve outro propósito além do antirreplay já visto na RFC 7523** — para um access token, `jti` é sobretudo um identificador para fins de auditoria/correlação de logs e, eventualmente, para permitir uma lista de revogação granular por token individual (em vez de por client ou por usuário inteiro).

## 6. Relação com outras RFCs

- Estratégia concorrente/complementar direta à **RFC 7662 (Introspecção)** — o "ponto de pouso" da troca já discutida no capítulo anterior: validar localmente por assinatura (esta RFC) vs. perguntar ao AS a cada requisição (RFC 7662). Uma implementação pode inclusive combinar as duas, como discutido na seção 5.4.
- `iss` amarra diretamente ao `issuer` do metadata da **RFC 8414** — mesmo valor, mesma âncora de identidade, usada pelo RS para descobrir onde buscar as chaves de verificação (`jwks_uri`).
- `aud` é o mecanismo concreto que operacionaliza a preocupação de audience da **RFC 6819**, e é o alvo natural do que a **RFC 8707 (Resource Indicators)** deixa o *client* pedir do lado da requisição — vale reter a divisão de responsabilidades: 8707 é sobre o pedido ("quero um token para ESTE recurso"), 9068 é sobre o token emitido ("é aqui que essa decisão fica registrada, de forma que o próprio RS possa verificar").
- É um dos formatos que o `issued_token_type` da **RFC 8693 (Token Exchange)** pode indicar — a troca de token pode devolver exatamente um JWT seguindo este perfil, sinalizado por um valor de `issued_token_type` como `urn:ietf:params:oauth:token-type:access_token` combinado com o próprio conteúdo do token seguindo esta RFC.
- `jti` espelha o mesmo conceito de identificador único já visto no `client_assertion` da RFC 7523 — a ideia de "toda vez que assinamos algo, damos um identificador único a ele" se repete em múltiplas RFCs deste livro, sempre com o mesmo propósito de fundo (permitir rastreamento/rejeição individual).
- Não precisa de relação especial com a **RFC 7519 (JWT)** além de ser a spec de formato-base sobre a qual este perfil se apoia — a 7519 define o que é um JWT genericamente (estrutura, claims registradas, processamento); a 9068 é um **perfil** que restringe e especializa esse formato genérico para um propósito específico (ser um access token OAuth). É exatamente por isso que a 7519 não tem capítulo próprio neste livro, mas aparece referenciada em vários pontos como a fundação sobre a qual RFC 7523 (client assertions) e RFC 9068 (access tokens) constroem.

## 7. O que mudou desde a publicação (2021)

- Relativamente recente entre as RFCs deste livro, mas com espírito retroativo: formaliza algo que **muitos fornecedores já faziam de forma ad-hoc havia anos**. JWT como access token já existia na prática bem antes de 2021 — grandes provedores de identidade já emitiam JWTs como access tokens desde meados da década anterior, só sem estrutura comum entre eles. Por isso a adoção da RFC 9068 foi relativamente rápida: ela formalizou uma prática de mercado já madura, em vez de introduzir algo totalmente novo que o mercado precisasse assimilar do zero.
- Cada vez mais tratada como expectativa padrão para novas implementações de AS que optam por tokens em formato JWT, em vez de cada fornecedor reinventar nomes de claim — o mesmo ganho de interoperabilidade que a RFC 8414 trouxe para descoberta de metadata, agora aplicado ao formato do próprio token.
- Conecta com uma tendência maior no ecossistema, que aparece em capítulos futuros deste livro (RFC 8705 mTLS, RFC 9449 DPoP): amarrar o access token JWT a uma chave/certificado específico via uma claim `cnf` (confirmation) — exatamente o ponto de extensão que este perfil habilita para **sender-constraining** (tornar o token inútil, mesmo se roubado, para quem não possui a chave/certificado correspondente). Essa é, provavelmente, a evolução mais significativa em curso sobre o formato definido por esta RFC: de "prova de que o AS autorizou algo" para "prova de que o AS autorizou algo **e** de que quem apresenta o token é quem deveria possuí-lo".

> **Nota de laboratório**: nenhum lab construído ainda para esta RFC neste projeto — todos os labs emitem tokens **opacos** (48 caracteres hexadecimais), nunca JWT. Seria o gap natural para um laboratório futuro: trocar o formato do `access_token` por um JWT seguindo este perfil, e então o resource server passaria a validar por assinatura local em vez de ler o Redis diretamente (fechando também o gap equivalente já apontado no capítulo da RFC 7662, mas por um caminho diferente — validação local em vez de introspecção remota).

## Exemplo em Java (JDK 21, sem frameworks)

Os exemplos abaixo cobrem os dois lados do ciclo de vida: o Authorization Server **emitindo** um access token JWT seguindo o perfil desta RFC, e o Resource Server **validando-o localmente** — sem nenhuma chamada de rede, em contraste direto com o custo de round-trip do `/introspect` da RFC 7662 discutido no capítulo anterior. Usamos apenas `java.security` (`KeyPairGenerator`, `Signature`) para a assinatura RS256, `java.util.Base64` para a codificação compacta, e o utilitário `SimpleJson` (`SimpleJson.object`, `SimpleJson.parseFlat`), definido no Capítulo 1 (RFC 6749) deste livro, para montar/interpretar os objetos JSON envolvidos.

> Vale repetir aqui a mesma ressalva do capítulo da RFC 7523: assinar e verificar JWTs manualmente com `Signature`, como fazemos abaixo, é apenas para expor a mecânica — em produção, use uma biblioteca JOSE validada (ex.: Nimbus JOSE+JWT), que trata corretamente casos como confusão de algoritmo, `alg: none`, e as demais nuances já discutidas na seção 5.5 deste capítulo e na seção 5.5 do capítulo da RFC 7523.

### 4.1 Emitindo um access token JWT (lado do Authorization Server)

```java
import java.nio.charset.StandardCharsets;
import java.security.PrivateKey;
import java.security.Signature;
import java.time.Instant;
import java.util.Base64;
import java.util.LinkedHashMap;
import java.util.Map;
import java.util.UUID;

/**
 * Monta um access token JWT conforme RFC 9068: header com "typ":"at+jwt"
 * (o marcador que distingue este JWT de um ID Token OIDC ou de qualquer
 * outro JWT que por acaso circule pelo mesmo sistema — secao 5.1) e as
 * claims obrigatorias do perfil (iss, exp, iat, aud, sub, client_id, jti).
 */
public final class JwtAccessTokenIssuer {

    private static final Base64.Encoder B64URL =
            Base64.getUrlEncoder().withoutPadding();

    public static String emitir(String issuer, String audienceResourceServer,
                                 String subjectResourceOwner, String clientId,
                                 String scope, int ttlSegundos,
                                 PrivateKey chavePrivadaDoAS, String kid) throws Exception {

        Map<String, Object> header = new LinkedHashMap<>();
        header.put("typ", "at+jwt");   // <- e' este marcador que a secao 5.1 explica
        header.put("alg", "RS256");
        header.put("kid", kid);        // permite ao RS escolher a chave publica certa

        long agora = Instant.now().getEpochSecond();
        Map<String, Object> payload = new LinkedHashMap<>();
        payload.put("iss", issuer);                      // = "issuer" do metadata RFC 8414
        payload.put("aud", audienceResourceServer);       // RS(s) destinatario(s) — secao 5.2
        payload.put("sub", subjectResourceOwner);         // o USUARIO (nao o client!)
        payload.put("client_id", clientId);               // o APP agindo — claim SEPARADA de sub
        payload.put("iat", agora);
        payload.put("exp", agora + ttlSegundos);
        payload.put("jti", UUID.randomUUID().toString()); // identificador unico do token
        payload.put("scope", scope);

        String headerB64 = B64URL.encodeToString(
                SimpleJson.object(header).getBytes(StandardCharsets.UTF_8));
        String payloadB64 = B64URL.encodeToString(
                SimpleJson.object(payload).getBytes(StandardCharsets.UTF_8));
        String assinavel = headerB64 + "." + payloadB64;

        Signature assinador = Signature.getInstance("SHA256withRSA");
        assinador.initSign(chavePrivadaDoAS);
        assinador.update(assinavel.getBytes(StandardCharsets.US_ASCII));
        String assinaturaB64 = B64URL.encodeToString(assinador.sign());

        return assinavel + "." + assinaturaB64;
    }
}
```

### 4.2 Validando o token localmente (lado do Resource Server) — sem round-trip de rede

```java
import java.nio.charset.StandardCharsets;
import java.security.PublicKey;
import java.security.Signature;
import java.time.Instant;
import java.util.Base64;
import java.util.Map;
import java.util.Set;

/**
 * Contraste direto com o capitulo da RFC 7662: ali, o resource server fazia
 * um POST /introspect e ESPERAVA uma resposta de rede do AS a cada chamada
 * (TokenIntrospectionClient.introspectar, no capitulo anterior). Aqui, com
 * o access token em formato JWT (RFC 9068), a validacao inteira acontece
 * DENTRO DO PROCESSO do resource server — nenhuma chamada HTTP, nenhuma
 * dependencia de o AS estar no ar no momento da requisicao. O custo que se
 * paga em troca esta' descrito na secao 5.4: revogar este token especifico
 * antes do "exp" nao tem efeito imediato aqui, porque ninguem consulta o AS
 * de novo depois da emissao.
 */
public final class JwtAccessTokenValidator {

    public record TokenValidado(Map<String, Object> claims) {}

    public static TokenValidado validar(String jwtCompacto, PublicKey chavePublicaDoAS,
                                         String issuerEsperado, String audienceEsperada)
            throws Exception {

        String[] partes = jwtCompacto.split("\\.");
        if (partes.length != 3) {
            throw new IllegalArgumentException("JWT mal formado — esperado 3 segmentos");
        }

        Base64.Decoder b64url = Base64.getUrlDecoder();
        String headerJson = new String(b64url.decode(partes[0]), StandardCharsets.UTF_8);
        Map<String, String> header = SimpleJson.parseFlat(headerJson);

        // 1) Checagem de TIPO primeiro (fail fast, secao 5.1) — antes mesmo
        //    de gastar o custo de uma verificacao de assinatura, rejeita
        //    qualquer JWT que nao se autodeclare um access token deste perfil.
        if (!"at+jwt".equals(header.get("typ"))) {
            throw new SecurityException(
                    "typ inesperado (" + header.get("typ") + ") — isto pode ser um "
                    + "JWT de outro proposito, ex.: ID Token OIDC (RFC 9068 secao 5.1)");
        }

        // 2) O algoritmo aceito e' FIXADO pelo validador, nunca lido cegamente
        //    do header e usado sem checagem — previne confusao de algoritmo
        //    (RS256-para-HS256, ou aceitacao acidental de "alg":"none").
        if (!"RS256".equals(header.get("alg"))) {
            throw new SecurityException(
                    "Algoritmo nao suportado por esta politica de validacao: " + header.get("alg"));
        }

        // 3) SO ENTAO verifica a assinatura criptografica.
        String assinavel = partes[0] + "." + partes[1];
        byte[] assinatura = b64url.decode(partes[2]);
        Signature verificador = Signature.getInstance("SHA256withRSA");
        verificador.initVerify(chavePublicaDoAS);
        verificador.update(assinavel.getBytes(StandardCharsets.US_ASCII));
        if (!verificador.verify(assinatura)) {
            throw new SecurityException("Assinatura invalida — token forjado ou corrompido");
        }

        // 4) So depois da assinatura confirmada e' que as CLAIMS podem ser
        //    consideradas confiaveis o suficiente para orientar decisoes.
        String payloadJson = new String(b64url.decode(partes[1]), StandardCharsets.UTF_8);
        Map<String, String> claims = SimpleJson.parseFlat(payloadJson);

        if (!issuerEsperado.equals(claims.get("iss"))) {
            throw new SecurityException("iss inesperado — token nao veio do AS esperado");
        }

        String audienceDoToken = claims.get("aud");
        if (audienceDoToken == null || !audienceDoToken.contains(audienceEsperada)) {
            // secao 5.2 — um token valido para OUTRO resource server nao e'
            // valido para este, mesmo com assinatura perfeita.
            throw new SecurityException(
                    "aud nao inclui este resource server — token nao foi emitido para aqui");
        }

        long exp = Long.parseLong(claims.get("exp"));
        if (Instant.now().getEpochSecond() >= exp) {
            throw new SecurityException("Token expirado");
        }

        return new TokenValidado(Map.copyOf(claims));
    }

    public static boolean autorizaEscopo(TokenValidado validado, String escopoNecessario) {
        Object scopeObj = validado.claims().get("scope");
        String scopeString = scopeObj == null ? "" : scopeObj.toString();
        Set<String> escopos = Set.of(scopeString.split(" "));
        return escopos.contains(escopoNecessario);
    }
}
```

O contraste com o capítulo anterior é o ponto central deste exemplo: `JwtAccessTokenValidator.validar` acima não faz **nenhuma** chamada de rede — todo o trabalho é decodificação Base64URL e verificação criptográfica local, executado inteiramente dentro do processo do resource server, contra `TokenIntrospectionClient.introspectar` (RFC 7662, capítulo anterior), que dependia de uma chamada HTTP síncrona ao Authorization Server a cada requisição recebida. É exatamente a troca discutida na seção 5.4 e na seção 6 deste capítulo: velocidade e desacoplamento de disponibilidade do AS, ao custo de não conseguir mais que o AS diga "revoguei esse token" no meio da vida dele.
