# RFC 7523 — JSON Web Token (JWT) Profile for OAuth 2.0 Client Authentication and Authorization Grants

## 1. Contexto e motivação

Esta RFC define, na verdade, **duas extensões independentes** que só compartilham o mesmo mecanismo de base — um JWT assinado apresentado ao token endpoint. É fácil confundir as duas ao ler o título, e vale separar isso com cuidado desde a primeira linha, porque o resto do capítulo depende dessa distinção ficar firme:

- **§2.1 — JWT como Authorization Grant.** Um jeito de trocar uma asserção assinada por um emissor terceiro confiável (um JWT, ou uma asserção SAML — a RFC 7521, o documento "guarda-chuva" que a 7523 concretiza para JWT, também tem uma irmã para SAML na RFC 7522) diretamente por um `access_token`, sem passar pelo fluxo interativo de `/authorize`. É pensado como uma ponte entre sistemas de identidade baseados em asserção — tipicamente federações corporativas, SAML Identity Providers legados — e o modelo de token do OAuth 2.0.
- **§2.2 — JWT como Autenticação de Client.** Um jeito do **client** provar sua identidade no token endpoint assinando um JWT com sua própria chave privada, em vez de apresentar um `client_secret` estático. É o método amplamente conhecido pelo nome que o OpenID Connect deu a ele — **`private_key_jwt`** — embora a RFC 7523 em si não use esse rótulo; ela apenas define o mecanismo genérico de "cliente se autentica com um JWT assinado".

Essas duas metades resolvem problemas completamente diferentes, e é comum uma implantação usar só uma delas (como o próprio lab deste projeto faz — só §2.2). Não há nada que force as duas a andarem juntas.

### 1.1 Por que o grant JWT-bearer (§2.1) existe

Antes desta RFC, uma organização que já tinha investido pesado em infraestrutura de identidade federada (SAML 2.0, WS-Federation, um IdP corporativo que já emite asserções assinadas para dezenas de sistemas internos) e queria adotar OAuth 2.0 para suas APIs enfrentava um dilema: ou reimplementava toda aquela lógica de confiança dentro do fluxo `/authorize` (redirecionamentos, telas de login duplicadas, um segundo sistema de sessão), ou aceitava que os dois mundos ficassem desconectados. O grant JWT-bearer oferece uma terceira via: pegue a asserção que o IdP já emite, apresente-a diretamente ao token endpoint do OAuth AS, e receba um `access_token` de volta — sem o resource owner jamais ver um navegador. É, na essência, uma forma de **federação de confiança encurtada em uma única chamada HTTP**, adequada sobretudo para comunicação servidor-a-servidor onde o "usuário" já foi autenticado por outro sistema e essa autenticação precisa ser traduzida para o vocabulário OAuth.

### 1.2 Por que a autenticação de client via JWT (§2.2) existe

A motivação da segunda metade conecta direto com um problema que atravessa todo o núcleo do OAuth: um `client_secret` estático, se vazar, é uma credencial de impersonação completa e permanente até ser rotacionado manualmente. Pior — o vazamento não precisa acontecer em trânsito; um comprometimento do **armazenamento do lado do AS** (um dump de banco de dados, um backup mal protegido) também expõe esse segredo, porque o AS precisa guardá-lo em algum formato recuperável (ou ao menos um hash comparável) para poder validar `client_secret_basic`/`client_secret_post`.

Com `private_key_jwt`, a inversão é completa: o AS só precisa conhecer a **chave pública** do client. Um vazamento do armazenamento do AS expõe apenas chaves públicas — que, por definição, não servem para impersonar ninguém. A prova de posse da chave privada acontece a cada chamada, via assinatura, e nunca trafega o segredo em si (diferente de `client_secret_post`, que literalmente coloca o segredo no corpo da requisição a cada vez). Esse é o mesmo argumento de fundo, aplicado ao client, que levou o ecossistema a preferir assinaturas assimétricas sobre segredos compartilhados em praticamente todo lugar onde a escolha existe (mTLS na RFC 8705 é a outra grande alternativa assimétrica, indo por um caminho de camada de transporte em vez de um artefato JWT).

### 1.3 Onde isso se encaixa historicamente

A RFC 7523 é de 2015, contemporânea de um período em que o ecossistema OAuth começava a amadurecer para cenários de alto valor (financeiro, saúde, governo) onde `client_secret` estático já soava frágil demais. Não por acaso, é também a época em que perfis de segurança mais rígidos (que décadas depois viriam a influenciar a RFC 9700) começaram a exigir ou fortemente recomendar métodos assimétricos de autenticação de client.

## 2. Terminologia e papéis

Nenhum papel novo em relação à RFC 6749 — client, AS, resource owner continuam os mesmos. A RFC introduz vocabulário específico para os artefatos que ela define:

- **Assertion (asserção)** — o termo genérico, herdado da RFC 7521, para "um pacote de claims assinado que uma parte apresenta como evidência de algo". Um JWT é uma forma concreta de assertion; SAML é outra.
- **JWT Bearer Token / JWT Bearer Grant** — quando a assertion é usada como grant (§2.1): `grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer`, parâmetro `assertion` carregando o JWT completo e compacto.
- **Client Assertion** — quando a assertion é usada para autenticar o client (§2.2): `client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer` + `client_assertion` (o JWT assinado pelo client). Isso é usado **junto** com qualquer `grant_type` normal — não substitui o grant, substitui *como o client se autentica* dentro dele.
- **Issuer da assertion vs. Issuer do AS** — vale notar uma inversão sutil de papéis entre as duas metades: no grant §2.1, o `iss` do JWT identifica quem **emitiu a asserção externa** (o IdP SAML/federação, uma parte terceira do ponto de vista do AS OAuth). No client assertion §2.2, o `iss` (e também o `sub`) do JWT é o **próprio client_id** — o client está assinando algo sobre si mesmo, não repassando uma asserção de terceiro. É fácil, ao ler rapidamente as duas seções da RFC, achar que `iss` sempre significa "uma autoridade externa" — mas em §2.2 ele significa "o próprio ator que está se autenticando".
- **Bearer** — no sentido usado aqui (como em "Bearer Grant"), significa que a posse da assertion assinada corretamente é suficiente para uso — não há um desafio adicional de prova de posse em tempo real além da assinatura já embutida. É o mesmo sentido de "bearer" que qualifica o `access_token` Bearer da RFC 6750, generalizado para este artefato.

## 3. Fluxo

### 3.1 §2.1 — JWT como Authorization Grant

```
[Emissor de confianca, ex: IdP SAML/federacao corporativa]
      | emite/assina um JWT com claims sobre uma identidade
      v
Client
      |
      | POST /token
      | grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer
      | &assertion=<JWT compacto: header.payload.signature>
      v
Authorization Server
      | 1. decodifica o JWT, identifica o "iss" (emissor)
      | 2. verifica se ha relacao de confianca PRE-ESTABELECIDA com esse iss
      |    (chave publica pre-registrada, ou descoberta via federacao)
      | 3. valida assinatura, exp, aud (= este AS), demais claims
      v
Client <- access_token (e, opcionalmente, refresh_token — a RFC deixa a
                        criterio do AS; muitas implementacoes NAO emitem
                        refresh_token aqui, ja que a assertion original
                        pode ser reapresentada quando precisar de novo token)
```

Note o que **não** acontece: nenhum redirecionamento de navegador, nenhuma tela de login, nenhuma interação síncrona do resource owner. Tudo acontece em uma única chamada servidor-a-servidor. Isso torna esse grant adequado para integração de sistemas (B2B, pipelines batch, pontes de federação), mas inadequado como substituto do Authorization Code Grant em cenários onde o consentimento explícito e em tempo real do usuário é necessário — a própria confiança no emissor da assertion é que faz o papel do consentimento aqui, implicitamente.

### 3.2 §2.2 — JWT como Autenticação de Client (combinável com qualquer grant)

```
Client (ja possui um par de chaves RSA/EC proprio, gerado/gerenciado por ele mesmo)
      |
      | monta um JWT novo a cada chamada ao /token:
      |   header: {"alg":"RS256","typ":"JWT"}
      |   payload: {
      |     "iss": "<client_id>",
      |     "sub": "<client_id>",         (identico ao iss, por definicao da RFC)
      |     "aud": "<identificador do token endpoint/AS>",
      |     "exp": <curto, tipicamente 60-120s no futuro>,
      |     "iat": <agora>,
      |     "jti": "<identificador aleatorio unico>"
      |   }
      | assina com a CHAVE PRIVADA do client
      v
POST /token
grant_type=authorization_code (ou refresh_token, client_credentials, ...)
&code=... (ou refresh_token=..., conforme o grant)
&client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer
&client_assertion=<o JWT montado acima, compacto>
      v
Authorization Server
      | 1. extrai client_id do "iss"/"sub" do client_assertion (ainda sem
      |    confiar nele — e so um indice para buscar a chave publica)
      | 2. busca a chave PUBLICA registrada para esse client_id
      |    (via jwks estatico ou jwks_uri, registrados pela RFC 7591)
      | 3. verifica assinatura com essa chave publica
      | 4. valida claims: iss==sub==client_id esperado, aud==este AS,
      |    exp no futuro (mas dentro de uma janela maxima aceitavel),
      |    jti nao reutilizado
      | 5. SO ENTAO processa o grant_type normalmente, como se o client
      |    tivesse sido autenticado por client_secret_basic
      v
Client <- access_token (resposta identica a de qualquer outro metodo de
                        autenticacao de client — RFC 7523 nao muda o
                        formato da resposta do /token, so como o client
                        provou sua identidade antes de chegar la)
```

A observação central: **cada chamada ao `/token` carrega uma `client_assertion` nova**, montada e assinada na hora. Não é um token de longa duração reaproveitado — é mais parecido, conceitualmente, com uma prova de posse renovada a cada uso (o mesmo espírito de "prove de novo, a cada vez" que aparece, em formato diferente, na DPoP).

## 4. Parâmetros e endpoints normativos

Nenhum endpoint novo — as duas metades reaproveitam o `/token` da RFC 6749. Toda a superfície nova é de **parâmetros** e de **claims dentro do JWT**.

### 4.1 Parâmetros de requisição

| Parâmetro | Usado em | Obrigatório | Descrição |
|---|---|---|---|
| `grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer` | §2.1 | sim | Identifica o grant como JWT-bearer |
| `assertion` | §2.1 | sim | O JWT (ou asserção SAML, na RFC irmã 7522) compacto |
| `client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer` | §2.2 | sim, quando usando este método | Identifica o formato da `client_assertion` |
| `client_assertion` | §2.2 | sim, quando usando este método | O JWT assinado pelo client |
| `scope` | ambos | opcional | Mesmo parâmetro de sempre — escopo requisitado |

Um detalhe fácil de escorregar: em §2.2, `client_assertion_type` e `client_assertion` **acompanham** o `grant_type` real da operação (`authorization_code`, `refresh_token`, `client_credentials`...) — eles não competem com ele. Uma requisição de Authorization Code Grant autenticada via `private_key_jwt` carrega **cinco** parâmetros relevantes ao mesmo tempo: `grant_type=authorization_code`, `code`, `redirect_uri`, `client_assertion_type`, `client_assertion`.

### 4.2 Claims dentro do JWT (ambos os usos)

| Claim | §2.1 (grant) | §2.2 (client assertion) |
|---|---|---|
| `iss` | Emissor da asserção externa (o IdP, a federação) | `client_id` do próprio client |
| `sub` | O sujeito de quem a asserção fala (pode ou não ser igual ao `iss`) | `client_id` — idêntico ao `iss` aqui, por definição |
| `aud` | Identificador do AS (tipicamente a URL do token endpoint) | Idem — identificador do AS/token endpoint |
| `exp` | Obrigatória | Obrigatória, e tipicamente com janela **bem mais curta** (minutos, não horas) |
| `nbf` | Opcional ("not before") | Opcional |
| `iat` | Opcional, mas recomendada | Recomendada — usada por implementações para impor uma janela máxima de "quão no passado" a assertion pode ter sido emitida |
| `jti` | Opcional, mas fortemente recomendada contra replay | Fortemente recomendada — é o principal mecanismo antirreplay de §2.2 |

Vale insistir num ponto que a RFC deixa implícito mas que gera confusão prática: em §2.2, **`aud` deve ser o identificador do próprio Authorization Server/token endpoint** — não do resource server, não de um recurso qualquer. É comum, num sistema com múltiplos ASs (ambientes, regiões, tenants), um erro de configuração colocar o `aud` errado e o AS legitimamente rejeitar a assertion. Isso não é um bug do protocolo — é exatamente o que `aud` foi desenhado para impedir: uma assertion cunhada para o AS de homologação não deveria, por acidente ou má-fé, ser aceita pelo AS de produção.

### 4.3 Respostas de erro

Como a assertion (em ambos os casos) é parte do processo de **autenticação/autorização da requisição**, e não do fluxo interativo, os erros seguem o vocabulário já estabelecido do `/token` (RFC 6749 §5.2):

- **`invalid_client`** — a assertion de §2.2 falhou (assinatura inválida, `aud`/`iss`/`sub` incorretos, expirada, `jti` já usado). É o código correto porque o problema é a **identidade do client**, não o grant em si.
- **`invalid_grant`** — a assertion de §2.1 falhou (emissor não confiável, assinatura inválida, expirada). Aqui o problema é o **grant/asserção apresentada**, não a identidade de quem chama.

Essa distinção entre `invalid_client` (§2.2) e `invalid_grant` (§2.1) é sutil mas semanticamente importante: no primeiro caso, é o *chamador* que falhou em se provar; no segundo, é o *material apresentado como prova de autorização* que falhou em ser aceito.

## 5. Segurança já tratada na própria RFC 7523

### 5.1 Nenhum segredo compartilhado necessário para autenticação de client

Como já discutido na motivação: o AS só precisa da chave **pública**. Um vazamento do armazenamento do AS não dá capacidade de impersonação — muito diferente de um `client_secret` vazado, que é diretamente reutilizável por quem o obtiver.

### 5.2 Proteção contra replay via `exp` + `jti`

Uma `client_assertion` capturada (por um proxy comprometido, um log mal protegido, um ataque de rede) só vale por uma janela curta — e o `jti`, se rastreado pelo AS, permite rejeitar reapresentação da mesma asserção mesmo **dentro** dessa janela de validade. É o mesmo espírito do código de uso único (`authorization_code`) aplicado aqui ao próprio artefato de autenticação: uma coisa é a assertion estar dentro do prazo de validade; outra, independente, é ela já ter sido gasta.

Dois detalhes operacionais que a RFC não especifica, mas que toda implementação real precisa decidir:

- **Por quanto tempo guardar o `jti`?** Guardar para sempre é impraticável; guardar só até o `exp` da própria assertion é o mínimo necessário e suficiente — depois que ela expira, reapresentá-la já falharia na checagem de `exp` de qualquer forma, então rastrear o `jti` além desse ponto não agrega proteção. O lab deste projeto usa exatamente essa estratégia: TTL do registro de `jti` no Redis = TTL máximo aceito para o `exp` da assertion.
- **`jti` é obrigatório?** A RFC 7523 o lista como opcional na letra da norma, mas sem `jti` — ou algum mecanismo equivalente — a proteção antirreplay dentro da janela de `exp` simplesmente não existe. Implementações sérias (e o próprio lab deste projeto) tratam `jti` como obrigatório na prática, mesmo a RFC não exigindo.

### 5.3 `aud` amarra a asserção a um AS específico

Uma `client_assertion` construída para um AS não deveria ser aceita por outro, mesmo que apresentada lá — é mais uma instância do mesmo padrão recorrente de restrição de audience que aparece na RFC 8707 (Resource Indicators) e no `aud` dos Request Objects da RFC 9101 (JAR). O caso concreto de risco: uma organização com AS de sandbox e AS de produção compartilhando o mesmo par de chaves de client (reuso indevido de credenciais entre ambientes) — sem `aud`, uma assertion vazada do ambiente de sandbox seria diretamente utilizável em produção.

### 5.4 Confiança pré-estabelecida no emissor (§2.1)

Para o grant do §2.1, o AS precisa de uma relação de confiança **pré-estabelecida** com o emissor (`iss`) da asserção — JWTs autoassinados de partes desconhecidas obviamente não deveriam ser aceitos. Isso normalmente significa chave/certificado do emissor pré-registrado (fora de banda, num processo administrativo) ou descoberto via federação confiável (um metadado de federação SAML, por exemplo). Um AS que aceitasse **qualquer** `iss` sem essa checagem estaria, na prática, permitindo que qualquer parte cunhasse tokens para qualquer sujeito — uma falha catastrófica de design, não uma nuance.

### 5.5 Nuances de segurança que a RFC pressupõe mas não detalha exaustivamente

Vale a pena o leitor ter em mente, porque são exatamente os pontos onde implementações reais tropeçam:

- **Confusão de algoritmo ("alg confusion").** Um JWT declara seu próprio algoritmo de assinatura no header (`alg`). Um validador ingênuo que lê esse campo e o usa cegamente para decidir *como* verificar abre uma classe conhecida de vulnerabilidade: se o validador aceita `alg: none` (sem assinatura) ou permite que uma chave pública RSA seja reinterpretada como segredo HMAC (confundindo RS256 com HS256 — o ataque clássico "RS256-to-HS256"), um atacante pode forjar assertions sem jamais possuir a chave privada. A defesa correta é o **validador** — não o token — decidir de antemão qual algoritmo é esperado para aquele client_id, e rejeitar qualquer coisa diferente, nunca delegar essa decisão ao próprio `alg` do header recebido.
- **Ataques de temporização (timing attacks) na verificação de assinatura.** Implementações de baixo nível de comparação criptográfica que não são de tempo constante podem, em tese, vazar informação através de quanto tempo a verificação leva. Bibliotecas JOSE maduras já tratam disso; uma implementação artesanal (como o exemplo didático deste capítulo) tipicamente não se preocupa com isso — outro motivo para nunca usar código manual em produção.
- **Deriva de relógio (clock skew).** Como `exp`/`iat`/`nbf` dependem de sincronismo de relógio entre client e AS, implementações costumam tolerar uma pequena margem (segundos a poucos minutos) — mas essa margem, se grande demais, amplia a janela de replay possível mesmo com `jti` funcionando corretamente.
- **Rotação de chave do client sem downtime.** Como o AS precisa conhecer a chave pública vigente do client, revogar/rotacionar uma chave comprometida exige um mecanismo de atualização (reregistro via RFC 7591, ou um `jwks_uri` que o AS resolve dinamicamente) — se o client só tem uma chave estática registrada uma vez, uma chave privada comprometida vira um segredo estático de fato, na prática, até alguém rotacionar manualmente.

## 6. Relação com outras RFCs

- A metade de autenticação de client é exatamente o **`private_key_jwt`** — é aqui que esse método, mencionado no capítulo da RFC 9700 ("prefere métodos assimétricos a `client_secret` estático"), é definido concretamente.
- `jwks`/`jwks_uri` usados para validar assinaturas vêm do metadata de registro da **RFC 7591** — conexão direta com aquele capítulo: é lá que o client informa sua chave pública ao AS pela primeira vez.
- Descoberto via **RFC 8414**: `token_endpoint_auth_methods_supported` listaria `private_key_jwt` se suportado, e `token_endpoint_auth_signing_alg_values_supported` indica quais algoritmos de assinatura o AS aceita (o lab deste projeto anuncia só `["RS256"]`).
- O grant do §2.1 é conceitualmente antecessora/irmã da **RFC 8693 (Token Exchange)** — ambas fazem ponte entre "tenho algum tipo de token/asserção externa" e "quero um token OAuth", mas a 8693 é mais geral (qualquer tipo de token, distinção subject/actor explícita, direcionamento por audience/resource via RFC 8707). A 8693 não substituiu a 7523 — coexistem para níveis de complexidade diferentes; a 7523 permanece mais simples para o caso específico "tenho um JWT/SAML assertion, quero trocar por access_token", sem a generalidade (e complexidade) adicional do Token Exchange.
- **RFC 8705 (mTLS)** é a outra grande alternativa assimétrica de autenticação de client — em vez de assinar um JWT a cada chamada, o client apresenta um certificado de cliente na própria camada TLS. As duas soluções resolvem o mesmo problema de fundo (eliminar o segredo estático) por caminhos completamente diferentes: uma no nível de aplicação (JWT no corpo da requisição), outra no nível de transporte (handshake TLS). Uma implantação pode até suportar ambas e deixar o client escolher.
- Vale distinguir das **outras** duas assinaturas de JWT que aparecem no roteiro, para não confundir: o Request Object da **RFC 9101 (JAR)** protege a integridade da *authorization request*; o `client_assertion` desta RFC autentica o *client* no token endpoint; e o JWT-bearer grant desta mesma RFC troca uma *asserção externa* por token. Três propósitos diferentes, todos usando "um JWT assinado" como mecanismo — o leitor que só lembra "JWT assinado no OAuth" sem saber qual dos três está diante de si é um convite a erro de design.

## 7. O que mudou desde a publicação (2015)

- A metade de **autenticação de client** (`private_key_jwt`) cresceu bastante em relevância — explicitamente recomendada sobre segredo estático pela RFC 9700 (2025), uma década depois, e exigida por perfis FAPI (Financial-grade API) para clients confidenciais em muitos casos de alto valor. Segue a mesma trajetória "recomendado → cada vez mais esperado" já vista com PKCE, embora `private_key_jwt` não tenha se tornado obrigatório universal como o PKCE se tornou.
- A metade do **grant JWT-bearer** (§2.1) cresceu comparativamente menos — seu caso de uso de "ponte" foi em boa parte absorvido por designs novos usando a RFC 8693 (Token Exchange), mais flexível e mais expressiva para cenários modernos de delegação/impersonação. A 7523 continua válida e mais simples, ainda usada especialmente em pontes legadas SAML-para-OAuth que já existiam antes da 8693 existir.
- A discussão de "qual método de autenticação de client escolher" hoje frequentemente se resume a uma comparação de três vias assimétricas praticamente equivalentes em garantia de segurança, mas bem diferentes em modelo operacional: `private_key_jwt` (RFC 7523, nível de aplicação), `tls_client_auth`/`self_signed_tls_client_auth` (RFC 8705, nível de transporte), e — cada vez mais discutido, embora fora do escopo direto deste projeto — atestação de dispositivo/chave em hardware. A escolha entre as duas primeiras costuma depender de qual infraestrutura já existe: se a organização já tem PKI de mTLS madura, RFC 8705 é natural; se o client já opera em ambiente onde gerar e assinar JWTs é trivial (a maioria dos runtimes modernos), `private_key_jwt` é mais simples de operacionalizar sem tocar na camada de transporte.

> **Nota de laboratório**: implementado em [`rfc7523/`](../../../rfc7523/README.md) — réplica do lab básico da RFC 6749, mas **sem `client_secret` nenhum**: o client-demo gera seu próprio par de chaves RSA-2048, registra a pública via `jwks` (RFC 7591), e autentica todo `grant_type` (Authorization Code, refresh, Client Credentials) via `client_assertion` (§2.2). Só a metade de autenticação de client é implementada — o grant JWT-bearer do §2.1 fica de fora, por escolha de escopo. O Authorization Server (`rfc7523/authorization-server/src/index.js`) valida a `client_assertion` exigindo `alg=RS256`, checando `iss`/`sub` (ambos = `client_id`), `aud` (= URL base do próprio AS, montada a partir do header `Host` da requisição) e `exp` (com uma janela máxima aceita de 120 segundos), e rastreia o `jti` já usado no Redis via `SET NX` com TTL igual a essa mesma janela — o mesmo prazo usado tanto para validar a assertion quanto para lembrar que ela já foi gasta. Há inclusive um botão na UI que reenvia deliberadamente a mesma `client_assertion` para provar a rejeição por replay. Os demais labs (`rfc6749/`, `rfc7636/`, `rfc9126/`, `rfc7592/`) continuam usando `client_secret_basic`/`client_secret_post`.

## Exemplo em Java (JDK 21, sem frameworks)

Os exemplos abaixo constroem, assinam e enviam uma `client_assertion` (RFC 7523 §2.2) usando **apenas** a biblioteca padrão do JDK — `java.security` para geração de chaves e assinatura, `java.util.Base64` para a codificação Base64URL sem padding que o formato JWT compacto exige, e `java.net.http.HttpClient` para a chamada ao token endpoint. O utilitário `SimpleJson` (métodos `SimpleJson.object(Map)` e `SimpleJson.parseFlat(String)`), definido no Capítulo 1 (RFC 6749) deste livro, é reaproveitado para montar/interpretar os objetos JSON planos envolvidos — não é redefinido aqui.

> **Aviso didático, para não deixar dúvida:** montar e verificar JWTs "na mão" com `java.security.Signature`, como fazemos abaixo, serve para **expor a mecânica** do formato — três partes Base64URL separadas por ponto, cada uma com um papel específico — e não deve ser copiado para um sistema real. Uma biblioteca JOSE madura (a referência do ecossistema Java é o **Nimbus JOSE+JWT**) trata dezenas de detalhes sutis que uma implementação artesanal tende a errar: rejeição categórica de `alg: none`, prevenção de confusão entre algoritmos assimétricos e simétricos (o ataque "RS256-para-HS256" mencionado na seção 5.5), comparação de assinatura em tempo constante, parsing robusto contra entradas malformadas ou adversariais, e suporte correto a todas as variantes de curva/tamanho de chave. Cada uma dessas é uma vulnerabilidade em potencial se implementada incorretamente — e "incorretamente" aqui não significa "com bugs óbvios", significa "sutilmente errado de um jeito que só aparece sob ataque".

### 4.1 Gerando o par de chaves do client (RSA-2048)

```java
import java.security.KeyPair;
import java.security.KeyPairGenerator;
import java.security.NoSuchAlgorithmException;
import java.security.SecureRandom;

/**
 * O client (nao o AS!) gera e guarda este par de chaves. A publica e' o que
 * vai para o AS via registro dinamico (RFC 7591, campo "jwks"); a privada
 * NUNCA sai do processo do client — e' ela que assina cada client_assertion.
 *
 * RSA-2048 e RS256 (RSASSA-PKCS1-v1_5 com SHA-256) e' o par minimo que a
 * maioria dos ASs aceita hoje; perfis mais rigorosos (FAPI) frequentemente
 * exigem 2048 bits como piso e recomendam considerar PS256 (RSASSA-PSS)
 * ou ES256 (curva eliptica) como alternativas mais modernas.
 */
public final class ClientKeyMaterial {

    public static KeyPair gerarParDeChaves() throws NoSuchAlgorithmException {
        KeyPairGenerator gerador = KeyPairGenerator.getInstance("RSA");
        gerador.initialize(2048, SecureRandom.getInstanceStrong());
        return gerador.generateKeyPair();
        // Em producao: a chave privada resultante deveria ser protegida em
        // repouso (HSM, KMS, ou ao menos um keystore criptografado) — jamais
        // gravada em texto plano em disco ou em variavel de ambiente.
    }
}
```

### 4.2 Montando e assinando o `client_assertion` (RFC 7523 §2.2)

```java
import java.nio.charset.StandardCharsets;
import java.security.PrivateKey;
import java.security.Signature;
import java.time.Instant;
import java.util.Base64;
import java.util.LinkedHashMap;
import java.util.Map;
import java.util.UUID;

/**
 * Constroi o JWT compacto (header.payload.assinatura, cada parte em
 * Base64URL sem padding — e' isso que RFC 7515 §2 chama de "JWS Compact
 * Serialization") que serve como client_assertion.
 *
 * Claims conforme RFC 7523 §3:
 *   iss/sub = client_id (o client se autenticando, nao um terceiro)
 *   aud     = identificador do token endpoint/AS — nunca do resource server
 *   exp     = janela CURTA (aqui, 90s) — quanto menor, menor a superficie
 *             de replay caso a assertion vaze antes de ser usada
 *   jti     = identificador aleatorio unico — e' o que permite ao AS
 *             detectar reapresentacao da MESMA assertion (replay)
 */
public final class ClientAssertionBuilder {

    private static final Base64.Encoder B64URL =
            Base64.getUrlEncoder().withoutPadding();

    public static String montarESinar(String clientId, String audienceTokenEndpoint,
                                       PrivateKey chavePrivada) throws Exception {

        // Header: alg deve refletir o que a chave privada realmente suporta —
        // nunca aceite "alg" vindo de configuracao externa nao confiavel na
        // hora de assinar (isso e' preocupacao de quem VALIDA, mas quem
        // assina tambem deveria fixar o algoritmo, nao inferi-lo de outrem).
        Map<String, Object> header = new LinkedHashMap<>();
        header.put("alg", "RS256");
        header.put("typ", "JWT");

        long agora = Instant.now().getEpochSecond();
        Map<String, Object> payload = new LinkedHashMap<>();
        payload.put("iss", clientId);
        payload.put("sub", clientId);               // identico ao iss, por definicao (§2.2)
        payload.put("aud", audienceTokenEndpoint);   // amarra a assertion a ESTE AS
        payload.put("iat", agora);
        payload.put("exp", agora + 90);              // janela curta de validade
        payload.put("jti", UUID.randomUUID().toString()); // defesa antirreplay

        String headerB64 = B64URL.encodeToString(
                SimpleJson.object(header).getBytes(StandardCharsets.UTF_8));
        String payloadB64 = B64URL.encodeToString(
                SimpleJson.object(payload).getBytes(StandardCharsets.UTF_8));

        String assinavel = headerB64 + "." + payloadB64;

        Signature assinador = Signature.getInstance("SHA256withRSA");
        assinador.initSign(chavePrivada);
        assinador.update(assinavel.getBytes(StandardCharsets.US_ASCII));
        byte[] assinatura = assinador.sign();

        String assinaturaB64 = B64URL.encodeToString(assinatura);

        return assinavel + "." + assinaturaB64; // JWT compacto completo
    }
}
```

### 4.3 Enviando o `client_assertion` ao token endpoint

```java
import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.net.http.HttpRequest.BodyPublishers;
import java.nio.charset.StandardCharsets;
import java.security.PrivateKey;
import java.util.Map;

/**
 * Troca um authorization_code por access_token, autenticando o client via
 * private_key_jwt em vez de client_secret_basic/post — note que
 * client_assertion_type e client_assertion viajam ao LADO do grant_type
 * normal, nunca no lugar dele (RFC 7523 §2.2).
 */
public final class TokenRequestComPrivateKeyJwt {

    public static Map<String, String> trocarCodigoPorToken(
            String tokenEndpoint, String clientId, String code, String redirectUri,
            PrivateKey chavePrivada) throws Exception {

        String clientAssertion = ClientAssertionBuilder.montarESinar(
                clientId, tokenEndpoint, chavePrivada);

        String corpo = "grant_type=authorization_code"
                + "&code=" + code
                + "&redirect_uri=" + redirectUri
                + "&client_assertion_type=" +
                    "urn:ietf:params:oauth:client-assertion-type:jwt-bearer"
                + "&client_assertion=" + clientAssertion;
                // Em producao: os valores acima (code, redirect_uri, JWT) devem
                // passar por URL-encoding — omitido aqui por brevidade didatica.

        HttpClient http = HttpClient.newHttpClient();
        HttpRequest req = HttpRequest.newBuilder()
                .uri(URI.create(tokenEndpoint))
                .header("Content-Type", "application/x-www-form-urlencoded")
                .POST(BodyPublishers.ofString(corpo, StandardCharsets.UTF_8))
                .build();

        HttpResponse<String> resp = http.send(req, HttpResponse.BodyHandlers.ofString());

        if (resp.statusCode() != 200) {
            // invalid_client aqui tipicamente significa: assinatura invalida,
            // aud/iss/sub incorretos, exp expirado, ou jti ja usado (replay).
            throw new IllegalStateException(
                    "Token endpoint recusou a client_assertion: " + resp.body());
        }

        return SimpleJson.parseFlat(resp.body()); // access_token, token_type, expires_in...
    }
}
```

Note o contraste com o Capítulo 1 (RFC 6749): lá, a autenticação do client é uma única linha (`Authorization: Basic base64(client_id:client_secret)` ou dois parâmetros no corpo). Aqui, a "credencial" é reconstruída — assinada do zero — a cada chamada, o que é exatamente o ponto: nada estático e reutilizável trafega pela rede.
