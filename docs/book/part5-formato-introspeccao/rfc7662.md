# RFC 7662 — OAuth 2.0 Token Introspection

## 1. Contexto e motivação

Quando o `access_token` é **opaco** — uma string aleatória sem estrutura interpretável, como em todos os labs deste projeto até este capítulo — o resource server não tem como, sozinho, saber se ele é válido, qual escopo carrega, ou a quem foi emitido. Ele precisa perguntar a alguém que saiba. Antes desta RFC (2015), essa pergunta era resolvida de forma **proprietária** por cada Authorization Server — o mesmo tipo de lacuna de interoperabilidade que motivou a RFC 7009 para revogação e a RFC 8414 para descoberta: sem um formato comum, cada fornecedor de AS expunha seu próprio endpoint ad-hoc de validação, com seu próprio esquema de request/response, e um resource server escrito para um AS não funcionava com outro.

A RFC 7662 formaliza um **endpoint de introspecção**: o resource server apresenta o token, o AS responde com um JSON estruturado dizendo se está ativo e, se estiver, seus metadados (escopo, client, usuário, expiração...). É a terceira peça que completa o ciclo de vida do token, ao lado da RFC 6749 (emissão) e da RFC 7009 (revogação): **emitir, validar, revogar** — três operações distintas, três RFCs, um só objeto de vida (o token) atravessando todas elas.

### 1.1 O problema de arquitetura que a introspecção resolve

Vale nomear explicitamente o desenho arquitetural que está por trás disso. Num sistema OAuth real, o Authorization Server e o Resource Server são frequentemente **processos separados, mantidos por times separados, às vezes empresas separadas** (pense num AS central de uma organização emitindo tokens que múltiplos microsserviços, escritos por times diferentes, precisam aceitar). O AS é o único que sabe, com autoridade, se um token ainda é válido — ele tem acesso ao armazenamento onde tokens são emitidos e revogados. O resource server, por definição, não tem esse acesso direto (e não deveria ter — compartilhar o armazenamento interno do AS com N resource servers diferentes seria um acoplamento arquitetural ruim, além de um risco de segurança, pois qualquer RS comprometido teria acesso de leitura a todos os tokens de todos os clients).

A introspecção resolve isso com o padrão mais simples possível: uma chamada HTTP síncrona, autenticada, do RS para o AS, perguntando "este token específico ainda vale?". É o equivalente, em desenho de sistemas, de um serviço consultando a fonte de verdade em vez de manter uma cópia local potencialmente desatualizada.

### 1.2 Por que não simplesmente compartilhar o token opaco "batendo" contra algum banco comum

Alguém poderia perguntar: por que não deixar o RS ler diretamente o armazenamento (banco/cache) onde o AS guarda os tokens, evitando a chamada de rede? É exatamente isso que **todos os labs deste projeto fazem hoje** (ver nota de laboratório, seção 6) — e funciona *só porque é o mesmo laboratório*, com AS e RS compartilhando deliberadamente o mesmo Redis para fins didáticos. Num sistema de produção real, com AS e RS mantidos por partes diferentes, isso é inviável: exigiria dar a cada RS acesso de leitura direto à infraestrutura de dados do AS, quebrando o isolamento entre serviços, criando uma superfície de ataque enorme (qualquer RS comprometido veria os tokens de todo mundo) e acoplando o esquema de armazenamento do AS à API que os RSs consomem (uma mudança interna no AS quebraria RSs). A introspecção existe precisamente para dar ao RS uma **interface estável e desacoplada** para a mesma pergunta, sem esses custos.

## 2. Terminologia e papéis

Nenhum papel novo — mas a RFC usa consistentemente o termo **"protected resource"** para quem chama a introspecção, reforçando que o público-alvo pretendido é o resource server, não qualquer parte arbitrária. Isso tem uma consequência de design que vale destacar: a RFC **não** define introspecção como um serviço de "autoatendimento" onde o portador de um token pergunta sobre o próprio token. O padrão de uso pretendido é sempre "uma parte que **recebeu** o token de outra (o client, numa requisição de API) quer validá-lo perante quem o emitiu" — nunca "eu, que possuo este token, quero saber sobre ele".

Essa distinção importa na prática: implementações que expõem introspecção sem autenticação adequada, ou que a tratam como um endpoint de conveniência para qualquer chamador, estão se afastando do modelo de confiança pretendido pela RFC (ver seção 5.1).

## 3. Fluxo

```
Client                    Resource Server                Authorization Server
  |                              |                                |
  | GET /api/recurso             |                                |
  | Authorization: Bearer <tok>  |                                |
  |----------------------------->|                                |
  |                              |                                |
  |                              | POST /introspect               |
  |                              | Authorization: Basic <credenciais
  |                              |                    do proprio RS,
  |                              |                    registradas p/ este fim>
  |                              | token=<tok>                     |
  |                              | &token_type_hint=access_token   |
  |                              |-------------------------------->|
  |                              |                                | consulta o
  |                              |                                | armazenamento
  |                              |                                | de tokens
  |                              |    200 OK sempre                |
  |                              |    {"active": true, "scope": ...,|
  |                              |     "exp": ..., "client_id": ...}|
  |                              |<--------------------------------|
  |                              |                                |
  |    (RS decide, com base em "active"/scope/exp, se atende      |
  |     a requisicao original)                                    |
  |<-----------------------------|                                |
```

Dois pontos centrais no fluxo:

1. **Quem chama `/introspect` é o Resource Server, autenticado como tal** — não o client, não o resource owner. As credenciais usadas (`Authorization: Basic` no exemplo, mas a RFC não fixa o método) são do próprio RS, registradas junto ao AS especificamente para esse propósito.
2. **A resposta é sempre HTTP 200**, mesmo quando o token é inválido, expirado ou desconhecido — o corpo é que carrega a informação de validade, nunca o código de status HTTP (ver seção 5.2 para a razão de design).

### 3.1 Exemplo de resposta — token ativo

```json
{
  "active": true,
  "scope": "profile email",
  "client_id": "s6BhdRkqt3",
  "username": "alice",
  "token_type": "Bearer",
  "exp": 1787510000,
  "iat": 1787506400,
  "sub": "alice",
  "aud": "https://rs.exemplo.com",
  "iss": "https://as.exemplo.com"
}
```

### 3.2 Exemplo de resposta — token inválido, expirado ou desconhecido

```json
{
  "active": false
}
```

Se o token não existe, expirou ou foi revogado: `{"active": false}` — e **nenhum outro campo** deveria acompanhar isso. A RFC é explícita que, quando `active` é `false`, o servidor **não deveria** incluir outros campos — é uma medida deliberada de minimização de informação (ver seção 5.2).

## 4. Parâmetros e endpoints normativos

### 4.1 Endpoint

- **Introspection endpoint** — novo, descoberto via **RFC 8414** como `introspection_endpoint` no metadata do AS.

### 4.2 Parâmetros de requisição

| Parâmetro | Obrigatório | Descrição |
|---|---|---|
| `token` | sim | O valor do token a verificar (access ou refresh) |
| `token_type_hint` | não | `access_token` ou `refresh_token` — mesma lógica de "dica" já vista na RFC 7009: acelera a busca no armazenamento do AS, mas o AS deve tentar os demais tipos se a dica não bater, nunca tratá-la como garantia |

A RFC é deliberadamente **genérica quanto ao tipo de token** que pode ser introspectado — tanto `access_token` quanto `refresh_token` são candidatos válidos, e o `token_type_hint` existe justamente para não obrigar o AS a varrer todos os armazenamentos possíveis quando o chamador já sabe qual tipo está enviando.

### 4.3 Autenticação do chamador

**Obrigatória** — o endpoint precisa estar protegido; não é aberto a qualquer parte. A RFC não fixa um único método (poderia ser `client_secret_basic`, um certificado mTLS, ou qualquer outro método de autenticação de client já suportado pelo AS) — o ponto normativo é que **deve haver** autenticação, delegando o método específico para o mesmo cardápio já usado no restante do AS.

### 4.4 Campos da resposta

| Campo | Presente quando `active=false`? | Descrição |
|---|---|---|
| `active` | sempre (obrigatório) | Booleano — o único campo garantido em toda resposta |
| `scope` | não deveria | String espaço-delimitada, mesmo formato de sempre |
| `client_id` | não deveria | A quem o token foi emitido |
| `username` | não deveria | Identificador legível do resource owner, se aplicável |
| `token_type` | não deveria | Tipicamente `Bearer` |
| `exp`, `iat`, `nbf` | não deveria | Timestamps Unix — expiração, emissão, "não antes de" |
| `sub` | não deveria | De quem o token fala |
| `aud` | não deveria | Para quem o token foi destinado |
| `iss` | não deveria | Quem emitiu |
| `jti` | não deveria | Identificador único do token |

Não é acaso que boa parte desses nomes espelha exatamente as claims padrão de JWT definidas na RFC 7519 (`iss`, `sub`, `aud`, `exp`, `iat`, `nbf`, `jti`) — a RFC 7662 reaproveita deliberadamente esse vocabulário semântico, de modo que o **mesmo conjunto de conceitos** ("quem emitiu, para quem, até quando, com que escopo") sirva tanto para um token opaco introspectado quanto para um JWT autocontido (RFC 9068, capítulo seguinte). Um resource server que já sabe interpretar essas claims de um JWT não precisa reaprender um vocabulário novo para interpretar a resposta de introspecção de um token opaco.

## 5. Segurança já tratada na própria RFC 7662

### 5.1 O endpoint precisa estar protegido

Introspecção revela informação potencialmente sensível sobre um token — escopo concedido, identidade do usuário, client ao qual pertence — e não deveria estar aberta a chamadores arbitrários ou não autenticados. Isso conecta direto com a distinção de papéis da seção 2: introspecção **não é** pensada para "o próprio portador do token perguntar sobre si mesmo" — é para o **resource server**, que recebeu o token de outra parte, validá-lo perante quem o emitiu. Um endpoint de introspecção aberto seria, na prática, um oráculo de metadados de token para qualquer parte que conseguisse capturar (ou adivinhar) um valor de token — mesmo sem conseguir *usar* esse token para acessar recursos, aprenderia coisas sobre ele (a quem pertence, que escopo tem, quando expira).

### 5.2 `active: false` revela o mínimo possível

A RFC recomenda que, para um token inválido, a resposta traga só o campo `active: false`, sem mais nada — mesmo princípio anti-oráculo já visto na RFC 7009 (ali operacionalizado via "sempre retorna 200, mesmo para token já inexistente"; aqui via um campo `active` minimalista quando falso). O raciocínio de fundo é idêntico ao da revogação: se a resposta para "token inexistente" fosse diferente (em forma, em código de status, ou em quais outros campos aparecem) da resposta para "token existe mas está expirado" ou "token existe mas foi revogado", um chamador malicioso poderia usar essa diferença para **sondar** quais tokens existem no sistema, mesmo sem autoridade para vê-los de outra forma — um vetor de enumeração. Manter a resposta uniforme (`{"active": false}`, sempre, para qualquer razão de invalidade) fecha esse canal lateral de informação.

### 5.3 TLS obrigatório

Como em qualquer endpoint que manipula material de token — o valor do `token` viaja no corpo da requisição, e a resposta carrega metadados sensíveis —, TLS é mandatório. Sem ele, tanto o token quanto os metadados de introspecção (identidade do usuário, escopo) trafegariam em claro.

### 5.4 Custo operacional e o trade-off de atualidade vs. desempenho

Como a introspecção tipicamente acontece a cada requisição recebida pelo resource server (a menos que haja cache local), ela cria uma **dependência de rede síncrona** no caminho crítico de toda chamada de API, e um possível vetor de sobrecarga no AS se muitos RSs introspectarem com alta frequência. Isso não é um detalhe de implementação — é uma característica estrutural do modelo: cada requisição ao RS agora depende da disponibilidade e latência do AS, mesmo que a operação em si nada tenha a ver com autenticação.

Implantações costumam mitigar isso com **cache local de curta duração** no lado do RS (segundos a poucos minutos), trocando uma fração de atualidade da informação de revogação por uma redução considerável de round-trips. O trade-off é explícito e precisa ser uma decisão consciente: um cache de 60 segundos significa que um token revogado no AS pode continuar sendo aceito pelo RS por até 60 segundos depois — uma janela de exposição real, ainda que pequena, que a equipe de segurança precisa aprovar conscientemente, não descobrir depois de um incidente.

### 5.5 Nuances adicionais que a prática revela

- **Introspecção de refresh_token.** Como a RFC é genérica quanto ao tipo de token, um AS pode (e alguns fazem) permitir introspectar um `refresh_token` também — mas isso levanta uma questão de escopo de autorização adicional: nem todo RS deveria ter permissão de introspectar refresh tokens (que costumam ter vida muito mais longa e maior poder), então implementações reais tipicamente restringem quem pode introspectar o quê, com base em qual credencial de RS está autenticada.
- **`token_type_hint` como otimização, não como garantia.** Assim como na RFC 7009, um chamador pode enviar a dica errada (ou nenhuma) — o AS deve continuar funcional, só potencialmente mais lento, nunca deve simplesmente falhar ou assumir que a dica está correta sem verificar.
- **Quem pode introspectar o token de quem.** A RFC não impõe uma regra única aqui, mas implementações sérias costumam restringir a introspecção ao(s) resource server(s) para os quais aquele token foi efetivamente emitido (via `aud`, quando presente) — evitando que um RS "curioso" introspecte tokens destinados a outros RSs só porque possui credenciais válidas de chamador.
- **Introspecção não substitui verificação de escopo do lado do RS.** Saber que `active: true` e que o `scope` inclui `read:orders` não dispensa o RS de aplicar sua própria lógica de autorização (ex.: o usuário específico tem permissão sobre *aquele* recurso específico?) — introspecção resolve "este token é válido e o que ele autoriza em termos amplos", não "esta operação específica é permitida".

## 6. Relação com outras RFCs

- Fecha o trio de gerenciamento de ciclo de vida com **RFC 6749** (emissão) e **RFC 7009** (revogação) — emitir, revogar, e agora validar. As três RFCs, lidas em conjunto, cobrem completamente o que significa "gerenciar um token do nascimento à morte".
- É exatamente o que os resource servers de **todos os labs deste projeto** ainda não fazem: cada `rfc*/resource-server` valida o `access_token` lendo **diretamente** do mesmo Redis que o AS escreve — só funciona porque é o mesmo laboratório, com AS e RS compartilhando deliberadamente a mesma infraestrutura de dados para fins didáticos. Um resource server de verdade, desacoplado do AS (mantido por outro time, outra empresa, sem acesso a essa infraestrutura), chamaria `/introspect` no AS em vez disso.
- Descoberta via **RFC 8414** como `introspection_endpoint`.
- Contraste direto com o próximo capítulo, **RFC 9068 (JWT Profile for Access Tokens)**: se o AS emite tokens em formato JWT em vez de opaco, o resource server pode validar **localmente**, por assinatura, sem round-trip de rede nenhum — introspecção e token-como-JWT são as duas estratégias concorrentes para o mesmo problema de fundo ("como o RS sabe que o token é válido, e o que ele autoriza").
- `token_type_hint` reaproveita exatamente o mesmo padrão de dica opcional já visto na RFC 7009 — mesmo desenho, RFCs irmãs, resolvendo problemas espelhados (revogar vs. validar).
- O vocabulário de campos da resposta (`iss`, `sub`, `aud`, `exp`, `iat`, `nbf`, `jti`) é deliberadamente compartilhado com a **RFC 7519 (JWT)** e, por extensão, com a **RFC 9068** — a mesma semântica de claims serve nos dois formatos.

## 7. O que mudou desde a publicação (2015)

- Spec estável e essencialmente universal onde quer que tokens opacos sejam usados — companheira natural de qualquer implantação que não use JWT autocontido como formato de access token.
- A ascensão de access tokens em formato JWT (formalizada depois pela RFC 9068 em 2021, e adotada por convenção de mercado até antes disso) reduziu a **necessidade** de introspecção em cenários de alto throughput, já que valida localmente evita o round-trip por requisição — mas introspecção continua essencial sempre que o status de revogação **em tempo real** importa mais do que evitar aquele round-trip, ou quando o token é mantido opaco de propósito (tamanho menor no cabeçalho HTTP, nenhuma informação vazando do próprio conteúdo do token para quem o interceptar).
- Um padrão híbrido comum hoje, que não era bem o desenho original de 2015 mas surgiu como prática de mercado: JWT para o caso geral (validação local, rápida, sem depender do AS estar no ar) **mais** uma checagem de revogação — via introspecção ou uma lista de revogação consultada esporadicamente — só quando a operação em questão exige garantia extra (uma transação financeira de alto valor, uma operação administrativa irreversível). Esse meio-termo reconhece que "JWT vs. opaco" não precisa ser uma escolha binária e permanente para toda e qualquer chamada.

> **Nota de laboratório**: nenhum lab deste projeto implementa `/introspect` ainda — todos os resource servers (`rfc6749/resource-server`, `rfc7636/resource-server`, `rfc7523/resource-server`, etc.) validam o `access_token` lendo diretamente do Redis compartilhado com o respectivo Authorization Server, o atalho já descrito na seção 6. Um gap natural para um laboratório futuro seria desacoplar essa leitura direta, substituindo-a por uma chamada real a `POST /introspect` — nesse ponto, o resource server deixaria de conhecer o esquema interno de armazenamento do AS e passaria a depender só do contrato JSON desta RFC.

## Exemplo em Java (JDK 21, sem frameworks)

Os exemplos a seguir implementam, do lado do resource server, uma chamada de introspecção completa usando apenas `java.net.http.HttpClient` para a chamada HTTP e o utilitário `SimpleJson` (`SimpleJson.object`, `SimpleJson.parseFlat`), definido no Capítulo 1 (RFC 6749) deste livro, para montar o corpo e interpretar a resposta.

### 4.1 Chamando `POST /introspect` autenticado

```java
import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.net.http.HttpRequest.BodyPublishers;
import java.nio.charset.StandardCharsets;
import java.util.Base64;
import java.util.Map;

/**
 * O RESOURCE SERVER (nao o client!) chama este endpoint, autenticado com
 * suas PROPRIAS credenciais (registradas junto ao AS especificamente para
 * este fim) — nunca com o token do usuario que esta sendo verificado.
 *
 * A resposta HTTP e' SEMPRE 200 — mesmo para token invalido/expirado/
 * revogado. O corpo (via campo "active") e' que carrega essa informacao;
 * tratar um status != 200 aqui como "token invalido" seria um erro de
 * implementacao — um != 200 significa problema na PROPRIA chamada de
 * introspeccao (ex.: credenciais do RS invalidas), nao no token investigado.
 */
public final class TokenIntrospectionClient {

    private final HttpClient http = HttpClient.newHttpClient();
    private final String introspectionEndpoint;
    private final String rsCredencialBasic; // Base64("resource_server_id:senha")

    public TokenIntrospectionClient(String introspectionEndpoint,
                                     String resourceServerId, String resourceServerSenha) {
        this.introspectionEndpoint = introspectionEndpoint;
        this.rsCredencialBasic = Base64.getEncoder().encodeToString(
                (resourceServerId + ":" + resourceServerSenha)
                        .getBytes(StandardCharsets.UTF_8));
    }

    public Map<String, String> introspectar(String token, String tokenTypeHint)
            throws Exception {

        String corpo = "token=" + token
                + (tokenTypeHint != null ? "&token_type_hint=" + tokenTypeHint : "");

        HttpRequest req = HttpRequest.newBuilder()
                .uri(URI.create(introspectionEndpoint))
                .header("Content-Type", "application/x-www-form-urlencoded")
                .header("Authorization", "Basic " + rsCredencialBasic) // credencial do RS, nao do usuario
                .POST(BodyPublishers.ofString(corpo, StandardCharsets.UTF_8))
                .build();

        HttpResponse<String> resp = http.send(req, HttpResponse.BodyHandlers.ofString());

        if (resp.statusCode() != 200) {
            // Isto indica falha na PROPRIA chamada (ex.: credenciais do RS
            // rejeitadas) — nao confundir com "token invalido", que vem
            // sempre como 200 + {"active": false}.
            throw new IllegalStateException(
                    "Falha ao chamar introspection endpoint: HTTP " + resp.statusCode());
        }

        return SimpleJson.parseFlat(resp.body());
    }
}
```

### 4.2 Interpretando a resposta e aplicando a decisão de autorização

```java
import java.time.Instant;
import java.util.Map;
import java.util.Set;

/**
 * A resposta de /introspect nunca deveria ser tratada como "true = deixa
 * passar" sem mais checagens — active=true so' significa que o token EXISTE
 * e nao expirou/foi revogado; ainda cabe ao resource server checar se o
 * escopo cobre a operacao pedida, exatamente como faria com um JWT local.
 */
public final class DecisaoDeAutorizacao {

    public static boolean tokenAutorizaOperacao(Map<String, String> introspeccao,
                                                 String escopoNecessario) {

        boolean ativo = "true".equals(introspeccao.get("active"));
        if (!ativo) {
            // Cobre TODOS os motivos de invalidade — expirado, revogado,
            // nunca existiu — a resposta e' deliberadamente uniforme
            // (RFC 7662 §2.2) para nao revelar qual dos tres aconteceu.
            return false;
        }

        String expStr = introspeccao.get("exp");
        if (expStr != null) {
            long exp = Long.parseLong(expStr);
            if (Instant.now().getEpochSecond() >= exp) {
                // Defesa em profundidade: mesmo que o AS diga active=true,
                // um RS cauteloso pode revalidar exp localmente (util se
                // o resultado veio de um cache local do proprio RS, e nao
                // de uma chamada fresca — ver secao 4.3 a seguir).
                return false;
            }
        }

        String scopeString = introspeccao.getOrDefault("scope", "");
        Set<String> escoposConcedidos = Set.of(scopeString.split(" "));
        return escoposConcedidos.contains(escopoNecessario);
    }
}
```

### 4.3 Cache local de curta duração (mitigando o custo do round-trip)

```java
import java.time.Instant;
import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;

/**
 * Implementa a mitigacao discutida na secao 5.4: cache de curtissima duracao
 * para nao pagar o round-trip de rede a CADA requisicao recebida pelo RS.
 * O trade-off e' explicito — um token revogado no AS pode continuar sendo
 * aceito aqui por ate CACHE_TTL_SEGUNDOS depois da revogacao. Escolher esse
 * numero e' uma decisao de seguranca, nao so' de performance.
 */
public final class IntrospeccaoComCache {

    private static final long CACHE_TTL_SEGUNDOS = 30;

    private record Entrada(Map<String, String> resposta, long expiraEm) {}

    private final ConcurrentHashMap<String, Entrada> cache = new ConcurrentHashMap<>();
    private final TokenIntrospectionClient clienteIntrospeccao;

    public IntrospeccaoComCache(TokenIntrospectionClient clienteIntrospeccao) {
        this.clienteIntrospeccao = clienteIntrospeccao;
    }

    public Map<String, String> introspectarComCache(String token) throws Exception {
        long agora = Instant.now().getEpochSecond();

        Entrada emCache = cache.get(token);
        if (emCache != null && emCache.expiraEm() > agora) {
            return emCache.resposta(); // evita o round-trip desta vez
        }

        Map<String, String> fresca = clienteIntrospeccao.introspectar(token, "access_token");
        cache.put(token, new Entrada(fresca, agora + CACHE_TTL_SEGUNDOS));
        return fresca;
        // Nota: um cache ingenuo como este NAO invalida entradas quando o
        // token e' revogado no meio da janela de TTL — e' exatamente a
        // janela de exposicao que a secao 5.4 pede para ser uma decisao
        // consciente da equipe de seguranca, nao um acidente de implementacao.
    }
}
```
