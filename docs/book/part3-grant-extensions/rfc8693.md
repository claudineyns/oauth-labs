# RFC 8693 — OAuth 2.0 Token Exchange

## 1. Contexto e motivação

A RFC 8693 nasce de um problema que praticamente qualquer arquitetura de microsserviços moderna encontra, e que fica particularmente evidente em ambientes bancários/FSI com múltiplas camadas de API: o resource owner (usuário final) autoriza um client uma vez, recebe um access_token, e esse token viaja para o primeiro serviço que o recebe (um gateway, um Backend-for-Frontend). Mas o pedido original quase nunca termina ali — o gateway precisa, para atender aquele mesmo pedido, chamar um segundo serviço downstream, e depois talvez um terceiro. A pergunta que a RFC 8693 responde é: **com que credencial o gateway deveria fazer essas chamadas subsequentes?**

A resposta ingênua — repassar exatamente o mesmo access_token recebido do usuário — é precisamente o anti-padrão de **"confused deputy"** já catalogado no capítulo da RFC 6819 deste livro. O problema não é hipotético nem sutil: aquele token foi emitido pelo Authorization Server pensando numa audience específica (o primeiro serviço, API-1), com um escopo pensado para as operações que API-1 expõe. Ao repassar o mesmo token para API-2, várias garantias implícitas quebram silenciosamente:

- **API-2 não tem como saber, só olhando o token, que ele não foi emitido pensando nela** — a menos que o AS pratique audience restriction rigorosa (RFC 8707, capítulo anterior deste livro) e API-2 valide isso ativamente, o token "funciona" em qualquer resource server que aceite a mesma chave de assinatura/introspecção, mesmo que ele nunca devesse ter sido chamado com aquele token.
- **O escopo concedido pelo usuário para API-1 pode ser mais amplo do que o necessário para a chamada específica a API-2** — repassar o token inteiro repassa também privilégios que a chamada atual nem precisa exercer, violando least-privilege na própria cadeia interna de chamadas, não só na borda externa.
- **Não há registro de que um intermediário (o gateway) esteve envolvido** — do ponto de vista de API-2, a chamada parece ter vindo diretamente do usuário, quando na verdade veio de um serviço agindo em nome dele. Para auditoria — crítico em ambiente regulado — essa distinção importa.

A RFC 8693 resolve isso formalizando um mecanismo de **troca**: o gateway apresenta o token que recebeu ao token endpoint do AS (não para o usuário se autenticar de novo — o usuário não está envolvido nesta troca) e recebe de volta um **token novo**, especificamente re-audienciado e/ou re-escopado para o destino real da próxima chamada, carregando de forma explícita e auditável tanto **quem originalmente pediu** (o subject — o usuário) quanto, quando aplicável, **quem está agindo agora em nome dele** (o actor — o próprio gateway).

Vale também situar os cenários correlatos que a RFC cobre, além do caso de gateway/BFF que abre o capítulo, porque a spec foi desenhada deliberadamente ampla:

- **Tradução de formato de token** — trocar uma asserção SAML (comum em ambientes corporativos legados, especialmente bancários com SSO baseado em SAML de longa data) por um JWT OAuth, permitindo que um sistema legado de identidade alimente uma arquitetura OAuth moderna sem reescrever o IdP.
- **Confiança cross-domain** — trocar um token emitido por um IdP A por um token aceito num sistema que confia especificamente em IdP B, quando existe uma relação de confiança configurada explicitamente no Authorization Server (uma federação de confiança, não uma tradução automática qualquer).
- **"Downscoping" deliberado** — trocar um token de escopo amplo por um mais restrito antes de repassá-lo adiante, mesmo sem trocar de audience — uma aplicação direta de least-privilege dentro da própria cadeia de chamadas de um mesmo serviço, útil quando um componente interno só precisa de uma fração do que o token original autoriza.

## 2. Terminologia e papéis

Esta é uma das RFCs do roteiro que introduz vocabulário genuinamente novo, não apenas parâmetros — e a precisão aqui importa porque a distinção central da RFC (impersonação vs. delegação) depende inteiramente desses termos:

- **Subject** — a entidade sobre quem o token efetivamente fala; tipicamente o resource owner/usuário final, mas pode ser qualquer entidade cuja identidade o token representa (inclusive, em cenários machine-to-machine, um serviço).
- **Actor** — quem está de fato exercendo a ação no momento presente, que pode (e no caso de interesse deste capítulo, é) diferente do subject. No exemplo do gateway: o usuário é o subject, o gateway é o actor.
- **Impersonação** — o token resultante da troca representa **só** o subject. O fato de um intermediário (actor) ter solicitado e efetuado a troca não fica registrado em lugar nenhum do token resultante. Do ponto de vista do resource server que recebe esse token novo, a chamada parece ter vindo diretamente do subject — "isto é o usuário", ponto final, como se ele tivesse chamado diretamente, sem intermediário algum visível.
- **Delegação** — o token resultante registra **os dois**, subject e actor, explicitamente. O resource server downstream enxerga uma cadeia de custódia auditável: "isto é o usuário, mas o gateway X está agindo em nome dele agora". É este o padrão que a claim `act` (mencionada informalmente pela RFC e consolidada por perfis JWT posteriores) representa — um encadeamento de "quem age em nome de quem", podendo em teoria se aninhar (um actor agindo em nome de outro actor que já agia em nome de um subject original, numa cadeia de múltiplos hops).
- **Security token** — a RFC evita deliberadamente o termo "access token" ao descrever o que é trocado, preferindo o termo genérico "security token", porque o mecanismo é **agnóstico de formato**: o que entra e o que sai pode ser um access token OAuth comum, um ID Token, um refresh token, um JWT arbitrário, ou até uma asserção SAML — qualquer coisa identificável por uma das URIs de tipo de token pré-registradas.

A escolha entre impersonação e delegação não é do client sozinho decidir livremente — é uma **política do Authorization Server**, tipicamente configurada por combinação de qual client está pedindo a troca, qual subject_token está sendo trocado, e para qual audience/resource. Um AS bem projetado para ambiente regulado deveria, na prática, favorecer fortemente delegação sobre impersonação sempre que a cadeia de chamadas tiver relevância de auditoria — que, em contexto bancário, é quase sempre.

## 3. Fluxo

Uma única requisição ao token endpoint já existente, com um `grant_type` novo — sem nenhum redirect de usuário envolvido, porque o Token Exchange é inteiramente back-channel, tipicamente machine-to-machine entre serviços:

```
POST /token
grant_type=urn:ietf:params:oauth:grant-type:token-exchange
&subject_token=<token a trocar>
&subject_token_type=urn:ietf:params:oauth:token-type:access_token
&resource=https://api-2.exemplo.com
&scope=... (opcional, mais restrito que o original)
&actor_token=... &actor_token_type=... (opcional — presente em delegação, representa quem esta pedindo a troca)
```

Vale examinar dois cenários concretos lado a lado, porque a diferença entre eles é exatamente a diferença entre impersonação e delegação na prática:

**Cenário A — impersonação pura**: o gateway envia só `subject_token` (o token do usuário) + `resource` (o destino, API-2). Não envia `actor_token`. O AS, se configurado para permitir impersonação para este client, emite um token novo cujo subject continua sendo o usuário original, sem qualquer registro do gateway ter mediado a troca.

**Cenário B — delegação explícita**: o gateway envia `subject_token` (do usuário) **e** `actor_token` (um token que identifica o próprio gateway, tipicamente obtido via Client Credentials Grant previamente) + `actor_token_type`. O AS, reconhecendo que este client tem permissão de atuar como actor para este tipo de subject, emite um token novo cujas claims incluem tanto o subject (usuário) quanto uma claim de ator encadeado — o resource server final consegue diferenciar exatamente quem pediu originalmente e quem mediou.

A resposta, no formato padrão do token endpoint (`access_token`, `token_type`, `expires_in`, `scope`, `refresh_token` opcional), ganha um campo novo e **obrigatório**: **`issued_token_type`**. Esse campo existe porque, diferente de qualquer grant anterior no roteiro, o Token Exchange pode devolver algo que **não** é um access_token OAuth comum — se o `subject_token` de entrada era uma asserção SAML e o cenário é de tradução de formato, o token devolvido pode ser um JWT com semântica diferente de um access_token tradicional, e o client precisa de um jeito programático de saber exatamente o que recebeu de volta, sem precisar inferir pelo formato.

## 4. Parâmetros e endpoints normativos

Nenhum endpoint novo — reaproveita inteiramente o `/token` da RFC 6749, com `grant_type=urn:ietf:params:oauth:grant-type:token-exchange`. A tabela de parâmetros da requisição:

| Parâmetro | Obrigatório | Descrição |
|---|---|---|
| `grant_type` | Sim | Sempre `urn:ietf:params:oauth:grant-type:token-exchange` |
| `subject_token` | Sim | O token de segurança a ser trocado |
| `subject_token_type` | Sim | URI identificando o tipo do subject_token |
| `actor_token` | Não | Presente apenas em cenários de delegação — representa quem está pedindo a troca |
| `actor_token_type` | Condicional | Obrigatório se `actor_token` estiver presente |
| `resource` | Não | URI indicando o destino/recurso pretendido do token novo (RFC 8707) |
| `audience` | Não | Alternativa/complemento a `resource` — identifica a audience pretendida de forma mais abstrata que uma URI de recurso |
| `scope` | Não | Permite pedir um escopo mais restrito que o do subject_token original — nunca mais amplo |
| `requested_token_type` | Não | Permite ao client pedir explicitamente que tipo de token quer de volta |

Os valores pré-registrados de tipo de token (usados em `subject_token_type`, `actor_token_type` e na resposta `issued_token_type`) seguem o padrão de URI `urn:ietf:params:oauth:token-type:`, com sufixos: `access_token`, `refresh_token`, `id_token`, `saml1`, `saml2`, `jwt`. Um AS pode, em teoria, suportar tipos adicionais não pré-registrados, mas os seis acima cobrem a esmagadora maioria dos cenários práticos.

A resposta, além dos campos padrão do token endpoint, inclui obrigatoriamente `issued_token_type` — o client deve tratar esse campo como autoritativo sobre o que de fato recebeu, em vez de assumir que voltou um `access_token` só porque pediu um.

Erros seguem o vocabulário genérico já conhecido do token endpoint (`invalid_request`, `invalid_grant`, `invalid_scope`) — a RFC não introduz um código de erro dedicado só para falhas de troca, preferindo reaproveitar a semântica existente: um `subject_token` inválido, expirado ou de um tipo não reconhecido tipicamente resulta em `invalid_grant`; uma combinação de client/subject/resource não autorizada pela política do AS tipicamente resulta em `invalid_target` (definido pela RFC 8707, para quando o `resource` pedido não é um destino válido para aquele token) ou `invalid_scope`.

## 5. Segurança já tratada na própria RFC 8693

- **Risco central: escalonamento de privilégio via troca em si**. Este é o ponto que a RFC trata com mais insistência, e o que separa uma implementação correta de uma perigosa: o Token Exchange, mal implementado, vira **ele mesmo** um vetor de escalonamento de privilégio. Se o AS aceitar qualquer troca de qualquer client para qualquer resource/audience sem validação rigorosa, um serviço que legitimamente possui um token de baixo privilégio poderia trocá-lo por um de privilégio mais alto — exatamente o oposto do propósito da RFC. A defesa exigida: o AS precisa validar explicitamente se **aquele client específico** está autorizado a trocar **aquele subject_token específico** pelo **resource/audience pedido especificamente** — uma matriz de política de três dimensões (client × subject × destino), não uma regra genérica de "qualquer troca é permitida".
- **Política sobre quem pode atuar como actor**: de forma análoga, o AS deve controlar explicitamente quais clients têm permissão de aparecer como `actor_token` em cenários de delegação, e quais combinações subject/actor fazem sentido — não é uma capacidade que qualquer client registrado deveria ganhar por padrão.
- **Princípio de não-ampliação**: o token resultante de uma troca deve, como regra geral, **restringir ou manter** — nunca ampliar — o escopo ou a audience em relação ao token original. O Token Exchange existe para re-direcionar e reduzir superfície, não para um serviço "upgradar" seu próprio nível de acesso através de uma troca conveniente. Um AS que permitisse `scope` mais amplo no token de saída do que no de entrada estaria invertendo o propósito inteiro da spec.
- **Auditabilidade de cadeias de delegação**: quando múltiplos hops de delegação se encadeiam (um actor trocando em nome de outro actor que já agia em nome de um subject original), a RFC espera que essa cadeia fique registrada de forma rastreável — o conceito de uma claim `act` aninhada (`act` dentro de `act`, representando cada hop) nasce justamente dessa necessidade, embora a estrutura exata da claim tenha sido deixada para perfis JWT subsequentes formalizarem, não a própria RFC 8693.
- **Confidencialidade do `subject_token`/`actor_token` em trânsito**: como qualquer requisição ao token endpoint, esta troca deve acontecer sobre TLS — os tokens de entrada carregam a mesma sensibilidade de qualquer token de segurança, e a RFC não introduz nenhuma exceção a essa exigência básica.
- Vale destacar, para um leitor com background FSI: em cadeias de chamada internas de sistemas bancários — que frequentemente atravessam múltiplos domínios de confiança (core banking, camada de integração, APIs de parceiros) — a disciplina de Token Exchange como **único mecanismo legítimo** de "trocar de contexto" entre domínios, em vez de replay do mesmo token ou de credenciais compartilhadas hardcoded entre serviços, é diretamente relevante para requisitos de segregação e auditoria típicos de regulação financeira.

## 6. Relação com outras RFCs

- Reaproveita a infraestrutura do token endpoint da RFC 6749 — o mesmo padrão estrutural de extensão via `grant_type` novo que a **RFC 8628 (Device Authorization Grant)**, capítulo anterior deste livro, também usa: em vez de endpoints de emissão paralelos, ambas preferem estender a semântica do `/token` já existente.
- É a solução formal e nomeada para o cenário de **"confused deputy"** catalogado na RFC 6819 (Threat Model): em vez de replay do mesmo token entre resource servers diferentes — o antipadrão descrito na abertura deste capítulo —, o mecanismo correto passa a ser trocar por um token novo, corretamente audienciado e/ou escopado para o destino real.
- Companheira direta da **RFC 8707 (Resource Indicators)**, tema de capítulo anterior deste livro: ambas usam um parâmetro `resource` para indicar o destino pretendido de um token. São specs do mesmo espaço de problema — ambientes com múltiplos resource servers, onde "para quem este token é válido" precisa ser explícito e verificável. O Token Exchange demonstra que a questão de audience correta não é só "evitar passivamente um ataque" (o enquadramento típico da RFC 8707 sozinha) — é também "ter um mecanismo **ativo** para emitir tokens corretamente audienciados em cadeias de chamada legítimas", uma dimensão complementar da mesma preocupação.
- Formato-agnóstica por design, conecta diretamente com a **RFC 7523 (JWT Profile for OAuth 2.0 Authorization Grants)** — um JWT é um dos tipos de subject/actor token explicitamente reconhecidos, e a RFC 7523 já estabelece o padrão de usar JWTs como portadores de asserção dentro do vocabulário OAuth.
- Conceito equivalente, em espírito, ao padrão **"On-Behalf-Of" (OBO)** usado por provedores de identidade corporativos (o exemplo mais citado sendo Azure AD/Microsoft Entra ID) — um padrão de mercado que antecede formalmente a RFC 8693, mas que hoje se alinha e, em implementações mais recentes, mapeia diretamente para o `grant_type` de Token Exchange desta RFC.

## 7. O que mudou desde a publicação (2020)

- A spec permanece estável, sem revisão formal — mas ganhou relevância crescente e sustentada com a adoção generalizada de arquiteturas de microsserviços e service mesh: Token Exchange se tornou peça padrão em padrões de API gateway e Backend-for-Frontend, exatamente para resolver o problema descrito na abertura deste capítulo — "como chamar a API downstream com um token corretamente escopado, sem repassar o token do usuário cru".
- Ganhou tração particular em arquiteturas **zero-trust**, onde a expectativa arquitetural passou a ser que **cada hop de serviço** carregue um token distintamente escopado/audienciado para aquele hop específico, em vez de um único token amplo circulando sem modificação por toda a cadeia de chamadas internas — um princípio diretamente relevante para o contexto de cadeias de APIs internas bancárias, onde diferentes domínios (pagamentos, core banking, canais digitais) tipicamente exigem essa segregação por exigência regulatória, não só por boa prática.
- A distinção subject/actor e o padrão de claim `act` encadeada foram adotados de forma informal por várias implementações de mercado como a maneira de-facto de representar cadeias de delegação dentro de JWTs — mesmo sem uma RFC separada fechando formalmente a estrutura exata dessa claim. Isso vive hoje mais em documentos de perfil e convenções específicas de fornecedor (Microsoft, Okta, entre outros) construídas sobre a fundação conceitual que a RFC 8693 estabeleceu, do que numa segunda spec IETF dedicada.

> **Nota sobre laboratório**: este projeto não possui, até o momento, um laboratório para a RFC 8693. O cenário natural para um lab desta RFC exigiria pelo menos um segundo resource server (além do já existente nos labs de RFC 6749/7636/9126) e um serviço "gateway" intermediário, demonstrando a troca de token como alternativa concreta ao replay do mesmo token entre APIs — incluindo, idealmente, os dois cenários (impersonação e delegação) lado a lado, com o resource server final mostrando a diferença observável na claim de identidade recebida. Por ora, este capítulo se concentra nos exemplos em Java abaixo, que constroem as requisições de troca do lado do client contra um Authorization Server hipotético.

## Exemplo em Java (JDK 21, sem frameworks)

Os exemplos usam `java.net.http.HttpClient` e o utilitário `SimpleJson` (métodos `SimpleJson.object(Map)` e `SimpleJson.parseFlat(String)`), definido no Capítulo 1 (RFC 6749) deste livro, para montar e ler os corpos JSON das requisições e respostas de troca.

### Exemplo 1 — troca simples (impersonação), re-audienciando para outra API

```java
import java.net.URI;
import java.net.URLEncoder;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.nio.charset.StandardCharsets;
import java.util.Map;

public final class TokenExchangeClient {

    private static final String GRANT_TYPE_TOKEN_EXCHANGE =
            "urn:ietf:params:oauth:grant-type:token-exchange";
    private static final String TYPE_ACCESS_TOKEN =
            "urn:ietf:params:oauth:token-type:access_token";
    private static final String TYPE_JWT =
            "urn:ietf:params:oauth:token-type:jwt";

    private final HttpClient http = HttpClient.newHttpClient();
    private final String tokenEndpoint;

    public TokenExchangeClient(String tokenEndpoint) {
        this.tokenEndpoint = tokenEndpoint;
    }

    // Troca um access_token recebido da chamada do usuário (subject_token)
    // por um token novo, audienciado para uma API downstream diferente —
    // sem enviar actor_token: cenário de IMPERSONAÇÃO (o token novo
    // representa só o subject, sem registro do gateway ter mediado).
    public Map<String, String> trocarParaOutraAudience(String subjectToken,
                                                         String resourceDestino,
                                                         String scopeRestrito) throws Exception {
        StringBuilder body = new StringBuilder();
        body.append("grant_type=").append(enc(GRANT_TYPE_TOKEN_EXCHANGE));
        body.append("&subject_token=").append(enc(subjectToken));
        body.append("&subject_token_type=").append(enc(TYPE_ACCESS_TOKEN));
        body.append("&resource=").append(enc(resourceDestino));
        if (scopeRestrito != null) {
            body.append("&scope=").append(enc(scopeRestrito));
        }

        HttpRequest request = HttpRequest.newBuilder()
                .uri(URI.create(tokenEndpoint))
                // Autenticação do CLIENT que está pedindo a troca (o gateway,
                // não o usuário) — aqui via client_secret_basic, um dos
                // métodos já vistos no capítulo da RFC 6749.
                .header("Authorization", "Basic " + java.util.Base64.getEncoder()
                        .encodeToString("gateway-svc:s3gr3d0-do-gateway".getBytes(StandardCharsets.UTF_8)))
                .header("Content-Type", "application/x-www-form-urlencoded")
                .POST(HttpRequest.BodyPublishers.ofString(body.toString()))
                .build();

        HttpResponse<String> response = http.send(request, HttpResponse.BodyHandlers.ofString());
        Map<String, String> json = SimpleJson.parseFlat(response.body());

        if (response.statusCode() != 200) {
            throw new RuntimeException("Token exchange falhou: "
                    + json.getOrDefault("error", "erro desconhecido"));
        }

        // Campo obrigatório e específico desta RFC: informa que TIPO de
        // token voltou — pode não ser um access_token comum.
        String issuedType = json.get("issued_token_type");
        System.out.println("Token recebido é do tipo: " + issuedType);
        return json;
    }

    private static String enc(String v) {
        return URLEncoder.encode(v, StandardCharsets.UTF_8);
    }
}
```

### Exemplo 2 — delegação explícita, com `actor_token` identificando o gateway

```java
import java.net.URI;
import java.net.URLEncoder;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.nio.charset.StandardCharsets;
import java.util.Map;

public final class DelegatedTokenExchange {

    private static final String GRANT_TYPE_TOKEN_EXCHANGE =
            "urn:ietf:params:oauth:grant-type:token-exchange";
    private static final String TYPE_ACCESS_TOKEN =
            "urn:ietf:params:oauth:token-type:access_token";

    private final HttpClient http = HttpClient.newHttpClient();
    private final String tokenEndpoint;

    public DelegatedTokenExchange(String tokenEndpoint) {
        this.tokenEndpoint = tokenEndpoint;
    }

    // Diferença central em relação ao Exemplo 1: envia actor_token, obtido
    // previamente via Client Credentials Grant (o gateway autenticando a si
    // mesmo, sem usuário envolvido). O AS, reconhecendo essa combinação como
    // delegação autorizada, emite um token cujas claims registram TANTO o
    // subject (usuário) QUANTO o actor (o gateway) — auditável no RS final.
    public Map<String, String> trocarComDelegacao(String subjectToken,
                                                    String actorTokenDoGateway,
                                                    String resourceDestino) throws Exception {
        StringBuilder body = new StringBuilder();
        body.append("grant_type=").append(enc(GRANT_TYPE_TOKEN_EXCHANGE));
        body.append("&subject_token=").append(enc(subjectToken));
        body.append("&subject_token_type=").append(enc(TYPE_ACCESS_TOKEN));
        body.append("&actor_token=").append(enc(actorTokenDoGateway));
        body.append("&actor_token_type=").append(enc(TYPE_ACCESS_TOKEN));
        body.append("&resource=").append(enc(resourceDestino));

        HttpRequest request = HttpRequest.newBuilder()
                .uri(URI.create(tokenEndpoint))
                .header("Authorization", "Basic " + java.util.Base64.getEncoder()
                        .encodeToString("gateway-svc:s3gr3d0-do-gateway".getBytes(StandardCharsets.UTF_8)))
                .header("Content-Type", "application/x-www-form-urlencoded")
                .POST(HttpRequest.BodyPublishers.ofString(body.toString()))
                .build();

        HttpResponse<String> response = http.send(request, HttpResponse.BodyHandlers.ofString());
        Map<String, String> json = SimpleJson.parseFlat(response.body());

        if (response.statusCode() != 200) {
            throw new RuntimeException("Token exchange (delegação) falhou: "
                    + json.getOrDefault("error", "erro desconhecido"));
        }
        // O resource server que receber este token novo, ao decodificar as
        // claims (fora do escopo deste exemplo — ver capítulo de JWT), veria
        // tanto o subject original quanto uma claim de ator identificando o
        // gateway como quem mediou a chamada.
        return json;
    }

    private static String enc(String v) {
        return URLEncoder.encode(v, StandardCharsets.UTF_8);
    }
}
```

### Exemplo 3 — obtendo o `actor_token` do gateway via Client Credentials, antes da delegação

```java
import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.nio.charset.StandardCharsets;
import java.util.Map;

public final class ObterActorToken {

    // O actor_token não é "inventado" pelo gateway — ele precisa ser um
    // token de segurança de verdade, emitido pelo mesmo AS (ou um AS de
    // confiança), tipicamente via Client Credentials Grant (RFC 6749 §4.4),
    // já que aqui não há usuário nenhum envolvido — é o próprio gateway se
    // autenticando como uma identidade de serviço.
    public static String obterActorTokenDoGateway(String tokenEndpoint,
                                                    String gatewayClientId,
                                                    String gatewayClientSecret) throws Exception {
        HttpClient http = HttpClient.newHttpClient();
        String body = "grant_type=client_credentials&scope=service-identity";

        String credenciais = gatewayClientId + ":" + gatewayClientSecret;
        HttpRequest request = HttpRequest.newBuilder()
                .uri(URI.create(tokenEndpoint))
                .header("Authorization", "Basic " + java.util.Base64.getEncoder()
                        .encodeToString(credenciais.getBytes(StandardCharsets.UTF_8)))
                .header("Content-Type", "application/x-www-form-urlencoded")
                .POST(HttpRequest.BodyPublishers.ofString(body))
                .build();

        HttpResponse<String> response = http.send(request, HttpResponse.BodyHandlers.ofString());
        Map<String, String> json = SimpleJson.parseFlat(response.body());
        if (response.statusCode() != 200) {
            throw new RuntimeException("Falha ao obter actor_token: " + json.get("error"));
        }
        return json.get("access_token");
    }
}
```

### Exemplo 4 — "downscoping" sem trocar de audience

```java
public final class DownscopingExample {

    // Cenário: um serviço interno recebeu um token com escopo amplo
    // ("accounts:read accounts:write transfers:execute"), mas só precisa,
    // para uma chamada específica, do escopo "accounts:read". Em vez de
    // repassar o token amplo adiante (violando least-privilege), troca por
    // um token novo, mesma audience, escopo estritamente mais restrito.
    public static void main(String[] args) throws Exception {
        var client = new TokenExchangeClient("https://as.exemplo.com/token");

        var tokenReduzido = client.trocarParaOutraAudience(
                "TOKEN_AMPLO_DO_SERVICO_A",
                "https://api.exemplo.com/contas", // mesma audience de destino
                "accounts:read" // escopo estritamente mais restrito que o original
        );

        System.out.println("Novo access_token (escopo reduzido): "
                + tokenReduzido.get("access_token"));
        // Este token reduzido é o que deveria ser repassado adiante para
        // qualquer componente que só precise de leitura — nunca o original.
    }
}
```
