# RFC 8628 — OAuth 2.0 Device Authorization Grant

## 1. Contexto e motivação

Os quatro grants originais da RFC 6749 partem todos de uma premissa implícita: o dispositivo onde o fluxo começa tem um **user-agent** razoável (um browser capaz de navegar, exibir um formulário de login, seguir redirects) e, na maioria dos casos, um **método de entrada de texto** decente (teclado físico ou virtual utilizável). Essa premissa é confortável para desktop e para a maioria dos smartphones — e completamente falsa para uma classe grande e crescente de dispositivos: smart TVs, dispositivos de streaming (set-top boxes), consoles de videogame, impressoras conectadas, terminais de ponto de venda, dispositivos IoT industriais, e ferramentas de linha de comando (CLIs) rodando num terminal sem nenhum browser à disposição.

Antes da RFC 8628 (publicada em 2019, embora a ideia já circulasse informalmente havia anos sob o nome "OAuth Device Flow"), as alternativas disponíveis para esse tipo de dispositivo eram todas insatisfatórias, e vale enumerar por que cada uma falha:

- **Implementar um teclado na tela** para o usuário digitar usuário e senha diretamente no dispositivo limitado (a experiência clássica de "navegar" letra por letra com um controle remoto numa Smart TV). Isso é ruim por dois motivos: a UX é péssima (qualquer um que já tentou digitar uma senha complexa com um controle de TV sabe disso), e — mais grave do ponto de vista arquitetural — isso **reintroduz exatamente o anti-padrão que o OAuth inteiro existe para eliminar**: o dispositivo (um client) coletando a senha do usuário diretamente, em vez de delegar essa coleta para o Authorization Server. É o mesmo problema estrutural do Resource Owner Password Credentials Grant, só que forçado pela limitação de hardware em vez de por preguiça de implementação.
- **Usar o próprio ROPC** — que tem exatamente essa fraqueza estrutural (client vê a senha em claro) somada às limitações já conhecidas do grant (não funciona com MFA de forma nativa, não separa credencial de autorização, e foi formalmente deprecado por práticas atuais, incluindo a RFC 9700).
- **Não ter fluxo nenhum padronizado** — cada fabricante inventando seu próprio mecanismo proprietário de "ativação", sem interoperabilidade entre AS diferentes.

A ideia central da RFC 8628, e o que a torna elegante, é uma inversão simples: em vez de tentar melhorar a entrada de texto no dispositivo limitado, **tirar essa etapa do dispositivo limitado inteiramente** e transferi-la para um **segundo dispositivo** que o usuário quase certamente já tem à mão — o próprio celular, ou um notebook — que tem browser de verdade e teclado de verdade. O dispositivo limitado (o client, no vocabulário OAuth) só precisa fazer duas coisas: mostrar um código curto e uma URL curta na tela, e ficar consultando o Authorization Server em segundo plano até a autorização acontecer em algum outro lugar.

O exemplo que qualquer leitor já viu na prática, mesmo sem saber que é OAuth: ligar uma Smart TV nova e ver "Para ativar o Netflix, acesse netflix.com/ativar num computador ou celular e digite o código ABCD-1234". Essa tela **é**, literalmente, a implementação desta RFC — o "código" é o `user_code`, a URL é a `verification_uri`, e a TV, por trás da tela, está fazendo polling no token endpoint enquanto espera.

Um ponto de contexto histórico interessante: a RFC 8628 formaliza um padrão que várias grandes plataformas (Google, entre outras) já vinham implementando de forma consistente mas não normatizada havia anos antes da publicação — o documento chega, em boa parte, para dar interoperabilidade e um vocabulário comum a um padrão que o mercado já tinha convergido informalmente.

## 2. Terminologia e papéis

A característica estrutural mais importante deste fluxo, que molda todo o vocabulário: **em nenhum momento existe um redirect de user-agent envolvendo o dispositivo original**. Isso é uma ruptura real com o modelo dos outros grants baseados em `/authorize` — não há `redirect_uri`, não há `state` no sentido de proteção de CSRF de um redirect (porque não há redirect), e o dispositivo (client) e o "user-agent" que efetivamente interage com o AS **são fisicamente separados**, rodando em hardware diferente, possivelmente em rede diferente.

Vocabulário novo introduzido pela RFC:

- **`device_code`** — um identificador opaco e de alta entropia, análogo em espírito a um authorization code de vida um pouco mais longa. Fica **só no dispositivo** (o client) — nunca é mostrado ao usuário, nunca sai do dispositivo exceto nas chamadas de polling ao token endpoint. Funciona como a "credencial de sessão" que o dispositivo usa para perguntar repetidamente "já fui autorizado?".
- **`user_code`** — um código curto, **desenhado explicitamente para ser digitado por um humano**: charset restrito (a RFC recomenda evitar caracteres visualmente ambíguos como `0` vs `O`, `1` vs `I` vs `l`), formato tipicamente com um hífen no meio para facilitar leitura em voz alta ou digitação em duas partes (`WDJB-MJHT`, por exemplo). É o único artefato deste fluxo que o resource owner efetivamente vê e manipula.
- **`verification_uri`** — a URL curta e fácil de digitar (ou de lembrar) que o usuário acessa no segundo dispositivo. A RFC recomenda que essa URL seja deliberadamente curta e memorável — não é incomum ver domínios dedicados só para isso (`netflix.com/ativar`, por exemplo), porque o usuário pode estar digitando de memória, olhando para uma TV a alguns metros de distância.
- **`verification_uri_complete`** (opcional) — a mesma URL, mas já com o `user_code` embutido como parâmetro de query. Existe para um caso de uso específico: exibir um **QR code** na tela do dispositivo, que ao ser escaneado leva o usuário direto para a tela de confirmação já com o código preenchido — eliminando completamente a digitação manual do `user_code`. Muitos dispositivos modernos (consoles, algumas Smart TVs) mostram QR code e código textual lado a lado, cobrindo os dois estilos de usuário.

Um ponto sutil sobre papéis: no vocabulário da RFC, o "dispositivo" continua sendo o **client** (no sentido OAuth) — é ele quem faz as chamadas HTTP ao AS. O "segundo aparelho" (celular ou notebook do usuário) **não é um client OAuth novo** — ele só está rodando um browser comum acessando uma página web comum do Authorization Server (a tela de verificação), participando do fluxo de login/consentimento exatamente como participaria em qualquer outro grant baseado em navegador.

## 3. Fluxo

```
1. Device → AS: POST /device_authorization   client_id=...&scope=...
2. AS → Device: { device_code, user_code, verification_uri, verification_uri_complete, expires_in, interval }
3. Device exibe: "Acesse <verification_uri> e digite o código <user_code>" (ou um QR code)
4. Usuário, em OUTRO dispositivo: abre verification_uri, digita o user_code (ou escaneia o QR)
5. AS autentica o usuário normalmente — mesma tela de login/consentimento do Authorization Code Grant
6. Enquanto isso, Device consulta em loop:
   POST /token  grant_type=urn:ietf:params:oauth:grant-type:device_code&device_code=...&client_id=...
   - AS responde authorization_pending (400) enquanto o passo 4-5 nao terminou
   - Device espera `interval` segundos entre tentativas (AS pode responder slow_down se o poll for rapido demais)
7. Assim que o usuario conclui a autorizacao, o proximo poll retorna a resposta normal de token (access_token, refresh_token...)
```

Vale examinar com mais cuidado a máquina de estados do polling no passo 6, porque é a parte operacionalmente mais delicada de implementar corretamente, e onde a maioria dos bugs de implementação de device flow acontece na prática:

- **Estado inicial**: o `device_code` foi emitido, o usuário ainda não fez nada no segundo dispositivo (ou está no meio do processo). Cada poll retorna `authorization_pending` — um erro HTTP 400 no vocabulário do token endpoint, mas semanticamente "ainda não, continue tentando", não uma falha real.
- **Polling rápido demais**: se o client não respeita o `interval` devolvido no passo 2 (ou continua usando um `interval` desatualizado depois de já ter recebido um `slow_down`), o AS pode responder `slow_down` — que carrega uma instrução implícita: **aumente o intervalo em pelo menos 5 segundos** a partir de agora, e continue. Isso não é um erro fatal, é uma correção de ritmo. Um client bem implementado mantém o `interval` como uma variável mutável ao longo do loop, nunca fixo desde o início.
- **Usuário nega**: se o usuário, na tela de consentimento do segundo dispositivo, explicitamente recusa a autorização, o próximo poll recebe `access_denied` — este sim um erro terminal, o loop deve parar e o dispositivo deve informar o usuário que a autorização foi negada.
- **Expiração**: o `device_code` (e o `user_code` associado) têm um `expires_in` — tipicamente alguns minutos. Se o usuário demora demais (ou simplesmente nunca acessa a `verification_uri`), o próximo poll depois da expiração recebe `expired_token` — também terminal; o dispositivo precisa reiniciar do zero (novo `POST /device_authorization`, novo `user_code` exibido).
- **Sucesso**: assim que o passo 5 é concluído do lado do usuário, o **próximo** poll do dispositivo (não instantaneamente — só quando o loop chegar na próxima tentativa, respeitando `interval`) recebe a resposta normal de token, no mesmo formato de qualquer outro grant (`access_token`, `token_type`, `expires_in`, `refresh_token` se aplicável). Esse é o único ponto onde o dispositivo "descobre" que foi autorizado — não há nenhum tipo de callback, webhook ou push notification definido pela spec; é estritamente poll-based.

Um detalhe de timing que vale destacar para quem for implementar um client deste grant: como não há garantia de quando exatamente o usuário vai concluir o passo 5 em relação ao ritmo de polling do dispositivo, o client deve estar preparado para ficar em `authorization_pending` por um tempo potencialmente longo (minutos) sem tratar isso como anômalo — é o comportamento normal e esperado da maior parte da vida útil de um fluxo bem-sucedido.

## 4. Parâmetros e endpoints normativos

- **Device authorization endpoint** — endpoint inteiramente novo introduzido por esta RFC, tipicamente `POST /device_authorization` (o caminho exato é decisão do AS; descoberto de forma padronizada via RFC 8414 como o campo `device_authorization_endpoint` no metadata).
  - Request (`application/x-www-form-urlencoded`): `client_id` (obrigatório — mesmo client_id que seria usado em qualquer outro grant deste client), `scope` (opcional, mesma semântica de sempre).
  - Response (JSON): `device_code`, `user_code`, `verification_uri`, `verification_uri_complete` (opcional), `expires_in` (segundos até o `device_code`/`user_code` expirarem), `interval` (segundos mínimos entre polls; se omitido, o padrão assumido pela spec é 5).
- **Reaproveitamento do `/token`** — este é um dos pontos de design mais elegantes da RFC: em vez de inventar um endpoint de emissão de token paralelo, ela só define um **`grant_type` novo** para o token endpoint já existente da RFC 6749: `urn:ietf:params:oauth:grant-type:device_code`. Toda a infraestrutura de resposta de sucesso/erro do token endpoint (formato do corpo, cabeçalhos de cache, tratamento de erro) é reaproveitada sem modificação — só a semântica de "o que estou pedindo" muda.
- **Erros específicos do polling (§3.5)**, todos devolvidos como erro padrão do token endpoint (HTTP 400, corpo `{"error": "..."}`), com quatro valores próprios deste grant além dos erros genéricos já existentes na RFC 6749:
  - `authorization_pending` — ainda aguardando o usuário completar o passo 4-5; continue tentando no `interval` atual.
  - `slow_down` — o client está consultando rápido demais; aumente o `interval` em pelo menos 5 segundos e continue.
  - `access_denied` — o usuário negou explicitamente a autorização; pare de tentar.
  - `expired_token` — `device_code`/`user_code` expiraram antes da conclusão; pare de tentar, é preciso recomeçar do passo 1.

Uma observação de implementação relevante para quem constrói o lado servidor: o AS precisa manter, associados ao mesmo `device_code`, tanto o estado de autorização (pendente/aprovado/negado) quanto o timestamp de expiração e o `interval` atual esperado daquele client específico — inclusive para detectar corretamente quando aplicar `slow_down` (o AS precisa lembrar quando foi o poll anterior daquele `device_code` para saber se o atual veio cedo demais).

## 5. Segurança já tratada na própria RFC 8628 (§5)

- **Entropia baixa do `user_code` é uma escolha deliberada, não um descuido** — ele precisa ser digitável por um humano em segundos, o que impõe um teto prático de tamanho e um charset restrito bem abaixo da entropia normalmente esperada de um artefato OAuth (compare com os 256 bits recomendados para um `code_verifier` da PKCE, capítulo anterior). Para compensar essa entropia estruturalmente menor, a RFC exige contrapartidas operacionais: **rate limiting** agressivo no endpoint de verificação (impedindo que um atacante tente forçar bruta muitos `user_code`s por segundo) e **expiração curta** (minutos, não horas) para o `user_code`/`device_code`, reduzindo a janela em que um `user_code` de baixa entropia seria viável de adivinhar. É um perfil de risco genuinamente diferente do resto do OAuth, e a própria RFC é explícita sobre estar fazendo essa troca conscientemente.
- **Confidencialidade do `device_code`** — apesar de não precisar ser digitável (por isso pode ter entropia alta), o `device_code` ainda precisa ficar confidencial no dispositivo durante toda a janela de espera: quem o possuir pode fazer o polling em nome do dispositivo legítimo. Como este grant costuma ser usado por clients públicos (dispositivos sem capacidade de guardar segredo — TVs, consoles), o `device_code` funciona, durante essa janela, quase como uma credencial ao portador de curta duração.
- **`slow_down`/`interval` como proteção operacional do AS** — sem esse mecanismo, um dispositivo mal implementado (ou deliberadamente malicioso) poderia fazer polling agressivo, sobrecarregando o token endpoint. O `interval` cresce sob demanda do próprio AS, não é uma configuração estática negociada previamente.
- **Reconhecimento (parcial) de risco de phishing já no texto original**: a RFC já observa que mostrar um "código real" de autorização para induzir alguém a autorizar algo que não pediu é um risco conceitual, e recomenda que a tela de consentimento do AS deixe claro **para qual aplicação/dispositivo** a autorização está sendo concedida. Mas essa recomendação, sozinha, se mostrou insuficiente na prática — ver item 7 abaixo, porque é exatamente aqui que a história pós-publicação fica interessante.

## 6. Relação com outras RFCs

- Adiciona um **quinto grant type** ao vocabulário da RFC 6749, especificamente desenhado para a classe de dispositivo ("input-constrained") que os quatro grants originais não atendiam bem.
- Reaproveita inteiramente a infraestrutura do token endpoint da RFC 6749 — mesmo padrão estrutural de extensão via `grant_type` novo que a **RFC 8693 (Token Exchange)**, próximo capítulo deste livro, também usa. Vale comparar os dois: ambos evitam criar um endpoint de emissão paralelo, preferindo estender a semântica do `/token` já existente — um padrão de design que se repete no ecossistema de extensões do OAuth.
- Descoberto via **RFC 8414** (Authorization Server Metadata) como `device_authorization_endpoint` — o mesmo padrão de descoberta já visto para `revocation_endpoint` e `introspection_endpoint` em capítulos anteriores deste livro.
- **PKCE (RFC 7636) não se aplica a este grant** — e vale entender por quê: PKCE protege contra interceptação de um `code` entregue via redirect de user-agent; aqui não há `redirect_uri` nem redirect nenhum envolvendo o dispositivo original, então a superfície de ataque que a PKCE endereça simplesmente não existe nesta forma. O risco análogo deste grant (phishing de `user_code`) tem uma forma estrutural diferente — ver item 7.
- Fecha um ciclo aberto no capítulo da **RFC 6819** deste livro: naquele capítulo, "phishing de device code" já foi apontado como uma classe de ameaça que só passaria a existir depois da publicação da RFC 8628 (2019) — este é o capítulo onde essa ameaça, antecipada estruturalmente, finalmente ganha um mecanismo concreto ao qual se aplicar.
- Fora do escopo deste livro, mas conceitualmente próximo: **CIBA** (Client-Initiated Backchannel Authentication), uma extensão do OpenID Connect que também desacopla "onde a requisição começa" de "onde a autenticação do usuário acontece" — só que CIBA não depende de o usuário digitar um código: o AS notifica o dispositivo de autenticação do usuário diretamente (push notification, por exemplo), um modelo "decoupled" de geração diferente, mas resolvendo uma preocupação de UX aparentada.

## 7. O que mudou desde a publicação (2019)

- O texto normativo da RFC em si permanece estável, sem revisão formal desde a publicação — mas um padrão de abuso real e significativo emergiu **depois**, e não estava adequadamente coberto pelo threat model original: **phishing de device code**, também chamado de "device code phishing" ou explorado sob o guarda-chuva de ataques de "adversary-in-the-middle" contra fluxos de autenticação moderna.
- O mecanismo do ataque: o atacante **inicia o próprio fluxo legítimo** (faz o `POST /device_authorization` ele mesmo, com um client_id de uma aplicação real e confiável — por exemplo, o próprio client oficial do Microsoft 365, cujo client_id é público) e obtém um `user_code` genuíno, válido, gerado pelo AS real. Em seguida, usando engenharia social — tipicamente um pretexto de "suporte técnico" por telefone ou uma campanha de phishing por e-mail/SMS — convence a vítima a acessar a `verification_uri` legítima e digitar **o código do atacante**. A vítima, ao se autenticar normalmente (tudo acontece no domínio real do AS, com TLS válido — não há nada "falso" visualmente para a vítima detectar), efetivamente autoriza a sessão do atacante, não a sua própria. O atacante, do outro lado do polling, recebe o token.
- O que torna esse ataque particularmente insidioso, e por isso vale destacar num livro voltado a arquitetos: **não há nenhum indicador técnico visivelmente errado para a vítima notar** — o domínio é o real, o certificado TLS é válido, a tela de login é a tela de login genuína do provedor de identidade. A única defesa possível é a vítima perceber que está digitando um código que **não veio de um dispositivo que ela mesma está tentando ativar** — uma defesa inteiramente dependente de atenção humana e contexto, exatamente a categoria de defesa que a engenharia social é desenhada para contornar. Esse ataque foi documentado em campanhas reais e amplamente reportadas contra contas Microsoft 365/Entra ID a partir de 2022, com atribuição a grupos patrocinados por estados.
- As mitigações que emergiram são **práticas operacionais e de produto**, não emendas formais ao texto da RFC 8628:
  - **"Number matching"** — em vez de (ou além de) o usuário digitar o `user_code` no segundo dispositivo, o fluxo passa a exigir que o usuário **confirme, no dispositivo onde está se autenticando, um número exibido no dispositivo original que iniciou o pedido** — invertendo a direção da verificação e forçando o usuário a olhar concretamente para o dispositivo que ele mesmo está tentando ativar, dificultando (mas não eliminando) o pretexto de phishing.
  - Exibir **contexto adicional** durante a tela de consentimento — nome da aplicação, localização geográfica aproximada de onde partiu o pedido, horário — para dar à vítima mais sinais para desconfiar de um pedido que ela não iniciou.
  - Reduzir a **vida útil** do `user_code`/`device_code` ainda mais do que o mínimo já recomendado pela spec original, encurtando a janela de oportunidade do atacante.
  - Conscientização de segurança organizacional — treinar usuários para desconfiar de qualquer solicitação de "digite este código" que chegue por telefone ou mensagem não solicitada, independentemente de o domínio parecer legítimo.
- Vale reter esta lição como o ponto mais importante do capítulo do ponto de vista arquitetural: este é um exemplo direto e bem documentado de um grant **tecnicamente correto e implementado fielmente conforme a spec**, cujo risco real e explorado em produção só apareceu com a escala de uso — exatamente o tipo de lição que a RFC 6819 tenta antecipar estruturalmente, mas que a prática mostrou que nem sempre um threat model publicado antecipa tudo. Para um arquiteto avaliando adotar este grant hoje, a decisão correta não é "a RFC cobre a segurança, então está resolvido" — é reconhecer que controles operacionais pós-publicação (number matching, em particular) deveriam ser tratados como parte do baseline de adoção responsável, não como um extra opcional.

> **Nota sobre laboratório**: este projeto não possui, até o momento, um laboratório para a RFC 8628 — os labs existentes cobrem RFC 6749 (grant básico), RFC 7636 (PKCE) e RFC 9126 (PAR), todos baseados em redirect de browser. O Device Authorization Grant tem uma forma visualmente muito diferente (sem redirect nenhum, com um loop de polling e dois "dispositivos" separados) e seria um bom candidato a laboratório futuro — simulando um "dispositivo" (uma aba de browser ou processo dedicado, fazendo polling) enquanto um segundo "aparelho" (outra aba, representando o celular do usuário) completa a autorização de forma independente. Por ora, este capítulo se concentra nos exemplos em Java abaixo, que implementam o fluxo do lado do dispositivo (client) contra um Authorization Server hipotético.

## Exemplo em Java (JDK 21, sem frameworks)

Os exemplos usam `java.net.http.HttpClient` para as chamadas HTTP e o utilitário `SimpleJson` (métodos `SimpleJson.object(Map)` e `SimpleJson.parseFlat(String)`), definido no Capítulo 1 (RFC 6749) deste livro, para montar/ler os corpos JSON — todos "achatados" (sem aninhamento), o que é suficiente para as respostas deste grant.

### Exemplo 1 — iniciar a Device Authorization Request

```java
import java.net.URI;
import java.net.URLEncoder;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.nio.charset.StandardCharsets;
import java.util.Map;

public final class DeviceAuthorizationClient {

    private final HttpClient http = HttpClient.newHttpClient();
    private final String deviceAuthorizationEndpoint;
    private final String tokenEndpoint;
    private final String clientId;

    public DeviceAuthorizationClient(String deviceAuthorizationEndpoint,
                                      String tokenEndpoint, String clientId) {
        this.deviceAuthorizationEndpoint = deviceAuthorizationEndpoint;
        this.tokenEndpoint = tokenEndpoint;
        this.clientId = clientId;
    }

    // RFC 8628 §3.1 — POST /device_authorization. Sem autenticação forte de
    // client aqui (tipicamente clients públicos — TVs, CLIs — não têm
    // client_secret); o client_id sozinho identifica a aplicação.
    public Map<String, String> iniciarDeviceAuthorization(String scope) throws Exception {
        String body = "client_id=" + URLEncoder.encode(clientId, StandardCharsets.UTF_8)
                + "&scope=" + URLEncoder.encode(scope, StandardCharsets.UTF_8);

        HttpRequest request = HttpRequest.newBuilder()
                .uri(URI.create(deviceAuthorizationEndpoint))
                .header("Content-Type", "application/x-www-form-urlencoded")
                .POST(HttpRequest.BodyPublishers.ofString(body))
                .build();

        HttpResponse<String> response = http.send(request, HttpResponse.BodyHandlers.ofString());
        if (response.statusCode() != 200) {
            throw new RuntimeException("Falha ao iniciar device authorization: HTTP "
                    + response.statusCode() + " - " + response.body());
        }
        // device_code, user_code, verification_uri, verification_uri_complete,
        // expires_in, interval
        return SimpleJson.parseFlat(response.body());
    }
}
```

### Exemplo 2 — exibir instruções ao usuário (simulando a tela do dispositivo)

```java
public final class DeviceScreen {

    // Em produção isto seria a UI real do dispositivo (TV, console...). Aqui,
    // simulamos com saída de console — o ponto didático é que o dispositivo
    // não precisa (nem deveria) coletar usuário/senha: só mostra um código
    // curto e uma URL, e delega toda a autenticação para o segundo aparelho.
    public static void exibirInstrucoes(java.util.Map<String, String> deviceAuthResponse) {
        String userCode = deviceAuthResponse.get("user_code");
        String verificationUri = deviceAuthResponse.get("verification_uri");
        String verificationUriComplete = deviceAuthResponse.get("verification_uri_complete");

        System.out.println("==============================================");
        System.out.println(" Para ativar este dispositivo:");
        System.out.println(" 1. Acesse: " + verificationUri);
        System.out.println(" 2. Digite o código: " + userCode);
        if (verificationUriComplete != null) {
            System.out.println(" (ou escaneie o QR code apontando para "
                    + verificationUriComplete + ")");
        }
        System.out.println("==============================================");
    }
}
```

### Exemplo 3 — loop de polling no `/token`, tratando cada estado do RFC 8628 §3.5

```java
import java.net.URI;
import java.net.URLEncoder;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.nio.charset.StandardCharsets;
import java.util.Map;

public final class DevicePolling {

    private static final String GRANT_TYPE_DEVICE_CODE =
            "urn:ietf:params:oauth:grant-type:device_code";

    private final HttpClient http = HttpClient.newHttpClient();
    private final String tokenEndpoint;
    private final String clientId;

    public DevicePolling(String tokenEndpoint, String clientId) {
        this.tokenEndpoint = tokenEndpoint;
        this.clientId = clientId;
    }

    // Faz o polling até obter sucesso, negação explícita, ou expiração.
    // O `interval` é tratado como mutável — cresce sempre que o AS responde
    // slow_down, nunca diminui, e o loop dorme por esse tempo entre cada
    // tentativa, exatamente como o §3.5 da RFC prescreve.
    public Map<String, String> aguardarAutorizacao(String deviceCode, int intervalInicialSegundos)
            throws Exception {
        int interval = intervalInicialSegundos;

        while (true) {
            Thread.sleep(interval * 1000L);

            String body = "grant_type=" + URLEncoder.encode(GRANT_TYPE_DEVICE_CODE, StandardCharsets.UTF_8)
                    + "&device_code=" + URLEncoder.encode(deviceCode, StandardCharsets.UTF_8)
                    + "&client_id=" + URLEncoder.encode(clientId, StandardCharsets.UTF_8);

            HttpRequest request = HttpRequest.newBuilder()
                    .uri(URI.create(tokenEndpoint))
                    .header("Content-Type", "application/x-www-form-urlencoded")
                    .POST(HttpRequest.BodyPublishers.ofString(body))
                    .build();

            HttpResponse<String> response = http.send(request, HttpResponse.BodyHandlers.ofString());
            Map<String, String> json = SimpleJson.parseFlat(response.body());

            if (response.statusCode() == 200) {
                // Sucesso: access_token, token_type, expires_in, refresh_token...
                return json;
            }

            String error = json.getOrDefault("error", "");
            switch (error) {
                case "authorization_pending" -> {
                    // Ainda esperando o usuário completar o passo no segundo
                    // dispositivo — continua o loop no mesmo interval.
                    System.out.println("Aguardando autorização do usuário...");
                }
                case "slow_down" -> {
                    // RFC 8628 §3.5: aumentar o interval em pelo menos 5s.
                    interval += 5;
                    System.out.println("AS pediu slow_down — novo interval: " + interval + "s");
                }
                case "access_denied" -> throw new RuntimeException(
                        "Usuário negou a autorização explicitamente.");
                case "expired_token" -> throw new RuntimeException(
                        "device_code/user_code expiraram antes da conclusão — reinicie o fluxo.");
                default -> throw new RuntimeException(
                        "Erro inesperado do token endpoint: " + error);
            }
        }
    }
}
```
