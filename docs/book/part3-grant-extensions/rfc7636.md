# RFC 7636 — Proof Key for Code Exchange by OAuth Public Clients (PKCE)

## 1. Contexto e motivação

Para entender por que a RFC 7636 existe, é preciso primeiro entender por que o Authorization Code Grant da RFC 6749, sozinho, é insuficiente para uma classe inteira de clients. A RFC 6749 já distingue **clients confidenciais** (podem guardar um `client_secret` com segurança — um backend web, por exemplo, rodando num servidor que o usuário não controla) de **clients públicos** (não podem — um app mobile, uma SPA rodando inteiramente no browser, uma CLI instalada na máquina do usuário). No token endpoint, um client confidencial autentica a si mesmo com o secret; um client público não tem nada equivalente para apresentar. Esse é o buraco que a RFC 7636 preenche.

O cenário concreto de 2015 que motivou a RFC é bem específico e vale reconstituir em detalhe, porque a lógica do ataque explica exatamente por que a defesa tem o formato que tem. Apps mobile nativos, antes de app links/universal links serem universais, recebiam o redirect de volta do Authorization Server via um **esquema de URI customizado** — algo como `com.exemplo.meuapp://oauth/callback`. O sistema operacional (Android, em particular, era o caso mais discutido) permite que **múltiplos apps instalados registrem o mesmo esquema customizado**. Não há dono exclusivo de `myapp://callback` da forma como há dono de um domínio HTTPS verificado. Isso significa que um app malicioso, sabendo (ou adivinhando, ou lendo o `client_id` público de outro app) qual esquema um app legítimo usa, pode registrar esse mesmo esquema para si. Quando o sistema operacional recebe o redirect do browser/AS de volta para `myapp://oauth/callback?code=xyz`, ele pode entregar essa Intent/URI tanto para o app legítimo quanto para o malicioso — o comportamento exato depende do SO e de detalhes de instalação, mas o ponto estrutural é: **o `redirect_uri` baseado em esquema customizado não é um canal que só o destinatário pretendido consegue ler**.

Agora o problema de fundo: se o app malicioso intercepta esse `code`, o que ele precisa para trocá-lo por um token no `/token`? Segundo a RFC 6749 pura, só o `code` e o `client_id` — e o `client_id` de um client público **não é segredo, é público por definição** (o próprio nome do tipo de client já entrega isso). Não existe `client_secret` para autenticar a troca, porque client público não tem um. Resultado: o interceptador tem literalmente tudo que precisa para completar a troca sozinho, antes ou em vez do app legítimo. A interceptação do `code` é, sozinha, suficiente para roubo de sessão completo.

É importante notar o que esse ataque **não é**: não é uma falha de TLS (o redirect pode estar todo em HTTPS até o momento em que o SO decide para qual app entregar a URI local), não é uma falha do Authorization Server, e não é uma falha de o resource owner ter feito algo errado. É uma falha estrutural do **canal de entrega do `code` no dispositivo do usuário**, canal que a RFC 6749 nunca modelou como potencialmente compartilhado entre múltiplas partes não confiáveis.

A ideia da RFC 7636 é elegante justamente por não tentar consertar o canal (não dá — o SO é quem arbitra esquemas de URI, e a spec não controla isso). Em vez disso, ela garante que **possuir o `code` sozinho não seja mais suficiente**. A defesa: o client legítimo gera, no início do fluxo — antes de qualquer coisa tocar o browser ou um redirect — um segredo de alta entropia que **nunca trafega em claro** pelo canal vulnerável. Só uma versão derivada e unidirecional dele (o `code_challenge`) vai para a requisição de autorização. Quando chega a hora de trocar o `code` por um token, o client tem que provar posse do segredo original — e o interceptador, que só viu o `code` (não a requisição de autorização original, que não passou pelo mesmo esquema de URI vulnerável, mas sim por HTTPS direto do app para o AS), simplesmente não tem esse segredo.

Vale insistir num ponto sutil que costuma confundir: o `code_challenge` **também** viaja por um canal em tese observável (query string do `/authorize`, que pode acabar em logs de proxy, histórico de browser, `Referer`). Mas isso não importa para o ataque específico que a PKCE resolve — porque quem intercepta o **redirect de volta** (`redirect_uri?code=...`) não necessariamente observou a **ida** (`/authorize?...&code_challenge=...`), e mesmo que observasse, o `code_challenge` com S256 não permite reconstruir o `code_verifier` (hash unidirecional). O modelo de ameaça da PKCE é especificamente "quem só vê o code consegue completar a troca?" — e a resposta vira não.

## 2. Terminologia e papéis

Não há papel novo em relação à RFC 6749 — client, Authorization Server, resource owner continuam os mesmos. O vocabulário novo é todo criptográfico e merece precisão:

- **`code_verifier`**: uma string aleatória de alta entropia, gerada pelo client no início de cada fluxo de autorização (um verifier novo por tentativa de login, nunca reaproveitado entre fluxos). A RFC especifica o charset permitido — `[A-Z] [a-z] [0-9] "-" "." "_" "~"` (o conjunto "unreserved" da RFC 3986, que dispensa qualquer percent-encoding em URLs) — e o comprimento: **mínimo 43, máximo 128 caracteres**. Esses números não são arbitrários: 43 caracteres em base64url corresponde a 256 bits de entropia bruta (32 bytes aleatórios), o mesmo patamar de segurança de uma chave SHA-256 — abaixo disso, a RFC considera a entropia insuficiente para resistir a força bruta num prazo razoável; 128 é um teto prático para não estourar limites de tamanho de URL em implementações mais restritivas.
- **`code_challenge`**: o que de fato viaja na requisição de autorização — uma transformação do `code_verifier` que o AS consegue verificar depois, mas que não permite (no caso de S256) reconstituir o verifier original a partir dela.
- **`code_challenge_method`**: qual transformação foi usada. Dois valores definidos:
  - `plain` — `code_challenge = code_verifier`, sem transformação nenhuma. Existe por compatibilidade com dispositivos incapazes de computar SHA-256 (a própria RFC cita como motivação hipotética; na prática, praticamente nenhum dispositivo moderno tem essa limitação).
  - `S256` — `code_challenge = BASE64URL-ENCODE(SHA256(ASCII(code_verifier)))`, sem padding (`=`) e usando o alfabeto URL-safe (`-`/`_` em vez de `+`/`/`). É o método recomendado pela RFC desde o dia 1, e hoje é, na prática, o único aceitável — ver §5.

Um detalhe de nomenclatura que vale reter: "PKCE" é pronunciado popularmente "pixy" na comunidade, e o nome completo — **P**roof **K**ey for **C**ode **E**xchange — já entrega a arquitetura: uma prova (`code_verifier`) de posse de uma chave (o segredo gerado), apresentada no momento da troca do code (`code exchange`, o passo 6 do fluxo).

## 3. Fluxo

```
1. Client gera code_verifier (aleatório, alta entropia, 43-128 chars)
2. Client calcula code_challenge = BASE64URL(SHA256(code_verifier))     [método S256]
3. Client → AS: GET /authorize?...&code_challenge=xxx&code_challenge_method=S256
4. AS associa code_challenge (+ método) ao authorization code que vai emitir
5. AS → Client: redirect com code=...
6. Client → AS: POST /token  grant_type=authorization_code&code=...&code_verifier=<verifier original>
7. AS recalcula BASE64URL(SHA256(code_verifier)) e compara com o code_challenge armazenado
8. Bate → emite tokens. Não bate → invalid_grant.
```

Vale detalhar o que acontece dentro do passo 4, porque é onde o AS efetivamente cria o vínculo criptográfico que sustenta toda a garantia: o `code_challenge` (e o método) precisam ficar **atrelados ao `code` emitido**, tipicamente como um campo a mais no registro do code (junto com `client_id`, `redirect_uri`, `scope`, expiração) guardado server-side — não é algo que o AS possa "confiar de volta" no próprio `code` sem persistir, porque o `code` em si costuma ser só um identificador opaco. Se o AS emitisse o `code` sem persistir o challenge associado, o passo 7 não teria contra o que comparar, e toda a defesa desmoronaria silenciosamente — um erro de implementação real que vale checar em qualquer AS caseiro.

Também vale detalhar o caminho de falha do passo 8 com mais precisão do que o resumo sugere. Existem três formas de o passo 7 falhar, e a RFC trata as três da mesma forma (rejeição com `invalid_grant`), mas elas têm origens diferentes:
- **`code_verifier` ausente** na troca, quando a requisição original trouxe `code_challenge` — o AS deve rejeitar; aceitar cairia num "downgrade" silencioso (ver §5).
- **`code_verifier` presente mas incorreto** — o hash recalculado não bate com o challenge armazenado. É exatamente o caso do ataque de interceptação: quem só tem o `code` não tem o verifier certo, então qualquer tentativa (inclusive um verifier aleatório improvisado) falha aqui.
- **`code_challenge` ausente na requisição original, mas `code_verifier` presente na troca** (ou vice-versa em alguns perfis mais estritos) — tipicamente também rejeitado; a spec deixa alguma liberdade de política ao AS aqui, mas a prática recomendada (e exigida por OAuth 2.1) é que o AS **sempre** exija `code_challenge` na requisição de autorização, tornando esse caso irrelevante por construção.

Um ponto que costuma gerar confusão: PKCE **não substitui** o passo do usuário se autenticar e consentir — ele roda em paralelo a isso, é ortogonal ao login. O `code_challenge` vai junto com os mesmos parâmetros de sempre (`response_type=code`, `client_id`, `redirect_uri`, `scope`, `state`); a tela de login/consentimento do AS não muda em nada por causa da PKCE. A diferença toda está nos dois pontos: o que acompanha o `/authorize` (o challenge) e o que passa a ser exigido no `/token` (o verifier).

## 4. Parâmetros e endpoints normativos

Nenhum endpoint novo — PKCE estende os dois endpoints já existentes na RFC 6749:

| Parâmetro | Onde | Obrigatoriedade | Descrição |
|---|---|---|---|
| `code_challenge` | Authorization Request (`/authorize`) | Obrigatório quando o client usa PKCE | O challenge derivado do verifier |
| `code_challenge_method` | Authorization Request (`/authorize`) | Opcional (mas deveria ser tratado como obrigatório em prática atual) | `plain` ou `S256` |
| `code_verifier` | Token Request (`/token`) | Obrigatório se a authorization request usou `code_challenge` | O verifier original, em claro |

Um detalhe normativo com peso prático real: a RFC original (2015), se `code_challenge_method` vem omitido, instrui o AS a **assumir `plain`** como padrão. Isso é hoje amplamente considerado um detalhe infeliz da spec original — um AS que segue essa regra ao pé da letra, sem política adicional, fica vulnerável a um client (ou atacante forçando o client) que simplesmente omita o parâmetro, caindo silenciosamente para o método mais fraco. A prática recomendada atual — e o comportamento que qualquer AS bem-comportado deveria ter — é **rejeitar** a requisição se `code_challenge_method` vier ausente ou vier como algo diferente de `S256`, em vez de aceitar o padrão implícito da spec. Isso é coerente com a RFC 9700, que trata esse padrão de "aceitar silenciosamente o caminho mais fraco quando um parâmetro está ausente" como uma classe geral de risco a evitar em qualquer extensão do protocolo.

Quanto a erros: não há um código de erro novo — a RFC reaproveita o vocabulário de erro já existente do token endpoint (RFC 6749 §5.2). A falha de verificação do PKCE se manifesta como `invalid_grant`, o mesmo erro usado para qualquer outra rejeição de authorization code (code expirado, code já usado, `redirect_uri` que não bate). Do ponto de vista do client, isso significa que **não dá para diferenciar, pela resposta HTTP, se a falha foi "PKCE errado" ou "code expirado"** — o que é intencional: dar esse detalhe ao chamador ajudaria um atacante a refinar tentativas (ver também a discussão equivalente sobre respostas uniformes na RFC 7009, item de revogação).

## 5. Segurança já tratada na própria RFC 7636 (§5)

- **`plain` vs `S256` — a diferença central de garantia**: com `plain`, `code_challenge` **é** `code_verifier` — não há transformação nenhuma. Isso significa que qualquer observador da requisição de autorização original (histórico de browser local, um proxy corporativo fazendo TLS termination, logs de servidor que gravam a query string completa) vê o verifier em claro, e para *aquela* tentativa específica, a proteção nunca existiu — o observador tem exatamente o que precisaria para completar a troca. Com S256, ver o `code_challenge` não permite computar o `code_verifier` de volta (propriedade de hash unidirecional do SHA-256) — só quem gerou o verifier original o possui. É por isso que a RFC já recomendava S256 como preferencial desde 2015, e por que a prática atual (reforçada pela RFC 9700 e por OAuth 2.1) é evitar `plain` categoricamente, a menos que o dispositivo seja genuinamente incapaz de computar SHA-256 (praticamente inexistente hoje).
- **Ataque de downgrade**: se um atacante consegue, de alguma forma, fazer o client (ou uma versão adulterada dele) não enviar `code_challenge`, ou enviar com `plain` em vez de `S256`, a janela de vulnerabilidade original reabre. A defesa correta não depende do client "se lembrar" de fazer certo — depende do **AS aplicar a exigência por política**: um AS bem configurado hoje rejeita qualquer authorization request sem `code_challenge` (ou com método diferente de `S256`), independentemente do que o client mandou historicamente. Isso é coerente com o princípio geral (RFC 9700) de que controles de segurança não deveriam ser opt-in do lado do client quando o AS tem poder de os tornar obrigatórios.
- **PKCE não é (sozinha) proteção CSRF**: um erro conceitual comum é achar que, com PKCE, o parâmetro `state` da RFC 6749 se torna dispensável. Não é o caso. PKCE resolve um problema diferente — impedir que **quem intercepta o code** complete a troca. CSRF no fluxo de autorização é outro ataque: induzir a vítima a completar um fluxo de autorização **iniciado pelo atacante**, atrelando a sessão da vítima a uma conta/recurso do atacante. A RFC 9700 discute que o `code_verifier`, por ser mantido pelo client entre o passo 1 e o passo 6 (tipicamente atrelado à sessão do browser via cookie ou armazenamento local), pode incidentalmente **também** ajudar a mitigar CSRF, mas só se o client de fato vincular esse verifier à sessão do usuário que iniciou o fluxo — algo que a spec da PKCE não impõe estruturalmente. Um client que gerasse o verifier de forma desvinculada da sessão do usuário (o que a RFC não proíbe explicitamente) perderia esse benefício incidental. `state` continua sendo o mecanismo desenhado especificamente para CSRF, e não deveria ser removido "porque agora tem PKCE".
- **Reuso de `code_verifier` entre tentativas**: embora a RFC não seja explícita sobre proibir reuso do mesmo verifier em múltiplos fluxos de login, a prática recomendada é gerar um verifier novo a cada tentativa — reuso reduziria a superfície de garantia sem ganho nenhum de usabilidade (gerar um verifier novo é computacionalmente trivial), e um verifier de vida longa é um alvo mais valioso caso algum canal auxiliar (armazenamento local do client, por exemplo) seja comprometido.
- **PKCE não protege contra um client comprometido**: se o próprio app legítimo está comprometido (malware no dispositivo, por exemplo), PKCE não ajuda — o atacante tem acesso ao processo que gera e guarda o verifier. PKCE resolve especificamente a interceptação do `code` num canal compartilhado *fora* do processo do client legítimo, não comprometimento do client em si.

## 6. Relação com outras RFCs

- É a mitigação direta, nomeada e específica da ameaça de **interceptação de authorization code** catalogada na RFC 6819 (Threat Model) — fecha explicitamente um ciclo aberto por aquele documento: a RFC 6819 identifica o risco, a RFC 7636 é a resposta formal a ele, três anos depois.
- Escopada originalmente (o próprio título da RFC diz: "by OAuth Public Clients") para clients **públicos** — a **RFC 9700** amplia a recomendação para **todo client, inclusive confidencial**. A lógica: mesmo um client com `client_secret` se beneficia de PKCE, porque o verifier é um segredo **adicional e independente** do secret — se o secret vazar (configuração errada, log acidental, repositório de código com credencial hardcoded), PKCE ainda oferece uma segunda camada de defesa contra a troca do code por outra parte.
- No draft **OAuth 2.1**, PKCE deixa de ser uma extensão opcional documentada à parte e passa a fazer parte da **definição própria** do Authorization Code Grant — ou seja, deixa de ser "RFC 6749 + RFC 7636 opcionalmente" e passa a ser só "o Authorization Code Grant, que já inclui PKCE por definição".
- Interage diretamente com as próximas RFCs deste capítulo: **RFC 9126 (PAR)** e **RFC 9101 (JAR)** mudam **como** o `code_challenge`/`code_challenge_method` são transmitidos ao AS (via um push autenticado por back-channel, ou dentro de um objeto de requisição assinado, em vez de query string crua) — mas não alteram em nada o mecanismo de verificação em si no `/token`. Isso é um padrão recorrente que vale destacar: PAR e JAR resolvem "como os parâmetros chegam ao AS com integridade/confidencialidade"; PKCE resolve "como provar posse de um segredo na troca do code" — são preocupações ortogonais que se compõem sem atrito.
- Combinada com **RFC 8252 (OAuth 2.0 for Native Apps, BCP informativo)** — que recomenda PKCE como parte do conjunto de práticas para apps nativos, junto com uso de `AppAuth`-style browsers externos em vez de WebViews embutidos.

## 7. O que mudou desde a publicação (2015)

- De "recomendado para clients públicos" para "obrigatório para todo client" — uma década de consolidação via RFC 9700 (2025).
- `plain` como método, embora ainda tecnicamente definido na spec, é hoje considerado essencialmente obsoleto na prática — implementações bem-comportadas de AS **exigem** `S256` e rejeitam qualquer coisa diferente, em vez de honrar o `plain` como opção legítima.
- PKCE deixou de ser só uma mitigação para apps nativos mobile (seu caso de uso original) e passou a ser parte central da arquitetura recomendada para **SPAs** também — coincidindo com a recomendação (também consolidada na RFC 9700 e em guias práticos como o próprio OAuth 2.1) de abandonar o Implicit Grant em favor de Authorization Code + PKCE mesmo em contextos onde não há backend confidencial nenhum.
- A ideia de "code_challenge/code_verifier" como padrão de "compromisso criptográfico de mão única, verificado depois" também influenciou, conceitualmente, o desenho de outras extensões de sender-constraining discutidas em capítulos anteriores deste livro (DPoP, mTLS) — todas compartilham a lógica de "provar posse de algo sem revelar o segredo no canal vulnerável".

> **Observação sobre o lab**: o `rfc6749/authorization-server` e o `client-demo` implementam o Authorization Code Grant conforme o piso da RFC 6749, **sem PKCE** — não há `code_challenge`/`code_verifier` em nenhum passo do fluxo. Esse gap foi fechado no lab `rfc7636/`: uma réplica autocontida do lab da RFC 6749 (mesmos containers, convenções, formatos de token), com PKCE (S256 obrigatório — o AS rejeita qualquer coisa diferente) na Authorization Code Grant. O `authorization-server` calcula `BASE64URL(SHA256(code_verifier))` (arquivo `pkce.js`) e compara contra o `code_challenge` recebido na authorization request. O lab tem um fluxo dedicado — botão "Interceptar code sem o code_verifier" — que simula exatamente o ataque descrito no item 1 deste capítulo: completa um login real, mas na troca final usa um `code_verifier` propositalmente errado, e a tela de resultado mostra a rejeição `invalid_grant` do AS na prática. O lab também acrescenta Token Revocation (RFC 7009) com cascata por família de tokens, tema de um capítulo anterior deste livro.

## Exemplo em Java (JDK 21, sem frameworks)

Os exemplos a seguir usam somente a biblioteca padrão do JDK 21: `java.net.http.HttpClient` para chamadas HTTP, `java.security.SecureRandom`/`MessageDigest` para a criptografia da PKCE, e `java.util.Base64` para as codificações base64url exigidas pela RFC. O utilitário `SimpleJson` (métodos `SimpleJson.object(Map)` e `SimpleJson.parseFlat(String)`), definido no Capítulo 1 (RFC 6749) deste livro, é reaproveitado para montar e ler corpos JSON simples.

### Exemplo 1 — gerar `code_verifier` e `code_challenge` (S256)

```java
import java.security.MessageDigest;
import java.security.NoSuchAlgorithmException;
import java.security.SecureRandom;
import java.util.Base64;
import java.nio.charset.StandardCharsets;

public final class Pkce {

    private static final SecureRandom RNG = new SecureRandom();

    // RFC 7636 §4.1: o code_verifier deve ter entre 43 e 128 caracteres,
    // usando apenas o charset "unreserved" (A-Z a-z 0-9 - . _ ~). Gerar
    // 32 bytes aleatórios e codificar em base64url (sem padding) produz
    // uma string de 43 caracteres desse charset — no piso mínimo exigido,
    // mas já carregando 256 bits de entropia bruta, o mesmo patamar de um
    // hash SHA-256. Não há ganho real em ir além disso.
    public static String generateCodeVerifier() {
        byte[] entropy = new byte[32];
        RNG.nextBytes(entropy);
        return Base64.getUrlEncoder().withoutPadding().encodeToString(entropy);
    }

    // RFC 7636 §4.2, método S256: code_challenge = BASE64URL(SHA256(verifier)).
    // O hash é computado sobre os bytes ASCII do verifier (nunca sobre uma
    // representação já codificada) — divergir disso produz um challenge que
    // o AS jamais vai reconhecer como correspondente ao verifier certo.
    public static String computeCodeChallengeS256(String codeVerifier) {
        try {
            MessageDigest sha256 = MessageDigest.getInstance("SHA-256");
            byte[] hash = sha256.digest(codeVerifier.getBytes(StandardCharsets.US_ASCII));
            return Base64.getUrlEncoder().withoutPadding().encodeToString(hash);
        } catch (NoSuchAlgorithmException e) {
            // SHA-256 é garantido presente em qualquer JVM conforme a spec
            // da plataforma — chegar aqui indicaria um runtime quebrado.
            throw new IllegalStateException("SHA-256 indisponível na JVM", e);
        }
    }

    public static void main(String[] args) {
        String verifier = generateCodeVerifier();
        String challenge = computeCodeChallengeS256(verifier);
        System.out.println("code_verifier  = " + verifier + " (" + verifier.length() + " chars)");
        System.out.println("code_challenge = " + challenge);
        // O code_verifier fica só na memória do client até o passo do /token.
        // Só o code_challenge (acima) vai para a authorization request.
    }
}
```

### Exemplo 2 — montar a authorization request com PKCE

```java
import java.net.URI;
import java.net.URLEncoder;
import java.nio.charset.StandardCharsets;
import java.util.LinkedHashMap;
import java.util.Map;

public final class AuthorizationRequestBuilder {

    // Monta a URL de /authorize incluindo code_challenge/code_challenge_method,
    // além dos parametros já conhecidos da RFC 6749 (response_type, client_id,
    // redirect_uri, scope, state). Cada valor passa por URLEncoder — igual a
    // qualquer outro parâmetro de query string, o code_challenge não recebe
    // tratamento especial de encoding (já é base64url, um charset seguro
    // para URL, mas o encoding de query string genérico não faz mal).
    public static URI build(String authorizationEndpoint, String clientId,
                             String redirectUri, String scope, String state,
                             String codeChallenge) {
        Map<String, String> params = new LinkedHashMap<>();
        params.put("response_type", "code");
        params.put("client_id", clientId);
        params.put("redirect_uri", redirectUri);
        params.put("scope", scope);
        params.put("state", state);
        params.put("code_challenge", codeChallenge);
        params.put("code_challenge_method", "S256"); // nunca "plain" na prática atual

        StringBuilder query = new StringBuilder();
        for (var entry : params.entrySet()) {
            if (!query.isEmpty()) query.append('&');
            query.append(URLEncoder.encode(entry.getKey(), StandardCharsets.UTF_8))
                 .append('=')
                 .append(URLEncoder.encode(entry.getValue(), StandardCharsets.UTF_8));
        }
        return URI.create(authorizationEndpoint + "?" + query);
    }

    public static void main(String[] args) {
        String verifier = Pkce.generateCodeVerifier();
        String challenge = Pkce.computeCodeChallengeS256(verifier);

        URI authorizeUrl = build(
                "https://as.exemplo.com/authorize",
                "a1b2c3d4e5f6a7b8", // client_id (público, sem segredo)
                "myapp://oauth/callback",
                "profile",
                "xyzABC123", // state, contra CSRF — independente da PKCE
                challenge);

        System.out.println("Abrir no user-agent: " + authorizeUrl);
        // O code_verifier NÃO participa desta URL — fica guardado localmente
        // (memória do processo, ou storage seguro do app) até o passo 6.
    }
}
```

### Exemplo 3 — trocar o `code` por token, enviando o `code_verifier`

```java
import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.net.URLEncoder;
import java.nio.charset.StandardCharsets;
import java.util.Map;

public final class TokenExchange {

    private static final HttpClient HTTP = HttpClient.newHttpClient();

    public static Map<String, String> trocarCodePorToken(String tokenEndpoint,
                                                           String clientId,
                                                           String code,
                                                           String redirectUri,
                                                           String codeVerifier) throws Exception {
        String body = "grant_type=authorization_code"
                + "&code=" + URLEncoder.encode(code, StandardCharsets.UTF_8)
                + "&redirect_uri=" + URLEncoder.encode(redirectUri, StandardCharsets.UTF_8)
                + "&client_id=" + URLEncoder.encode(clientId, StandardCharsets.UTF_8)
                // client público: sem client_secret. A "autenticação" desta
                // troca é justamente a posse do code_verifier correto.
                + "&code_verifier=" + URLEncoder.encode(codeVerifier, StandardCharsets.UTF_8);

        HttpRequest request = HttpRequest.newBuilder()
                .uri(URI.create(tokenEndpoint))
                .header("Content-Type", "application/x-www-form-urlencoded")
                .POST(HttpRequest.BodyPublishers.ofString(body))
                .build();

        HttpResponse<String> response = HTTP.send(request, HttpResponse.BodyHandlers.ofString());

        // Resposta de sucesso e de erro do /token têm o mesmo formato JSON
        // "achatado" (sem aninhamento) — SimpleJson.parseFlat cobre os dois.
        Map<String, String> json = SimpleJson.parseFlat(response.body());

        if (response.statusCode() != 200) {
            // Erro típico quando o code_verifier não bate com o code_challenge
            // registrado: HTTP 400, {"error":"invalid_grant", ...}
            throw new RuntimeException("Token endpoint recusou a troca: "
                    + json.getOrDefault("error", "erro desconhecido")
                    + " — " + json.getOrDefault("error_description", ""));
        }
        return json; // access_token, token_type, expires_in, refresh_token...
    }
}
```

### Exemplo 4 — reproduzindo o ataque de interceptação (verifier incorreto)

```java
public final class InterceptacaoDemo {

    // Simula o que um atacante que só capturou o `code` do redirect
    // conseguiria fazer: ele NÃO tem o code_verifier original (que nunca
    // trafegou por esse canal), então só pode tentar um verifier qualquer
    // — aleatório, ou reaproveitado de outra tentativa. Em qualquer caso,
    // o hash recalculado pelo AS não vai bater com o code_challenge
    // registrado, e a troca falha.
    public static void main(String[] args) throws Exception {
        String codeInterceptado = "AUTH_CODE_CAPTURADO_PELO_ATACANTE";
        String verifierAdivinhado = Pkce.generateCodeVerifier(); // um chute qualquer

        try {
            TokenExchange.trocarCodePorToken(
                    "https://as.exemplo.com/token",
                    "a1b2c3d4e5f6a7b8",
                    codeInterceptado,
                    "myapp://oauth/callback",
                    verifierAdivinhado);
            System.out.println("Troca bem-sucedida — isso NÃO deveria acontecer!");
        } catch (RuntimeException falhaEsperada) {
            // Este é o resultado correto: invalid_grant. É exatamente o
            // comportamento que o lab rfc7636/ demonstra na prática, no
            // fluxo "Interceptar code sem o code_verifier".
            System.out.println("Troca rejeitada como esperado: " + falhaEsperada.getMessage());
        }
    }
}
```
