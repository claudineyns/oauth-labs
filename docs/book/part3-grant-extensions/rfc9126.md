# RFC 9126 — OAuth 2.0 Pushed Authorization Requests (PAR)

## 1. Contexto e motivação

A requisição de autorização tradicional, exatamente como definida na RFC 6749 §4.1.1, transporta **todos** os seus parâmetros como query string, através do user-agent do usuário (o front-channel): `GET /authorize?response_type=code&client_id=...&redirect_uri=...&scope=...&state=...`. Esse desenho fazia sentido em 2012, quando o conjunto de parâmetros era pequeno e estável. O problema é que o ecossistema OAuth não parou de crescer desde então — cada extensão relevante deste próprio livro adiciona parâmetros à mesma requisição: PKCE acrescenta `code_challenge`/`code_challenge_method`; Resource Indicators acrescenta `resource`; Rich Authorization Requests (fora do escopo deste roteiro, mas real em produção) acrescenta um `authorization_details` potencialmente extenso. O resultado observável é uma URL que só cresce, e que cresce **exposta exatamente onde este próprio livro, no capítulo da RFC 6750, já ensinou que nada sensível deveria estar**: histórico local do browser, logs de servidor e de proxy corporativo, e o cabeçalho `Referer` — que, dependendo da política de referrer do browser e do site de destino, pode vazar a URL completa (com todos os parâmetros) para terceiros simplesmente por o usuário ter clicado num link a partir daquela página.

Há um segundo problema, estruturalmente mais interessante do que "a URL ficou grande", e que vale entender com precisão porque é a motivação central da RFC, não um efeito colateral: os parâmetros da requisição de autorização, ao chegarem ao Authorization Server via o browser do usuário, **passaram por um canal cuja integridade não está de forma alguma atestada como vinda do client**. O AS recebe uma query string e precisa confiar, sem nenhuma prova criptográfica, que ela reflete exatamente o que o client pretendia enviar. Nada estrutural impede uma adulteração no caminho — uma extensão de browser maliciosa reescrevendo a URL antes do redirect efetivo, uma cadeia de redirecionamento intermediária (comum em cenários de single sign-on corporativo com múltiplos hops) alterando um parâmetro, ou simplesmente um proxy de rede fazendo algum tipo de rewrite não intencional. O AS não tem, na RFC 6749 pura, nenhuma forma de detectar isso — ele processa a query string como recebida, e ponto.

A solução da RFC 9126 (publicada em 2021) inverte a direção do transporte dos parâmetros sensíveis: em vez de deixar que eles viajem pelo browser do usuário até o AS, o client os **empurra** (push) diretamente para um endpoint dedicado do AS, por um canal back-channel **autenticado** — o mesmo tipo de canal, com as mesmas garantias de autenticação de client, que já é usado no token endpoint desde a RFC 6749. Esse push acontece **antes** de qualquer coisa tocar o browser. Em troca do push, o client recebe de volta uma referência curta, opaca e de vida curta — o `request_uri` — que é literalmente **tudo** que vai para a URL que o browser do usuário efetivamente vê e navega.

Vale insistir num ponto que separa PAR de uma simples "otimização de tamanho de URL": o ganho real não é só "a URL ficou menor" — é que a integridade e a autenticidade dos parâmetros passam a depender de um canal HTTPS servidor-a-servidor autenticado por credencial de client, exatamente a mesma garantia de confiança que o token endpoint já tinha desde sempre, em vez de depender das propriedades — muito mais fracas e variáveis — de um redirect de browser passando por múltiplas camadas de software fora do controle direto do client ou do AS.

## 2. Terminologia e papéis

Nenhum papel novo em relação à RFC 6749. Vocabulário introduzido:

- **Pushed Authorization Request endpoint** (comumente abreviado "PAR endpoint") — um endpoint inteiramente novo, tipicamente exposto como `/par`, onde o client faz o `POST` autenticado carregando os parâmetros da requisição de autorização.
- **`request_uri`** — uma referência opaca, de vida curta e **uso único**, devolvida pelo PAR endpoint como resposta ao push. Esse valor substitui completamente a lista de parâmetros na requisição de autorização subsequente feita pelo browser.

Um ponto terminológico que merece atenção antecipada, porque volta a aparecer com mais força no próximo capítulo: o termo `request_uri` **também existe, com o mesmo nome mas semântica diferente**, na RFC 9101 (JAR) — lá, é uma URL hospedada pelo *client*, buscada pelo *AS*; aqui, é uma referência opaca gerada pelo *AS* depois de receber o push do *client*. A coincidência de nome não é acidental (os dois conceitos de fato têm um parentesco de propósito — reduzir o que trafega na query string do `/authorize`), mas são mecanismos distintos, com fluxo de geração e uso invertidos. O próximo capítulo deste livro trata dessa distinção com mais detalhe.

## 3. Fluxo

```
1. Client → AS: POST /par  (autenticado — client_secret, mTLS, private_key_jwt...)
   response_type=code&client_id=...&redirect_uri=...&scope=...&state=...&code_challenge=...&code_challenge_method=S256

2. AS valida os parametros (mesma validacao que faria num /authorize normal) e os guarda server-side

3. AS → Client: { request_uri: "urn:ietf:params:oauth:request_uri:6esc_11ACC5bwc014ltc14eY22c", expires_in: 60 }

4. Client → User-Agent: redireciona para
   GET /authorize?client_id=...&request_uri=urn:ietf:params:oauth:request_uri:6esc_11ACC5bwc014ltc14eY22c

5. AS busca os parametros guardados pelo request_uri, segue com login/consentimento normalmente
6. ... resto do Authorization Code Grant sem mudanca (redirect com code, troca por token...)
```

Vale examinar com atenção o que acontece dentro do passo 2, porque é onde o AS efetivamente concentra toda a validação que antes só aconteceria no momento do `/authorize` tradicional — e um ponto de design implícito da RFC é que **essa validação deve acontecer integralmente no momento do push**, não ser adiada para quando o `request_uri` for consumido no passo 5. Isso significa: o AS confere `client_id` válido, `redirect_uri` registrado para aquele client, `response_type` suportado, `scope` dentro do que o client tem permissão de pedir, e (se presente) `code_challenge_method` aceitável — exatamente as mesmas checagens que uma authorization request tradicional receberia, só que antecipadas. Se alguma dessas checagens falhar, o `POST /par` retorna um erro imediatamente (o mesmo vocabulário de erro do `/authorize`, ex.: `invalid_scope`), e o client nunca chega a redirecionar o usuário — uma melhoria de UX incidental: erros de configuração do client são detectados antes de gastar um redirect do usuário.

O passo 4, por contraste, fica deliberadamente minimalista: a requisição de autorização que efetivamente toca o browser carrega só `client_id` (para o AS saber de qual client é essa referência, e não confiar cegamente na referência sozinha) e `request_uri`. Nenhum outro parâmetro da requisição original aparece ali — nem mesmo redundantemente. O AS, ao processar o passo 5, é quem recupera o conjunto completo de parâmetros a partir do que foi armazenado no passo 2, associado àquele `request_uri` específico.

Um detalhe de ciclo de vida que merece destaque: o `request_uri` é **de uso único**. Isso significa que o AS deve invalidar (apagar ou marcar como consumido) o registro associado assim que o passo 5 o consome pela primeira vez — uma segunda tentativa de `GET /authorize` com o mesmo `request_uri` deve falhar, independentemente de o primeiro uso ter tido sucesso ou não. Esse comportamento espelha exatamente a mesma disciplina de uso único já vista no authorization code da RFC 6749 (RFC 6819 já cataloga replay de code como ameaça relevante) — e não é coincidência: ambos são artefatos de vida curta cujo valor de reuso para um atacante deveria ser sempre zero.

## 4. Parâmetros e endpoints normativos

- **PAR endpoint** — endpoint novo, descoberto de forma padronizada via RFC 8414 (Authorization Server Metadata) como o campo `pushed_authorization_request_endpoint`.
- **Requisição** (`application/x-www-form-urlencoded`, igual ao `/token`): o mesmo conjunto de parâmetros que uma authorization request tradicional carregaria — `response_type`, `client_id`, `redirect_uri`, `scope`, `state`, e qualquer parâmetro de extensão relevante (`code_challenge`/`code_challenge_method` da PKCE, `resource` da RFC 8707, e assim por diante) — **mais autenticação do client**, usando qualquer um dos métodos já suportados no token endpoint (`client_secret_basic`, `client_secret_post`, `private_key_jwt`, mTLS, conforme o perfil do AS).
- **Resposta** (JSON): dois campos —
  - `request_uri` — no formato `urn:ietf:params:oauth:request_uri:<valor opaco>` (o prefixo URN é uma convenção da RFC, não obrigatória em todo detalhe de sintaxe, mas amplamente seguida).
  - `expires_in` — tempo de vida em segundos, tipicamente muito curto (a própria RFC cita a ordem de grandeza de ~60 segundos como típica — comparável à vida útil de um authorization code).
- A requisição de autorização subsequente (`/authorize`) fica reduzida, na prática, a **`client_id` + `request_uri`** — nenhum outro parâmetro deveria estar presente; a RFC deixa como decisão de política do AS como tratar parâmetros extras conflitantes que apareçam junto (a prática recomendada é rejeitar, para não abrir uma ambiguidade sobre qual conjunto de parâmetros é a "fonte da verdade").
- **Erros**: se o `request_uri` apresentado ao `/authorize` for desconhecido, expirado, ou já consumido, o AS deve rejeitar — a terminologia comum em implementações de mercado usa `invalid_request_uri` como valor de erro (não formalmente cunhado com esse nome exato no corpo principal da RFC 9126, mas amplamente adotado na prática como o análogo natural de "sua referência está velha ou já foi usada").

Um ponto normativo importante para quem avalia adotar PAR como requisito de baseline: a RFC define um metadado adicional, `require_pushed_authorization_requests`, que um AS pode publicar em seu documento de metadata (RFC 8414) para declarar que **exige** PAR para todo client — ou seja, rejeita qualquer tentativa de `/authorize` tradicional com parâmetros soltos na query string, mesmo que tecnicamente válidos. Essa é exatamente a postura que perfis regulatórios como o FAPI 2.0 adotam (ver item 6).

## 5. Segurança já tratada na própria RFC 9126

- **Integridade por autenticação do canal, não por criptografia do conteúdo**: como o push acontece por um back-channel autenticado (o client se autentica no PAR endpoint com as mesmas credenciais que usaria no token endpoint), o AS tem uma garantia forte — comparável à que já tinha para requisições de token — de que os parâmetros vieram efetivamente do client registrado, não de um terceiro no meio do caminho. Essa é uma garantia estruturalmente diferente e mais forte do que confiar num redirect de browser sujeito a log, cache intermediário, extensão de browser maliciosa, ou simplesmente vazamento incidental antes de a requisição sequer chegar ao AS.
- **Redução de exposição em URL**: PAR generaliza, para **todos** os parâmetros de uma authorization request, o mesmo princípio que a RFC 6750 (Bearer Token Usage) já aplicava especificamente a tokens — "nunca em URL logável". Depois de adotar PAR, nada sensível (nem `scope`, nem `code_challenge`, nem `resource`, nem qualquer parâmetro de extensão futura) trafega numa URL que possa acabar em histórico de browser, log de proxy, ou cabeçalho `Referer`.
- **`request_uri` de uso único e vida curta**: segue exatamente a mesma lógica de mitigação de replay já estabelecida para o authorization code na RFC 6749 — limitar tanto **quantas vezes** (uma) quanto **por quanto tempo** (segundos) um valor capturado poderia ser reaproveitado por um atacante que o interceptasse. Vale uma observação importante sobre o que essa proteção **não** cobre: reutilizar um `request_uri` capturado não concede a um atacante nenhum privilégio novo — na melhor das hipóteses para o atacante, ele só reproduziria o mesmo fluxo já iniciado pelo client legítimo, redirecionando para o mesmo `redirect_uri` já registrado para aquele client (não para um destino arbitrário escolhido pelo atacante). Isso significa que capturar um `request_uri` sozinho não é, por si só, um vetor de sequestro de conta — é mais análogo a "reiniciar" o mesmo login que o usuário legítimo já estava fazendo, o que na prática tem valor de ataque limitado, embora ainda seja corretamente tratado como algo a impedir por disciplina defensiva.
- **PAR reduz, mas não elimina, a motivação para assinar a requisição**: no caso simples (parâmetros não sensíveis, cenário de baixo risco), a integridade que vem da autenticação do canal do PAR já é suficiente, tornando desnecessário o esforço adicional de assinar um Request Object (o mecanismo do próximo capítulo, RFC 9101/JAR). Mas as duas técnicas **não são mutuamente exclusivas** — de fato, foram desenhadas para compor: é possível empurrar, via PAR, um objeto de requisição já assinado (um JWT, no formato da RFC 9101) como o corpo do push. O resultado combina integridade por assinatura criptográfica **e** opacidade de URL ao mesmo tempo — o padrão que perfis de alta garantia como FAPI 2.0 adotam como baseline (ver item 6 e o próximo capítulo).
- **PAR não substitui autenticação do resource owner nem consentimento** — é importante não confundir "os parâmetros chegaram com integridade" com "o usuário está protegido". PAR resolve exclusivamente o transporte da requisição de autorização; toda a lógica de login, MFA e tela de consentimento do lado do AS continua inteiramente inalterada pelo passo 5 em diante.

## 6. Relação com outras RFCs

- Generaliza, para **todos** os parâmetros sensíveis de uma authorization request, o princípio de "nunca em URL logável" já estabelecido na **RFC 6750** especificamente para tokens de portador.
- Companheira direta da **RFC 9101 (JAR)**, próximo capítulo deste livro — as duas endereçam a mesma preocupação de fundo (integridade e tamanho do front-channel da requisição de autorização) por mecanismos diferentes e **combináveis**, não concorrentes: PAR ataca o transporte (esconder do browser, via canal autenticado); JAR ataca o conteúdo (provar que os parâmetros não foram adulterados, via assinatura). A combinação das duas — empurrar um Request Object assinado via PAR — é discutida em detalhe no próximo capítulo.
- Descoberta via **RFC 8414** como `pushed_authorization_request_endpoint`, seguindo o mesmo padrão de descoberta já visto para `revocation_endpoint` (RFC 7009), `introspection_endpoint` (RFC 7662) e `device_authorization_endpoint` (RFC 8628), todos capítulos anteriores deste livro.
- Especialmente relevante em conjunto com a **RFC 7636 (PKCE)**, capítulo anterior deste livro: `code_challenge`/`code_challenge_method` são exatamente o tipo de parâmetro que mais se beneficia de sair da query string visível do browser — combinar PAR com PKCE significa que nem mesmo o challenge (que sozinho já não vaza o verifier, mas ainda é informação de protocolo) fica exposto em log ou histórico.
- Recomendada de forma geral pela **RFC 9700**, mas — e este é um ponto que vale destacar especificamente para um leitor com contexto FSI — **exigida, não apenas recomendada**, por perfis setoriais de alta garantia: o **FAPI 2.0** (especificação da OpenID Foundation, amplamente adotada em open banking e mercados financeiros regulados ao redor do mundo) torna PAR **obrigatório** para qualquer AS conforme o perfil, no mesmo padrão de exigência incondicional já visto no capítulo da RFC 9700 para sender-constraining de tokens (DPoP/mTLS).

## 7. O que mudou desde a publicação (2021)

- Spec relativamente recente e estável, sem revisão formal desde a publicação — mas com adoção crescendo de forma consistente, puxada em boa parte pela exigência incondicional do FAPI 2.0 em mercados regulados (open banking europeu, brasileiro, e outros que seguem perfis derivados do FAPI).
- PAR está seguindo uma trajetória de consolidação muito parecida com a que a própria PKCE seguiu no capítulo anterior deste livro: de "medida de hardening opcional, adotada seletivamente" para "expectativa de baseline" em Authorization Servers voltados ao público, especialmente — mas não exclusivamente — em contextos de alta sensibilidade como o financeiro.
- A combinação PAR + JAR ("empurrar um objeto de requisição assinado") deixou de ser uma curiosidade de spec e passou a ser um padrão comum, quase um dado adquirido, em implementações conformes a perfis FAPI — o próximo capítulo detalha exatamente como essa combinação funciona na prática.

> **Nota sobre o lab**: este projeto implementa a RFC 9126 no lab `rfc9126/` — uma réplica autocontida da arquitetura do `rfc6749/` (mesmos containers, convenções e formatos de token do restante do projeto), com o Authorization Code Grant exigindo PAR incondicionalmente: o Authorization Server expõe um endpoint `/par` autenticado, que recebe e valida os parâmetros da authorization request e devolve um `request_uri` (`urn:ietf:params:oauth:request_uri:...`) de uso único; o `/authorize` deste lab **só aceita** requisições que carreguem `client_id` + `request_uri` — não há caminho para os parâmetros tradicionais soltos na query string, refletindo exatamente a postura `require_pushed_authorization_requests` discutida no item 4. O README do lab descreve o exercício mais didático dele: comparar lado a lado, no log de eventos (`./containers/logs.sh events`), o tamanho e o conteúdo da URL de `/authorize` deste lab (mínima, opaca) contra a URL equivalente do lab `rfc6749/` (que carrega `scope`, `redirect_uri` e `state` em claro na própria URL) — tornando a redução de exposição literalmente visível na prática, não só teórica. O lab também demonstra o uso único do `request_uri`: uma segunda tentativa com a mesma referência falha explicitamente com a mensagem "request_uri inválido, expirado ou já utilizado".

## Exemplo em Java (JDK 21, sem frameworks)

Os exemplos usam `java.net.http.HttpClient` para as chamadas HTTP e o utilitário `SimpleJson` (métodos `SimpleJson.object(Map)` e `SimpleJson.parseFlat(String)`), definido no Capítulo 1 (RFC 6749) deste livro, para ler a resposta JSON do PAR endpoint.

### Exemplo 1 — `POST /par` autenticado, recebendo `request_uri`

```java
import java.net.URI;
import java.net.URLEncoder;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.nio.charset.StandardCharsets;
import java.util.Base64;
import java.util.Map;

public final class PushedAuthorizationRequestClient {

    private final HttpClient http = HttpClient.newHttpClient();
    private final String parEndpoint;
    private final String clientId;
    private final String clientSecret;

    public PushedAuthorizationRequestClient(String parEndpoint, String clientId, String clientSecret) {
        this.parEndpoint = parEndpoint;
        this.clientId = clientId;
        this.clientSecret = clientSecret;
    }

    // Empurra todos os parametros de uma authorization request tradicional
    // (RFC 6749 §4.1.1 + PKCE da RFC 7636) por um back-channel AUTENTICADO,
    // em vez de deixa-los trafegar soltos na query string vista pelo browser.
    public Map<String, String> empurrarAuthorizationRequest(String redirectUri,
                                                              String scope,
                                                              String state,
                                                              String codeChallenge) throws Exception {
        StringBuilder body = new StringBuilder();
        body.append("response_type=code");
        body.append("&client_id=").append(enc(clientId));
        body.append("&redirect_uri=").append(enc(redirectUri));
        body.append("&scope=").append(enc(scope));
        body.append("&state=").append(enc(state));
        body.append("&code_challenge=").append(enc(codeChallenge));
        body.append("&code_challenge_method=S256");

        String credenciais = clientId + ":" + clientSecret;
        HttpRequest request = HttpRequest.newBuilder()
                .uri(URI.create(parEndpoint))
                // Autenticação do client no PAR endpoint — mesmos métodos já
                // suportados no token endpoint. Isto é o que dá ao AS a
                // garantia de integridade que substitui a confiança (fraca)
                // no canal de um redirect de browser comum.
                .header("Authorization", "Basic " + Base64.getEncoder()
                        .encodeToString(credenciais.getBytes(StandardCharsets.UTF_8)))
                .header("Content-Type", "application/x-www-form-urlencoded")
                .POST(HttpRequest.BodyPublishers.ofString(body.toString()))
                .build();

        HttpResponse<String> response = http.send(request, HttpResponse.BodyHandlers.ofString());
        Map<String, String> json = SimpleJson.parseFlat(response.body());

        // RFC 9126 §2.2: sucesso é HTTP 201 (Created) — não 200 — porque o
        // AS de fato CRIOU um recurso novo (o registro da requisição pushed).
        if (response.statusCode() != 201) {
            throw new RuntimeException("PAR endpoint recusou o push: "
                    + json.getOrDefault("error", "erro desconhecido"));
        }
        // { request_uri: "urn:ietf:params:oauth:request_uri:...", expires_in: 60 }
        return json;
    }

    private static String enc(String v) {
        return URLEncoder.encode(v, StandardCharsets.UTF_8);
    }
}
```

### Exemplo 2 — montar a URL minimalista de `/authorize` a partir do `request_uri`

```java
import java.net.URI;
import java.net.URLEncoder;
import java.nio.charset.StandardCharsets;

public final class AuthorizeComRequestUri {

    // Compare esta URL com a do capítulo da RFC 7636: aqui, NADA além de
    // client_id e request_uri aparece na query string que o browser navega.
    // scope, redirect_uri, state, code_challenge — tudo já foi entregue via
    // POST /par autenticado; o browser nunca os vê.
    public static URI montarUrlAutorizacao(String authorizationEndpoint,
                                            String clientId,
                                            String requestUri) {
        String query = "client_id=" + URLEncoder.encode(clientId, StandardCharsets.UTF_8)
                + "&request_uri=" + URLEncoder.encode(requestUri, StandardCharsets.UTF_8);
        return URI.create(authorizationEndpoint + "?" + query);
    }

    public static void main(String[] args) throws Exception {
        var parClient = new PushedAuthorizationRequestClient(
                "https://as.exemplo.com/par", "banco-app-123", "segredo-do-client");

        String codeVerifier = Pkce.generateCodeVerifier(); // reaproveitando o capítulo da RFC 7636
        String codeChallenge = Pkce.computeCodeChallengeS256(codeVerifier);

        var parResponse = parClient.empurrarAuthorizationRequest(
                "https://app.exemplo.com/callback",
                "accounts:read",
                "estado-anti-csrf-abc123",
                codeChallenge);

        URI authorizeUrl = montarUrlAutorizacao(
                "https://as.exemplo.com/authorize",
                "banco-app-123",
                parResponse.get("request_uri"));

        System.out.println("URL minimalista para abrir no user-agent: " + authorizeUrl);
        System.out.println("expires_in do request_uri: " + parResponse.get("expires_in") + "s");
        // A partir daqui, o resto do Authorization Code Grant + PKCE segue
        // exatamente como no capítulo anterior — redirect com code, troca
        // por token enviando o code_verifier original.
    }
}
```

### Exemplo 3 — comparando o tamanho da URL antes/depois de PAR

```java
public final class ComparacaoTamanhoUrl {

    // Ilustra numericamente o ganho de PAR — útil para justificar a adoção
    // em uma revisão de arquitetura: menos bytes sensíveis trafegando por
    // um canal (browser) que a organização não controla totalmente.
    public static void main(String[] args) {
        String urlTradicional = "https://as.exemplo.com/authorize"
                + "?response_type=code&client_id=banco-app-123"
                + "&redirect_uri=https%3A%2F%2Fapp.exemplo.com%2Fcallback"
                + "&scope=accounts%3Aread%20accounts%3Awrite"
                + "&state=estado-anti-csrf-abc123"
                + "&code_challenge=E9Melhor-code-challenge-fake-para-exemplo"
                + "&code_challenge_method=S256";

        String urlComPar = "https://as.exemplo.com/authorize"
                + "?client_id=banco-app-123"
                + "&request_uri=urn%3Aietf%3Aparams%3Aoauth%3Arequest_uri%3A6esc_11ACC5bwc014ltc14eY22c";

        System.out.println("Sem PAR : " + urlTradicional.length() + " caracteres");
        System.out.println("Com PAR : " + urlComPar.length() + " caracteres");
        System.out.println("Redução : " + (urlTradicional.length() - urlComPar.length())
                + " caracteres a menos expostos em log/histórico/Referer");
    }
}
```
