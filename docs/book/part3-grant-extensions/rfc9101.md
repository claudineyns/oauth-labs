# RFC 9101 — The OAuth 2.0 Authorization Framework: JWT-Secured Authorization Request (JAR)

## 1. Contexto e motivação

O capítulo anterior deste livro (RFC 9126, PAR) abriu com o mesmo diagnóstico que serve de ponto de partida aqui: a requisição de autorização tradicional (RFC 6749 §4.1.1) manda cada parâmetro como um par chave-valor solto na query string, sem nenhuma verificação de integridade embutida. Vale reforçar exatamente o que isso significa na prática, porque a RFC 9101 ataca essa mesma lacuna por um ângulo diferente do PAR: nada garante ao Authorization Server que os parâmetros que ele recebeu chegaram **exatamente** como o client os montou originalmente. Um intermediário de rede em algum ponto do caminho, uma extensão de browser maliciosa instalada na máquina do usuário, ou uma cadeia de redirecionamento manipulada (comum em cenários de SSO corporativo com múltiplos hops de identidade) poderiam, em tese, alterar um único parâmetro individual — trocar `scope=profile` por `scope=profile+admin`, por exemplo, ou trocar um `redirect_uri` por outro sutilmente diferente — sem que essa adulteração deixe rastro algum detectável pelo AS.

A RFC 9101 (JAR — JWT-Secured Authorization Request, publicada em 2021) resolve esse problema de um jeito estruturalmente diferente do PAR, e vale marcar bem essa diferença porque é fácil confundir as duas abordagens à primeira vista: em vez de **esconder** os parâmetros do browser (a estratégia do PAR — movê-los para um back-channel autenticado), a JAR **empacota todos eles num único JWT assinado pelo próprio client** — o chamado **Request Object** — e envia esse JWT como um parâmetro único na requisição. Qualquer adulteração em qualquer campo, por menor que seja, quebra a assinatura criptográfica, e o AS detecta e rejeita isso deterministicamente. A garantia de integridade aqui vem de **criptografia de chave pública**, não de nenhuma propriedade do canal de transporte por onde a requisição passou — o JWT pode, em teoria, transitar por qualquer canal, confiável ou não, que a assinatura continua provando que o conteúdo não foi alterado desde que o client o assinou.

Essa diferença de fundamento — "confiar porque o canal é autenticado" (PAR) versus "provar criptograficamente, independente do canal" (JAR) — não é só uma curiosidade acadêmica: ela é exatamente o que torna as duas técnicas complementares em vez de concorrentes, um ponto que este capítulo retoma em detalhe no item 6.

## 2. Terminologia e papéis

Nenhum papel novo em relação à RFC 6749. Vocabulário introduzido pela RFC:

- **Request Object** — um JWT cujas claims **são**, literalmente, os parâmetros de uma authorization request comum (`response_type`, `client_id`, `redirect_uri`, `scope`, `state`, `code_challenge`, `code_challenge_method`, e qualquer outro parâmetro de extensão relevante), somadas às claims padrão de qualquer JWT: `iss` (o `client_id`, identificando quem assinou), `aud` (identificador do Authorization Server, tipicamente seu `issuer`), e `exp` (expiração — crítico para limitar a janela de replay, ver item 5).
- **`request`** — o parâmetro de query string que carrega o Request Object **por valor**: o JWT compacto inteiro, codificado, diretamente embutido na URL do `/authorize`.
- **`request_uri`** — o parâmetro que carrega o Request Object **por referência**: uma URL, hospedada pelo próprio client, que o AS busca (um `GET` feito pelo próprio AS) para obter o JWT.

> **Atenção redobrada ao nome, retomando o aviso do capítulo anterior**: o `request_uri` desta RFC (9101) é **conceitualmente diferente** do `request_uri` da RFC 9126 (PAR), apesar do nome idêntico. Vale a comparação lado a lado, porque a confusão entre os dois é um erro real e recorrente em discussões técnicas:
>
> | | RFC 9101 (JAR) `request_uri` | RFC 9126 (PAR) `request_uri` |
> |---|---|---|
> | Quem hospeda a URL | O **client** | O **Authorization Server** |
> | Quem busca o conteúdo | O **AS** faz `GET` na URL do client | O **client** já recebeu o conteúdo de volta no push; o `/authorize` só referencia |
> | Como o conteúdo chega lá | O client publica o Request Object numa URL própria, antecipadamente | O AS gera a referência como resposta a um `POST /par` do client |
> | O que garante integridade | A assinatura do JWT (JAR) | A autenticação do client no momento do push (PAR) |
>
> Os dois mecanismos usam o mesmo nome de parâmetro porque, superficialmente, resolvem o mesmo tipo de necessidade ("não colocar tudo na query string do `/authorize`") — mas são artefatos com direção de fluxo invertida e origem de confiança diferente. Isso não impede que sejam combinados (ver item 6) — na verdade, a combinação é o padrão recomendado em perfis de alta garantia.

## 3. Fluxo

**Por valor** (`request`):
```
1. Client monta um JWT com claims = todos os parametros da authorization request + iss, aud, exp
2. Client assina o JWT com uma chave registrada no AS
3. Client → User-Agent: GET /authorize?client_id=...&request=<JWT compacto>
4. AS valida a assinatura (chave do client, via jwks/jwks_uri registrados), confere exp/aud/iss,
   extrai os parametros das claims do JWT (nao da query string solta)
5. Segue com login/consentimento normalmente, usando os parametros ja verificados
```

**Por referência** (`request_uri`):
```
1-2. mesma construcao do JWT
3. Client hospeda o JWT numa URL propria (ex.: https://client.exemplo/reqs/abc123)
4. Client → User-Agent: GET /authorize?client_id=...&request_uri=https://client.exemplo/reqs/abc123
5. AS busca o JWT nessa URL, entao valida assinatura/claims como acima
```

Vale examinar com mais cuidado o passo 4 em cada modalidade, porque é onde as duas variantes divergem de forma relevante para uma decisão de arquitetura:

No modo **por valor**, o JWT compacto inteiro (header.payload.assinatura, tudo codificado em Base64URL) vai embutido na própria URL do `/authorize`. Isso resolve o problema de integridade (a assinatura protege o conteúdo), mas **não** resolve o problema de tamanho de URL que motivou o capítulo anterior — na verdade, um Request Object assinado tende a ser **maior** do que os parâmetros soltos equivalentes, porque carrega overhead de JWT (header, claims padrão, a assinatura em si, que para RSA facilmente passa de 340 bytes codificados). Ou seja: por valor resolve integridade, mas piora exposição de URL.

No modo **por referência**, a URL do `/authorize` fica pequena (só `client_id` + a URL de referência do client) — só que agora o AS precisa fazer, ele mesmo, uma requisição HTTP de saída para buscar o conteúdo, o que introduz uma superfície de risco nova e específica: SSRF (ver item 5). Além disso, essa variante introduz uma dependência operacional que o modo por valor não tem — o client precisa manter um endpoint disponível e responsivo hospedando o Request Object, para o AS conseguir buscá-lo no momento exato do passo 5; se esse endpoint estiver fora do ar, o fluxo de autorização inteiro falha ali.

O passo de validação (4, em ambas as variantes) é onde o AS precisa ser rigoroso: validar a assinatura contra a chave pública correta do client (obtida via `jwks` embutido no registro do client, ou buscada dinamicamente via `jwks_uri`), conferir que `exp` ainda não passou, e idealmente confirmar que `aud` de fato identifica este AS especificamente (evitando que um Request Object assinado para um AS seja reaproveitado contra outro, num cenário de múltiplos ASs confiando na mesma chave do client — incomum, mas não impossível de configurar incorretamente). Só depois dessa validação completa o AS deveria tratar as claims do JWT como a fonte autoritativa dos parâmetros da requisição — nunca misturar parâmetros da query string solta (fora do JWT) com os das claims verificadas, para não abrir uma brecha onde um atacante injeta um parâmetro adicional não coberto pela assinatura.

## 4. Parâmetros e endpoints normativos

Nenhum endpoint novo — ao contrário da RFC 9126, que introduz o `/par` como endpoint dedicado, a JAR reaproveita o `/authorize` já existente inteiramente, só adicionando dois parâmetros possíveis de query string: `request` e `request_uri` (mutuamente exclusivos — a RFC não define comportamento de usar os dois juntos, e a prática recomendada é o AS rejeitar se ambos vierem presentes).

- **Claims do Request Object**: `iss` (= `client_id`), `aud` (= identificador do AS, tipicamente o `issuer`), `exp` (padrão JWT, obrigatório para limitar replay) — mais **todos** os parâmetros normais de uma authorization request, como claims adicionais no mesmo nível (não aninhados): `response_type`, `client_id` (novamente, agora como claim), `redirect_uri`, `scope`, `state`, `code_challenge`, `code_challenge_method`, `resource`, e qualquer outro parâmetro de extensão relevante para o AS em questão.
- **Descoberta da chave de assinatura do client**: via `jwks` (o conjunto de chaves públicas embutido diretamente no registro do client, útil para clients com chave estática) ou `jwks_uri` (uma URL que o AS busca dinamicamente para obter o conjunto de chaves, útil para rotação de chave sem precisar re-registrar o client) — ambos campos fazem parte do metadata de registro do client, tema da RFC 7591 (Dynamic Client Registration), categoria de RFCs de descoberta/registro deste roteiro.
- **Validação obrigatória do lado do AS**: verificar a assinatura contra a chave correta, verificar `exp`, e — prática fortemente recomendada, embora a redação da RFC deixe alguma margem — conferir `aud`. Para o modo por referência especificamente, a RFC recomenda que o AS **restrinja de onde busca** o `request_uri` (ver item 5).
- **Metadados de descoberta relacionados (RFC 8414)**: `request_parameter_supported` (o AS aceita `request`?), `request_uri_parameter_supported` (o AS aceita `request_uri`?), `require_signed_request_object` (o AS exige que toda authorization request venha como Request Object assinado, recusando parâmetros soltos — a postura equivalente, para JAR, ao `require_pushed_authorization_requests` do capítulo anterior).
- **Erros**: a RFC reaproveita, na medida do possível, o vocabulário de erro já existente do `/authorize` (`invalid_request`, `invalid_request_object` sendo um valor comumente adotado na prática para especificamente sinalizar falha de validação do JWT — assinatura inválida, `exp` vencido, claims malformadas).

## 5. Segurança já tratada na própria RFC 9101

- **Integridade por assinatura, garantia mais forte e mais geral que a do PAR**: mesmo que o canal de transporte da requisição não seja confiável em nenhum ponto do caminho, qualquer adulteração no conteúdo quebra a assinatura de forma detectável — não importa onde ou como a adulteração ocorreu. Vale comparar explicitamente com o mecanismo do capítulo anterior: a PAR confia na integridade **porque o canal do push é autenticado** (uma garantia de "confiança no transporte"); a JAR **prova** a integridade criptograficamente, de forma independente das propriedades de qualquer canal por onde o JWT passe depois de assinado (uma garantia de "prova no conteúdo"). Isso torna a JAR aplicável mesmo em cenários onde o Request Object precisaria trafegar por canais que o client não controla totalmente (por exemplo, embutido numa URL que passa por múltiplos redirecionamentos de terceiros antes de chegar ao AS).
- **Mitigação de replay via `exp` (e, opcionalmente, `jti`)**: a claim `exp` limita por quanto tempo um Request Object capturado poderia ser reaproveitado — um AS bem-comportado rejeita qualquer Request Object cujo `exp` já tenha passado, mesmo que a assinatura seja perfeitamente válida. Para AS que queiram impor também uso único (não só limite de tempo), a RFC permite o uso de uma claim `jti` (JWT ID) opcional, que o AS pode rastrear e recusar em caso de reapresentação — análogo em espírito ao uso único do `request_uri` da PAR, mas aqui é uma escolha de política adicional do AS, não uma exigência normativa central da spec.
- **Risco de SSRF no modo por referência — o ponto de segurança mais discutido desta RFC na prática**: como é o **próprio Authorization Server** quem faz a requisição HTTP de saída para buscar o conteúdo apontado por `request_uri`, um client malicioso (ou um valor de `request_uri` não devidamente vinculado e validado contra o client registrado) poderia, em tese, induzir o AS a fazer requisições a URLs arbitrárias — potencialmente endereços internos da rede do próprio AS, serviços de metadata de cloud (o clássico alvo de SSRF em ambientes AWS/GCP/Azure), ou qualquer outro destino que o atacante queira que o AS "visite" com a autoridade de rede do próprio AS. A mitigação recomendada, e que qualquer AS de produção deveria implementar como não-negociável: **restringir de quais hosts/padrões o AS aceita buscar `request_uri`**, tipicamente exigindo que a URL bata com um padrão pré-registrado especificamente para aquele client (não aceitar qualquer URL arbitrária que a requisição de autorização apresente). Este é, de longe, o risco mais citado em análises de segurança desta RFC, e a razão pela qual muitas implementações de AS optam por só suportar o modo por valor, ou por só suportar `request_uri` combinado com PAR (ver abaixo), evitando o SSRF por completo ao nunca deixar o client apontar para uma URL arbitrária de sua escolha.
- **JAR sozinha não dá confidencialidade — só integridade**: um ponto que merece ênfase porque é fácil supor o contrário. O Request Object, na forma básica descrita pela RFC, é um JWS (JSON Web Signature) — **assinado, não criptografado**. Qualquer parte que consiga observar o `request` ou o conteúdo apontado por `request_uri` (um proxy, um log, o histórico de browser no modo por valor) ainda lê `scope`, `redirect_uri`, e qualquer outro parâmetro em **texto claro** — a assinatura impede adulteração não detectada, não impede leitura. Quem precisa também de confidencialidade (esconder o conteúdo, não só protegê-lo de adulteração) precisa adicionalmente **criptografar** o Request Object como um JWE (JSON Web Encryption) — uma combinação (assinar e depois criptografar, "sign-then-encrypt", ou o inverso conforme o perfil) comum em implementações FAPI de alta garantia, mas que a RFC 9101 básica não exige por si só.
- **Confiança na chave do client precisa ser gerenciada com cuidado**: se o `jwks_uri` do client for buscado dinamicamente pelo AS a cada validação (em vez de cacheado com uma política de expiração razoável), isso introduz uma dependência de disponibilidade nova (o AS depende do endpoint do client estar no ar) e uma superfície adicional (o mesmo tipo de risco de host não confiável do `request_uri`, embora aqui o conteúdo buscado — um conjunto de chaves públicas — seja normalmente menos sensível de adulterar do que redirecionar o próprio AS para um destino arbitrário).

## 6. Relação com outras RFCs

- Companheira direta da **RFC 9126 (PAR)**, capítulo anterior deste livro — e aqui está a combinação mais importante deste par de capítulos, que vale detalhar passo a passo porque é exatamente o padrão que perfis de alta garantia adotam como baseline: o client (1) monta o Request Object — o JWT com todos os parâmetros de autorização como claims (o mecanismo desta RFC, JAR); (2) assina esse JWT com sua chave privada; (3) empurra o JWT assinado inteiro como o corpo de um `POST /par` (o mecanismo do capítulo anterior, PAR), autenticando-se no PAR endpoint da forma usual; (4) recebe de volta o `request_uri` **opaco gerado pelo AS** (o `request_uri` da RFC 9126, não desta RFC); (5) usa esse `request_uri` opaco no `/authorize`. O resultado combina as duas garantias ao mesmo tempo: os parâmetros ficam **escondidos do browser** (confidencialidade de transporte, cortesia da PAR) **e** são verificavelmente autênticos e íntegros (cortesia da assinatura da JAR) — e, como efeito colateral bem-vindo, essa combinação especificamente **evita o risco de SSRF** discutido no item 5, porque o AS nunca precisa buscar um `request_uri` hospedado pelo client — o Request Object já chegou inteiro, assinado, no próprio corpo do push.
- A chave de assinatura do client (via `jwks`/`jwks_uri`) vem do metadata de registro estabelecido pela **RFC 7591 (Dynamic Client Registration)**, categoria de RFCs de descoberta/registro deste roteiro.
- Há um paralelo conceitual direto com **RFC 7523** (uso de `private_key_jwt` para autenticação de client no token endpoint) — a mesma ideia estrutural (um JWT assinado pela chave privada do client, provando que só o client poderia tê-lo produzido), aplicada a um propósito diferente: a RFC 7523 autentica o client no momento da troca de token; a RFC 9101 protege a integridade da requisição de autorização em si. Vale reconhecer o padrão comum às duas: "JWT assinado pelo client" é um primitivo reutilizável do ecossistema OAuth, aplicado em pontos distintos do fluxo conforme a necessidade.
- Descoberta via **RFC 8414**: os campos `request_parameter_supported`, `request_uri_parameter_supported` e `require_signed_request_object` permitem a um client (ou a uma ferramenta de auditoria de conformidade) verificar programaticamente se e como um AS específico suporta JAR, sem precisar de documentação fora de banda.
- Fortemente usada — e, na prática, frequentemente **exigida** — em perfis **FAPI** (FAPI 1.0 Advanced e, de forma ainda mais consolidada, FAPI 2.0), quase sempre já combinada com PAR exatamente no padrão descrito acima. Um arquiteto avaliando conformidade FAPI para um AS ou client deveria tratar "PAR + JAR combinados" como a unidade de análise relevante, não as duas specs isoladamente.

## 7. O que mudou desde a publicação (2021)

- Spec relativamente recente e estável, sem revisão formal — mas seguiu uma trajetória de adoção **diferente** da do PKCE (capítulo anterior deste livro), e vale marcar bem essa diferença para não generalizar incorretamente o padrão de "toda extensão de segurança vira baseline universal com o tempo": a JAR **não** se tornou obrigatória de forma ampla e incondicional via RFC 9700 — ao contrário do PKCE, que passou de "recomendado para públicos" para "obrigatório para todos". A JAR continua sendo, mesmo hoje, uma ferramenta de **"alta garantia"**, adotada seletivamente onde a organização (ou o regulador) exige integridade estrutural mais forte do que o baseline geral — setor financeiro sendo o exemplo mais citado — em vez de um requisito de linha de base esperado de qualquer AS público, do jeito que PKCE se tornou.
- A combinação PAR + JAR se consolidou, na prática de mercado, como o padrão de fato em implementações conformes a FAPI 2.0 — reforçando a leitura de que essas duas RFCs se entendem melhor, e são adotadas melhor, como um par desenhado para compor, do que isoladamente uma da outra.
- Vale reter, como conclusão de todo este capítulo de Extensões de Grant Type: das cinco RFCs cobertas nesta parte do livro, PKCE é hoje universal (todo client, todo cenário); Device Authorization Grant e Token Exchange são adotados conforme a necessidade arquitetural específica (dispositivo sem browser; cadeias de chamada multi-serviço); e PAR/JAR representam o par de extensões de "alta garantia", cuja adoção — ainda que crescente — permanece concentrada onde o perfil de risco ou a exigência regulatória especificamente demanda esse nível adicional de rigor.

> **Nota sobre laboratório**: este projeto não possui, até o momento, um laboratório dedicado para a RFC 9101. O cenário natural, e um bom candidato futuro, seria estender o lab já existente `rfc9126/` (que implementa PAR) para também assinar o Request Object antes de empurrá-lo — exercitando exatamente a combinação PAR + JAR descrita no item 6 deste capítulo, e mostrando as duas proteções (opacidade de transporte e integridade por assinatura) lado a lado, na prática, dentro da mesma dança de eventos HTTP que os demais labs do projeto já expõem. Por ora, este capítulo se concentra nos exemplos em Java abaixo, que constroem, assinam e transmitem um Request Object do zero, usando somente a biblioteca padrão do JDK.

## Exemplo em Java (JDK 21, sem frameworks)

Os exemplos usam `java.security.KeyPairGenerator` para gerar um par de chaves RSA, `java.security.Signature` (algoritmo `SHA256withRSA`) para assinar, `java.util.Base64` para as codificações Base64URL exigidas pelo formato JWT compacto, e o utilitário `SimpleJson` (método `SimpleJson.object(Map)`), definido no Capítulo 1 (RFC 6749) deste livro, para serializar as claims como JSON antes de codificá-las. Nenhuma biblioteca de JOSE/JWT é usada — a montagem do JWT é feita manualmente, passo a passo, para deixar explícito o que uma biblioteca como Nimbus JOSE normalmente esconde.

### Exemplo 1 — gerar o par de chaves RSA do client

```java
import java.security.KeyPair;
import java.security.KeyPairGenerator;
import java.security.NoSuchAlgorithmException;

public final class ClientKeyPair {

    // Em produção, este par seria gerado uma vez e persistido com segurança
    // (HSM, keystore protegido) — nunca gerado a cada requisição. Aqui,
    // geramos em memória só para tornar o exemplo autocontido.
    public static KeyPair gerarParRsa() {
        try {
            KeyPairGenerator generator = KeyPairGenerator.getInstance("RSA");
            generator.initialize(2048); // 2048 bits: piso aceitável para RSA hoje
            return generator.generateKeyPair();
        } catch (NoSuchAlgorithmException e) {
            throw new IllegalStateException("Algoritmo RSA indisponível na JVM", e);
        }
    }
}
```

### Exemplo 2 — montar e assinar o Request Object (JWT compacto, manualmente)

```java
import java.nio.charset.StandardCharsets;
import java.security.KeyPair;
import java.security.Signature;
import java.time.Instant;
import java.util.Base64;
import java.util.LinkedHashMap;
import java.util.Map;

public final class RequestObjectBuilder {

    private static final Base64.Encoder B64URL = Base64.getUrlEncoder().withoutPadding();

    // Monta o Request Object: um JWT cujas claims SÃO os parâmetros da
    // authorization request (RFC 6749 §4.1.1 + PKCE), somados às claims
    // padrão iss/aud/exp exigidas pela RFC 9101 §4.
    public static String montarESassinar(String clientId, String audienceAs,
                                          String redirectUri, String scope, String state,
                                          String codeChallenge, KeyPair chaveDoClient) throws Exception {

        // --- Header: {"alg":"RS256","typ":"JWT"} ---
        Map<String, Object> header = new LinkedHashMap<>();
        header.put("alg", "RS256");
        header.put("typ", "JWT");
        String headerJson = SimpleJson.object(header);
        String headerB64 = B64URL.encodeToString(headerJson.getBytes(StandardCharsets.UTF_8));

        // --- Payload: claims padrao de JWT + parametros da authorization request ---
        long agora = Instant.now().getEpochSecond();
        Map<String, Object> claims = new LinkedHashMap<>();
        claims.put("iss", clientId);           // quem assinou o Request Object
        claims.put("aud", audienceAs);          // para qual AS esta requisicao se destina
        claims.put("exp", agora + 60);          // vida curta: 60s, limita a janela de replay
        claims.put("response_type", "code");
        claims.put("client_id", clientId);
        claims.put("redirect_uri", redirectUri);
        claims.put("scope", scope);
        claims.put("state", state);
        claims.put("code_challenge", codeChallenge);
        claims.put("code_challenge_method", "S256");

        String payloadJson = SimpleJson.object(claims);
        String payloadB64 = B64URL.encodeToString(payloadJson.getBytes(StandardCharsets.UTF_8));

        // --- Assinatura sobre "header.payload" (a "signing input" do JWT) ---
        String signingInput = headerB64 + "." + payloadB64;
        Signature assinador = Signature.getInstance("SHA256withRSA");
        assinador.initSign(chaveDoClient.getPrivate());
        assinador.update(signingInput.getBytes(StandardCharsets.US_ASCII));
        byte[] assinatura = assinador.sign();
        String assinaturaB64 = B64URL.encodeToString(assinatura);

        // JWT compacto: header.payload.assinatura
        return signingInput + "." + assinaturaB64;
    }
}
```

### Exemplo 3 — enviar o Request Object por valor (`request=`)

```java
import java.net.URI;
import java.net.URLEncoder;
import java.nio.charset.StandardCharsets;
import java.security.KeyPair;

public final class EnviarPorValor {

    public static void main(String[] args) throws Exception {
        KeyPair chaveDoClient = ClientKeyPair.gerarParRsa();
        // Em produção, a chave PÚBLICA correspondente seria registrada
        // previamente no AS (via jwks ou jwks_uri no cadastro do client,
        // RFC 7591) — é contra ela que o AS valida a assinatura no passo 4.

        String verifier = Pkce.generateCodeVerifier(); // reaproveitando o capítulo da RFC 7636
        String challenge = Pkce.computeCodeChallengeS256(verifier);

        String requestObject = RequestObjectBuilder.montarESassinar(
                "banco-app-123",
                "https://as.exemplo.com", // aud: identifica o AS
                "https://app.exemplo.com/callback",
                "accounts:read",
                "estado-anti-csrf-abc123",
                challenge,
                chaveDoClient);

        // O JWT inteiro (grande, mas assinado) vai como o valor do
        // parametro `request` — note que isto NAO reduz o tamanho da URL,
        // so garante que qualquer adulteracao no caminho quebra a assinatura.
        String query = "client_id=" + URLEncoder.encode("banco-app-123", StandardCharsets.UTF_8)
                + "&request=" + URLEncoder.encode(requestObject, StandardCharsets.UTF_8);

        URI authorizeUrl = URI.create("https://as.exemplo.com/authorize?" + query);
        System.out.println("Abrir no user-agent (modo por valor): " + authorizeUrl);
        System.out.println("Tamanho do Request Object (JWT compacto): "
                + requestObject.length() + " caracteres");
    }
}
```

### Exemplo 4 — enviar por referência (`request_uri=`) e combinar com PAR (FAPI 2.0)

```java
import java.net.URI;
import java.net.URLEncoder;
import java.nio.charset.StandardCharsets;

public final class EnviarPorReferenciaOuComPar {

    // Modo por referência "puro" (RFC 9101 sozinha): o client hospeda o JWT
    // numa URL própria, e o AS é quem faz o GET para buscá-lo. Note o
    // request_uri aqui É uma URL do CLIENT — o oposto do request_uri da
    // RFC 9126 (PAR), que é uma referência OPACA gerada pelo AS. Um AS de
    // producao so deveria aceitar isto se a URL bater com um padrao
    // pre-registrado para este client (mitigacao de SSRF, ver item 5).
    public static URI montarUrlPorReferencia(String clientId, String requestObjectUrlDoClient) {
        String query = "client_id=" + URLEncoder.encode(clientId, StandardCharsets.UTF_8)
                + "&request_uri=" + URLEncoder.encode(requestObjectUrlDoClient, StandardCharsets.UTF_8);
        return URI.create("https://as.exemplo.com/authorize?" + query);
    }

    // Combinação recomendada por perfis FAPI 2.0: em vez de hospedar o JWT
    // numa URL propria (arriscando SSRF do lado do AS), o client empurra o
    // Request Object assinado via PAR (capitulo anterior) e usa o
    // request_uri OPACO devolvido pelo AS — nunca uma URL escolhida pelo
    // client. Isto some as duas protecoes (integridade da JAR + opacidade
    // da PAR) e elimina o risco de SSRF por completo.
    public static void main(String[] args) throws Exception {
        var chaveDoClient = ClientKeyPair.gerarParRsa();
        String verifier = Pkce.generateCodeVerifier();
        String challenge = Pkce.computeCodeChallengeS256(verifier);

        String requestObject = RequestObjectBuilder.montarESassinar(
                "banco-app-123", "https://as.exemplo.com",
                "https://app.exemplo.com/callback", "accounts:read",
                "estado-anti-csrf-abc123", challenge, chaveDoClient);

        // Passo PAR (capítulo anterior): empurra o Request Object assinado
        // inteiro como corpo do POST /par autenticado. Aqui o corpo do push
        // NAO é form-urlencoded parametro-a-parametro — é o proprio JWT,
        // enviado atraves do parametro "request" dentro do corpo do /par.
        var parClient = new PushedAuthorizationRequestClient(
                "https://as.exemplo.com/par", "banco-app-123", "segredo-do-client");

        // (Ilustrativo: em uma implementacao real, o metodo do PAR client
        // seria adaptado para aceitar o JWT pronto em vez de parametros
        // soltos — omitido aqui por brevidade, o ponto central é a ordem:
        // JAR monta e assina; PAR transporta; o resultado e um request_uri
        // OPACO, gerado pelo AS, usado no /authorize final.)
        System.out.println("Request Object assinado, pronto para push via PAR: "
                + requestObject.substring(0, 40) + "...(truncado)");
        System.out.println("Padrao FAPI 2.0: JAR (integridade) + PAR (opacidade) combinados.");
    }
}
```
